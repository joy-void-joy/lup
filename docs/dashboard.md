# The dashboard

Where the operator works with lup: every agent the host serves, across every repository, on one page. `lup-dev dashboard` opens it. Its package is `packages/lup-dashboard/` (`lup_dashboard`), which imports `lup-dev` and is never imported by it.

## Running

- **The host service runs it as its child** (`DashboardProcess`, `lup_dev/host/dashboard.py`), begun once the service listens and ended as it stops: `lup-dashboard serve <port>`, with `--address` for each address beyond localhost, found beside the interpreter running the service, where lup's own approval installs it beside `lup-dev`. Where it isn't installed, there's no dashboard, and `lup-dev dashboard` says why.
- **It goes with the service however the service ends:** the service writes the API's token on its input and keeps it open, and the dashboard ends when it closes. Its first line of output is the address it listens on, on localhost; one that ends before printing it, its port taken, is said.
- **On localhost, and on each address `LUP_DASHBOARD_ADDRESSES` names** (*Access*), **on one port** (`LUP_DASHBOARD_PORT`, 8766 by default), and **one token**, kept in the host's state with mode 600, which no room mounts, the same at each start, so a page left open reconnects on its own once the service starts again, after an approval among others.
- **`lup-dev dashboard`** prints the address with the token in its fragment and opens it in the browser, on localhost, starting the dashboard again where it's gone. Where the dashboard listens beyond localhost, it prints that address instead, the first named, drawn as a QR code for a phone to scan where `qrencode` is installed, an optional requirement of the host (`docs/launch.md`, *The command*); `--address` prints another the dashboard listens on. It refuses inside an agent's session.

## Access

Rooms share the host's network, so being on localhost keeps out only other machines.
- **Every call carries the token,** in the page's cookie (`HttpOnly`, `SameSite=Strict`, named after the port, since a browser shares localhost's cookies across ports) or as a bearer. The page is handed it in its address's fragment, which no request carries, trades it for the cookie and takes it out of the address. A page whose token is refused says so and stops, rather than retrying what retrying can't mend.
- **From another device,** as the operator's phone when they're out: `LUP_DASHBOARD_ADDRESSES`, in the host service's environment on the operator's machine, never in a project, names each address of the machine's the dashboard listens on beside localhost, separated by spaces, their WireGuard address among them (`LUP_DASHBOARD_ADDRESSES=10.8.0.2`). Each is bound whether or not the machine holds it yet (Linux's `IP_FREEBIND`), so a dashboard started before the tunnel is up answers there once it is. Addresses only, never `0.0.0.0`, which is refused: it would offer the dashboard on every network the machine joins, a café's among them, with the token as its only wall, where an address of the tunnel's lets in only the devices the tunnel admits. The token stays required there: the tunnel can't tell a room's process from the operator, and the dashboard answers trust's approvals, which install the code the host runs, so without it code in a room could approve its own push through any address bound. `lup-dev dashboard` hands the phone the token in the address it draws (*Running*), which the page trades for a cookie of that host's own, since a browser keeps cookies per host. Served over plain http there, the page keeps the clipboard to itself and says so (*The page*).
- **A request naming another host** than `127.0.0.1`, `localhost` or an address it listens on is refused, as is a call from a page of another origin.

## The API

The page asks the host service only what the operator's commands ask it: the host's own control requests, relayed as they are (`lup_dashboard/server.py`, FastAPI).
- **`POST /api/ask`** takes one request and returns its reply, a refusal among them. The page may send only the requests the operator's views need, listed in `lup_dashboard.api`; any other is refused before it reaches the host. An approval approved here is acted on as the operator's terminal acts on it, in a process of its own, since installing lup's own repository's copy restarts the host service, and the dashboard with it.
- **`/api/socket`,** a WebSocket, carries every watch a page holds, each under a number the page picks, answered at once and again each time it changes, through the host's watch socket (`docs/host.md`, *Watching*). One socket for every watch, since a browser keeps six connections to a host, which a stream per watch used up in three tabs.
- **The API's description** is the server's own OpenAPI document, made from the host's pydantic models, and the page's types are generated from it, so the two can't drift.

## The page

**Built** from `packages/lup-dashboard/page/`: TypeScript, React, React Aria Components for controls the keyboard reaches, cmdk for the command palette, and CodeMirror 6 with its vim mode for the review and the conversations. `packages/lup-dashboard/build.py` installs its packages from their lock, generates the types from the API's description, type-checks, runs its tests and builds, as `LupDevelopment`'s `dashboard` step and in trust's build of the copy the operator approves. Its packages are pinned exactly, nothing published in the last three days resolving. A page left open reloads itself when it reconnects to a build that isn't the one it loaded, as after lup is installed again and the dashboard restarted on it, its drafts kept on the host, so it never asks a server for what it no longer answers. Its tests are `packages/lup-dashboard/tests/` for the server and `page/src/*.test.ts` for the page.

**The review** is the page's one view: everything waiting for the operator, across every agent and repository, and each agent's work under its banner, as one buffer the operator moves through with vim and writes in (`page/src/review.ts`, `Review.tsx`).
- **Grouped by agent,** each group under a banner (*The banner*), its items after it and its drawers at its end (*The drawers*), in the order they arrived and never sorted again, so what the operator is reading doesn't move under them, and as the review is laid out anew the cursor's line stays where it is on screen, where it's in view, whatever came above it: a group appears where its first item puts it, or, for a conversation running or written to with no item, after every group with items, empty but for its banner, the messages written to it and its drawers, and keeps its place while anything's waiting; an item goes at the end of its group and stays there, a later item or a change of its rank or state moving nothing; what's left for later comes last, as the operator's own act moved it. On reload the order is the same, read from the items' numbers. An item's rank (`docs/inbox.md`, *Parties and items*) has two jobs only: the desktop notice, and which items `]a` and `[a` stop at. A flagged write is no item of the review, though the inbox keeps it: it's shown in its agent's "since you approved" drawer, and approved there (`docs/judging-writes.md`, *Asking the operator*).
- **Each item** under a header saying what it is, when it came, how long it has waited, and "new" since the operator last settled one. News, to mark read rather than answer, is in its own colour: a note, a turn's last words, a friction, how the work went, a stop. A question's decisions are numbered with their leans.
- **Markdown shows as Markdown,** in an item's text, in the operator's comments and in a conversation alike: emphasis, strong, code, headings and links as such, the marks that write them hidden, but on the line the cursor is on in a comment, where they show to be edited, as Markdown editors preview; a hidden mark no place for vim's cursor, which has no width to show on it, so a motion put on one goes on past it the way it was going, to the next character shown, as if the mark weren't there, and back where going on would leave the line (`page/src/editor.ts`, `pastHidden`); a table's columns lined up by padding drawn beside its cells and never written, so each row stays one line of the buffer, which vim moves over as one and a comment quotes as its source; and Enter in a comment's list starting the next item at the same indentation, ending the list on an empty item; `o` on an item opening the next one below it, as Enter at its end would, on an empty item too, since `o` leaves the line it's on as it is, and `O` the one before it, taking its number, the items after numbered one more. Each stretch written in Markdown is read on its own by `@codemirror/lang-markdown`'s GFM parser, mounted in the buffer's syntax tree where the stretch is, the comments under an item's lines left out of the item's text so a table or a list goes on past them (`page/src/markdown.ts`).
- **A change** (an approval, a held change, and the files of a "since you approved" drawer) shows each file whole, opened by the judge's reading of it: a header line saying what happened to the file and why it's open (held first, then flagged, else `automatic`, whose file folds away under its header); what the change adds and removes, each removed line in place; each line that matters barred, tinted in the colour of what it triggered, and saying it (`◂ held: adds an ignore`, `◂ flagged: public API: …`, `◂ told: regex: …`); runs of unchanged lines folded but for 3 lines around each change and each line that matters, under a summary line (`6 unchanged lines, 1–6`), so a held change and a drawer's file show every change they make; in an approval, which may change tens of thousands of lines, a file whose asks are each on a line folds every run but those lines and their context, changed ones among them (`17 lines, 2 changed, 1–16`); its text highlighted, each line painted as it comes into view, so a long approval paints only what's on screen. An approval's files read from their parse alone say `reading types` until the host has read them whole, then are laid out anew with no reload (`docs/trust.md`).
- **Each function's and class's body,** in Python, TypeScript and JavaScript, read from the file's syntax, folds under the line declaring it, open until closed. A run of lines never crosses a body's edge: one that would is cut there, and the line declaring a body around a change stays in view between the two parts, as git's hunk header names the function, so every fold sits whole inside another or beside it.
- **Under each item an agent's call made** is its moment in that conversation (`docs/inbox.md`, *An item's moment*), folded, read, never commented.
- **Every fold has a kind,** in the order they nest: the item whole under its header, folded once it's marked read or left for later; a file under its header, folded where it's automatic; a body; a run of unchanged lines; the item's context, folded; each of an agent's drawers, folded until opened, and in its conversation each earlier exchange, each run of calls and each call's input and output (*The drawers*). The margin has a column for each depth folds nest to, outermost leftmost: beside a fold's summary line, in its column, its kind's letter (`i`, `f`, `b`, `u`, `c`, the drawers' `t`, `s`, `v`, and a conversation's `e`, `k`, `d`, Space `z`'s) in its kind's colour, outlined where it's folded, as a folded one's placeholder is, a file's, a body's or an item's saying how many lines it hides. Each fold the cursor is in shows as a thin bar in its kind's colour down its letter's column, from under the letter to its last line, as indent guides do, so each bar begins with its letter (`page/src/margin.ts`). A fold is named by what it hides (its item, its kind, its file, the bodies it's in, and a run's bodies held or first line), never by where it's laid out, so an item or a drawer laid out again, as a drawer takes in what the agent wrote, keeps each fold as the operator left it.
- **The header over the review** names where the cursor is: the group, by its banner, then the item, the file and each fold it's in, each marked by its kind; while a comment or a message is written, outlined first, whom it goes to (`to lup-impl/parser`; a comment on an approval, the session whose push asked it); at its end, what waits below, so the operator knows without the text moving to show it: how many items are to answer, a question, a held change, an approval, and how many are new since they last sent, among those not yet marked read or left for later. On a narrow screen, as a phone's, it's two lines, the count left out, the group over the rest, a path cut at its start and a body around another left out; the page is one column there too, the banner and the drawers working as on a desktop.
- **Comments are written into the buffer,** each under the line or passage it's about, with vim's own keys; only comments can be edited. A comment on a file's lines quotes them under the path and line numbers, so the agent finds them. On a group's banner, the operator writes a message to that agent instead.
- **A thread under an item** (`docs/inbox.md`, *Replying by id*): an item an agent replied on by id comes back, its header saying "replied", with the operator's earlier comment under the line it was on, after `you:`, read, and the agent's reply under that, marked `↳` and set in; a ruling under its decision, a comment on the whole under the header. A comment opened on a reply's line, or on a passage of it, continues the thread: it's placed under that line, and reaches the agent as a quote of the reply by its id (`Comment.on`). The thread is read from the operator's own items answering the one shown (`Items.answers`), each comment by its part's id, only the copy sent to the item's sender, so a review's copy for another agent repeats none (`threadsOf`, `page/src/review.ts`).
- **Answering:** an item marked read, left for later, approved or declined, its comments going with the answer: a held change's to the agent waiting on it, an approval's to the session whose push asked it.
- **The draft** is kept on the host as it's written, so closing the page loses nothing. Sending makes it one reply, sent whole to each conversation with a comment on its items, a question among them, or a message to it: the operator answers related items together, across agents and repositories, and sends on moving to something unrelated. Each agent reads its own message and items first, then the others' commented items as context. A message only marked read tells its agent nothing and wakes no one, unless the reply reaches that agent anyway; a question only marked read is answered by the reply, and an approval or a held change only marked read is approved. The line under the review says, before it's sent, who it reaches, what it approves and what it leaves unanswered: an approval commented on stays unanswered, its comments going to the session that pushed, and a held change commented on is approved with them, since only declining declines, but for a hold at landing, which a comment leaves unapproved, its comments going to the conversation landing.

**The banner** over each agent's group carries what a tree's row would (`page/src/App.tsx`'s `banner`): its repository, worktree and conversation, by its path and under its parent; what it's doing and for how long (calling a tool, asking lup, between calls, ended), kept with the launch so a host service started again still shows it; what it's working on, its name after its task and the current entry of its task list where its runtime keeps one; and a context ring, the tokens in use against its window (`◔ 112k/1M`), read from its runtime's record (`inbox-show-conversation`'s `usage` and `tasks`; `docs/field-notes.md`, *A session's record*, *A thread's rollout*) at each of its hooks the host hears, which the listing watched says (`Talker.activity`), as its conversation drawer opens, and a minute apart at most besides; nothing is polled faster, since reading every agent's record every few seconds slowed the page. `h` on the banner turns the operator's switch to hold each flagged write of the conversation and its subagents, and the banner says "holding" (`docs/judging-writes.md`, *What each change gets*). Ctrl+K, the command palette, goes to any agent's group.

**The keys.** The line of keys under the review says where the cursor is (a comment, a banner, an item, a change, a file, a fold) and the keys that apply there, and `?` lists every key, in parts (`page/src/keys.ts`, `Keys.tsx`): that list, not this doc, is where each key is described. Space leads a chord (Space `c` opens a comment on an item whole, Space `d` marks it read, Space `a` and `x` approve and decline, Space `p` parks it, leaving it for later, Space `a` on a file of a "since you approved" drawer marks it reviewed and Space `A` every file it shows, Space `z` and a letter opens every fold of a kind in the item, as vim's fold keys begin with `z`, Shift and the letter closes them), and a chord begun and held a moment shows a panel of the keys that may follow; the line of keys, the list and that panel are read from one table, so they can't disagree. Vim's own keys move, fold, undo through the draft's history and edit comments, and Ctrl+Enter outside a comment sends (inside one, it ends the comment). The fold keys act on the item or the drawer the cursor is in, never the whole review (`page/src/folds.ts`): `za` toggles the innermost fold it's in, the item's own from its header or text; `zr` and `zm` open or close one more level of the item, its files, then their bodies and unchanged lines, then its context, and `zR` and `zM` all of it, the item's own fold opening first and never closed by them; in a conversation, `zr` opens the exchange before those open, one step further back each time, then the runs of calls, and `zm` closes the earliest first, neither `zr` nor `zR` opening a call's input and output, which is read as it opens, so `za` and Space `z` `d` open it; `zj` and `zk` go to the next fold's start and the previous fold's end, `[z` and `]z` to the start and end of the open fold the cursor is in. A closed fold counts as its summary line: no motion opens one (`j`, `w`, `b`, `$`, `}`, `G`, `]]` and the like), the cursor passing over it as over that line, onto the line after it going on, back onto the summary line coming back (`page/src/editor.ts`, `pastFolds`), as CodeMirror would otherwise open every fold the cursor lands in, whatever moved it; a search (`/`, `n`, `N`, `*`, `#`) and a jump to what's hidden (`]a`, `]c`, `]n`, a comment opened in a closed fold) open the folds around where they go, those alone, saying so under the review (`opened 2 folds to reach it`). A dead key, as `` ` `` or `"` on a layout where it waits for the next key, reaches vim once, as what it types with that key (`"` then Space a `"`; `"` then `+` a `"+`, on a layout typing both), never as what it shows while it waits (`¨`), and neither key reaches vim itself; nothing typed outside insert mode lands, so a jump never types into a comment. `"+` and `"*` are the system clipboard, one register (`page/src/clipboard.ts`): a yank into it, as `"+yy`, writes the clipboard, saying so under the review once it's written (`1 line copied to the clipboard`), never naming the register as vim would (`"*`), and a put from it, `"+p`, reads it, once the browser lets the page. A browser gives the clipboard only to a page on https or localhost: one reached over plain http keeps what's yanked into `"+` to itself, and says so in the page's top line, as it does where the browser refuses. Ctrl+C on a selection copies it wherever the page is served.

**The look:** the first lup's dark palette, Claude Code's `dark-daltonized` colours beside VS Code's high-contrast dark theme, each text colour at 7:1 or more on black, and on the tints a changed line and a line that matters carry, each the strongest of its colour that keeps that; monospace throughout, one row a line, structure from borders, emphasis by outlines and bars rather than fills.

**The demo:** `lup-dashboard demo` serves the real page over stand-in data (`lup_dashboard/demo.py`): launches over three repositories, subagents working, asking and ended, most kinds of item, an approval read from its parse first, a question arriving ten seconds after the page first asks for the inbox, to a group above the rest, a conversation for each agent, each call saying what it did with its input and output to read, the second runtime's in its own tools, a task list and a context for some, and for the parser subagent a branch with a new module flagged on it and its test, to which two writes come twenty seconds after the page first asks what it changed, as a call of its to `Edit` ends: the module grown, and a change to the clock beside it, flagged. A session building a view looks at it with the demo, on a port of its own (`--port 0`, since another session's demo may hold the usual one, #248), driving the room's Chromium headless through Playwright with `/usr/sbin/chromium` as its `executablePath`, since Playwright's own browser isn't installed; and the operator can open it to try one. Where a view needs real key events, a keyboard layout's dead keys among them, which headless Chromium never sees, the session starts `Xvfb` on a display of its own, sets that display's layout with `setxkbmap` (`-rules evdev -model pc105 -layout us -variant intl` for US-International), runs Playwright's Chromium with a window there (`headless: false`, and `--ozone-platform=x11`, since the room names a Wayland display for its clipboard), and types with `xdotool`; `DISPLAY` is set for those programs alone, since one set for the whole room breaks headless Chromium's WebGL.

## The drawers

At the end of each agent's group, after its items, three folds the operator pulls open, each a fold kind of its own (`FOLD_KINDS`, `page/src/keys.ts`), folded by default and opened with the fold keys, so what waits on the operator comes first and an agent's drawers stay with its items (`page/src/review.ts`'s `drawers`).
- **Tasks** (`t`): the agent's task list whole, as its runtime keeps it, each entry marked done, in progress or to do; "none kept" where it keeps none.
- **Since you approved** (`s`): everything its branch changed, read as the worktree stands, uncommitted changes among it (`policy-show-since`; `lup_dev/policy/since.py`), each file in path order: whole, with its diff from the version of it the operator last saw on that branch, the one they last marked reviewed or one kept beside a flag or a hold they approved, read or commented on, whichever came last, or from the integration branch's tip where they saw none, as a hold at landing starts from it (`docs/judging-writes.md`, *Landing a branch*); the parts the judge flagged marked and open, by its reading of the file's latest flag; a new module with its design in view and its bodies folded; a comment on its lines a remark recording the version it was written on, so the agent is told which quoted lines changed since. A file standing as they last saw it is one line in its place, with nothing under it: `reviewed at` the version, as git abbreviates its id, or the item they saw it in, so the drawer shows the whole branch and reviewing moves nothing. Its summary line says how many files are to review, how many have flagged writes waiting, which the branch's landing waits on, and how many are reviewed (`since you approved on feat · 3 to review · 1 flagged · 2 reviewed`): the agent's flags in a line, as the inbox lists them (`docs/inbox.md`, *The operator's face*).
  - **Reviewing:** Space `a` on a file, flagged or not, marks it reviewed at the version shown, as a forge's "viewed" box is ticked (`policy-review-since`; `lup_dev/policy/reviewed.py`), and it becomes that one line until the agent writes it again, when it comes back with only what changed since; Space `A` does so for every file shown. Each mark is kept on the host per repository, branch and path, with the version's bytes, so it outlasts a restart and the worktree's store. Marking a file approves the flags on it only where the file still stands at the version shown, a fresh snapshot says, since a write that came after the page read it is one the operator hasn't seen: its flags wait, and the file comes back with it.
  - **Live:** the drawer takes in what the agent writes as the page reads it, the file under the cursor among them, the cursor's line staying where it is on screen (*The review*). Each line changed since the operator last looked at its file has a dot after its number, in the drawer's colour, and the line after lines gone since is ruled above: against the version shown as the cursor last left that file, or as the drawer was first read on the page; a file that came after, or came back once reviewed, has each of its changes marked (`page/src/since.ts`). The page asks, with the version it shows, as a call of the agent's that may have written ends (one to a tool that isn't lup's own, as its activity shows), as the drawer opens, after a file is marked, and a minute apart at most besides, since each asking snapshots the worktree; the host answers without the files where nothing changed.
- **Conversation** (`v`): the whole conversation from its start, read from its runtime's record (`page/src/conversation.ts`), live, its latest part open: everything since the operator's last words, the steps there the summary line counts. It's kept small by folds rather than cut, so the operator brings in what came before a fold at a time, each loaded or laid out as it opens:
  - **Each exchange before the operator's last words** (`e`) folds under the first line of their words that opened it (`you: …`), so the folded conversation reads as what they said, line after line; what came before their first words folds under a line of its own. `zr` opens the latest exchange still folded, each one reaching a step further back (*The keys*). A resumed conversation's earlier launches are in the same record on both runtimes, so they're more exchanges, not marked apart (`docs/field-notes.md`, *A session's record*, *A thread's rollout*; #278).
  - **Each call is a line saying what it did** (`· Bash: Run the gate`), read from its input by its runtime's reader (`Called.gist`): a command's description, else the command; the file a read reads and the line it starts at (`Read: review.ts:480`); the file a write or an edit writes, the files a patch touches; a search's pattern; any other tool's first argument. A line, cut and marked where it's long, since the page reads every agent's record at each hook; the call's whole input is under it.
  - **A run of three calls or more** (`k`) starts as one line saying how many of which (`· called Bash ×2, Read`), and opens to a line each.
  - **A call's input and output** (`d`) fold under its line, read from the record only as the fold opens (`inbox-show-calls`; `Reader.calls`), those opened together asked together: each argument after its name, what the call returned whole, or that it hasn't returned yet, read again as the record grows. Where Claude Code gave the agent only the start of a command's output and saved the whole beside the record, the whole is read, only from the session's own folder.
  - **Every item the conversation sent or was sent** is a line where it happened with its text folded under it (`→ @51 question to you · answered by @53`, `← @53 your answer to @51`).
  - **What arrives is added at the end:** anyone reading keeps their cursor, their folds and what they're writing.
  - **A comment on the agent's words is a remark** (`docs/inbox.md`, *As tags*), under the line it's on, whichever exchange that is; the message to the agent is written under its banner, as it is for any group, and goes with the reply.

Each remark and message is part of the draft, kept on the host as it's written and sent with Ctrl+Enter as one reply (*The review*): the agent reads its remarks beside its message, each quote with the operator's reply under it.
