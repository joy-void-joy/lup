# The dashboard

Where the operator works with lup: every agent the host serves, across every repository, on one page. `lup-dev dashboard` opens it. Its package is `packages/lup-dashboard/` (`lup_dashboard`), which imports `lup-dev` and is never imported by it.

## Running

- **The host service runs it as its child** (`DashboardProcess`, `lup_dev/host/dashboard.py`), begun once the service listens and ended as it stops: `lup-dashboard serve <port>`, with `--address` for each address beyond localhost, found beside the interpreter running the service, where lup's own approval installs it beside `lup-dev`. Where it isn't installed, there's no dashboard, and `lup-dev dashboard` says why.
- **It goes with the service however the service ends:** the service writes the API's token on its input and keeps it open, and the dashboard ends when it closes. Its first line of output is the address it listens on, on localhost; one that ends before printing it, its port taken, is said.
- **On localhost, and on each address `LUP_DASHBOARD_ADDRESSES` names** (*Access*), **on one port** (`LUP_DASHBOARD_PORT`, 8766 by default), and **one token**, kept in the host's state with mode 600, which no room mounts, the same at each start, so a page left open reconnects on its own once the service starts again, after an approval among others.
- **`lup-dev dashboard`** prints the address with the token in its fragment and opens it in the browser, on localhost, starting the dashboard again where it's gone. Where the dashboard listens beyond localhost, it prints that address instead, the first named, drawn as a QR code for a phone to scan where `qrencode` is installed, an optional requirement of the host (`docs/launch.md`, *The command*); `--address` prints another the dashboard listens on, and `--copies` opens the plain page there instead, with nothing to paste (*The plain page*). It refuses inside an agent's session. `lup-dev dashboard timings` says how long its keys took to reach the screen in the operator's browsers (*Its timings*), in a room too.

## Access

Rooms share the host's network, so being on localhost keeps out only other machines.
- **Every call carries the token,** in the page's cookie (`HttpOnly`, `SameSite=Strict`, named after the port, since a browser shares localhost's cookies across ports) or as a bearer. The page is handed it in its address's fragment, which no request carries, trades it for the cookie and takes it out of the address. A page whose token is refused says so and stops, rather than retrying what retrying can't mend.
- **From another device,** as the operator's phone when they're out: `LUP_DASHBOARD_ADDRESSES`, in the host service's environment on the operator's machine, never in a project, names each address of the machine's the dashboard listens on beside localhost, separated by spaces, their WireGuard address among them (`LUP_DASHBOARD_ADDRESSES=10.8.0.2`). Each is bound whether or not the machine holds it yet (Linux's `IP_FREEBIND`), so a dashboard started before the tunnel is up answers there once it is. Addresses only, never `0.0.0.0`, which is refused: it would offer the dashboard on every network the machine joins, a café's among them, with the token as its only wall, where an address of the tunnel's lets in only the devices the tunnel admits. The token stays required there: the tunnel can't tell a room's process from the operator, and the dashboard answers trust's approvals, which install the code the host runs, so without it code in a room could approve its own push through any address bound. `lup-dev dashboard` hands the phone the token in the address it draws (*Running*), which the page trades for a cookie of that host's own, since a browser keeps cookies per host. Served over plain http there, the page keeps the clipboard to itself and says so (*The page*).
- **A request naming another host** than `127.0.0.1`, `localhost` or an address it listens on is refused, as is a call from a page of another origin.

## The API

The page asks the host service only what the operator's commands ask it: the host's own control requests, relayed as they are (`lup_dashboard/server.py`, FastAPI).
- **`POST /api/ask`** takes one request and returns its reply, a refusal among them. The page may send only the requests the operator's views need, listed in `lup_dashboard.api`, a module's view among them, which the host puts to the repository's process and watches at the view's own triggers, and one of its actions (`docs/host.md`, *The views the dashboard shows*); any other is refused before it reaches the host. An approval approved here is acted on as the operator's terminal acts on it, in a process of its own, since installing lup's own repository's copy restarts the host service, and the dashboard with it.
- **`/api/socket`,** a WebSocket, carries every watch a page holds, each under a number the page picks, answered at once and again each time it changes, through the host's watch socket (`docs/host.md`, *Watching*). One socket for every watch, since a browser keeps six connections to a host, which a stream per watch used up in three tabs.
- **The API's description** is the server's own OpenAPI document, made from the host's pydantic models, and the page's types are generated from it, so the two can't drift: the building blocks a view answers, and each repository's looks, its fold kinds, tones and drawers, which the listing gives (`Listed.looks`), among them.

## The page

**Built** from `packages/lup-dashboard/page/`: TypeScript, React, React Aria Components for controls the keyboard reaches, cmdk for the command palette, and CodeMirror 6 with its vim mode for the review and the conversations. `packages/lup-dashboard/build.py` installs its packages from their lock, generates the types from the API's description, type-checks, runs its tests and builds, as `LupDevelopment`'s `dashboard` step and in trust's build of the copy the operator approves. Its packages are pinned exactly, nothing published in the last three days resolving. A page left open reloads itself when it reconnects to a build that isn't the one it loaded, as after lup is installed again and the dashboard restarted on it, its drafts kept on the host, so it never asks a server for what it no longer answers. Its tests are `packages/lup-dashboard/tests/` for the server, `page/src/*.test.ts` for the page, and `page/drive/*.test.ts` for the driver sessions drive it with (*The demo*), run in the room alone, where Chromium is.

**The review** is the page's one view: everything waiting for the operator, across every agent and repository, in two panes, a list of who's there and one buffer at a time, each moved through with vim and written in (*The panes*; `page/src/review.ts`, `Review.tsx`). What's below holds within whichever buffer is on screen. The address reaches the same review as one buffer beside the overview (`?panes=off`), a fallback from the panes: it reads no concerns, so it lists none and lays out no concern's block.
- **A tree of views and blocks,** each part kept by an id it keeps across layouts (`Laid.nodes`): an agent's group by whose it is, its banner, an item by its number, each view mounted in them by its instance, its module, view and argument with its repository (`page/src/views.ts`), each of the view's blocks by the instance's id and its own, and what the operator wrote. The core lays out the frame: the groups, their banners and order, an item's header, what the operator's words an answer answers are, its edits, the passages its citations cite, the replies kept from before, its context and the comments. What's in the frame is each module's view, answering the building blocks (`docs/declaration.md`, *Views and blocks*): an item's body is its kind's view of it, its text and its files, and its summary, the words its header says after its number, before the core's (`edited`, `new`, when it came and how long it has waited); a drawer is a view of the agent, as each part of the banner after the core's words is. The page lays some of them out itself until each moves into its module (#113, step 4), each by a producer named after that module, answering the same generated block types the module's Python does, from what the page has read, and pinned by fixtures that module's Python will match (`page/src/views/`, `page/src/fixtures/views/`): lup's approvals, the core's; a held change, a flagged write, "since you approved" and holding, the judge's; questions, notes, turns' ends and the rest, the agent-facing inbox's; and the task list, what an agent's working on and their context's ring, the runtime adapters'. So CodeMirror carries the cursor, a selection, vim's visual one among them, the folds and the view through a layout as it does through typing, and nothing of where the reader is, is worked out again: the cursor moves only with the text, and where what it was on is gone, as an item a reply sent takes, it's on what follows. Each line a layout puts in or changes, but the operator's own words, flashes once as it arrives, for a moment of its own whatever comes after it, so what came while they read is seen to come; nothing is held back while they write. What the page reads as it loads isn't what came while they read: nothing flashes until the review, laid out from what it's read, has gone a second with no layout, or five seconds on under agents at work (`readBy`, `page/src/reconcile.ts`). **What's typed in a comment shows at once,** CodeMirror's own, and the review is laid out with it once typing pauses for 300 ms, as the comment ends, or as anything else lays the review out, which lays it out with what's typed: laying the whole review out at each key, before the key was drawn, made typing lag by seconds on a large review.
