# The dashboard

Where the operator works with lup: every agent the host serves, across every repository, in one page. `lup-dev dashboard` opens it.

Its package is `packages/lup-dashboard/` (`lup_dashboard`), which imports `lup-dev` and is never imported by it.

## Running

- **The host service runs it as its child** (`lup_dev/host/dashboard.py`, `DashboardProcess`), a `Companion` begun once the service listens and ended as it stops. The service runs `lup-dashboard serve <port>`, found beside the interpreter running the service: lup's own approval installs the dashboard there, in the person's own copy beside `lup-dev` (`uv tool install --with`, held to the lock like the rest; the repositories' judge copies leave it out), its page built by trust as the gate builds it. Where it isn't installed, there's no dashboard, and `lup-dev dashboard` says why.
- **Its input:** the service writes the API's token as its first line and keeps the input open; the dashboard ends when it closes, so it goes with the service however the service ends.
- **Its output:** its first line is the address it listens on, which the service reads; a dashboard that ends before printing it (a port another program holds) is said, and the service goes on without it.
- **On localhost, on one port** (`LUP_DASHBOARD_PORT`, 8766 by default), the same at each start, and **one token**, kept in the host's state (`HostLayout.dashboard_token`, mode 600), which no room mounts. So a page left open reconnects on its own once the service starts again, after an approval among others.
- **`lup-dev dashboard`** asks the service for the address (`ShowDashboard`), the token in its fragment, starting the dashboard again where it's gone; it prints it and opens it in the browser (`--no-open` only prints). It refuses inside an agent's session.

## The API

The page asks the host service only what the operator's commands ask it: the host's own control requests, relayed as they are.

- `POST /api/ask` takes one request (`lup_dashboard.api.Asked`) and returns its reply (`Replied`), a refusal among them.
- `/api/socket`, a WebSocket, carries every watch a page holds: the page starts one with a number it picks (`Watch`) and stops it (`Unwatch`), and the server sends each reply under its number (`Watched`), at once, then again each time it changes, through the host's watch socket (`docs/host-tools.md`, *Watching*); a watch the host ends, or can't serve, is said (`Ended`), and the page starts it again after a wait. One socket for every watch, since a browser keeps six connections to a host, which a stream per watch used up in three tabs. A socket whose token or origin is refused is closed with 4401 or 4403, which the page says rather than retrying.
- The requests the page may send: the launches served and their conversations (`ListLaunches`), a launch renamed, the operator's inbox listed, an item shown, answered, finished or sent, an approval answered and its diff read (one approved here acted on as the operator's terminal acts on it: `lup-dev inbox answer <n> --approve` started in a process of its own, `Host.settle`, which installs the copy and restarts the host service on it, outliving the dashboard it restarts), and the operator's draft shown, kept and sent. Any other is refused before it reaches the host.
- The server (`lup_dashboard/server.py`, FastAPI) talks to the host through `Host`, a seam its tests fill with a stand-in; `Sockets` reaches the running service, through `lup_dev/host/client.py`'s `answer` and `replies`.
- The API's description is the server's own OpenAPI document (`lup-dashboard openapi`), made from the host's pydantic models; the page's types are generated from it.

## Access

Rooms share the host's network, so being on localhost keeps out only other machines.

- Every call to the API carries the token: in the page's cookie (`HttpOnly`, `SameSite=Strict`, named after the port, since a browser shares localhost's cookies across ports) or as a bearer. A page whose token is refused says so and stops watching, rather than retrying what retrying can't mend.
- The page is handed the token in its address's fragment, which no request carries, trades it for the cookie (`POST /api/session`) and takes it out of the address.
- A request naming another host than `127.0.0.1` or `localhost` is refused, as is a call from a page of another origin.

## The page

- **Built** from `packages/lup-dashboard/page/`: TypeScript, React, React Aria Components for controls the keyboard reaches, cmdk for the command palette, CodeMirror 6 with its vim mode for the review and the conversations, and Vite, which writes the page into the package (`lup_dashboard/page/`, ignored by git). `packages/lup-dashboard/build.py` installs its packages from their lock, writes the API's description and generates the types from it, type-checks, runs its tests (Vitest), and builds. It's `LupDevelopment`'s `dashboard` step in lup's gate, run where one of its sources, the host's models among them, is newer than the page; trust runs it too when it builds the copy the operator approves. Its packages are pinned exactly, nothing published in the last three days resolving (`min-release-age`).
- **The review:** the page's home, beside the agents. Everything waiting for the operator, across every agent and repository, laid out as one buffer (`page/src/review.ts`, `Review.tsx`, on the editor it shares with the conversation, `editor.ts` and `comments.ts`), in groups, one per agent, each under a banner naming its repository, worktree and path, sorted so an agent's neighbours are its worktree's and its repository's. Each item is under a header saying what it is and when; a question's decisions are numbered with their leans; an approval, or a change held for the operator (`HeldChange`, `docs/judging-writes.md`, *Asking the operator*), shows its summary, then its whole diff, coloured as git colours it. Under each item an agent's call made is its context, its moment in the conversation that sent it (`ShowContext`, asked once the item is in the inbox): a line a step, the operator's words (`you:`) and the agent's (`agent:`), each run of calls in one line (`· called Bash ×2, Read`), the call that made the item marked (`→ called … · this item`); one whose context can't be read says why, in one line. The context and the whole diff are folded by default under a summary line (`▸ context · 9 steps, from your words 5m before this item`), with CodeMirror's own folds (`@codemirror/language`), and read, never commented: a comment opened on one of their lines goes nowhere. It's moved through with vim (CodeMirror 6 with `@replit/codemirror-vim`). The operator's comments are written into it, each under the line it's on, and edited as text with vim's own keys; only comments can be edited:
  - insert mode is writing a comment: a key that enters it opens one where the cursor is, or edits the one it's in, and the cursor stays in it while it lasts (the arrows stop at its ends; a click elsewhere ends it). `c` opens one on the item whole; `o`, `C`, and vim's other keys of insert mode (`i`, `a`, `I`, `A`, `s`…) on the line; `v` and a motion, then `c` or `s`, on the selection. A decision is answered on its line ("Yes, but…"). Inside a comment, `c` and the rest are vim's own;
  - Ctrl+Enter in a comment ends it, the cursor back on what it's about; Esc ends it where it is; an emptied comment is dropped. The line of keys under the review says when a comment is being written;
  - `u` and Ctrl+R undo and redo any change to the draft: a comment, from its opening to its end, is one step, so Esc then `u` drops one just written;
  - Space `d` marks an item read, Space `z` leaves it for later (what's on it stays drafted), Space `a` or `x` approves or declines an approval or a held change, the comments written under it going with the answer, an approval of a host zone approved here installed and the host service restarted on it, the page reconnecting on its own; `J` and `K` go to the next and previous item;
  - vim's fold keys: `za` opens or closes the fold under the cursor, `zo` and `zc` open and close it, `zR` and `zM` open and close them all; a click on a fold's `…` opens it, as does a motion or search into it. A fold the operator opened stays open each time the review is laid out again, as the draft or the inbox changes;
  - Ctrl+Enter elsewhere sends, at once: the line under the review names who the reply reaches as it's written.
- **The draft** is kept on the host as it's written (`Draft`, `inbox/store.py`; `ShowDraft`, `KeepDraft`), so closing the page loses nothing; a line under the review says what it covers and who it reaches. Sending it (`SendDraft`, `Delivery.reviewed`) makes it one reply, sent whole to every conversation with a comment on its items or a question among them (`Review`): the operator answers related items together, across agents and repositories, and sends on moving to something unrelated. Each is told its own items first, with the comments on them, or read with nothing to add; then each other agent's commented item, whole, whose it is and where, as context not to act on unless a comment says so. Each question it covers is answered by it, which lets a held `ask` go. A message only marked read (Space `d`) is taken off the list, telling its agent nothing and waking no one, unless the reply reaches that agent anyway. A draft covering nothing, or an item no conversation sent, is refused, saying which.
- **The demo says it's one** (`GET /api/about`), in the page's top line.
- **Selecting an agent** in the tree opens its conversation in the review's place (*The conversation*), its details under the tree. The review always shows everything waiting.
- **The agents tree:** each repository, its launches under it, each launch's session's conversation, each subagent under the conversation that spawned it, its subagents that are over folded under a count: those ended, and those no hook has been heard from since the host began keeping what each conversation does, which are from before; and what each is doing and for how long (`Talker.activity`): calling a tool, asking lup, between calls, ended. What each is doing is kept with the launch's conversations (`Conversations.activities`), so a host service started again still shows it. Arrows move through it, Enter selects, Left and Right fold.
- **The details** of the conversation selected: its kind, its session and subagent ids, its subagents, and its launch's runtime, worktree and id.
- **The command palette,** Ctrl+K: the review, and every agent's conversation, to go to.
- **The look:** the first lup's dark palette (its `palette.ts`): Claude Code's `dark-daltonized` colours beside VS Code's high-contrast dark theme, each text colour at 7:1 or more on black; monospace throughout, one row a line, structure from borders, emphasis by outlines and bars rather than fills.
- **The demo:** `lup-dashboard demo` serves the real page over stand-in data (`lup_dashboard/demo.py`): launches over three repositories, subagents working, asking and ended, a question and a note; a stand-in conversation for each agent, the parser subagent's growing a step each time it's asked, and the messages sent to them kept in memory. A session looks at a view with it while building it, driving the room's Chromium headless, and the operator can open it to try one.

## The conversation

Selecting an agent in the tree, or in the palette, opens its conversation in the review's place (`page/src/conversation.ts`, `Conversation.tsx`): one buffer with the review's look, vim keys and folds, its title bar saying whose it is. Space `r`, a click on the title bar's *waiting on you*, or the palette's *the review* brings the review back as it was left. Each subagent opens its own.

- **What it shows:** the whole conversation from its start, read from its runtime's record (`ShowConversation`): the operator's words (`you:`) and the agent's (`agent:`), their paragraphs kept, each run of calls in one line. What came before the operator's last words when it opened is folded under a summary line (`earlier · 37 steps, from 2h before your last words`).
- **Live:** the page asks for the steps after those it has each time the agents list changes, at every hook, and every five seconds besides, for a record written just after its hook. What arrives is added at the end, the text before it untouched: a reader on the last line, or writing their message at the end, is followed; anyone else keeps their cursor, what they see, the folds they opened and the comment they're writing.
- **Writing:** comments on the agent's lines, as in the review: `o`, `C` and the keys of insert mode on the line, `v` and a motion then `c` or `s` on the passage, each under the line it's on; none on the operator's words or the calls. `c` writes the operator's message on the whole, at the end under `── your message ──`; Ctrl+Enter in it goes back to where they were. `u`, Ctrl+R and the fold keys are the review's; `J` and `K` go to the next and previous turn.
- **Sending:** Ctrl+Enter outside a comment sends the comments and the message at once, as one message through lup (`SendItem`), the line under the buffer naming the conversation as they're written: each comment under what it quotes, set off with `> ` as a mail quotes, in the conversation's order, the message last. The agent reads it at its next call, or is woken. Once sent, the comments are cleared.
- **What was sent** shows where it was sent, after the steps the conversation had then, as `you, through lup · #N:` and its text: it reaches the agent through lup's tools, so its record doesn't hold it as the operator's words.
- **The draft** is kept for each conversation in the page and in its `localStorage`, with what was sent from here, so a reload keeps both; the host doesn't keep them.
