# The dashboard

Where the operator works with lup: every agent the host serves, across every repository, in one page. `lup-dev dashboard` opens it.

Its package is `packages/lup-dashboard/` (`lup_dashboard`), which imports `lup-dev` and is never imported by it.

## Running

- **The host service runs it as its child** (`lup_dev/host/dashboard.py`, `DashboardProcess`), a `Companion` begun once the service listens and ended as it stops. The service runs `lup-dashboard serve <port>`, found beside the interpreter running the service: lup's own approval installs the dashboard there, in the person's own copy beside `lup-dev` (`uv tool install --with`, held to the lock like the rest; the repositories' judge copies leave it out), its page built by trust as the gate builds it. Where it isn't installed, there's no dashboard, and `lup-dev dashboard` says why.
- **Its input:** the service writes the API's token as its first line and keeps the input open; the dashboard ends when it closes, so it goes with the service however the service ends.
- **Its output:** its first line is the address it listens on, which the service reads; a dashboard that ends before printing it (a port another program holds) is said, and the service goes on without it.
- **On localhost, on one port** (`LUP_DASHBOARD_PORT`, 8766 by default), the same at each start, and **one token**, kept in the host's state (`HostLayout.dashboard_token`, mode 600), which no room mounts. So a page left open reconnects on its own once the service starts again, after an approval among others.
- **`lup-dev dashboard`** asks the service for the address (`ShowDashboard`), the token in its fragment, starting the dashboard again where it's gone; it prints it and opens it in the browser (`--no-open` only prints). It refuses inside an agent's session.

## The API

The page asks the host service only what the operator's commands ask it: the host's own control requests, relayed as they are.

- `POST /api/ask` takes one request (`lup_dashboard.api.Asked`) and returns its reply (`Replied`), a refusal among them.
- `/api/socket`, a WebSocket, carries every watch a page holds: the page starts one with a number it picks (`Watch`) and stops it (`Unwatch`), and the server sends each reply under its number (`Watched`), at once, then again each time it changes, through the host's watch socket (`docs/host-tools.md`, *Watching*); a watch the host ends, or can't serve, is said (`Ended`), and the page starts it again after a wait. One socket for every watch, since a browser keeps six connections to a host, which a stream per watch used up in three tabs. A socket whose token or origin is refused is closed with 4401 or 4403, which the page says rather than retrying.
- The requests the page may send: the launches served and their conversations (`ListLaunches`), a launch renamed, the operator's switch for a conversation turned (`SetHolding`), the operator's inbox listed, an item shown, answered, finished or sent, an approval or a held change answered and each file it changes read (`ShowFiles`; an approval approved here acted on as the operator's terminal acts on it: `lup-dev inbox answer <n> --approve` started in a process of its own, `Host.settle`, which installs the copy and restarts the host service on it, outliving the dashboard it restarts), the operator's draft shown, kept and sent, what they write on a conversation shown and kept, and the items a conversation sent and was sent listed (`ListItems`). Any other is refused before it reaches the host.
- The server (`lup_dashboard/server.py`, FastAPI) talks to the host through `Host`, a seam its tests fill with a stand-in; `Sockets` reaches the running service, through `lup_dev/host/client.py`'s `answer` and `replies`.
- The API's description is the server's own OpenAPI document (`lup-dashboard openapi`), made from the host's pydantic models; the page's types are generated from it.

## Access

Rooms share the host's network, so being on localhost keeps out only other machines.

- Every call to the API carries the token: in the page's cookie (`HttpOnly`, `SameSite=Strict`, named after the port, since a browser shares localhost's cookies across ports) or as a bearer. A page whose token is refused says so and stops watching, rather than retrying what retrying can't mend.
- The page is handed the token in its address's fragment, which no request carries, trades it for the cookie (`POST /api/session`) and takes it out of the address.
- A request naming another host than `127.0.0.1` or `localhost` is refused, as is a call from a page of another origin.

## The page

- **Built** from `packages/lup-dashboard/page/`: TypeScript, React, React Aria Components for controls the keyboard reaches, cmdk for the command palette, CodeMirror 6 with its vim mode for the review and the conversations, its language packages highlighting a changed file, and Vite, which writes the page into the package (`lup_dashboard/page/`, ignored by git). `packages/lup-dashboard/build.py` installs its packages from their lock, writes the API's description and generates the types from it, type-checks, runs its tests (Vitest), and builds. It's `LupDevelopment`'s `dashboard` step in lup's gate, run where one of its sources, the host's models among them, is newer than the page; trust runs it too when it builds the copy the operator approves. Its packages are pinned exactly, nothing published in the last three days resolving (`min-release-age`).
- **The review:** the page's home, beside the agents. Everything waiting for the operator, across every agent and repository, laid out as one buffer (`page/src/review.ts`, `Review.tsx`, on the editor it shares with the conversation, `editor.ts` and `comments.ts`), in groups, one per agent, each under a banner naming its repository, worktree and path, the group with the newest item first, its items in the order they came. Each item is under a header saying what it is, when it came and how long it has waited, to the minute, and "new", marked at the line's start, where it came after the operator last settled an item of theirs, read, answered or decided (`Items.reviewed`, `Inbox.reviewed`); a session's last words of a turn, which lup made a note (`Message.ending`), are headed `turn ended`, in another colour, as news to mark read rather than a question; a question's decisions are numbered with their leans; an approval, or a change held for the operator (`HeldChange`, `docs/judging-writes.md`, *Asking the operator*), shows its summary, then each file it changes (`ShowFiles`, asked once the item is in the inbox; `page/src/code.ts`):
  - a header line: its path, and what happened to it (created, deleted, changed by how many lines added and removed, or binary, not shown);
  - then what it becomes, whole, each line numbered in a gutter of its own; what the change adds marked `+` on blue; each line it removes in place, where it was, numbered as it was and marked `−` on red; a deleted file's lines all removed;
  - each run of unchanged lines more than 3 lines from a change folded under a summary line (`▸ 27 unchanged lines, 1–27`), so 3 lines of context stay around each change;
  - its text highlighted by CodeMirror's own language packages, chosen by the file's name (Python, TypeScript and JavaScript, Markdown, TOML, JSON), each line painted as it comes into view, so a long approval costs only what's on screen.

  Under each item an agent's call made is its context, its moment in the conversation that sent it (`ShowContext`, asked once the item is in the inbox): a line a step, the operator's words (`you:`) and the agent's (`agent:`), each run of calls in one line (`· called Bash ×2, Read`), the call that made the item marked (`→ called … · this item`); one whose context can't be read says why, in one line. The context and a file's runs of unchanged lines are folded by default under a summary line (`▸ context · 9 steps, from your words 5m before this item`), with CodeMirror's own folds (`@codemirror/language`); the context is read, never commented: a comment opened on one of its lines goes nowhere. Every line of a changed file is commented as the item's own text is: a comment on a line or a passage quotes it under the file's path and the lines' numbers, each line marked as a diff marks it (`cli.py:30-31`, then ` diff: …` and `+files: …`; removed lines alone are numbered as the file was), so the agent finds them; one on a file's header, the file. It's moved through with vim (CodeMirror 6 with `@replit/codemirror-vim`). The operator's comments are written into it, each under the line it's on, and edited as text with vim's own keys; only comments can be edited:
  - insert mode is writing a comment: a key that enters it opens one where the cursor is, or edits the one it's in, and the cursor stays in it while it lasts (the arrows stop at its ends; a click elsewhere ends it). Space `c` opens one on the item whole; vim's change, `c` and a motion, on the passage the motion covers (`ct.`, `ciw`, `cip`; `cc` on the line's text); `o`, `C`, and vim's other keys of insert mode (`i`, `a`, `I`, `A`, `s`…) on the line; `v` and a motion, then `c` or `s`, on the selection. A decision is answered on its line ("Yes, but…"). Inside a comment, `c`, `J` and the rest are vim's own. A dead key, as `` ` `` on a layout where it waits for the next key, reaches vim as what it composes (`` ` `` then Space, `` ` ``), so marks and jumps work on such layouts; in a comment it composes into the text;
  - Ctrl+Enter in a comment ends it, the cursor back on what it's about; Esc ends it where it is; an emptied comment is dropped. The line of keys under the review says when a comment is being written;
  - `u` and Ctrl+R undo and redo any change to the draft: a comment, from its opening to its end, is one step, so Esc then `u` drops one just written;
  - Space `d` marks an item read, Space `z` leaves it for later (what's on it stays drafted), Space `a` or `x` approves or declines an approval or a held change, the comments written under it going with the answer, each under what it quotes: a held change's to the agent waiting on it, an approval's to the session whose push asked it (one a launch asked at its terminal has no session to tell, `docs/host-tools.md`, *Parties and items*); an approval of a host zone approved here installed and the host service restarted on it, the page reconnecting on its own; an item marked read folds whole under its header, opening again once unmarked; `]]` and `[[` go to the next and previous item;
  - vim's fold keys: `za` opens or closes the fold under the cursor, `zo` and `zc` open and close it, `zR` and `zM` open and close them all; a click on a fold's `…` opens it, as does a motion or search into it. A fold the operator opened stays open each time the review is laid out again, as the draft or the inbox changes;
  - Ctrl+Enter elsewhere sends, at once: the line under the review names who the reply reaches as it's written;
  - Space `h`, or Space `w` `h`, gives the keyboard to the agents tree, on the conversation selected, or its first row.
- **The draft** is kept on the host as it's written (`Draft`, `inbox/store.py`; `ShowDraft`, `KeepDraft`), so closing the page loses nothing; a line under the review says what it covers and who it reaches. Sending it (`SendDraft`, `Delivery.reviewed`) makes it one reply, sent whole to every conversation with a comment on its items or a question among them (`Review`): the operator answers related items together, across agents and repositories, and sends on moving to something unrelated. Each is told its own items first, with the comments on them, or read with nothing to add; then each other agent's commented item, whole, whose it is and where, as context not to act on unless a comment says so. Each question it covers is answered by it, which lets a held `ask` go. A message only marked read (Space `d`) is taken off the list, telling its agent nothing and waking no one, unless the reply reaches that agent anyway. Approvals and held changes it covers are answered by their own rule (`Delivery.answered_in`): one marked read alone is approved, and an approval of a host zone approved so is installed as Space `a` installs it; a held change commented on is approved with the comments, which its agent reads with the answer ("yes, but…"), since only Space `x` declines; an approval commented on stays unanswered, its comments going as a note to the session whose push asked it, whose next push supersedes it, or staying drafted where no known session pushed it. The line under the review says what the send approves and what it leaves unanswered, and the top line what it did (`Reviewed`). A draft covering nothing, or a message no conversation sent, is refused, saying which.
- **The demo says it's one** (`GET /api/about`), in the page's top line.
- **A page reloads itself on a new build.** `GET /api/about` says the page's build as it stands on disk, a digest of its `index.html`, which names each asset by its content's hash. Each time the page's socket goes live it asks again, and where the build isn't the one it first saw, as after lup is installed again and the dashboard restarted on it, it reloads, its drafts kept on the host and what's written in the last 300ms kept as it closes: a page left open never asks a server for what it no longer answers.
- **Selecting an agent** in the tree opens its conversation in the review's place (*The conversation*), its details under the tree. The review always shows everything waiting.
- **The agents tree:** each repository, its launches under it, each launch's session's conversation, each subagent under the conversation that spawned it, its subagents that are over folded under a count: those ended, and those no hook has been heard from since the host began keeping what each conversation does, which are from before; and what each is doing and for how long (`Talker.activity`): calling a tool, asking lup, between calls, ended. What each is doing is kept with the launch's conversations (`Conversations.activities`), so a host service started again still shows it. Arrows move through it, Enter selects, Left and Right fold. `h` turns the operator's switch for the conversation it's on, "hold each flagged write", and its row says "holding" while it's on (`Talker.holding`; `docs/judging-writes.md`, *What each change gets*). Space `l`, or Space `w` `l`, gives the keyboard back to the review or the conversation shown; Space leads a chord there as in the views, so a key after it is never the tree's own.
- **The details** of the conversation selected: its kind, its session and subagent ids, its subagents, whether its flagged writes are held, and its launch's runtime, worktree and id.
- **The command palette,** Ctrl+K: the review, and every agent's conversation, to go to.
- **The look:** the first lup's dark palette (its `palette.ts`): Claude Code's `dark-daltonized` colours beside VS Code's high-contrast dark theme, each text colour at 7:1 or more on black; monospace throughout, one row a line, structure from borders, emphasis by outlines and bars rather than fills.
- **The demo:** `lup-dashboard demo` serves the real page over stand-in data (`lup_dashboard/demo.py`): launches over three repositories, subagents working, asking and ended, a question, a note and a problem, an approval and a held change, whose stand-in files are in each language highlighted, changed, created, and one binary; a stand-in conversation for each agent, the parser subagent's growing a step each time it's asked, the items each sent and was sent (the parser's note replied to, an ended subagent's whose reply went to its session), and the messages sent to them, as items, and the switch turned on each kept in memory. A session looks at a view with it while building it, driving the room's Chromium headless, and the operator can open it to try one.

## The conversation

Selecting an agent in the tree, or in the palette, opens its conversation in the review's place (`page/src/conversation.ts`, `Conversation.tsx`): one buffer with the review's look, vim keys and folds, its title bar saying whose it is. Space `r`, a click on the title bar's *waiting on you*, or the palette's *the review* brings the review back as it was left; Space `h` gives the keyboard to the tree, as in the review. Each subagent opens its own.

- **What it shows:** the whole conversation from its start, read from its runtime's record (`ShowConversation`): the operator's words (`you:`) and the agent's (`agent:`), their paragraphs kept, each run of calls in one line, and the items of lup's inbox it sent and was sent among them. What came before the operator's last words when it opened is folded under a summary line (`earlier · 37 steps, 2 items, from 2h before your last words`).
- **Its items:** every item the conversation sent or was sent, in every state (`ListItems`, watched, so an answer arriving shows), each in a line with its whole text folded under it, CodeMirror's folds as in the review (`za` opens one); the line is read, never commented. The host gives each item's text as the agent wrote it (a question with its decisions and leans, a held change with what's held) or as it's told it (an answer beside its question's decisions, a review as its agent reads it).
  - **One it sent,** `→ #51 question to you · answered by #53`: what it is, whom to, and where it stands: answered and by which items (an answer, a reply, a review covering it), read, waiting on you, withdrawn and why, or a held change approved or declined, with the operator's comment under its text. It's just after the call that made it, where the record holds that call (`Item.call`, `Called.id`), the run of calls broken there; else, as for a turn's last message, which no call made, by when it was made.
  - **One it was sent,** `← #53 your answer to #51`: your answer, reply, review or message, `not told yet` until it's told. It's where it was told (`Told.at`), else when it was made: after the last step at or before then, a step its record gives no time taking the time of the last before it, so in a record with no times they're all at its end.
  - **Passed on:** an item for a subagent that had ended, told to its session's main conversation, shows in both: in the session's, for whom it was (`, for lup-impl/survey-legacy, which had ended`); in the subagent's, where it went (`passed on to lup-impl`). A subagent's other items show in its own conversation alone, at its calls, which its parent's record doesn't hold.
- **Live:** the page asks for the steps after those it has each time the agents list changes, at every hook, and every five seconds besides, for a record written just after its hook. What arrives is added at the end, the text before it untouched: a reader on the last line, or writing their message at the end, is followed; anyone else keeps their cursor, what they see, the folds they opened and the comment they're writing. An item arriving, or one changing as it's answered or told, changes its own lines alone, the reader kept as for a step.
- **Writing:** comments on the agent's lines, as in the review: `o`, `C` and the keys of insert mode on the line, `v` and a motion then `c` or `s` on the passage, each under the line it's on; none on the operator's words, the calls or the items. Space `c` writes the operator's message on the whole, at the end under `── your message ──`, and `c` with a motion comments on the passage it covers; Ctrl+Enter in it goes back to where they were. `u`, Ctrl+R and the fold keys are the review's, on the innermost fold the cursor is on, an item's text being inside what came before; `]]` and `[[` go to the next and previous turn, an item's line among them.
- **Sending:** Ctrl+Enter outside a comment sends the comments and the message at once, as one message through lup (`SendItem`), the line under the buffer naming the conversation as they're written: each comment under what it quotes, set off with `> ` as a mail quotes, in the conversation's order, the message last. The agent reads it at its next call, or is woken. Once sent, the comments are cleared.
- **What was sent** is an item it was sent, shown once: `← #N your message, from here`, after the steps the conversation had then rather than when it was told, its text folded under it. It reaches the agent through lup's tools, so its record doesn't hold it as the operator's words; until its item is listed, it's shown from what was kept of it.
- **The draft** is kept on the host for each conversation, with what was sent from here (`Talk`, `inbox/store.py`; `ShowTalk`, `KeepTalk`), as the review's is, so another browser or machine shows both: kept 300ms after each change, and as the page closes or another conversation opens in its place. What the host kept arrives once the conversation opens, unless the operator began writing first.
