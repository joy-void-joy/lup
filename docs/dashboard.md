# The dashboard

Where the operator works with lup: every agent the host serves, across every repository, on one page. `lup-dev dashboard` opens it. Its package is `packages/lup-dashboard/` (`lup_dashboard`), which imports `lup-dev` and is never imported by it.

## Running

- **The host service runs it as its child** (`DashboardProcess`, `lup_dev/host/dashboard.py`), begun once the service listens and ended as it stops: `lup-dashboard serve <port>`, with `--address` for each address beyond localhost, found beside the interpreter running the service, where lup's own approval installs it beside `lup-dev`. Where it isn't installed, there's no dashboard, and `lup-dev dashboard` says why.
- **It goes with the service however the service ends:** the service writes the API's token on its input and keeps it open, and the dashboard ends when it closes. Its first line of output is the address it listens on, on localhost; one that ends before printing it, its port taken, is said.
- **On localhost, and on each address `LUP_DASHBOARD_ADDRESSES` names** (*Access*), **on one port** (`LUP_DASHBOARD_PORT`, 8766 by default), and **one token**, kept in the host's state with mode 600, which no room mounts, the same at each start, so a page left open reconnects on its own once the service starts again, after an approval among others.
- **`lup-dev dashboard`** prints the address with the token in its fragment and opens it in the browser, on localhost, starting the dashboard again where it's gone. Where the dashboard listens beyond localhost, it prints that address instead, the first named, drawn as a QR code for a phone to scan where `qrencode` is installed, an optional requirement of the host (`docs/launch.md`, *The command*); `--address` prints another the dashboard listens on. It refuses inside an agent's session.

## Access

Rooms share the host's network, so being on localhost keeps out only other machines.
- **Every call carries the token,** in the page's cookie (`HttpOnly`, `SameSite=Strict`, named after the port, since a browser shares localhost's cookies across ports) or as a bearer. The page is handed it in its address's fragment, which no request carries, trades it for the cookie and takes it out of the address. A page whose token is refused says so and stops, rather than retrying what retrying can't mend.
- **From another device,** as the operator's phone when they're out: `LUP_DASHBOARD_ADDRESSES`, in the host service's environment on the operator's machine, never in a project, names each address of the machine's the dashboard listens on beside localhost, separated by spaces, their WireGuard address among them (`LUP_DASHBOARD_ADDRESSES=10.8.0.2`). Each is bound whether or not the machine holds it yet (Linux's `IP_FREEBIND`), so a dashboard started before the tunnel is up answers there once it is. Addresses only, never `0.0.0.0`, which is refused: it would offer the dashboard on every network the machine joins, a café's among them, with the token as its only wall, where an address of the tunnel's lets in only the devices the tunnel admits. The token stays required there: the tunnel can't tell a room's process from the operator, and the dashboard answers trust's approvals, which install the code the host runs, so without it code in a room could approve its own push through any address bound. `lup-dev dashboard` hands the phone the token in the address it draws (*Running*), which the page trades for a cookie of that host's own, since a browser keeps cookies per host. Served over plain http there, the page keeps the clipboard to itself and says so (*The page*).
- **A request naming another host** than `127.0.0.1`, `localhost` or an address it listens on is refused, as is a call from a page of another origin.

## The API

The page asks the host service only what the operator's commands ask it: the host's own control requests, relayed as they are (`lup_dashboard/server.py`, FastAPI).
- **`POST /api/ask`** takes one request and returns its reply, a refusal among them. The page may send only the requests the operator's views need, listed in `lup_dashboard.api`, a module's view among them, which the host puts to the repository's process and watches at the view's own triggers (`docs/host.md`, *The views the dashboard shows*); any other is refused before it reaches the host. An approval approved here is acted on as the operator's terminal acts on it, in a process of its own, since installing lup's own repository's copy restarts the host service, and the dashboard with it.
- **`/api/socket`,** a WebSocket, carries every watch a page holds, each under a number the page picks, answered at once and again each time it changes, through the host's watch socket (`docs/host.md`, *Watching*). One socket for every watch, since a browser keeps six connections to a host, which a stream per watch used up in three tabs.
- **The API's description** is the server's own OpenAPI document, made from the host's pydantic models, and the page's types are generated from it, so the two can't drift: the building blocks a view answers, and each repository's looks, its fold kinds, tones and drawers, which the listing gives (`Listed.looks`), among them.

## The page

**Built** from `packages/lup-dashboard/page/`: TypeScript, React, React Aria Components for controls the keyboard reaches, cmdk for the command palette, and CodeMirror 6 with its vim mode for the review and the conversations. `packages/lup-dashboard/build.py` installs its packages from their lock, generates the types from the API's description, type-checks, runs its tests and builds, as `LupDevelopment`'s `dashboard` step and in trust's build of the copy the operator approves. Its packages are pinned exactly, nothing published in the last three days resolving. A page left open reloads itself when it reconnects to a build that isn't the one it loaded, as after lup is installed again and the dashboard restarted on it, its drafts kept on the host, so it never asks a server for what it no longer answers. Its tests are `packages/lup-dashboard/tests/` for the server and `page/src/*.test.ts` for the page.

**The review** is the page's one view: everything waiting for the operator, across every agent and repository, and each agent's work under its banner, as one buffer the operator moves through with vim and writes in (`page/src/review.ts`, `Review.tsx`).
- **A tree of views and blocks,** each part kept by an id it keeps across layouts (`Laid.nodes`): an agent's group by whose it is, its banner, an item by its number, each view mounted in them by its instance, its module, view and argument with its repository (`page/src/views.ts`), each of the view's blocks by the instance's id and its own, and what the operator wrote. The core lays out the frame: the groups, their banners and order, an item's header, what the operator's words an answer answers are, its edits, the passages its citations cite, the replies kept from before, its context and the comments. What's in the frame is each module's view, answering the building blocks (`docs/declaration.md`, *Views and blocks*): an item's body is its kind's view of it, its text and its files, and its summary, the words its header says after its number, before the core's (`edited`, `new`, when it came and how long it has waited); a drawer is a view of the agent, as each part of the banner after the core's words is. The page lays some of them out itself until each moves into its module (#113, step 4), each by a producer named after that module, answering the same generated block types the module's Python does, from what the page has read, and pinned by fixtures that module's Python will match (`page/src/views/`, `page/src/fixtures/views/`): lup's approvals, the core's; a held change, a flagged write, "since you approved" and holding, the judge's; questions, notes, turns' ends and the rest, the agent-facing inbox's; and the task list, what an agent's working on and its context's ring, the runtime adapters'. A view no producer lays out is its module's, as `Transcripts`' conversation is, watched through the host for each agent running (`module-view`; `page/src/hooks.ts`, `useViews`) and drawn from its blocks, each span in its tone's look, which the looks write; a Markdown block's lines its own, which a comment may be on, anchored to the block by its id as any comment is; what a fold of it says is set off under its summary line (`Fold.barred`) set in, a bar in its kind's colour beside it; a fold of it read from another of its views says it's being read until the operator opens it, when the page asks that view too, and watches it at its own triggers. **The buffer is kept by the tree** (`page/src/reconcile.ts`): each line laid out is the innermost part's laid out on it (`Laid.owners`), and the editor keeps whose each line of its buffer is, carried through every change to it, what the operator types among them; a new layout is made from the buffer by the fewest changes that keep each part's lines its own, a line kept only as a line of the same part's: an unchanged part is left untouched, a changed one is changed in its own lines alone, by their own diff, a line replaced in place by what differs within it, a part gone is taken out and a new one put in where the tree puts it, and the lines of what the operator wrote are kept before anything else's, the comment the cursor is in first. So CodeMirror carries the cursor, a selection, vim's visual one among them, the folds and the view through a layout as it does through typing, and nothing of where the reader is, is worked out again: the cursor moves only with the text, and where what it was on is gone, as an item a reply sent takes, it's on what follows. Each line a layout puts in or changes, but the operator's own words, flashes as it arrives, so what came while they read is seen to come; nothing is held back while they write.
- **Grouped by agent,** each group under a banner (*The banner*), its drawers right under it (*The drawers*) and its items after them, a subagent's group under its parent's, after the parent's items, its banner set in, under its nearest forebear with a group where its parent has none, in the order they arrived and never sorted again, so what the operator is reading doesn't move under them, and as the review is laid out anew the cursor's line stays where it is on screen, where it's in view, whatever came above it: a group appears where its first item puts it, or, for a conversation running or written to with no item, after every group with items, empty but for its banner, the messages written to it and its drawers, and keeps its place for as long as it's laid out, nothing waiting or not, one gone, its items answered and its conversation over, coming back after the others as a new one does; an item goes at the end of its group and stays there, a later item or a change of its rank or state moving nothing; what's left for later comes last, as the operator's own act moved it. **The order is kept on the host** beside the draft (`inbox-order`, `inbox-keep-order`; `Order`, `lup_dev/inbox/store.py`), so a page reloaded, as after each restart, lays each group where it was, and the operator's other page, their phone's, shares it: a page lays out the groups as it last laid them, then the others where the host keeps them, so nothing it shows moves for what another did (`ordered`, `review.ts`); the host keeps each place where it is whatever order a page sends, adds those it lacks after them, and drops those a page says it no longer lays out (`toKeep`), every place it doesn't as it first lays the review out, so the order holds no more than what's laid out. A page lays the review out once the inbox, the conversations running, the draft and the order are all read, lest it tell the host a group it hasn't read yet is gone. An item's rank (`docs/inbox.md`, *Parties and items*) has two jobs only: the desktop notice, and which items `]a` and `[a` stop at. A flagged write is no item of the review, though the inbox keeps it: it's shown in its agent's "since you approved" drawer, and approved there (`docs/judging-writes.md`, *Asking the operator*).
- **Each item** under a header saying what it is, when it came, and "new" since the operator last settled one; how long it has waited is drawn after when it came (*What's drawn*). News, to mark read rather than answer, is in its own colour: a note, a turn's last words, a friction, how the work went, a stop. A question's decisions are numbered with their leans.
- **Markdown shows as Markdown,** in an item's text, in the operator's comments and in a conversation alike: emphasis, strong, code, headings and links as such, the marks that write them hidden, but on the line the cursor is on in a comment, where they show to be edited, as Markdown editors preview; a hidden mark no place for vim's cursor, which has no width to show on it, so a motion put on one goes on past it the way it was going, to the next character shown, as if the mark weren't there, and back where going on would leave the line (`page/src/editor.ts`, `pastHidden`); a table's columns lined up by padding drawn beside its cells and never written, so each row stays one line of the buffer, which vim moves over as one and a comment quotes as its source; and a comment's lists written as neovim's Markdown writes them: Enter, `o` and `O` open a line at the indentation of the one they're on and never with a bullet or a number, which the operator types where they want an item, since a list continued for them is bullets to delete wherever they didn't want one; `>>` and `<<`, and Tab and Shift+Tab or Ctrl+T and Ctrl+D in insert mode, move a line in to where the words of the item above it begin, nesting it under that item as Markdown reads it (2 columns under `- `, 3 under `1. `), and out to the item it's nested in, a selection's lines or a motion's by as much as the first, so an item's own items go with it (`page/src/markdown.ts`, `shifted`). - **A change** (an approval, a held change, and the files of a "since you approved" drawer) shows each file whole, opened by the judge's reading of it: a header line saying what happened to the file and why it's open (held first, then flagged), or why it folds whole under it: `automatic`, asking nothing held or flagged, since an agent's branch holds far more code than the operator reads line by line, which a key opens; a test or a data file, by the role the judge's reading gives it, whose lines the operator has little use for, and each file of a first approval, which trusts the repository as it is rather than asking it read (`· test`, `· data`, `· first approval`, where `automatic` would stand); what the change adds and removes, each removed line in place; each line that matters barred, tinted in the colour of what it triggered, and saying it (`◂ held: adds an ignore`, `◂ flagged: public API: …`, `◂ told: regex: …`); runs of unchanged lines folded but for 3 lines around each change and each line that matters, under a summary line (`6 unchanged lines, 1–6`), so every change shows, in every kind of change, an approval of tens of thousands of lines among them, and no changed line is ever among unchanged ones; its text highlighted, each line painted as it comes into view, so a long approval paints only what's on screen. - **Each function's and class's body,** in Python, TypeScript and JavaScript, read from the file's syntax, folds under the line declaring it, open until closed. A run of lines never crosses a body's edge: one that would is cut there, and the line declaring a body around a change stays in view between the two parts, as git's hunk header names the function, so every fold sits whole inside another or beside it.
- **Under each item an agent's call made** is its moment in that conversation (`docs/inbox.md`, *An item's moment*), folded, read, never commented.

**The banner** over each agent's group, a band of the agents' colour across, a subagent's a lighter one set in by how deep it's nested, its group's end a line saying whose (`end of parser, end of lup-impl`) and each item's end ruled, carries what a tree's row would: the core's words (`page/src/App.tsx`'s `banner`), its repository, worktree and conversation, by its path and under its parent, and, drawn after them (*What's drawn*), what it's doing and for how long (calling a tool, asking lup, between calls, ended), kept with the launch so a host service started again still shows it; then each part of it a view of the agent's says, in the order the looks list them (`Banner`): the runtime adapters', what it's working on, the current entry of its task list where its runtime keeps one, and a context ring, drawn, the tokens in use against the window of the model that made its last reply (`◔ 112k/1M`), the count alone where that window isn't known or is smaller than the count, read from its runtime's record (`inbox-show-conversation`'s `usage` and `tasks`; `docs/field-notes.md`, *A session's record*, *A thread's rollout*, *A model's context window*) at each of its hooks the host hears, which the listing watched says (`Talker.activity`), as its conversation drawer opens, and a minute apart at most besides; nothing is polled faster, since reading every agent's record every few seconds slowed the page. ## The drawers

Right under each agent's banner, before its items, three folds, each a fold kind of its own, named for its view and declared in Python under its owner, as the looks list each repository's drawers in order (`docs/declaration.md`, *Views and blocks*), so an agent's drawers stay with it, always where its banner is: its tasks, "since you approved" and its conversation, one under the other with no line between them, each a short label in its kind's colour saying what it holds, its view's summary line (`tasks 1/3`, `since you approved · 3 to review · 1 flagged`, `conversation · 33 steps`), bold where it holds what waits on the operator, folded until opened in place with the fold keys or a click on it; a drawer the operator opens stays open, as each fold is kept by what it hides (`page/src/review.ts`'s `drawers`). A drawer with nothing in it isn't shown, rather than a line saying it's empty: a task list the runtime doesn't keep, a branch with nothing changed since the operator approved it, a conversation or a branch not read yet.
- **Tasks** (`t`): the agent's task list whole, as its runtime keeps it, each entry marked done, in progress or to do.
- **Since you approved** (`s`): everything its branch changed, read as the worktree stands, uncommitted changes among it (`policy-show-since`; `lup_dev/policy/since.py`), each file in path order: whole, with its diff from the version of it the operator last saw on that branch, the one they last marked reviewed or one kept beside a flag or a hold they approved, read or commented on, whichever came last, or, where they saw none, from where the branch left the integration branch, the merge base of the two branches' tips, so what the integration branch took in since never shows as the branch undoing it, and a file both changed shows the branch's change alone, until the integration branch is merged into it, which moves that base to the tip merged; the parts the judge flagged marked and open, by its reading of the file's latest flag, and a file nothing flagged read by its role alone, by the repository's declaration the judge last loaded, so a test or a data file folds whole as it does in any change; a new module with its design in view and its bodies folded; a comment on its lines a remark recording the version it was written on, so the agent is told which quoted lines changed since.
