# The dashboard

Where the operator works with lup: every agent the host serves, across every repository, on one page. `lup-dev dashboard` opens it. Its package is `packages/lup-dashboard/` (`lup_dashboard`), which imports `lup-dev` and is never imported by it.

## Running

- **The host service runs it as its child** (`DashboardProcess`, `lup_dev/host/dashboard.py`), begun once the service listens and ended as it stops: `lup-dashboard serve <port>`, found beside the interpreter running the service, where lup's own approval installs it beside `lup-dev`. Where it isn't installed, there's no dashboard, and `lup-dev dashboard` says why.
- **It goes with the service however the service ends:** the service writes the API's token on its input and keeps it open, and the dashboard ends when it closes. Its first line of output is the address it listens on; one that ends before printing it, its port taken, is said.
- **On localhost, on one port** (`LUP_DASHBOARD_PORT`, 8766 by default), and **one token**, kept in the host's state with mode 600, which no room mounts, the same at each start, so a page left open reconnects on its own once the service starts again, after an approval among others.
- **`lup-dev dashboard`** prints the address with the token in its fragment and opens it in the browser, starting the dashboard again where it's gone. It refuses inside an agent's session.

## Access

Rooms share the host's network, so being on localhost keeps out only other machines.
- **Every call carries the token,** in the page's cookie (`HttpOnly`, `SameSite=Strict`, named after the port, since a browser shares localhost's cookies across ports) or as a bearer. The page is handed it in its address's fragment, which no request carries, trades it for the cookie and takes it out of the address. A page whose token is refused says so and stops, rather than retrying what retrying can't mend.
- **A request naming another host** than `127.0.0.1` or `localhost` is refused, as is a call from a page of another origin.

## The API

The page asks the host service only what the operator's commands ask it: the host's own control requests, relayed as they are (`lup_dashboard/server.py`, FastAPI).
- **`POST /api/ask`** takes one request and returns its reply, a refusal among them. The page may send only the requests the operator's views need, listed in `lup_dashboard.api`; any other is refused before it reaches the host. An approval approved here is acted on as the operator's terminal acts on it, in a process of its own, since installing the copy restarts the host service and the dashboard with it.
- **`/api/socket`,** a WebSocket, carries every watch a page holds, each under a number the page picks, answered at once and again each time it changes, through the host's watch socket (`docs/host.md`, *Watching*). One socket for every watch, since a browser keeps six connections to a host, which a stream per watch used up in three tabs.
- **The API's description** is the server's own OpenAPI document, made from the host's pydantic models, and the page's types are generated from it, so the two can't drift.

## The page

**Built** from `packages/lup-dashboard/page/`: TypeScript, React, React Aria Components for controls the keyboard reaches, cmdk for the command palette, and CodeMirror 6 with its vim mode for the review and the conversations. `packages/lup-dashboard/build.py` installs its packages from their lock, generates the types from the API's description, type-checks, runs its tests and builds, as `LupDevelopment`'s `dashboard` step and in trust's build of the copy the operator approves. Its packages are pinned exactly, nothing published in the last three days resolving. A page left open reloads itself when the build on disk changes, its drafts kept on the host, so it never asks a server for what it no longer answers.

**The review** is the page's home: everything waiting for the operator, across every agent and repository, as one buffer the operator moves through with vim and writes in (`page/src/review.ts`, `Review.tsx`).
- **Grouped by agent,** each group under a banner naming its repository, worktree and conversation: those with items first, by their first item's rank (`docs/inbox.md`, *Parties and items*), then a group for each other conversation running, empty but for its banner, then what's left for later. Within a sitting each group keeps its place as items come and go, so what the operator is reading doesn't move under them.
- **Each item** under a header saying what it is, when it came, how long it has waited, and "new" since the operator last settled one. News, to mark read rather than answer, is in its own colour: a note, a turn's last words, a friction, how the work went, a stop; a flagged write, last, in its own colour again, gathering a conversation's writes to one file. A question's decisions are numbered with their leans.
- **A change** (an approval, a held change, a flagged write) shows each file whole, opened by the judge's reading of it: a header line saying what happened to the file and why it's open (held first, then flagged, else `automatic`, whose file folds away under its header); what the change adds and removes, each removed line in place; each line that matters barred and saying what it triggered (`◂ held: adds an ignore`, `◂ flagged: public API: …`, `◂ told: regex: …`); runs of unchanged lines folded but for 3 lines around each change; its text highlighted, each line painted as it comes into view, so a long approval costs only what's on screen. An approval's files read from their parse alone say `reading types` until the host has read them whole, then are laid out anew with no reload (`docs/trust.md`).
- **Under each item an agent's call made** is its moment in that conversation (`docs/inbox.md`, *An item's moment*), folded, read, never commented.
- **Comments are written into the buffer,** each under the line or passage it's about, with vim's own keys; only comments can be edited. A comment on a file's lines quotes them under the path and line numbers, so the agent finds them. On a group's banner, the operator writes a message to that agent instead.
- **Answering:** an item marked read, left for later, approved or declined, its comments going with the answer: a held change's to the agent waiting on it, an approval's to the session whose push asked it. A flagged write is read or commented on, never declined.
- **The draft** is kept on the host as it's written, so closing the page loses nothing. Sending makes it one reply, sent whole to each conversation with a comment on its items, a question among them, or a message to it: the operator answers related items together, across agents and repositories, and sends on moving to something unrelated. Each agent reads its own message and items first, then the others' commented items as context. An item only marked read tells its agent nothing and wakes no one. The line under the review says, before it's sent, who it reaches, what it approves and what it leaves unanswered: an approval commented on stays unanswered, its comments going to the session that pushed, and a held change commented on is approved with them, since only declining declines.

**The agents tree:** each repository, its launches, each session's conversation and its subagents under it, those that are over folded under a count, and what each is doing and for how long (calling a tool, asking lup, between calls, ended), kept with the launch so a host service started again still shows it. `h` turns the operator's switch to hold each flagged write of a conversation, and its row says "holding" (`docs/judging-writes.md`, *What each change gets*). Under the tree, the details of the conversation selected. Ctrl+K, the command palette, goes to the review or any agent's conversation.

**The keys.** The line of keys under each view says where the cursor is (a comment, a banner, an item, a change, a file, a fold) and the keys that apply there, and `?` lists every key, in parts (`page/src/keys.ts`, `Keys.tsx`): that list, not this doc, is where each key is described. Space leads a chord (Space `c` opens a comment on an item whole, Space `d` marks it read, Space `a` and `x` approve and decline, Space `z` leaves it for later, Space `h` gives the keyboard to the tree), vim's own keys move, fold, undo through the draft's history and edit comments, and Ctrl+Enter sends. A dead key, as `` ` `` on a layout where it waits for the next key, reaches vim once, as the first text it types, and nothing typed outside insert mode lands, so a jump never types into a comment.

**The look:** the first lup's dark palette, Claude Code's `dark-daltonized` colours beside VS Code's high-contrast dark theme, each text colour at 7:1 or more on black; monospace throughout, one row a line, structure from borders, emphasis by outlines and bars rather than fills.

**The demo:** `lup-dashboard demo` serves the real page over stand-in data (`lup_dashboard/demo.py`): launches over three repositories, subagents working, asking and ended, each kind of item, an approval read from its parse first, flagged writes gathering, and a conversation for each agent. A session building a view looks at it with the demo, driving the room's Chromium headless, and the operator can open it to try one.

## The conversation

Selecting an agent in the tree or the palette opens its conversation in the review's place (`page/src/conversation.ts`, `Conversation.tsx`), with the review's look, keys and folds; Space `r` brings the review back as it was left.
- **What it shows:** the whole conversation from its start, read from its runtime's record: the operator's words after `you:` and the agent's as they are, each run of calls in one line, and every item the conversation sent or was sent, each a line where it happened with its text folded under it (`→ #51 question to you · answered by #53`, `← #53 your answer to #51`). What came before the operator's last words is folded under a summary line. An item for a subagent that had ended shows in both its conversation and its session's.
- **Live:** the page asks for the steps after those it has at every hook, and every five seconds besides. What arrives is added at the end, the text before it untouched: a reader on the last line is followed, and anyone else keeps their cursor, their folds and the comment they're writing.
- **Writing and sending:** comments on the agent's lines and passages, and a message on the whole at the end; Ctrl+Enter sends them as one message, each comment with the passage it quotes, which lup tells as tags (`docs/inbox.md`, *As tags*). The agent reads it at its next call, or is woken. What was sent shows once as an item it was sent. The draft is kept on the host for each conversation, so another browser or machine shows it.
