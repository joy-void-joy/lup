# The host service

One program per user on the operator's machine, outside every room, which rooms call for what only the host can do (`host/service.py`): the judge for each hook (`docs/judging-writes.md`), lup's tools and the inbox (`docs/inbox.md`), git and GitHub with the operator's credentials, the clipboard, and the dashboard, which it runs as its child (`docs/dashboard.md`).

## Using it

- **It starts on demand,** detached, from the first launch or command that finds none answering, and runs until it's stopped. A command that only reads, run in an agent's session, never starts it, since it would run on in that shell's environment (`reading`, `cli.py`). It holds a lock for its whole life, so a second refuses.
- **`lup-dev host`** runs it in the foreground, to watch it, and **`lup-dev host stop`** stops it. A launch outlives a stop (*Restarts and the sweep*).
- **`lup-dev sessions`** lists the launches it serves, each with its conversations as a tree and its container. It only reads, so an agent's session runs it too: on the host, every launch; in a room, its repository's alone (*How a room reaches it*).
- **What it prints,** started in the background, is appended to `service.log` in lup's state, which a client names when the service doesn't answer within 10 seconds; in the foreground, it prints to the terminal.

## How a room reaches it

Each launch has a socket directory of its own, mode 0700, mounted into its room at `/run/lup`. The service knows which launch speaks by the socket it hears on: under `--userns=keep-id` a room's processes have the operator's uid, so only the socket tells a room from the operator. One socket for every room would have each request name its launch, which the room would then say of itself, and HTTP on localhost would be reachable by every process on the machine.
- **`hook.sock`, the one hook.** Every hook of every runtime is one command, which pipes the runtime's payload unchanged to the socket with `socat` and prints the answer, so nothing in the room parses it (`piped`, `launch/session.py`; *The one hook*).
- **`mcp.sock`, lup's tool server.** In the room, the runtime's stdio server is lup's bridge (`packages/lup/src/lup/sessions/bridge.py`), on the room's Python and the standard library alone, carrying each line across. Each connection is one MCP session, kept while it's open so what's pushed to the session goes through it (`Pushes`, `host/pushes.py`). The server answers a probe for MCP's 2026-07-28 revision "method not found", so the runtime opens on the handshake: on that revision a server can send nothing unasked, which a push and the bridge's `list_changed` after a restart both need (`lup.tools.serving`; `docs/field-notes.md`, *Channels*). A tool that fails answers its failure as an error naming the tool, and the service's output has the traceback (`LaunchTools.answered`, `host/rooms.py`): left to `mcp`, a pydantic `ValidationError` a tool raises reaches the session as JSON-RPC's bare "Invalid request parameters", logged nowhere.
- **`request.sock`, the room's requests:** one typed request per connection from the room's programs: git's remote helper, the gate asking an issue's state, the clipboard, and modules' requests (`@lup.request`). Its routes are apart from the control socket's, so a room never reaches a control kind that writes, such as answering the inbox: the first lup's sessions approved their own questions by writing to a store they could reach.
- **The control kinds that only read** are served on `request.sock` too, so `lup-dev sessions`, `inbox` and `inbox show` work in a room (*Reading from a room*).
- **`messages.sock`,** Claude Code's own messaging socket, through which the service rings an idle session's doorbell where nothing can be pushed to it (`docs/inbox.md`, *How an agent is told*).

On the host alone:
- **The control socket.** One JSON request per connection, a pydantic model told apart by its `kind`, and one reply (`host/protocol.py`). Modules register the handlers for their own kinds, so a kind is added without editing the service. What the service can't carry out is replied as `Refused`, saying why.
- **Watching.** On the watch socket, a request is answered at once, then again each time its reply changes, with nothing polled (`host/watch.py`); the dashboard watches what the operator's commands fetch. A watch is asked again when the service answers a request or a hook, or writes an item of the inbox.

## Reading from a room

- **Every request model says whether it only reads,** a keyword of its class with no default (`class ShowItem(Request, reads=True)`, `host/protocol.py`), so a kind declared without it fails as its module is imported. A forgotten mark can neither leave a reading command refused in a room nor open one that acts to it.
- **A kind that reads is answered by a `Reading`** (`host/service.py`), which also answers a room of one repository, and is routed with `Route.reading`; a kind that writes, with `Route.to`. Each refuses a kind of the other mark, so a mismatch fails as the service is built. Each launch's `request.sock` routes every control kind that reads to that answer, for the repository in the host's record of the launch, never one the room names.
- **A room sees its repository alone:** its launches and their conversations, each session's name only for a session of theirs, and the items whose every conversation is of the repository, or an approval of it. An item of another repository is refused, and a list leaves it out, since the inbox and the launches are the operator's across every project, and a room's posts can be public. The operator's draft reply, what they write on a conversation before sending it, and the order their review lays its groups out in are refused to every room.
- **A room has no podman,** so the listing it's answered says whether each launch's container runs (`Listed.running`); the operator's terminal asks podman itself, which keeps the dashboard's watch from asking it at each change.
- **A service on a copy from before** answers a room's reading request as a kind it doesn't know, which `lup-dev` says is a copy to approve (`FromRoom`, `cli.py`).

## The one hook

| The hook | Claude Code | Codex |
|---|---|---|
| The service's answer | the decision it holds | the decision it holds |
| The service unreachable for a minute, status 1 | a non-blocking error in the transcript; the call goes ahead | the run marked failed; the call goes on |
| The launch's judge can't answer | a file tool's write is denied, saying why; at `PostToolUse`, the agent is told beside the call's result; any other hook warns the operator | at `PostToolUse`, the agent is told beside the call's result; any other hook warns the operator |
| The connection lost before an answer, at a call's start, its finish or a turn's end: status 2 | the call blocked, or lup's line told beside its result, or the turn's end held once on it | the same |
| The same at a session's or a turn's start: status 1 | a non-blocking error; the prompt goes on | the run marked failed; the prompt goes on |

- **A worktree asked for** (Claude Code's `WorktreeCreate`) is answered with no JSON: the runtime reads the last line its hook prints as the worktree's path. The judge names the worktree a field a line (`Making`, `policy/worktrees.py`), and the room's hook makes it with the room's own git and prints its root (`launch/worktree.sh`); an answer that isn't a path is why the judge made none, which the hook says on standard error, ending with status 1, as it does where its connection is lost: any status but 0 fails the making. Nothing is told there, and the asking conversation's activity stays as it was. Codex asks for none (`docs/judging-writes.md`, *A worktree the runtime asks for*).
- **A call spawning a subagent lup isolates** is answered with the worktree lup makes for it first, a field a line, then the answer the runtime reads: the room's hook makes the worktree with the room's own git and prints the rest (`launch/worktree.sh`). Where git fails, the hook ends with status 2, which blocks the call, its standard error told to the agent, so nothing spawns into a worktree that isn't there (`docs/judging-writes.md`, *A subagent lup isolates*).
- **A turn that ends on an error from the model's API** runs Claude Code's `StopFailure`, which reads neither the answer nor the status, so nothing there holds or tells, and a lost connection there is no one's: the service hears it as the end it is, a subagent's or the session's turn's (`StopFailure`, `adapters/claude.py`). Codex runs no hook for it.
- **Which hooks the judge reads** is each adapter's word (`heard`): every one, but on Claude Code a call's start and finish to lup's own tools or to a tool that only reads (`READING`, `adapters/claude.py`). The service answers the rest itself, in about 4.5 ms; one the judge reads where nothing changed takes 8 to 21 ms, the judgement and a hop to the repository's process (`docs/field-notes.md`, *A hook the judge doesn't read, and one it does*).
- **A hook the judge can't answer goes on,** since the judge steers and doesn't guard. Where the service is up, it refuses only a file tool's write on Claude Code, since let through unjudged it would land unseen; where the service can't be reached, even that write goes ahead, with the runtime's error shown.
- **`socat` waits 25 hours** for the answer, above a hold's day.
- **Every answer is something,** `{}` where nothing is decided or told (`UNDECIDED`, `host/service.py`), which both runtimes read as no decision, as they would nothing printed. So the hook tells an answer from a connection that ended without one: `socat` ends with status 0 and prints nothing whether the service closed the connection, as its stop does, exited, or was killed (`docs/field-notes.md`, *The room's hook when the host service goes away*). Such a hook fails rather than going on as no decision, which would let a held write land unreviewed (`lost`, `launch/session.py`): status 2 where it keeps a write from landing and tells the agent, 1 at a session's or a turn's start, where status 2 would drop the operator's prompt. A turn's end held so goes on once: the next end connects again, and a service still gone gives status 1.
- **A hook its runtime ends while it waits,** the operator interrupting its call, is seen as the connection's whole close (`hung_up`, `host/service.py`): the service marks the hook ended for the launch's judge (`HostLayout.ended`), so a hold its call waits on gives up (`docs/judging-writes.md`, *Asking the operator*).
- **The service holds each connection's task until it's answered,** on every socket it serves and in each repository's process (`unix_server`, `host/service.py`). asyncio holds a task only weakly, and once a room's hook has sent its payload, the task waiting on the repository's process for a hold's answer is reachable from nothing: Python's collector would free it mid-wait, closing the hook unanswered while the hold waited.

## Who's calling

Within a launch, each conversation has an id of lup's own, minted the first time a hook names it and kept with the launch across restarts (`Conversations`, `host/courier.py`), so lup's tools and calls name a conversation by lup's id, never a runtime's: the first lup, wired to each runtime's own, found they didn't stay uniform. The hook on a call to one of lup's tools rewrites its input to carry `caller` and `call`, the runtime's id for the call, which the server takes out before the tool sees its arguments (`stamp`, `host/rooms.py`). `call` anchors the item the call makes in the conversation's record. A process in the room could write another conversation's id into a call, but only within its own launch.

**A runtime's own agents aren't the operator's.** A subagent heard the first time is linked to its spawn as the runtime recorded it, and one that no spawn in the session's record links to is the runtime's own, run for its features, as Claude Code's progress summary of a background subagent forks its conversation and may call a tool it then denies, firing a `PreToolUse` that nothing ends (`docs/field-notes.md`, *A runtime's own agents*). Each adapter says how its runtime's are told apart (`Spawned.internal`). The service answers their hooks with nothing: no judge reads them, so no call of theirs counts as running and nothing of theirs holds; no module hears of them; nothing is told them, and the inbox never knows them, so `land` and `wait_inbox` never count one among a session's subagents. The listing leaves them out (`Launches.talkers`, `host/service.py`), so the dashboard shows no group for one and `sessions` counts none, running or ended.

## Each repository's judge and modules

- **Each launch is judged by its repository's own approved copy** (`docs/trust.md`), in the repository's process, `<copy>/bin/lup-dev worker <socket> <repository>`, which serves every launch of the repository (`host/workers.py`, `lup_dev/worker.py`). It stays running and answers each hook the judge reads as `lup-dev hook <runtime>` would, so a hook costs the judgement alone, where a process started for each hook would spend about 0.7 s starting Python and importing `lup-dev` before judging anything. Each request carries the launch it's for, never the process, so a module's state lives in one place for the repository, whichever launch, or none, is open.
- **It runs while something holds it** (`Holder`): each of the repository's launches does while it's open, and a request the operator puts with no launch open, a view the dashboard shows, while it's answered (`Workers.asked`, through `RepositoryAsking`), the process started from the copy approved for the repository where none runs. The first request after one opens starts it, and once nothing has held it for five minutes (`Workers.idle`) it ends, so a launch opening soon after another ended finds it running, its declaration loaded. A launch ending lets go of its hold, and a hook of its the judge is still answering is marked ended, as its runtime ending it is (*The one hook*): a hold it waits on gives up as an interrupted call's, rather than waiting a day in a process that outlives the launch. The service's stop ends every process at once.
- **The same process runs the repository's modules:** their tools, their answers to the rooms' requests, and their hooks at lup's events (`docs/declaration.md`, *What a module serves a launch*), made from the declaration at the commit the operator approved with the person's layer approved beside it, read through the repository's git directory whichever worktree a launch runs in (`docs/declaration.md`, *Where it lives*). A launch's hooks read its own runtime's records, since launches of one repository may run different runtimes. Where the modules can't be loaded, it says why in the service's output and answers the judge's hooks alone, as the judge has a stand-in for a declaration that can't load.
- **And their views** (`docs/declaration.md`, *Views and blocks*): the host asks the process for one (`Viewing`), for the operator or a room, and it answers its blocks, checked against the tones the modules declare. A module's commands don't come here: they run in the terminal's own process (`docs/declaration.md`, *Commands*), and a room learns its own launch, which a command run there is asked by, from the host (`room-launch`, `host/rooms.py`).
- **So do the judge's own tools that ask the engine:** `quiet`, which the host service serves beside `judged` and passes, with the launch and the conversation calling, to the repository's process (`JudgeCalling`, `host/workers.py`), as it passes a call to a module's tool; lifting a quiet reads the conversation's files with the engine kept warm there (`docs/judging-writes.md`, *Quiet*). A process of a copy that predates the tool refuses its kind, and the call answers that it didn't run.
- **Hooks at once.** Each hook runs in a thread of its own, never a pool's, so hooks that parallel calls, subagents and launches fire together are judged together, and a hold waiting a day for the operator delays no other. What judging keeps between hooks is on disk under `filelock`'s locks, which exclude a thread as they do a process; what it reaches, the engine, ruff, the clock and the inbox, holds no state and is made once for the process.
- **An approval switches cleanly.** The repository's judge is its command, a link to the copy approved last (`docs/trust.md`, *Each repository's own judge*), which the service follows at each request, reading what the operator approved beside it, since approving the person's layer alone installs no copy. Where either is another than the process runs, a process of the approval starts and answers from then on, and the one before finishes what it was asked, a hold among it, then ends: every launch of the repository is judged and served by the approved code from its next request, with no relaunch, and no hook meets a copy half installed. The tools and the kinds of request a session was offered stay those of the copy it opened with: one the new copy dropped is answered as one no module serves.
- **A failure.** A process that dies is started again at the next request, and what it was answering, whichever launch's, is answered as a request it couldn't: a hook gets the runtime's answer for a judge that couldn't (*The one hook*), with why. One crash interrupts everything in flight for the repository, the cost of a module's state living in one process.
- **The programs it runs are awaited on its event loop** (`lup.programs`, `awaited` and `started`): git and `gh` for a room, the clipboard's programs, the desktop's notices, the dashboard and the repositories' processes. So a hold in a repository's process holds a thread there and nothing of the service's, and a program whose wait is cancelled is killed. podman, renaming a container or sweeping, runs in a thread. Each is started from C, never by forking Python, which can deadlock a process with threads (#23).

**Why the judge is on the host:** not to guard it, since the judge steers. It asks a warm engine per worktree, a pyright process shared with the operator's own gate runs, where a cold one in each room would make the first edit wait for the whole project to type-check. The copy the operator approved is the one that judges, where in the room a branch reshaping the judge would judge its own edits. And holds wait for the operator's answer, which comes from the host.

## Restarts and the sweep

- **A launch outlives a restart of the service.** Each launch is recorded beside its sockets, and a service started after one stopped binds them again in the directory the room mounted, and brings the room's programs up to its own copy. A hook made meanwhile waits for it as the bridge does, trying to connect every half second for up to a minute (`piped`, `launch/session.py`, from the bridge's own defaults): `socat` reads the payload only once connected and never connects again, so a hook's payload is never sent twice, and one whose connection is lost once made isn't tried again: it fails, saying so (*The one hook*), and a hold its call waited on is settled at a later checkpoint (`docs/judging-writes.md`, *Asking the operator*). Neither runtime starts a stdio server again, so the bridge keeps the runtime's side open across the gap: a call made meanwhile waits up to a minute, and so does one that was being answered; once the service is back, the bridge replays the runtime's MCP `initialize`, sends each call that was being answered again, the same request under the same id, where its tool only reads or finds its wait again, and tells the runtime to list the tools again. Which calls may be sent again is each tool's own word, not the bridge's: `@lup.tool(reads=True)` marks `inbox`, `judged`, `read_issue` and `find_issues`, and `@lup.tool(idempotent=True)` marks `ask`, `wait_inbox` and `land`, whose wait the new service finds again (`docs/inbox.md`, *Holding a call*); the server publishes each as MCP's `readOnlyHint` and `idempotentHint`, which the bridge reads off the tool list going by. A call to a tool marked neither acts, so it isn't sent again: it gets an error saying so, since it may have been carried out.
- **A launch whose launcher died is swept.** Its launcher holds a lock the OS frees when it dies, and the sweep ends each launch whose lock it can take and whose container podman no longer has. It takes both, since either alone ends a live launch: a container appears moments after its registration, and a launcher killed with its terminal can leave its room running on. The sweep runs before each launch registers, and every 30 seconds beside the service.
- **A copy nothing runs is removed.** The sweep beside the service also removes each repository's approved copy that its link doesn't name and no repository's process runs, never one being installed (`lup_dev/copies.py`). It chooses them on the service's event loop, beside the processes starting, so it never chooses a copy as one starts from it.
