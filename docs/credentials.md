# The operator's credentials, used on the host

A room holds no SSH agent, key, token or `gh` login (`docs/launch.md`, *The mounts*). The host carries out a fixed set of actions with the operator's credentials for it, each held to the limits the project's declaration sets (`DESIGN.md`, *Defaults*). Lent into the room, credentials would answer to nothing: a forwarded SSH agent "can sign anything that key can sign, for every host it reaches", as the first lup found.

## What the declaration allows

`Core`'s `credentials` (`Credentials`, `declaration/kinds.py`) holds three selections, each changed where it stands with its reason (`docs/declaration.md`, *What a launch reads*):
- **`actions`,** from a fixed set: `fetch`, `push`, `force-push`, `delete-merged`, `delete-ref`, `read-issues`, `file-issue`, `edit-issue`, `close-issue` (closing and reopening), `comment`, `edit-comment`, `draft-pull-request`. `delete-merged` deletes a branch that has landed, and `delete-ref` any ref (*Deleting a branch that has landed*).
 lup's default is all but `force-push` and `delete-ref` (`catalog/credentials.py`), so an action a later release adds is allowed unless it's withheld too.
- **`protected`,** refs no push updates: `refs/heads/main`, since what reaches `main` is the operator's to merge, and `refs/tags/*`, since a tag marks a release.
- **`gated`,** refs a push from a room updates only once the gate passed on the commit it would put there: `refs/heads/dev` by default, lup's integration branch. Branches land there, which is what `delete-merged` checks.

Beyond the limits, an action is refused, saying that allowing it is the operator's call (`Limits.refusal`). The launch resolves the limits at the approved commit and sends them with its registration as plain data, so the host service never loads a project's declaration, which would run the project's code there.

## git through a remote helper

**In the room** (`remote/helper.py`, `remote/config.py`):
- **The room's git configuration** (`GIT_CONFIG_GLOBAL`) rewrites each URL the repository's remotes name to `lup::<url>` (`insteadOf`), so git runs `git-remote-lup`, written into the launch's `bin/`, for every push and fetch. Fetching needs it as much as pushing, since a remote's URL may use an alias of the operator's SSH configuration, which the room can't resolve.
- **The helper turns each batch git sends into one typed request** on `/run/lup/request.sock`: listing the remote's refs, pushing (each source resolved in the room to an object id, with its destination and whether it's forced), and fetching objects into the repository's own store, which the room shares. It runs on the room's Python with the standard library alone, which an import contract keeps.
- **No upstream is recorded:** `git push -u` pushes, fails to write the upstream ("Device or resource busy", since `config` is read-only) and exits 0, so the configuration sets `push.default = current` and `branch.autoSetupMerge = false`.
- **A push to a gated ref runs the gate first,** on the tip it would put there, so from a room's git the integration branch never moves to a tip the gate failed on, whoever forgot to run it; the commits between come with it unchecked. The helper runs `lup-dev check --at <commit>` through the project's runner, and holds the update where it fails, git printing the gate's report. A pass recorded for the commit's files answers at once, the usual case, since the gate ran on them before they were pushed. It runs in the room, since the commit pushed isn't the one the operator approved, and its gate on the host would run unapproved code there. So it steers: a room speaking to the socket directly, or setting `lup.gated` on git's command line, pushes ungated.

**On the host** (`remote/protocol.py`):
- **Where it pushes is the repository's word, never the room's:** git runs in the repository's own git directory, found by the launcher before the room started (through the worktree, which #165 would check), and the remote's URL is the one the repository's `config` gives. A URL from the room, even one equal to a remote's, is refused, or a room could point the operator's credentials at anything they reach. A destination must be a full `refs/…` name.
- **Each update is checked against the limits** before git runs (a force, a deletion, a protected destination), since a room can speak to the socket directly, and a deletion resting on `delete-merged` against the remote (*Deleting a branch that has landed*). Then what it would publish goes through `Publishing`, where the `Private` module refuses a value never published (`docs/private.md`).
- **It pushes by object id,** `git push <url> <oid>:<dst>`, one update at a time or an `--atomic` batch as one; an update git didn't force is never forced. The objects are already in the shared store, so none crosses the socket: only their ids, with the remote's name, the destinations and git's options.
- **The operator's credentials are the service's environment:** their SSH agent and git's credential helpers as the terminal had them when a launch started the service. Every push and fetch is said in the service's log.
- **A push that moves the integration branch** asks trust's approval of its tip, where it isn't the one approved (`docs/trust.md`), whether the room's git or `land` pushed it (*Landing through `land`*).

## Landing through `land`

`land` (`docs/judging-writes.md`, *Landing a branch*) merges a branch in the launch's room, and reads the merge's parents on the host from the commit alone (`Remotes.git`, `own_parents`), as it reads them to check the fast-forward. It pushes on the host as the room's push does, through the same handler (`PushHandler`, `remote/protocol.py`): the gated branch's tip on the remote listed and fetched, writing no ref; the tip pushed by object id within the limits, never forced; what it publishes put to `Publishing`; and trust's approval asked where it moves the integration branch. Then, for each branch it landed but those gated or protected (`policy/landing.py`):
- **its copy on the remote** is deleted where the remote holds it, as a deletion from the room is (*Deleting a branch that has landed*), so where the declaration withholds `delete-merged`, it stays, and is said;
- **its worktree is removed in the launch's room,** through `podman exec` into its container, by `git worktree remove` without `--force`: git keeps one with changes or untracked files, saying so, and takes what it ignores, the worktree's scratch; one whose `.venv` is hidden from the room fails there, part removed and the rest left with the host's `.venv` at its path (`docs/launch.md`, *The project's environment, the room's own*). Never on the host: the path is the one `<git directory>/worktrees/<name>/gitdir` names, which the room writes, so the host's recursive delete could be aimed outside the repository. Left alone, and said: the repository's main worktree, one the conversation landing works in, and one a conversation of a launch still served works in, as the judge's session index has it (`Holding.works`, `policy/worktrees.py`);
- **the local branch** is deleted on the host, `git update-ref -d` at the tip it landed at, where no worktree still has it checked out.

## Deleting a branch that has landed

A branch a session pushes, for its draft pull request, stays on the forge once it lands. `delete-merged`, allowed by default, deletes it, where nothing only the forge holds goes with it; `delete-ref` deletes any ref, whatever it holds (`Remotes.merged`, `remote/protocol.py`).
- **A branch, `refs/heads/…`,** never a protected ref, and never a gated one: the gated refs are where branches land (`Core.credentials`), lup's integration branch by default, a project's own where it names another.
- **Checked against the remote, never the room's refs,** since what a deletion loses is the remote's commits. The host lists the remote (`git ls-remote`), fetches the branch's tip and each gated branch's into the store, writing no ref, and deletes the branch only where its tip is in the history of one of them (`git merge-base --is-ancestor`). Where it isn't, the session is told that deleting the branch would lose its commits, and that deleting it anyway is `delete-ref`, the operator's call.
- **No race:** the deletion is pushed with `--force-with-lease=<branch>:<the tip checked>`, so where the branch moved since the check, git refuses it as stale and nothing is deleted. That lease is the host's, so it doesn't make the deletion a forced push, as a room's lease makes an update one; a lease the room gave on the branch must name the same tip.
- **No pull request is looked for.** A branch heading an open pull request is deleted too, which closes it; with its tip in a gated branch, nothing is left in it to merge, and the check is the same on any forge.
- **Each commit's parents read from the commit:** a room writes `info/grafts` and `objects/info/commit-graph`, and git reads a commit's parents from either before the commit itself, so each could make any branch look landed. The check reads neither (grafts from an empty file, `GIT_GRAFT_FILE`, and `core.commitGraph=false`), and replace refs are off for it as for every git lup runs (`docs/field-notes.md`, *What git reads a commit's parents from*).
- **What it doesn't stop:** the room writes the object store itself, so a room set on doing so can plant an object under the id of a gated branch's tip, naming the branch's tip as its parent. git reads an object by its id without hashing it again, and a fetch skips an object the store holds, so the branch would look landed. The forge's own answer would close it (GitHub's compare API), at the cost of a check tied to one forge.

## Running git on the host

A room can't write the git directory's `config` or `hooks/`, but it writes the rest: refs, `objects/`, `info/`, each worktree's directory and `.git` file, and the common directory's `config.worktree`. What host git does about each was measured on scratch repositories laid out as lup's against a hostile room (`docs/field-notes.md`, *Host-side git in a repository the room writes*):
- **Pinned to the git directory.** Host git for a room runs with `GIT_DIR` and `GIT_COMMON_DIR` both naming the repository's common git directory (`pinning`, `Git.pinned`, `git.py`), never found from a working directory. Naming it alone isn't enough: a `commondir` the room writes at its top, which a common git directory never has, turns it into a pointer that `--git-dir`, `-C` and `GIT_DIR` alone all follow to another directory's `config`. Pinned so: every push, fetch and `ls-remote` for a room, the GitHub tools' `gh` and the git it runs, and the reading of `config` for the room's git. `safe.directory` is no backstop: under `--userns=keep-id` the room's files are the operator's.
- **A self-contained object store.** Just before each push or fetch, after the git it runs to find the remote, the host refuses where `objects/info/alternates` exists, or anything under `objects/` is a link: alternates naming another repository's objects let a push copy its blob to the forge. A refused batch of a push is that batch's error, so each update's outcome is still said.
- **Refused at launch:** a repository whose `config` sets `extensions.worktreeConfig`, under which host git reads the room-written `config.worktree`, or includes a file inside the room's mounts.
- **Replace refs ignored,** by every git lup runs (`--no-replace-objects`, `Git.run`): a room writes `refs/`, and a replace ref of its own would hand git other content for an object whose id `git ls-tree` still lists, so an export of the approved commit, which trust's fingerprint of those ids calls unchanged, would carry the room's Python to the host. A launch says when the repository holds any.
- **Grafts and the commit-graph read,** by every git lup runs for a room but the check of a deletion: a room writes `info/grafts` and `objects/info/commit-graph`, git reads a commit's parents from them, and a push sends what they add, so a room changing them between the `publishing` check and the push could have it send commits the check didn't read (#208).
- **Quiet otherwise:** `core.fsmonitor` and hooks are off for every git lup runs, and automatic maintenance for the git that pushes and fetches for a room, since a fetch started a detached `git maintenance` that outlived it.

**Where the host's git still finds its directory through a worktree.** Several of the host's own reads run git in a worktree and let it follow the worktree's `.git`: among them trust on launch, the launch's reading of the common git directory (which becomes the registration's `repository`, the directory every pinned git trusts) and its export of the declaration, the room's setup and the person's layer, the judge's places and stores, the gate's own `gh` outside a room, and the command line's own. A room can plant a link there between launches, aiming the next of these at a `config` of its own. Checking each worktree's links before they're read is #165; protecting the `.git` file at the write is #54.

## GitHub through `gh`

- **From the host, through `gh`** and the operator's login (`forge/github.py`), each answer read with `--json` into a pydantic model naming the fields asked for; filing, commenting and opening a pull request answer with the link `gh` prints (`docs/field-notes.md`, *GitHub through `gh` on the host*).
- **The repository is named once,** by the launcher, from the repository's own remotes read in its git directory, and passed to every call as `--repo`, but for a reading call naming another. A worktree's `.git` file is the room's to write, so naming it from a worktree would let a room choose which repository the operator's login acts on.
- **Each tool's action is checked against the limits** before `gh` runs, and what a tool that writes would post goes through `Publishing` first.
- **What the tools do:** read and search any repository the operator's login can read; on the launch's own repository alone, file an issue with labels, edit one's title, body and labels, close one for a reason or reopen it, comment and edit a comment, and open a draft pull request from a pushed branch into the integration branch. None merges: work lands on the integration branch through git, and `main` is the operator's.
- **A search lists the first 100 matches,** in GitHub's order, and `find_issues`'s `limit` takes up to 1,000: GitHub's search gives no more for a query, and `gh search` refuses a larger `--limit`. Where as many came as were asked for, the answer's last line says more may match, and how to reach them: a larger `limit`, or past 1,000 a narrower query. `gh search --json` gives no total, so it can't say how many.
- **Closing comments first, then closes,** so a close that fails leaves the comment said, which the answer reports, rather than an issue closed without its reason. Closing and reopening check the number is an issue in the state they change, before anything is posted: a pull request is the operator's to close.
- **A comment is edited by its link,** found on the thread `gh` reads from the launch's repository by the issue's number, then changed through GraphQL by its node id. A node id from the room could name a comment in any repository the operator's login can edit.
- **An edit keeps GitHub's edit history,** which only the operator can clear, on the web, so an edit removing something that shouldn't be public doesn't unpublish it, and the tools' descriptions say to tell the operator.
- **Bodies go on `gh`'s standard input,** and every value the model writes as `--flag=value` or after `--`, never through a shell.
- **`gh` missing or logged out on the host:** each tool answers why, and the launch says it once; `gh` is an optional requirement of the host.

**The gate in a room.** The gate checks that each `issue=` a `defer` or an `ignore` waits on is still open (`docs/judging-writes.md`, *The `# lup:` directives*), and a room has no `gh`. So in a room it asks the host, an `IssueState` on the request socket answered by the `GitHub` module within `read-issues`; elsewhere it runs `gh` itself. An issue the host doesn't answer goes unchecked, said with its reason.
