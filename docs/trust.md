# Trust on launch

The code that runs on the operator's machine, outside every room, is approved before it runs, since what changes the walls goes through the operator (`DESIGN.md`, *Who it's for*): the project's declaration, which the host reads for the project's limits and roles, and the `lup-dev` that judges its sessions' writes. There's no install step to remember: a launch asks, the first time and whenever that code changed (`launch/trust.py`, whose docstring has the details).

## Using it

- **A launch asks** where the host zone changed: a summary first (what's approved and why it runs on the host, the commit approved before and the tip, and git's own count of each file changed), then "Show the whole diff?" where there's a diff to show, then whether to approve the zone at the tip and install its `lup-dev`, each no by default. The first approval on lup's own repository held about 110 files and 24,000 lines, unusable as a whole diff, so the summary comes first and stays on screen.
- **The question is an item in the operator's inbox,** answered at the launching terminal, in the dashboard, or with `lup-dev inbox answer N`, whichever comes first; the terminal stops asking once it's answered elsewhere. The dashboard shows each file changed whole, with the judge's reading of it.
- **`lup-dev trust`** makes the same check with no session after it: where the zone is the one approved, it says there's nothing to review, and installs the approved copy if it's missing; where there's something to ask, it refuses inside an agent's session, so nobody answers their own approval.
- **A push from a room that moves the integration branch** to a zone that isn't the one approved puts the approval of its tip in the inbox, naming the session that pushed, so the operator needn't notice that the code the host runs changed. Their comment on the answer reaches that session.
- **Declined,** the session launches on the copy approved before, and the launch says the tip isn't the code judging it; with none approved yet, nothing launches.

## The host zone

What the host runs for a project (`Trust.zone`):
- **the declaration,** `lup_project.py` or the package `lup_project/`, and every file of the project it imports, in turn, with the conditions modules its modules name (`declared`);
- **the `lup-dev` it runs,** as the lockfile resolves it (`Lock.tool`): from the repository's own workspace, as lup's does, the files of each workspace package `lup-dev` needs, the dashboard's among them, with uv's files and the engine's source; or a release from an index, held to its version and its dependencies' pins, ruff's among them, the judge's own (`docs/judging-writes.md`, *The engine: one typed tree*). A lock resolving `lup-dev` any other way, from git, a URL or a path outside the workspace, is refused: the host runs a release or the workspace's own source, and a copy built from git would also lack the engine, which is built and never committed;
- **the person's own layer,** by its content (*Trusted by its content*).

**Trusted by its content.** `lup_project.local.py` is Python the host runs, and a room writes the worktree, but git holds none of it. So its content joins the zone: unchanged, it asks nothing; changed, created or removed, its diff is in the summary itself, since git's count can't show a file git doesn't hold. The approval keeps the copy approved, which the judge and a launch read beside the commit's export, never the worktree's. Where the layer is all that changed and the commit approved is still the tip, approving installs nothing and restarts no service.

## Why it's this way

- **Read at the integration branch's tip** (`LUP_INTEGRATION_BRANCH`, `dev` by default), or at the worktree's `HEAD` where the repository has no such branch, never a branch's own copy. What's approved is what runs: once one is approved, a commit landing on the tip judges nothing until it's approved too.
- **Found without running the project's code.** The tip's files are exported from git's objects, and the declaration is read with `ast`, its imports followed by Python's own path finder, which imports nothing; loading it to find them would run the project's code on the host before the operator was asked. Every `import` statement counts, a `TYPE_CHECKING` block's too, since showing more than runs only costs reading. A file that doesn't parse, a relative import leaving its package, or a conditions module that isn't there is said with the question; a module imported by a name computed at run time, or a conditions module named by anything but a string, isn't followed.
- **A first approval trusts the zone as it is.** The operator chose it by pulling it; what trust guards is what changes afterwards, through pushes they haven't read. So its files are read by their roles alone, and no engine runs; the approval says it's a first one (`Approval.first`), and the dashboard folds each of its files under its header (`docs/dashboard.md`, *The review*).
- **Exported from git's objects, never with `git archive`,** which applies the repository's `.gitattributes`, so the copy could differ from the diff approved.
- **Each repository's own judge.** The approved copy is installed with `uv tool install` in a place of its own (`Layout.judge`), and each launch's hooks are judged by its repository's copy, so every session is judged by the code approved for its repository, and one project's approval can't replace another's judge. On lup's own repository the copy is also the user's `lup-dev`, which the host service runs from, so approving restarts the service on it; a project's release judges its own launches alone.
- **Built on the host by the commit's own steps.** A copy from the repository's workspace is built from the commit's export by its declaration's steps that build a file, the engine and the dashboard's page, run as the gate runs them (`UvToolchain.build`, `launch/trust.py`). They run the project's tools on the host, where no gate runs, so the declaration's requirements are checked first, as the gate checks them: lup's need Node, uv, and pnpm 11 or later, which installs the engine's and the page's packages, and a required one missing stops the install before anything is built, naming each.
- **Each copy in a directory of its own** (`lup_dev/copies.py`). A copy is installed where no process runs, never over the one judging, and the repository's command, a link, is switched to it in one rename once the install has finished: installed in place, a process starting between two of uv's writes would load the new code against the old dependencies. A repository's process started before keeps its copy until it has answered what it was asked, a hold among it; the repository's next request starts a process of the new one (`docs/host.md`, *Each repository's judge and modules*). Copies the link doesn't name, which no process runs, are removed by the host service's sweep.
- **The judge's reading comes in two passes** after a first approval, so a type check, seconds on lup's zone, doesn't hold the question up. Before it's asked, each file is read from its parse alone; once it's in the inbox, the host service reads its types and replaces the reading.
- **Two launches asking about the same zone** wait on one approval, and either answer, or the inbox's, reaches both.
