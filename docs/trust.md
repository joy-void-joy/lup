# Trust on launch

The code that runs on the operator's machine, outside every room, is approved before it runs, since what changes the walls goes through the operator (`DESIGN.md`, *Who it's for*): the project's declaration, which the host reads for the project's limits and roles, and the `lup-dev` that judges its sessions' writes. There's no install step to remember: a launch asks, the first time and whenever that code changed (`launch/trust.py`, whose docstring has the details).

## Using it

- **A launch asks** where the host zone changed: a summary first (what's approved and why it runs on the host, the commit approved before and the tip, and git's own count of each file changed), then "Show the whole diff?" where there's a diff to show, then whether to approve the zone at the tip and install its `lup-dev`, each no by default. The first approval on lup's own repository held about 110 files and 24,000 lines, unusable as a whole diff, so the summary comes first and stays on screen.
- **The question is an item in the operator's inbox,** answered at the launching terminal, in the dashboard, or with `lup-dev inbox answer N`, whichever comes first; the terminal stops asking once it's answered elsewhere. The dashboard shows each file changed whole, with the judge's reading of it.
- **`lup-dev trust`** makes the same check with no session after it: where the zone is the one approved, it says there's nothing to review, and installs the approved copy if it's missing; where there's something to ask, it refuses inside an agent's session, so nobody answers their own approval.
- **A push from a room that moves the running branch** to a zone that isn't the one approved puts the approval of its tip in the inbox, naming the session who pushed, so the operator needn't notice that the code the host runs changed. Their comment on the answer reaches that session.
- **Declined,** the session launches on the copy approved before, and the launch says the tip isn't the code judging it; with none approved yet, nothing launches.
- **Approved, and it doesn't answer,** what ran stays or comes back, the approval stays where it was, and you're told why (*The way back*).
- **`lup-dev restore`** goes back to a copy kept, with no host service and no dashboard (*The way back*).

## The host zone

What the host runs for a project (`Trust.zone`):
- **the declaration,** `lup_project.py` or the package `lup_project/`, and every file of the project it imports, in turn, with the conditions modules its modules name (`declared`);
- **the `lup-dev` it runs,** as the lockfile resolves it (`Lock.tool`): from the repository's own workspace, as lup's does, the files of each workspace package `lup-dev` needs, the dashboard's among them, with uv's files and the engine's source; or a release from an index, held to its version and its dependencies' pins, ruff's among them, the judge's own (`docs/judging-writes.md`, *The engine: one typed tree*). A lock resolving `lup-dev` any other way, from git, a URL or a path outside the workspace, is refused: the host runs a release or the workspace's own source, and a copy built from git would also lack the engine, which is built and never committed;
- **the person's own layer,** and **their profiles,** each by its content (*Trusted by its content*).

**Trusted by its content.** `lup_project.local.py` is Python the host runs, and a room writes the worktree, but git holds none of it. So its content joins the zone: unchanged, it asks nothing; changed, created or removed, its diff is in the summary itself, since git's count can't show a file git doesn't hold. The approval keeps the copy approved, which the judge and a launch read beside the commit's export, never the worktree's. Where the layer is all that changed and the commit approved is still the tip, approving installs nothing and restarts no service.

**The person's profiles** (`docs/declaration.md`, *Profiles*), `~/.config/lup/profiles.py`, are Python the host runs too, for each repository's launches, and no repository holds them, so they join each repository's zone by their content the same way: their diff in the summary, the copy approved kept with the repository's approval, and a launch running that copy, never the file. Approval is per repository, so one edit to the file asks again in each repository, at its next launch. They join the approval's files unread by the judge, at their path outside the repository, since the repository's roles and rules aren't theirs; the summary shows their whole diff.

## Which branch

A project's declaration names two branches (`docs/declaration.md`, *The branches*): the **integration branch**, what branches start from, and the **running branch**, what the host runs, what trust reads and what `land` lands on. Without `Versions` they're one branch, `dev` unless `Core` says.

- **Read from the declaration already approved, `dev` before the first approval.** Trust never runs a project's code before the operator approves it, so it can't load the tip's declaration to learn which tip to read. A yes reads the branches the declaration it approved names, the person's own layer on it, and keeps them with the approval (`Trust.answered`, `Approval.branches`), so whatever needs them reads a file and runs nothing of the project's (`approved_branches`). An approval recorded before they were kept reads as `dev`.
- **A change to them goes through an approval, which shows it.** The declaration is in the zone, so a commit changing either is in the approval's diff, as a person's layer changing either is in its summary. Nothing moves until it's approved, and the answer says what moved; declined, they stay. Trust asks next about the tip of the branch just named.
- **A running branch the repository doesn't hold yet** reads the integration branch's tip, then the worktree's `HEAD`. Naming a branch doesn't make it, and `HEAD` alone would ask the operator to approve whatever a launch's worktree has checked out.
- **A declaration that doesn't load** leaves them as they stood, as the judge's last declaration stands in for one that can't (`docs/judging-writes.md`, *A declaration that can't load has a stand-in*), and the answer says so.
- **A launch keeps the limits it registered,** the gated refs among them, so one already running refuses to `land` on a running branch approved since, until it's launched again (`docs/declaration.md`, *The branches*).

| What reads it | Branch |
|---|---|
| Trust: the zone at a launch, at `lup-dev trust`, and at a push moving it | running |
| `land`: what lands and where, unless the call says | running |
| A new session's bearings: what landed since the last (`docs/inbox.md`, *A new main session's bearings*) | running |
| "Since you approved": where a branch left, the baseline of a file the operator saw none of | integration |
| A thread parked until a branch or a commit lands, which wakes where work can start from it (`docs/inbox.md`, *Threads*) | integration |
| `draft_pull_request`: the branch it targets | integration |
| What a subagent kept in a landed worktree is told to start from | integration |

## Why it's this way

- **Read at the running branch's tip,** never a branch's own copy. What's approved is what runs: once one is approved, a commit landing on the tip judges nothing until it's approved too.
- **Found without running the project's code.** The tip's files are exported from git's objects, and the declaration is read with `ast`, its imports followed by Python's own path finder, which imports nothing; loading it to find them would run the project's code on the host before the operator was asked. Every `import` statement counts, a `TYPE_CHECKING` block's too, since showing more than runs only costs reading. A file that doesn't parse, a relative import leaving its package, or a conditions module that isn't there is said with the question; a module imported by a name computed at run time, or a conditions module named by anything but a string, isn't followed.
- **A first approval trusts the zone as it is.** The operator chose it by pulling it; what trust guards is what changes afterwards, through pushes they haven't read. So its files are read by their roles alone, and no engine runs; the approval says it's a first one (`Approval.first`), and the dashboard folds each of its files under its header (`docs/dashboard.md`, *The review*).
- **Exported from git's objects, never with `git archive`,** which applies the repository's `.gitattributes`, so the copy could differ from the diff approved.
- **Each repository's own judge.** The approved copy is installed with `uv tool install` in a place of its own (`Layout.judge`), and each launch's hooks are judged by its repository's copy, so every session is judged by the code approved for their repository, and one project's approval can't replace another's judge. On lup's own repository the copy is also what the operator's `lup-dev` and the host service run, the dashboard installed with it, so approving moves the service to it (*The way back*); a project's release judges its own launches alone.
- **Built on the host by the commit's own steps.** A copy from the repository's workspace is built from the commit's export by its declaration's steps that build a file, the engine and the dashboard's page, run as the gate runs them (`UvToolchain.build`, `launch/trust.py`). They run the project's tools on the host, where no gate runs, so the declaration's requirements are checked first, as the gate checks them: lup's need Node, uv, and pnpm 11 or later, which installs the engine's and the page's packages, and a required one missing stops the install before anything is built, naming each.
- **Each copy in a directory of its own** (`lup_dev/copies.py`). A copy is installed where no process runs, never over the one judging, and the repository's command, a link, is switched to it in one rename once the install has finished: installed in place, a process starting between two of uv's writes would load the new code against the old dependencies. A repository's process started before keeps its copy until it has answered what it was asked, a hold among it; the repository's next request starts a process of the new one (`docs/host.md`, *Each repository's judge and modules*). Copies the link doesn't name, which no process runs and which aren't kept (*The way back*), are removed by the host service's sweep.
- **The judge's reading comes in two passes** after a first approval, so a type check, seconds on lup's zone, doesn't hold the question up. Before it's asked, each file is read from its parse alone; once it's in the inbox, the host service reads its types and replaces the reading.
- **A push's approval has its types read in a checkout:** of the running branch, or where it has none of the integration branch, or else the repository's main worktree. A bare repository's own directory, trust's root for a push, holds no project, so from there nothing it imports resolves, which reads as findings the change doesn't have and hides those it does. Trust's own git stays in that directory, and git in the reading is pinned to the repository, since a room writes a worktree's `.git` and its push sets this off (`docs/credentials.md`, *Running git on the host*). A bare repository with neither checkout keeps the reading without its imports.
- **Two launches asking about the same zone** wait on one approval, and either answer, or the inbox's, reaches both.

## The way back

lup is used while it's built, so a landing can break the dashboard, the tool the fix would be made with. So the copies approved are kept, each switch to one can undo itself, and nothing about going back rests on what broke.

**Using it:**
- **`lup-dev restore`** lists the copies kept, what runs, whether the service answers and what each left of the ledger, and changes nothing. It works from any directory.
- **`lup-dev restore <commit>`,** or the commit's start, goes back: it stops the host service if one runs, ending it where it doesn't answer, snapshots the ledger, moves the service, the judge and your `lup-dev` to that copy with what was approved with it, starts the service, and checks that it answers. A commit approved whose copy is gone is built again from the commit, which takes minutes and needs uv and Node; a copy kept takes seconds and builds nothing.
- **`--ledger`** also puts the ledger back as that copy left it. It says first what that loses and asks. It's asked without `--ledger` where the copy can't read the ledger as it stands, since it left it at an earlier version of its tables.
- **The plain page** (`docs/dashboard.md`, *The plain page*) does the same from the browser, where the review can't, short of restoring the ledger, which stays the terminal's.
- It's refused in an agent's session, as approving is, since which code the host runs is the operator's.

**What's kept, and what it costs.** A copy is kept by its commit: the last five that answered, and every commit pinned (`Copies.pin`), which is how a branch on trial stays ready, so a copy can be built ahead of being switched to. Each adds about 46 to 59 MB beyond what they share (`docs/field-notes.md`, *What a kept copy costs*). A project's release can be fetched from its index again, so a project keeps only what runs.

**Your `lup-dev` is a launcher, not a copy** (`launcher`, `lup_dev/copies.py`): a few lines of shell, in uv's directory of commands, which run the copy the repository's link names, and for `restore` the copy that answered before it. A copy imports nearly everything as it starts, so one bad import or one dependency missing from the tool's environment takes the whole command down, and a command of that copy with it; the shell has nothing to break. What it can't get past is a copy's own interpreter gone, since every copy shares uv's Python: where `uv python uninstall` removes it, each needs building again. `uv tool list` no longer says what you run, and `uv tool uninstall lup-dev` would remove the launcher, its path being uv's as well: `lup-dev trust` puts it back at the next approval. uv's own install stays where it was, doing nothing once a kept copy has answered: `rm -r "$(uv tool dir)/lup-dev"` frees it.

**A switch** (`lup_dev/switching.py`). Nothing supervises the host service, so what acts on a switch watches it: the terminal answering an approval, the process a page starts for one, or `lup-dev restore`.
- **A copy that has never answered is tried on a state of its own first:** its service runs on a copy of the ledger, with its own sockets and a free port, reaching nothing past them (`LUP_HOST_REHEARSING`: no notice raised, no thread woken, no type read), beside the service your sessions use, which stays up. Two services can't share a state, so this is how the one running stays up until the other answers. A copy that fails here interrupts nothing. It's approved code that runs, so the wall doesn't move. A copy that has answered isn't tried again, so flipping between two is the hand-over alone.
- **Then the hand-over:** stop the service, snapshot the ledger, move the link and the approval, start the copy, ask again. Once it answers, your `lup-dev` names it, and the copy before is what `restore` runs from. Where it doesn't, it's ended and everything goes back, the ledger too where the copy moved its tables past what the one before reads: that costs the moments it was up, and the report says so. Signals are held back meanwhile (`uninterrupted`): cut short halfway, a switch leaves no service, with nobody left to start one.
- **"Answers" means served** (`Serving`): a real reading on the control socket, not a connection a kernel accepts for a stuck loop; the dashboard's address; the page; each script and stylesheet it names, whole; and the API relaying a reading back, with the token. There's no browser on the host, so a script that throws as it mounts, leaving the page blank, passes: the gate's `drive` step is what sees that, and this command and the plain page are what's left after it. Nothing watches the service after this check, so a crash a minute later is this command's too.

**What an approval comes to.** A copy that doesn't answer isn't approved: the approval stays where it was, the next launch asks about the tip again, and the operator is told why, at the terminal, or, where they approved on a page and may not be watching, by the approval coming back to their inbox with why first. It's in the service's log, and the plain page says what came of the last switch.

**Going back moves the approval with the copy,** the person's layer and profiles approved with it among it, so what runs is what was approved together. Each launch then asks about the tip again, its diff from that copy, until the branch moves; declining launches on the copy. An older approved copy runs again with no new review, by the operator's own command alone.

**The ledger's snapshot** (`lup_dev/snapshots.py`). A copy can change what the ledger stores, and conversions are one-way, so each switch keeps the ledger as the copy being left left it, once its service has stopped and nothing writes, in lup's state, which no room mounts: the database (17 MB as measured) and a hard link to each attachment, which costs no disk, since the store writes each whole under a name of its digest. The latest each kept copy left stays. It leaves out the launches' records, the judge's stores and the sessions' names, which move with sessions still running, and which going back leaves where they stand, as a restart does.

**Restoring loses what happened since,** which is said, counted where the tables still compare, before it's done. What it replaces is moved aside whole, into a directory beside the snapshots, not removed, though no lup reads it; a session waiting on an item that went gets no answer to it. The number sequence stays past every number used, so an item made after never takes the number of one a hold or a session still names, for an answer meant for that one to reach it.

**The first time.** The approval of the lup that brings all this is carried out by the lup before it, which installs as it always has. So `lup-dev trust`, run once by hand afterwards, installs the same commit as a kept copy and moves the service to it, uv's install being what it falls back to. A launch leaves that to the operator, since it restarts the service their sessions use. Until then, the next approval does the same.
