# Launch: a terminal session in a room, compiled from the declaration

**One sentence:** `lup launch claude` (or `codex`) starts the latest CLI in a podman container holding the repository, with the operator's own login and history, every setting of lup's compiled at launch from the project's declaration and passed outside the repository, and the one hook carrying each event to lup's host service, where the judge runs.

This is the first of #56's four pieces, each a note and a branch, each on both runtimes:
1. **this one:** the room, the compiled settings and guidance, the one hook, and the host service it reaches;
2. lup's MCP server in a launched session, the inbox and `lup inbox`, and the credential actions (git through a remote helper, GitHub through lup's tools);
3. `propose` and holds, replacing the checkpoint;
4. the dependency guard.

It pulls `DESIGN.md`'s build steps 3 (rooms) and 5 (launch) ahead of tools and runs, scoped to what a maintaining session needs, with the host service's skeleton from step 6. `DESIGN.md` is the design; the facts this note rests on, measured or read for it, are in `docs/field-notes.md` (*Claude Code 2.1.296: launching a session*, *Codex 0.162.1: launching a session*, *Rooms*). A choice the operator hasn't confirmed is marked **(leaning)** where it's stated.

What it leaves to other pieces:
- everything in pieces 2 to 4. A launched session pushes and reaches GitHub through piece 2, and lup's own sessions run in rooms with it (*Building it*);
- rooms from code: `Room` as an `Agent`, with `ask` and `spawn` in a container. The check `DESIGN.md` owed for it is answered: the SDK on the host drove the CLI in a container over stdio, and the CLI reached an in-process tool on the host;
- the clipboard, devices and a browser in the room, each with the first lup's evidence in `docs/field-notes.md`. The clipboard comes later; none blocks a maintaining session;
- budgets and `accounts`.

**It builds on the declaration's slice A** (`docs/declaration.md`, *Building it*). A launch reads `Core`'s session settings, each module's guidance, packages and requirements, and the runner, all parts of modules. So slice A lands first, and the command is `lup-dev launch` until slice C makes it `lup launch`.

## The command

```
lup-dev launch claude [<the runtime's own arguments>]
lup-dev launch codex  [<the runtime's own arguments>]
lup-dev host [stop]
lup-dev trust
```

A launch starts in the worktree it's run from. Any argument lup doesn't know reaches the CLI as given, so `lup-dev launch claude --resume` resumes. `lup-dev host` runs the host service in the foreground, for watching it; `lup-dev host stop` stops it. `lup-dev trust` makes a launch's check of what the host runs, and its question, with no session after it (*Trust on launch*).

A launch, in order:
1. checks the host zone against the copy the operator approved, and where it changed, asks, in the inbox and at the launching terminal, a summary first and the whole diff only when asked for (*Trust on launch*): the zone is read without running any of the project's code, so nothing of the project runs before the operator is asked;
2. loads the declaration at the commit the operator approved, as the judge does, so a branch can't change the room it runs in;
3. checks the host's requirements (podman and git; `gh` and `notify-send`, optional, each one missing said), names the repository on GitHub from its own remote with `gh`, or says once why it can't, and starts the host service if none is running, or restarts it on a copy just approved;
4. fetches the runtime's latest CLI if a newer one is out (*The CLIs*);
5. finds on the host the other repositories named for its sessions to read, saying once each one missing, then builds the room's image if its definition changed;
6. compiles lup's settings and guidance into a launch directory under lup's state, and refuses a repository whose `config` would have the host's git read what the room writes (*The room's git*);
7. registers the launch with the host service, which opens the launch's sockets (its hook's, lup's tool server's and its room's requests'), and keeps what the registration carries for the launch: the repository's git directory, its name on GitHub, and the limits on the operator's credentials the declaration sets;
8. writes the room's git configuration and lup's remote helper into the launch directory, then runs the container in the foreground with a terminal: its first process checks the modules' requirements inside the room, all at once, then becomes the CLI;
9. when the CLI exits: the container is removed, the launch unregistered, its directory removed.

Measured: a container starts in 0.55 to 0.9 s; an image already built and a CLI already current cost nothing more.

**As built** (`cli.py`'s `launch` and `launched`, with `Launcher` holding what it reaches on the machine, each a seam its tests stub):
- **Inside an agent's session it refuses,** before anything else, as `trust` does: the runtimes' own variables tell (`Runtime.inside`). A runtime lup doesn't know is refused, naming those it does.
- **Trust's report is said** whatever it came to: unchanged, approved, or declined with the copy approved before kept. Declined with nothing approved before, nothing launches.
- **The declaration at the approved commit** (`launch/session.py`, `approved_declaration`): the commit's Python modules and project files are exported from git's objects into a scratch directory, the declaration imported there and resolved, then the files of the project's own guidance sections exported beside them, so the guidance a session reads is the approved commit's too. The scratch directory lives as long as the launch.
- **The host's requirements** (`launch/room.py`, `host_needs`) are podman and git, which pushes and fetches for each room, and two optional ones: `gh`, without which lup's GitHub tools and the gate's issue states in a room are off, and `notify-send`, without which the inbox raises no desktop notice. They're checked as the gate checks a module's, all at once, naming how to install what's missing; a missing optional one is said, and the launch goes on.
- **The repository on GitHub is named once, here** (`cli.py`, `on_github`; `forge/github.py`, `named`): `gh repo view --json owner,name`, run in the repository's git directory, reads the repository's own remotes there, a remote's SSH alias resolved through ssh's own configuration (`docs/field-notes.md`, *GitHub through `gh` on the host*), and the registration carries the answer. Never from the worktree, whose `.git` file is the room's to write (#54). Where `gh` is missing, which its requirement said, it isn't asked; where it can't name the repository (no login, no remote on GitHub, offline), the launch says why once and registers none, and each GitHub tool then says so.
- **The latest CLI** comes from `CliCache`; where the channel couldn't give it, the version kept runs, and the launch says which and why.
- **Other repositories for sessions to read** (`docs/related-repositories.md`): the declaration's resolved `repositories`, a person's own layer's among them (`lup_project.local.py`, approved with the zone and put beside the commit's export by `approved_declaration`), each found on the host (`related`, `launch/room.py`); each one missing is said once, and the room passes it over.
- **The room** (`maintaining_room`) is made before its image is built, so its refusals (an environment on a system interpreter, a tree holding the home, another repository overlapping its mounts) come before a build that may take minutes; the image is then built where its tag is missing, and a build said with its duration.
- **The terminal settings** (`terminal_settings`): below, *Modules and public API*.
- **The room's git** (`room_git`, *The room's git*): the repository's `config` checked against everything the room mounts, its own and its terminal's, once the terminal settings say what that is; the configuration and the helper written into the launch's directory once the launch is registered, so they go with it.
- **The sweep, then registration,** under the launch's own lock (*On the host: the service*). The launch's id is 16 hex digits, its container `lup-<id>`.
- **What the registration carries** (`Register`, `host/protocol.py`), as plain data: the launch's id, its runtime, the worktree launched, its container's name and its repository's judge; the repository's git directory on the host (`repository`), which the launcher finds with git before the room starts, so the host acts in the repository's own directory, never one the room names; the repository on GitHub (`github`, a `GitHubRepository`, its owner and name; none where it couldn't be named); and the limits on the operator's credentials (`limits`, a `Limits` of the actions allowed and the protected ref patterns), `Core.credentials` resolved from the declaration at the approved commit, as the session settings are (`docs/declaration.md`, *What a launch reads*; `docs/host-tools.md`, *What the declaration allows*). The service records the registration whole with the launch, so a restarted service keeps them. GitHub's tools hold each of their actions to the limits, on the repository the registration names (*On the host: the service*); git's remote helper holds each push and fetch to them, in the git directory it names (*The room's git*).
- **The room opens** with the container named and the launch's socket directory mounted at `/run/lup`; every argument lup doesn't know goes after lup's own flags, so `lup-dev launch claude --resume` resumes, and `-p`, `--model` or anything else reaches the CLI as given.
- **When the CLI exits, or the launch fails on the way,** the registration ends and the launch's directory is removed; where the service can't end it, that's said, and the next launch's sweep ends it. The command exits with the CLI's status.
- **The model** is the operator's own (the operator's decision): the launch's declaration names none (`lup.Claude()`, `lup.Codex()`), so no `--model` is passed and each runtime reads the operator's own choice itself, from `~/.claude/settings.json`'s `model` or their `config.toml`'s, or runs its own default where they chose none. `--model` would outrank theirs on both runtimes, so a declaration names a model only where it means to impose one. Their reasoning effort stays theirs too, since the launch sets none. Set aside: reading their choice and passing it back with `--model`, which needed a model of lup's own where they chose none (Codex has no alias for its default, so lup would have named one that goes stale).
- **No runtime's SDK** (the operator's decision): `Claude` and `Codex` are the library's, and each imports its SDK only when an ask runs (`docs/library.md`, *The front door*), so their terminal compile needs neither extra, and `lup-dev`, depending on `lup` without extras, launches either runtime. Set aside: `lup-dev` depending on both extras, which would install each SDK's wheel and the runtime binary it ships (about 600 MB together), never run by a launch, which fetches the latest CLI.

## Trust on launch

The code that runs on the operator's machine, outside every room, is approved before it runs (`DESIGN.md`, *Policy*, *Trust on launch*). There is no install step to remember: the launch itself asks, the way the first lup's launcher asked adlib's operator, "the first time, and whenever adlib's own code has changed since". `lup-dev install` goes.

- **The host zone** is what the host runs for a project:
  - its declaration (`lup_project.py`, or the package `lup_project/`), and every file of the project the host runs or reads for it: each of the project's own modules the declaration imports, with the `__init__.py` of each package holding one, and in turn what they import; and each conditions module its modules name, with the packages holding it, which finding it runs (later its rule tables);
  - the `lup-dev` it runs: for lup's own repository, `lup-dev`'s and `lup`'s source and the engine's, which the operator builds from; for any other project, the `lup-dev` release its lock file pins.
  - the person's own layer of the declaration, `lup_project.local.py` (`docs/declaration.md`, *Where it lives*; `docs/related-repositories.md`, decisions 7 and 8), which git ignores, so it's in the zone by its content (`Zone.local`), read from the repository's main worktree whichever worktree trust runs from (a bare repository's own directory for lup's layout), and what it imports of the commit is followed with the declaration's. A room writes the worktree, so an edit made there runs nowhere until approved: the approval keeps the copy approved (`Approval.local`), which the judge puts beside the commit's export (`Worktree.exported`, an export for each copy) and a launch beside its own (`approved_declaration`), never reading the worktree's. Its content joins the fingerprint only where there's one, so a zone without it keeps the fingerprint it had. Where it changed, created or removed, its diff is in the summary itself, after git's count, since git's count can't show it: git's own diff of the two copies, written into a scratch directory as `approved/` and `worktree/` (`git diff --no-index`, `compared`). Approved where nothing else changed, nothing is installed and no service restarts: the copy is the commit's already, and the judge reads the layer from the approval at each hook (`Trusted.installed`). Declined, the copy approved before stays.
  - **As built,** which is which is read from the tip's `uv.lock` (`launch/trust.py`, `Lock.tool`). Where it resolves `lup-dev` from the repository's own workspace, as lup's does, the zone holds uv's files (`pyproject.toml`, `uv.toml`, `uv.lock`, `.python-version`, which say where the workspace's packages are and pin the copy's dependencies), the `pyproject.toml` and `src/` of each workspace package `lup-dev` needs, and the engine's source (`packages/lup-dev/checker/`). Where it pins a release from an index, the zone holds that release and the version of every package it needs, which the copy is held to: a dependency bump the host doesn't run asks nothing. A lock resolving `lup-dev` from git, a URL or a path outside the workspace is refused, naming it: a copy built from git would lack the engine, which is built, never committed.
- **Read at the integration branch's tip,** never a branch's own copy; where the repository has no such branch, at the worktree's `HEAD`. What's approved is what runs: the host service answers the repository's hooks with the copy installed from that commit, and the judge reads the declaration there, its commit kept with the approval (`lup_dev/approval.py`; `docs/judging-writes.md`, *The declaration, from the approved commit*). A commit landing on the tip judges nothing until the next launch's approval; before any approval, the judge reads the tip, as it did before approvals existed.
- **Found without running the project's code** (`launch/trust.py`, `declared`): the tip's Python modules and project files are exported from git's objects into a scratch directory, and the declaration is read there with `ast`, its imports followed to the files they resolve to as the judge's import would find them (from the root, `src/`, and each uv workspace member, by Python's own path finder, `FileFinder`, which imports nothing), each package's `__init__.py` on the way, and in turn their imports; and the string a module gives as its `conditions` (`conditions = "audiobook.conditions"`, `Core(conditions=…)`) found the same way. A conditions module is read on the host, never run, so what it imports isn't followed; the packages holding it are, since finding it runs them. An import found nowhere in the project (the standard library, `lup_dev`, a dependency) isn't the project's. Every import counts, a `TYPE_CHECKING` block's or a function's too, since showing more than runs costs only reading. What can't be followed is said with the question: a file that doesn't parse, a relative import leaving its package, a conditions module that isn't there. Loading the declaration to find them, as the judge does, would run the project's code on the host before the operator was asked; and a declaration using what the running `lup-dev` predates wouldn't load at all. Not followed: a module imported by a name computed at run time (`importlib.import_module(name)`), or a conditions module named by anything but a string.
- **Its fingerprint is kept with the copy the operator approved,** per repository, in lup's state (`repositories/<id>/approved.json`). A launch compares the tip's host zone with it. The fingerprint is git's listing of the zone's files at the commit (each path, mode and object) with the `lup-dev` it runs, so a commit that leaves the zone alone asks nothing.
- **Changed, or never approved:** the launch says what changed since the approved copy, a summary first, and asks, yes or no. The question is an item in the operator's inbox from the start (`docs/host-tools.md`, decision 14), which the launching terminal answers too: `lup-dev inbox answer` at any terminal, and the dashboard once it exists, answer the same item, whichever comes first.
  - **The summary first** (`launch/trust.py`, `Change.summary`), since the first approval on lup's own repository, its whole zone in a pager, about 24,000 lines, was unusable: what's approved and why it runs on the host ("The host runs this repository's declaration and this `lup-dev` outside every room: they judge its sessions' writes, and carry out their pushes and GitHub actions with your credentials."); the commit approved before and the tip; then git's own count of each file, `git diff --stat --compact-summary`, coloured, as git prints it, nothing of it parsed: each file on a line with its lines changed and a bar of those added and removed, a file created or removed marked, then the totals; wide enough that git never shortens a path (`--stat=100000`), its bar 40 columns at most. Then "Show the whole diff?", no by default, a yes paging it (not asked where no file changed); then "Approve?", no by default.
  - **As built:** git's own diff and count, coloured, with no external diff command or text conversion the repository's configuration could name; the paths the approval held since its commit, and a path joining the zone (a module newly imported, a conditions module newly named) whole, in a count of its own; everything whole where the approved commit is gone from the repository. A release's change is said by its versions. Inside an agent's session nothing is asked: it refuses.
  - **In the inbox** (`inbox/store.py`, `Approval`; `inbox/protocol.py`): the launch puts the approval in the operator's inbox (`AskApproval`), starting the host service where none runs, as a launch does; the item holds the question, the summary, and what it's of (the repository and the zone's fingerprint), its whole diff kept beside it in a file of its own (`diffs/<number>.json`), read only on request, so listing the inbox never carries megabytes. It's from the operator's own launch to the operator, with a desktop notice, and its answer is its state (`Decided`: yes or no, and when), since no party's inbox waits for it. The launch waits on it over a control connection held open until it's answered (`AwaitApproval`, `HostClient.held`); its terminal prints the summary, then says it's item *N* of the inbox, `lup-dev inbox answer N` answering it from any terminal, and asks, watching its own input and that connection at once (`select`). Answered there, its answer answers the item (`AnswerApproval`); answered elsewhere first, the terminal stops asking, drops what was typed, and says so: "Item 12 was approved elsewhere." The first answer holds; a later one changes nothing and says so. `lup-dev inbox show N` shows the summary, `--diff` the whole diff through the pager; `lup-dev inbox answer N` asks as the launching terminal does, racing it the same way, or takes `--approve` or `--decline`; each refuses inside an agent's session, as every `lup-dev inbox` command does.
  - **Two launches at once** asking about the same zone wait on one approval: the second's ask joins the item waiting, both terminals ask, and either one's answer, or the inbox's, reaches both. The approval's lock is held to read the zone and ask, and again to act on the answer, but not while it's awaited; the first to take it again installs and records, the other reads what it recorded and installs nothing.
  - **A host service restarting while a launch waits,** as approving lup's own repository restarts it, closes the waiting connection with no reply; the launch waits on the item again from the service that runs next, which reads it from the inbox's store, giving a restart by another's hand its patience before starting a service of its own (`HostClient.rejoined`).
  - **Declined,** from any terminal: every launch waiting keeps the copy approved before, or with none approved, doesn't launch. The next launch asks again, as a new item.
  - **A service that doesn't know approvals,** one running a `lup-dev` older than the one launching (a development checkout's `uv run lup-dev trust` against the user's service), refuses the kind; the launch says so, with `lup-dev host stop` as what to do. The usual path never meets it: the old copy asks in its terminal, and approving the new one restarts the service on it.
  - **Interrupted** (Ctrl-C at the terminal): the item stays waiting in the inbox, and the next launch asking about the same zone joins it. An answer given while no launch waits on it is recorded on the item, and installs nothing: the next launch asks again **(leaning)**.
  - **Yes:** the engine is built, the zone's copy installed as the repository's own judge, the approval recorded, and the session launched. On lup's own repository the copy is lup's own command too, so it's also installed as the user's `lup-dev`, and the host service, which runs from that, restarted on it (its rooms keep their sockets: *On the host: the service*).
    - **As built:** the commit is exported whole into a scratch directory, never installed from a worktree, so what installs is the commit shown: each file written from git's objects (`git ls-tree`, then `git cat-file`; `lup_dev/git.py`, `Git.export`), not through `git archive`, which applies the repository's `.gitattributes` (`export-subst` rewrites a file, `export-ignore` leaves one out), so its copy could differ from the diff approved; the engine is built there through the declaration's own step and runner, as the gate builds it, and `uv tool install` installs `packages/lup-dev` from there, its dependencies held to the lock (a release, from its index, held to its pins). Built once, it's installed in the repository's own place (below), and on lup's own repository in uv's tools too; a running service is then stopped and started again from that copy's command (`uv tool dir --bin`); where none runs, the launch starts one. A project's release restarts nothing: each hook runs the repository's copy afresh.
- **Each repository's own judge (the operator's decision).** One host service runs for the user, and the `lup-dev` a person runs is the per-user install; but each launch's hooks are judged by its own repository's approved copy, installed by trust on launch in a place of its own under lup's data, `$XDG_DATA_HOME/lup/judges/<repository>/` (`Layout.judge`), as a uv tool there (`UV_TOOL_DIR` and `UV_TOOL_BIN_DIR` set for that install alone), its command `bin/lup-dev`. A launch's registration names that command, and the service runs it for each of the launch's hooks (*On the host: the service*), so every session is judged by the code approved for its repository, and a second project's approval can't replace the first's judge. lup's own repository is the one whose copy is lup's own command (`Tool.lups_own`: the copy is its workspace's own source), so its approval updates the per-user install too.
  - Set aside: **one copy, reinstalled when switching projects**, which would judge one project's session with another's approved code whenever two run at once, and rebuild on every switch; **a service per repository**, which would multiply the services, their sockets and their restarts, where the hooks need only a process each.
  - **A copy approved but missing** from its place (removed, or never installed there) is installed from the approved zone at the next launch or `lup-dev trust`, asking nothing, since it was approved; and said in the report.
  - **No:** the session launches on the copy approved before, and the launch says the tip isn't the code judging it. With no copy approved yet, it doesn't launch.
- **What it costs:** each repository's copy is a Python environment of its own, about the size of the per-user install, and a hook pays a process's start (Python and `lup-dev`'s imports) on top of judging. After a large merge, the next launch's diff is large (the declaration's slice A was about 5,000 lines of the judge). That is the review; it comes at launch rather than at a separate step, a summary first. The first approval in lup's own repository holds its whole zone: about 110 files and 24,000 lines at `dev`'s tip when this was built, its summary a line for each file.
- **Until `launch` exists,** `lup-dev trust` runs the same check and question with no session after it, so the operator approves a judge on lup's own repository.

## The room

### The image

- **lup's base, then the packages the selected modules ask for.** The image is `archlinux` with its mirror set to one day's snapshot of the Arch Linux Archive, which lup's release pins, then one `pacman -Syu` of every package the selected modules name. With the base image and the day pinned together (`catalog/room.py`'s `RoomBase`) the upgrade has nothing to do; were they to part, `-Sy` alone would be Arch's unsupported partial upgrade. Measured on a small set: git alone builds in 7 s and adds 137 MB to the 408 MB base. Size isn't the constraint; leaving nothing behind is (*Footprint*, below).
- **Each module has a `packages` part,** a selection like every other kind, each package with its reason:

  ```python
  class Studio(Module):
      packages: Packages = Packages.of(
          Package(name="ffmpeg", why="encodes the episodes"),
          Package(name="noto-fonts-cjk", why="pages set Japanese text"),
      )
  ```

  A requirement, a tool lup checks for, names the package providing it in lup's image (`Requirement(tool="node", …, package="nodejs")`), and that package joins the image without being listed twice. The image is derived from the declaration, so it can't drift from what the modules need. Mounting the host's binaries instead fails on linkage: the host's `uv` needed `libjemalloc.so.2`, and Arch's `node` links abseil and icu.
- **`Core`'s default `packages` is a standard machine.** Every agent meets the same one, whatever the host is: bash and the usual tools, none of the operator's shell setup. The CLIs run an agent's commands in the user's shell, aliases included: on this machine that's a shell with `cp`, `grep` and `ls` aliased to other tools, which tripped every research job for this note, and once nearly had uv recreate the shared `.venv` through the shell's `:r` modifier. The set starts from the first lup's, which its sessions used for months:
  - **the shell:** bash, coreutils, findutils, grep, sed, gawk, diffutils, file, which, less, tree, procps-ng, util-linux, lsof, inetutils, tzdata, and the `en_US.UTF-8` locale;
  - **work:** git, curl, ca-certificates, openssh, jq, go-yq, ripgrep, fd, python (for scripts outside a project), socat (the hook, *The one hook*);
  - **for the runtimes:** poppler, since Claude Code's Read renders a PDF's pages with `pdftoppm` ("pdftoppm is not installed. Install poppler-utils … to enable PDF page rendering", in its binary); ttf-liberation, one font family, so anything that renders text finds a face;
  - **editors,** for Ctrl+G, which opens `$EDITOR` in the room: vim, neovim, nano, emacs-nox and helix.

  From the first lup's, three leave the base: bun, which installed its CLIs and is a project's own now (adlib's studio uses it); github-cli, since the room holds no GitHub login and piece 2 reaches GitHub from the host; and the virtual display behind its clipboard, until the clipboard's piece.
- **From the modules:** nodejs with `CodeRules` (the engine is pyright's code, bundled for Node); uv with `Python`'s runner; npm with lup's own module, which builds the engine from source; ffmpeg, the Noto fonts and Chromium's libraries with adlib's own.
- **The pinned snapshot** makes a build reproducible, and every package is at least as old as the pin: the minimum package age `DESIGN.md` asks for (*Policy*). Moving the pin is a release's decision, checked when it's chosen, since some days are missing from the archive (2026-08-16's `core.db` answers 404). A tool whose snapshot version is too old for its requirement fails the launch's check, naming both versions.
- **Tagged by its definition's digest** (`lup-room:<digest>`), and built when that tag is missing.

### Footprint

The first lup left 46 images of 4.5 to 5.5 GB on this machine, kept alive by readable per-checkout tags, and 25 GB of per-project environments nothing pruned. Here:
- one image per definition, labelled with its project; after a build, the project's older lup images that no container uses are removed;
- no environment of lup's own: the project's `.venv` is shared (*The project's environment*);
- the CLI cache keeps each runtime's current version and the one before it, for a session still running: about 250 MB a version for Claude Code, 430 MB for Codex's package;
- every build is recorded with its duration and size, one JSON line in lup's state, which the first lup never recorded.

### The CLIs

- **The latest, fetched at launch.** A launch asks each vendor's own release channel (the one its installer uses) for the latest version, downloads it into lup's cache on the host when it's newer, checks its published checksum, and mounts it read-only into the room. So `lup launch claude` runs the latest Claude Code, whatever the host has installed, or without one. Offline, the cached version runs, and the launch says so.
  - The channels, read in each installer (`docs/field-notes.md`, *The CLIs' release channels*): Claude Code's `downloads.claude.ai`, a version's binary checked against its manifest, downloaded compressed with zstd as the installer does; Codex's `releases.openai.com`, its package checked against the release's `digest`, unpacked whole, since the binary runs helpers found beside it. A download that doesn't match is never used, and the cached version runs, saying why.
  - Each channel is spelled in its runtime's adapter in `lup_dev`, since lup's rules keep a runtime's name out of every other module; `launch/clis.py` holds the cache and the seam the adapters fill.
  - The checksums arrive over HTTPS from the vendor. Both vendors also sign: a GPG signature on Claude Code's manifest, a Sigstore bundle for each Codex package. lup doesn't check either yet.
- **Never baked into the image:** the first lup installed its CLIs into the image from npm at every release, a 1 GB layer rebuilt on most days.
- **Asks from code keep the CLI their SDK pins** (`docs/library.md`, *Pinned runtimes*): their guarantees are checked per version, which a launched terminal, the operator's own, doesn't need. In the room, the CLI's own updater is off, since its file is read-only.
- Checked: the CLIs run on the bare base image. Claude Code's native build links only glibc; Codex's is static, and ships its own `rg` and `bwrap`.

### The mounts

Everything is mounted at its host path: a linked worktree's `.git` file and the environment's links hold absolute paths, and the runtimes key their history on the working directory's path.

| What | Mode | Why |
|---|---|---|
| The repository: its git directory and every worktree, as one tree | read-write | the agent's work, and the other worktrees it's asked to read or clean up |

- **One mount for the whole repository.** The first lup mounted each worktree on its own, and a mount point can't be deleted from inside, so agents couldn't remove a worktree they were done with ("EBUSY"). Mounted as one tree, `git worktree add` and `remove` work as on the host, and an agent reads any other worktree it's pointed at. The refs are writable too: an agent can move or delete a branch, as it can today, and the reflog keeps what was moved. A worktree's `.git` file stays writable for the same reason, so #54 stays the judge's. The tree is the nearest directory holding the git directory and every worktree; where that would hold the operator's home (a worktree kept far from the others), the launch refuses and says to keep them under one directory.
- **Other repositories, read-only** (`related`, `launch/room.py`): a relative path is from the directory holding the project's own repository (the parent of a bare repository's git directory, or of a clone's working tree), an absolute one as it says, a leading `~` the operator's home; each is resolved, and mounted at that path. One that isn't there is passed over, said once by the launch and marked missing in the guidance. One overlapping the room's own mounts, the project itself, a directory inside what the room mounts, or one holding it, is refused, naming both: mounted read-only, it would sit over or under what the room writes.
- **Not mounted:** the SSH agent, `gh`'s login, and the rest of the home, the operator's shell configuration among it. `~/.gitconfig` isn't either: it holds the operator's aliases and an LFS filter the image lacks, so the git identity is passed as `GIT_AUTHOR_*` and `GIT_COMMITTER_*`, read from the host's git.

### The room's git

`git push` and `git fetch` work in the room as on the host, carried out by the host with the operator's credentials, within the limits the project's declaration sets (`docs/host-tools.md`, *git through a remote helper*, *What the declaration allows*).
- **`GIT_CONFIG_GLOBAL=<launch>/gitconfig`** (`remote/config.py`, `room_config`), the room's own in place of the operator's: for each URL the repository's remotes name, their push URLs among them, `url."lup::<url>".insteadOf = <url>`, so git runs lup's helper for every push and fetch; `branch.autoSetupMerge = false` and `push.default = current`, since nothing records an upstream in a room whose writes to `config` fail (`git push -u` pushes, says it couldn't write the upstream, and ends with status 0); `lup.requestSocket`, the launch's request socket, where the helper asks the host; and `lup.gate` and `lup.gated`, the gate a push to the integration branch runs first (`docs/host-tools.md`, *git through a remote helper*).
- **`git-remote-lup` first on the room's `PATH`** (`<launch>/bin`, then the image's own: `layout.py`'s `ROOM_PATH`), written from `remote/helper.py`, which runs on the room's Python with the standard library alone. Each batch git hands it is one request on `/run/lup/request.sock`; the host runs git in the repository's own git directory, to the remote the repository's `config` names, each update checked against the limits (`remote/protocol.py`). Both files are mounted read-only on every runtime, since only Claude Code's terminal mounts the launch's directory.
- **Refused at launch** (`launch/room.py`, `room_git`): a repository whose `config` sets `extensions.worktreeConfig`, under which git reads the git directory's `config.worktree` too, which the room writes; and one whose `config` includes, through `include.path` or any `includeIf` whatever its condition, a file inside one of the room's mounts, its own or its terminal's, each include resolved as git resolves it (relative to the file holding it, `~` the operator's home, an `:(optional)` one too) and followed through every file it includes. Either would have the host's git, pushing for the room, read what the room wrote (`docs/field-notes.md`, *Host-side git in a repository the room writes*).

### The user, the process, the network

- `--userns=keep-id`: the operator's uid inside, so what the agent writes is the operator's on the host.
- `--init`: without it, the first lup piled 4,045 zombies against its pids limit, and an unrelated test run failed.
- `--cap-drop=all` and `no-new-privileges`, so no inherited capability carries in (`DESIGN.md`, *Policy*).
- No memory or pids limit by default. The pids limit counts threads, and the first lup's 4,096 broke a test run.
- **The host's network.** The room shares the host's localhost both ways: a preview server an agent starts opens in the operator's browser, and the agent reaches what the operator runs, for working on something together live. The sign-in's browser callback reaches the CLI too, which the first lup found failing without it. The cost: code in the room reaches anything listening on the host's loopback; the wall is for damage, not for containing the agent (`DESIGN.md`, *Policy*). A room can declare its own network instead.
- **A terminal:** `-it`, with `TERM`, `COLORTERM`, `LANG`, `TZ`, `EDITOR` and `VISUAL` passed. The terminal's size carries through. The first lup's sessions lost colour, their locale, their time zone and Ctrl+G until it passed these and installed the editors.

## The project's environment, shared with the host

- **One environment.** The worktree's `.venv` is the host's, used as it is.
  - Why the first lup didn't: its container ran the image's system Python while the host's `.venv` pointed at a uv-managed one, so each side took the other's environment as broken and rebuilt it ("so host and container stopped clobbering each other's `.venv`"). It moved to an environment per project root outside the checkout, mounted over `.venv-contained`: a mount point agents couldn't remove, which nothing on the host pruned, 25 GB across 31 directories today, whose scripts went stale when a repository moved.
  - Mounting the host's interpreter at its own path removes the cause: both sides run the same Python, so one `.venv` is valid on both. Built into the image, an environment would rebuild the image at every change of the lock; installed at each start, it's the first lup's "minutes the first time".
- **The runner says what a room must mount:** `Runner.room()` returns mounts and environment variables. `Uv()` gives uv's interpreters read-only and uv's cache read-write, at their host paths, with `UV_CACHE_DIR`, `UV_PYTHON_INSTALL_DIR` (so a worktree made in the room gets its `.venv` on the store's interpreter rather than the image's) and `UV_PYTHON_DOWNLOADS=never`. `Plain()` mounts nothing, and a project's own runner says what it needs.
- **The interpreter must resolve inside.** A launch checks that the environment's interpreter resolves under the room's mounts, and refuses otherwise, naming it. Without the interpreter, `uv run` printed "Ignoring existing virtual environment linked to non-existent Python interpreter" and set about recreating the shared `.venv`; `UV_PYTHON_DOWNLOADS=never` stops it before it can, and the check says why. An environment on a system interpreter, outside uv's store, is refused with how to move it onto one uv manages.
- **Checked:** with these mounts, `uv run --frozen pytest` audited the environment and wrote nothing to `.venv`, and lup's whole suite passed in the room in 417 s, against 418 s on the host, with nodejs in the image for the engine.

## Your login and history

**The operator's own `~/.claude` and `~/.codex` are mounted into the room, read-write, at their paths.** A first launch needs nothing: it's the login the operator already has.
- **One login, so nothing to keep in step.** Claude Code replaces its credentials file inside `~/.claude`, and the whole directory is the mount, so the room and the host read and write the same file; Codex rewrites `auth.json` in place. A refresh on either side is a refresh for both, as with two sessions on the host. `/login` and `codex login` work in the room, and log the host in with it.

- **What changes in the room:**

- **What the agent can read:** the login and every transcript in those directories. lup isn't containing the agent, and the login is the runtime's own, readable by any session without a container today.

## The one hook and the host service

### In the room: a pipe

Each hook command pipes the runtime's payload, unchanged, to the launch's socket with `socat`, and prints the answer, so nothing in the room parses it. As built (`launch/session.py`, `piped`), it's one command for every runtime and event, `sh -c` running this script, each word in it quoted with `shlex`:

```
socat -t 90000 - UNIX-CONNECT:/run/lup/hook.sock || { echo 'lup: this hook couldn'"'"'t reach lup'"'"'s host service on /run/lup/hook.sock, so it wasn'"'"'t judged. On the host, `lup-dev host` serves this session again.' >&2; exit 1; }
```

`-t` is how long socat waits for the answer once the payload is sent: 90,000 s, 25 hours, above a hold's day, the same as the hook's own timeout (`hooked`). Any failure, socat's own or a shell without it, ends the command with status 1 and a line on standard error saying the hook wasn't judged and that `lup-dev host` on the host serves the session again. Status 2 would block the call on both runtimes, so the command never ends with it. The host service answers the payload by running the launch's repository's own copy of `lup-dev` (*On the host: the service*).
- **The judge stays on the host,** for practical reasons, not to guard it:
  - the judge asks a warm engine per worktree, a pyright process; on the host it's shared with the operator's own gate runs, where in each room a cold one would make the first edit wait for the whole project to type-check;
  - the installed judge, the one the operator approved, is the one that judges; in the room it would be the project's own copy, so a branch reshaping the judge would judge with its own edits;
  - holds wait for the operator's answer, which comes from the host.
- **What each runtime does with each end of the hook,** from Claude Code's hooks reference and Codex's source (`hooks/src/events/`, at `rust-v0.156.1`, each event's `parse_completed`); each adapter's docstring holds the evidence:

  | The hook | Claude Code | Codex |
  |---|---|---|
  | The service's answer, status 0 | the decision it holds | the decision it holds |
  | Status 0, nothing printed | "no decision to report": the call goes through the normal permission flow | the run completes with no decision |
  | Status 1: the service unreachable, or socat missing | a non-blocking error: "a `<hook name> hook error` notice in the transcript with `Failed with non-blocking status code:` and the first line of your hook's stderr", and "the action goes ahead" | the run marked failed, with the entry "hook exited with code 1" (the hook's standard error isn't shown), and the call goes on |
  | The launch's judge can't answer (below) | a file tool's write is denied, telling the agent why; any other hook warns the operator in `systemMessage`, the call going on | at `PostToolUse`, the agent is told beside the call's result; any other hook warns the operator in `systemMessage`, shown as a warning entry, the call going on |

  That a hook which can't be judged goes on is the intended outcome, since the judge steers and doesn't guard (`DESIGN.md`, *Policy*); what goes on is said where the runtime shows it, rather than read as no decision. Only a file tool's write on Claude Code is refused, as when judging itself fails: let through unjudged, it would land unseen.
- **The events** are each adapter's `hooks`: Claude Code's `SessionStart`, `PreToolUse` on every call, and `Stop` and `SubagentStop`, so the host service hears each conversation's start, calls and turn's ends, as the inbox needs (`docs/host-tools.md`, *How an agent is told*); Codex's `SessionStart`, `PreToolUse` and `PostToolUse`, since Codex is judged after each call, and `Stop` and `SubagentStop`. Piece 3 removes the checkpoint and reshapes the rest.
  - **Which of them the judge reads** is the adapter's word (`heard`, *On the host: the service*): on Claude Code, `SessionStart` and the file tools' writes (`WRITING`), judged before they land; on Codex, every one. The service answers the rest itself, without starting the judge's process: what the runtime takes as no decision, never a block, with a call to lup's tools stamped with its caller. Measured on this machine, such a hook costs 4.5 ms end to end, against 665 ms for one the judge's process answers (`docs/field-notes.md`, *A hook the judge doesn't read*).
  - **Codex's turn's end is hooked** because Codex sends no `PostToolUse` for a call that didn't succeed (a patch that failed to apply, a call interrupted: `core/src/tools/registry.rs` at `rust-v0.162.1`), so the call stays counted and its session's checkpoints wait on it; the turn's end clears what the conversation left, as the judge's design has it (`docs/judging-writes.md`, *It degrades gracefully*). The operator's decision, 2026-10-13.
  - **What it does there is the judge's whole set's turn's end** (`docs/judging-writes.md`, *While a subagent works*): the session's `Stop` runs a checkpoint, waits for the importers pass, and holds the turn (`decision: "block"`, which Codex turns into a continuation prompt) on the type errors and ruff's findings left in the files its own conversation touched, except a file a subagent at work touched too, once per finding across turns: an end that follows a block (`stop_hook_active`) ends whatever's left, the operator told in `systemMessage`, and a finding a turn ended past holds no later end until it changes (`docs/host-tools.md`, *No turn that won't end*). A refusal, a move, an answer to a hold, the notes removed and mail hold it once each. A subagent's `SubagentStop` runs its checkpoint and never holds on findings, only on what it must be told. Claude Code's room has no checkpoint, so its judge reads no turn's end, and its writes, counted at `PreToolUse` and never finished, hold back nothing; the service answers its turn's ends itself. The timeout is hours, for holds: Claude Code documents no maximum for a command hook, and Codex took 99999 s.
- **Not set in the room yet:** Codex's `additionalContextLimit` on `PostToolUse`, which would let a report past Codex's default of 2,500 tokens arrive whole. The library's `Hook` has no field for it; past the default, Codex keeps the whole report in a file and shows a preview pointing there, so nothing is lost.
- **A protected path's ask on Claude Code** is the runtime's own prompt: a hook's `ask` prompts under `bypassPermissions` too, seen live on 2026-10-13 (*Checks owed*). Where a runtime can't ask before a call (`Runtime.asks_before`), as on Codex, the change is held until it's answered with `lup-dev holds`.

### On the host: the service

The host service is a program lup runs on the operator's machine, outside every room, which rooms call for what only the host can do: the judge for each hook; lup's inbox, its tools served on each launch's `mcp.sock` (`docs/host-tools.md`, *The inbox*); GitHub with the operator's `gh` and its login, for lup's GitHub tools and the gate's issue states in a room (`docs/host-tools.md`, *GitHub through `gh`*); pushes and fetches with the operator's credentials (*The room's git*); later, spawning sessions, budgets, and the dashboard's backend (`DESIGN.md`, *Modules*).
- **One per user,** the installed `lup-dev`'s, started by the first launch that finds none, and running until it's stopped: found or started on demand, as the engine is.
- **Each launch judged by its repository's own copy** (the operator's decision, *Trust on launch*): a registration names the copy's command, and each hook its judge reads is answered by running it, `<copy>/bin/lup-dev hook <runtime>`, a process of its own for each hook, the payload on its input and its answer what it prints (`host/service.py`, `judged`, the `judge` seam its tests stub). A registration whose copy isn't there is refused, saying that approving the repository's host zone installs it.
- **Each hook read through the `Courier`** (`host/courier.py`; `docs/host-tools.md`, *Who's calling*), which `cli.py` builds from the adapters, as it builds the `Answerer`. Its `heard` says the hook's event, the runtime's ids for the session and the subagent, the call and its tool, and whether the judge reads it. The service mints lup's own id for each conversation the first time a hook names it (`Conversations`), kept with the runtime's ids for as long as it serves the launch. A hook the judge doesn't read the service answers itself, without starting the judge: what the runtime takes as no decision. Every answer goes out through the `Courier`'s `told`, which adds what the conversation is told and rewrites a call to lup's tools to carry `caller`, the conversation's id. What it's told is the `Post`'s, the inbox's (`inbox/delivery.py`), which `cli.py` hands the service as it hands it the courier: asked at every hook with what room the judge's answer leaves (`Heard.fits`, what the runtime's hook tells whole, less the judge's answer), it returns what waits for the conversation, counted told, and takes it back as waiting where the hook was gone before its answer was written. The `Courier`'s `woken` spells the line that starts a turn of an idle session on its messaging socket, where its runtime has one. A payload the `Courier` can't read goes to the judge as it is; an answer of the judge's it can't add to goes out as the judge gave it; either is said.
- **Sockets per launch,** in a directory of its own, mounted into that launch's room at `/run/lup`: `hook.sock` for the hook; `mcp.sock`, lup's tools for the launch's session, one MCP session per connection (`lup.tools.serving.serve`, each line read up to 16 MiB), each call routed to the core's tool (`RoomTools`, `host/rooms.py`) or to the launch's modules' process (`host/workers.py`) with the launch and the conversation its `caller` names, a call without one taken as the main conversation's and said; and `request.sock`, one typed request per connection from the room's programs, routed to the core's `RoomHandler`s with the launch attached (`RoomRoute.to`), or to the launch's modules' process for a kind they answer, apart from the control socket's routes, so a room never reaches a control kind (`docs/host-tools.md`, *The server*, *The room's requests*). The service knows which launch speaks by the socket it hears it on, and the sockets go with the launch. Seen through `SO_PEERCRED`, a room's process has the operator's uid (keep-id), so the uid can't tell a room from the operator; the socket can.
  - One socket for every room would have each request name its launch, which the room would then say of itself.
  - HTTP on localhost, reachable from rooms on the host's network, would be reachable by every process on the machine, and couldn't tell rooms apart.
- **Its control is a socket on the host only,** taking typed requests: one JSON request per connection, a pydantic model discriminated by `kind`, and one JSON reply. The service's own kinds are a launch's registration and its end, listing the launches served, and stopping the service. Modules register the handlers for their kinds: the inbox's, the operator's (`inbox/protocol.py`: list, show, answer, done, send), behind `lup-dev inbox`.
  - A handler (`Handler`) names the model of its requests and answers each on the event loop; `Route.to(handler)` routes its kind there, read from the model, so the kind is spelled once. A handler's requests and replies are its module's own models, beside it, so a kind is added without editing the service or the protocol **(leaning)**. A closed union of every kind in `host/protocol.py` would have each module add its models there. Two handlers for one kind, on the control socket and the room's alike, and two modules serving one tool, are refused when the service is built.
  - What the service can't carry out is replied as `Refused`, with why: a request that doesn't parse, a kind no handler answers, a launch registered twice or running a runtime lup doesn't know, ending a launch that isn't served, and a handler's failure, which is said with its traceback.
- **GitHub through `gh` on the host** (`forge/`; `docs/host-tools.md`, *GitHub through `gh`*), on the one repository the launch's registration names, passed to every command as `--repo`, but for reading, which reaches another the operator's login can read where a call names it (`docs/related-repositories.md`), each run in the repository's git directory:
  - **lup's GitHub tools** (`lup/github/tools.py`, `GitHubTools`, the `GitHub` module's, served from the launch's own process): `read_issue`, `find_issues`, `file_issue`, `comment` and `draft_pull_request`. Each checks its action (`read-issues`, `file-issue`, `comment`, `draft-pull-request`) against the launch's limits before `gh` runs, and refuses one beyond them, saying the declaration doesn't allow it (`Core.credentials`) and that allowing it is the operator's call (`Limits.refusal`). No tool merges, or closes or edits an issue. A draft pull request goes from a branch already on GitHub into the integration branch (`LUP_INTEGRATION_BRANCH`, as the service reads it); a branch that isn't there is said, before `gh pr create` runs. `read_issue` and `find_issues` take an optional `repository`, `owner/name` (`GitHubRepository.read`), any the operator's login can read, passed as `--repo` in the launch's own's place, within `read-issues`; one that isn't `owner/name` is refused before `gh` runs, and the tools that write take none. A search leaves out a match in another repository than the one asked, which a query's own qualifiers can reach, and says how many.
  - **The gate's issue states in a room** (`forge/protocol.py`): the room's `IssueState` on `request.sock`, answered by the `GitHub` module's `Stating` (`lup/github/stating.py`) with `gh issue view --json state`, within `read-issues`. The gate asks it through `HostIssues` (`codescan/directives.py`) wherever `/run/lup/request.sock` is there; an issue the host doesn't answer (no service, an older one that refuses the kind by its name, `gh` out of reach, reading beyond the limits) goes unchecked, said with the host's reason.
  - **Each answer read into a model:** `--json` where `gh` gives it, the fields asked for named by the model that reads them; a command that answers with a link alone (filing, commenting, opening a pull request) passed on as `gh` printed it. Bodies go on `gh`'s standard input, every value the model writes as `--flag=value` or after `--`, and a branch's existence is asked with GitHub's GraphQL, the branch's name a variable.
  - **Where `gh` can't:** missing, or its status 4, which `gh` gives where a command needs a login, each said as such; any other failure in `gh`'s own words.
- **git, pushing and fetching for a room** (`remote/protocol.py`; *The room's git*): in the repository's own git directory, to a remote its `config` names, each update held to the launch's limits, with git's standard error said once for each push and fetch.
- **Each hook's judge, each `gh` and each git for a room is spawned through asyncio and awaited on the event loop** (`host/service.py`, `judged`, with `Asked.directory` where the program runs), which goes on serving meanwhile; a hold holds its judge's process, and nothing of the service's, while it waits. A wait cancelled, as when the service stops, kills its program. It runs a program other than with `sh`, with an `ignore` saying why: `sh` forks, running Python in the child before the program starts, which can deadlock a process with threads (Python warns of it, #23), and waiting on it would hold a thread per program for as long as it runs: a judge for a hold's hours, `gh` for GitHub's answer, git for a push.
- **Where the judge can't answer,** its command missing, or ending with any status but 0 (`lup-dev hook` answers judging's own failures in the hook's terms, so it fails only where it can't read the payload, or can't start), the service answers in the runtime's own terms through the `Answerer`, which `cli.py` builds from the adapters (each adapter's `unanswered`; what each runtime then does is in the table above). What the judge wrote to its standard error is said in full in the service's output, `service.log` when it runs in the background, and the answer points there. socat prints nothing and ends with status 0, which the runtime would take as no decision, only where answering failed even so, which the service says with its traceback (measured: 0 closed unanswered, 1 with no service).
- **A launch outlives a restart of the service (leaning).** Each launch is recorded beside its socket directory, under lup's runtime directory, and a service started after one stopped serves every recorded launch again, binding its sockets in the directory the room mounted. A restart closes each `mcp.sock` connection, and neither runtime starts a stdio server again, so lup's tools stop in a running session until `/mcp` reconnects them (Claude Code) or the session is resumed (Codex), while its hook goes on (`docs/host-tools.md`, *The server*). A stop closes the sockets and keeps the records; a launch's end removes its record and its directory, with whatever the room left in it.
- **A launch whose launcher died is swept by the next launch.** A registration names the launch's id, its runtime, its worktree, its repository's git directory, copy and name on GitHub, its container's name (`lup-<id>`), and the limits on the operator's credentials (*The command*). Its launcher holds the launch's own lock (`Layout.launch(id).lock`, under lup's state) from before it registers until its registration ends, a lock the OS frees when the launcher dies. Before registering, a launch lists the launches served (`ListLaunches`) and ends each whose lock it can take and whose container podman no longer has (`Podman.exists`), removing its directory, and says so. Both, since either alone ends a live launch: a container is made moments after its registration, so the container alone would end a launch still starting; and a launcher killed while its room runs on (a terminal closed under it) leaves a session still calling its hook.
- **One service runs at a time:** it holds a lock for its whole life, which the OS frees, so a second `lup-dev host` refuses, naming the socket; a control socket left by a service that died is replaced. Launches starting at once may each start one; all but the first refuse, and each client waits until the socket answers.
- **A stop doesn't wait for the answers in flight (leaning):** the sockets close at once, the next service may start, and the answers' threads finish before the old process exits, so a hold is still answered and logged as usual, but its hook hears nothing.
- **Started detached** by the client, as `python -m lup_dev.cli host` with the interpreter running the client **(leaning)**: the installed `lup-dev`'s whenever the launch runs from it. What it prints is appended to `service.log` in lup's state, which the client names when it doesn't answer in time.
- **Its waits go through `lup_dev.clock`,** so its tests drive time: the client waits up to 10 seconds for a service it started to answer, and for one it stopped to be gone.

## Modules and public API

### The library

`DESIGN.md` says one declaration compiles to SDK options for code and to a command line for a terminal, and that a room wraps an agent with a wall (*Calling agents*). So the terminal compile and the room are the library's, and the environment's maintaining session is a room it declares.

```python
from lup import Claude
from lup.rooms import Container, Image, Mount, Room

room = Room(
    agent=Claude(model="opus"),
    container=Container(
        image=Image(definition=CONTAINERFILE),
        mounts=[Mount(source=repository), Mount(source=hooks, read_only=True)],
        network="host",
    ),
)
status = room.launch(arguments=["--resume"], settings=settings)   # a terminal; returns the CLI's exit status
```
