# Launch: a terminal session in a room, compiled from the declaration

`lup-dev launch claude` (or `codex`) starts the runtime's latest CLI in a podman container holding the repository, with the operator's own login and history. lup's settings and guidance are compiled at launch from the project's declaration, at the commit the operator approved, and passed outside the repository; one hook carries each of the session's events to lup's host service on the operator's machine, where the judge runs. What the service gives a session beside its judge, lup's tools, the inbox and the operator's credentials, is `docs/host-tools.md`'s.

## What we have

Paths are under `packages/lup-dev/src/lup_dev/` unless they name another package.

### The command

```
lup-dev launch claude|codex [--name NAME] [--mount DIR|MODULE]… [--mount-rw DIR]… [<the runtime's own arguments>]
lup-dev mount [--rw] [--launch LAUNCH] DIR|MODULE
lup-dev rename LAUNCH NAME
lup-dev sessions
lup-dev host [stop]
lup-dev trust
```

- **A launch starts in the worktree it's run from.** Any argument lup doesn't know reaches the CLI as given, after lup's own flags, so `lup-dev launch claude --resume` resumes, and `-p` or `--model` reach the CLI. It exits with the CLI's status.
- **Lending a directory to one launch:** `--mount DIR` read-only and `--mount-rw DIR` writable, each repeatable, mounted at the directory's own path, last among the room's mounts, and listed in the guidance's *Lent to this launch*, with whether git sees a repository there and its `pyproject.toml`'s description where it has one (`Lent`, `lent`, `launch/room.py`). `--mount` also takes a module's name, lending its data (`--mount transcripts`, `docs/declaration.md`, *What a module is*), and refuses a name that's neither a directory nor such a module, naming those there are. Nothing is declared and nothing asks: lending is the operator's own command. A repository every session of the project reads is a `Repository` in the person's layer instead (`docs/related-repositories.md`).
- **Lending to a running room:** `lup-dev mount [--rw] PATH`, at the operator's terminal, mounts a directory under the room's `/lent`, by its name (numbered where taken), read-only, or writable with `--rw`, and tells the session where through the inbox; `lup-dev mount transcripts` lends a module's data, read-only. It picks the launch whose worktree holds the directory it runs in, the only one running, or the one `--launch` names. For it, each room mounts `<launch>.lent` at `/lent` as a slave of a mount made shared in podman's namespace before the room starts, and a directory lent read-only is made so in `<launch>.stage`, a private one, before it's mounted there (`receiving`, `lend`; `docs/field-notes.md`, *Lending to a running room*). The launch's end unmounts both and removes them (`unlent`), as does the sweep for a launch whose launcher is gone.
- **`lup-dev rename`** and **`lup-dev sessions`** name and list the launches (*Names*); `lup-dev host` runs the host service in the foreground, for watching it, and `lup-dev host stop` stops it; `lup-dev trust` makes a launch's check of what the host runs, and its question, with no session after it (*Trust on launch*).

A launch, in order (`launch` and `launched`, `cli.py`, with `Launcher` holding what it reaches on the machine, each a seam its tests stub):
1. **refuses inside an agent's session,** before anything else, as `trust` does: the runtimes' own variables tell (`Runtime.inside`). A runtime lup doesn't know is refused, naming those it does;
2. **checks the host zone** against the copy the operator approved, asking where it changed, and says what came of it: unchanged, approved, or declined with the copy approved before kept (*Trust on launch*). With nothing approved, nothing launches;
3. **reads the declaration at the approved commit,** with the person's own layer approved beside it (`approved_declaration`, `launch/session.py`): the commit's Python modules and project files are exported from git's objects into a scratch directory, the declaration imported there and resolved, and the files of the project's own guidance sections exported beside them. So neither a branch nor an edit made in a room changes the room a launch runs in or the guidance its session reads. The scratch directory lives as long as the launch;
4. **checks the host's requirements** (`host_needs`, `launch/room.py`) as the gate checks a module's, all at once, naming how to install what's missing: podman and git; and, optional, each one missing said and the launch going on, `gh` (lup's GitHub tools and the gate's issue states in a room), `notify-send` (the inbox's desktop notices), and `wl-paste` or `xclip` (the clipboard);
5. **names the repository on GitHub** (`on_github`; `named`, `forge/github.py`): `gh repo view --json owner,name` in the repository's git directory, a remote's SSH alias resolved through ssh's own configuration (`docs/field-notes.md`, *GitHub through `gh` on the host*), never in a worktree, whose `.git` file is the room's to write (#54). Where `gh` is missing it isn't asked; where it can't name the repository (no login, no remote on GitHub, offline), the launch says why once and registers none, and each GitHub tool then says so;
6. **starts the host service** where none answers;
7. **fetches the runtime's latest CLI** where a newer one is out (*The CLIs*); where the channel can't give it, the version kept runs, and the launch says which and why;
8. **finds the other repositories** the declaration names for its sessions to read, on the host (`related`; `docs/related-repositories.md`), saying once each one missing, which the room passes over; and makes the data directory of each module whose data the room mounts;
9. **makes the room** (`maintaining_room`) before its image is built, so its refusals (an environment on a system interpreter, a tree holding the home, another repository overlapping its mounts, an `$EDITOR` that isn't a command line) come before a build that may take minutes; the image is then built where its tag is missing, and the build said with its duration;
10. **compiles the terminal settings** (`terminal_settings`) into the launch's own directory under lup's state, and checks the repository's `config` against everything the room mounts (*The room's git*);
11. **under the launch's own lock, sweeps, then registers** the launch with the host service (*On the host: the service*), which opens its sockets, and says its name. The launch's id is 16 hex digits, its container `lup-<id>`;
12. **writes the room's programs** into the launch's directory (git's configuration and helper, the clipboard's `wl-paste` and `wl-copy`), prepares the room to be lent directories while it runs, and runs the container in the foreground with a terminal, the launch's socket directory mounted at `/run/lup`;
13. **when the CLI exits, or the launch fails on the way,** ends the registration and removes the launch's directory; where the service can't end it, that's said, and the next launch's sweep ends it.

A container starts in 0.55 to 0.9 s; an image already built and a CLI already current cost nothing more.

**What the registration carries** (`Register`, `host/protocol.py`), as plain data: the launch's id and name, its runtime, the worktree launched, its container's name and its repository's judge; the repository's git directory on the host (`repository`), which the launcher finds with git before the room starts, so the host acts in the repository's own directory, never one the room names; the repository on GitHub (`github`, a `GitHubRepository`, none where it couldn't be named); and the limits on the operator's credentials (`limits`, a `Limits`), `Core.credentials` resolved at the approved commit (`docs/host-tools.md`, *What the declaration allows*). The service records it whole with the launch, so a restarted service keeps it.

**The model is the operator's own:** the launch's declaration names none (`lup.Claude()`, `lup.Codex()`), so no `--model` is passed and each runtime reads the operator's own choice itself, or runs its own default where they chose none. `--model` would outrank theirs on both runtimes, so a declaration names a model only where it means to impose one. Their reasoning effort stays theirs too.

**No runtime's SDK:** `Claude` and `Codex` import their SDK only when an ask runs (`docs/library.md`, *The front door*), so their terminal compile needs neither extra, and `lup-dev`, depending on `lup` without extras, launches either runtime without installing each SDK's wheel and the runtime binary it ships (about 600 MB together), which a launch, fetching the latest CLI, would never run.

### Names

Each launch has an id, which never changes and under which everything of it is filed (its sockets, its record, its inbox items' whereabouts), and a name, for people and commands (`host/names.py`):
- **At launch** it's `--name NAME` exactly, refused where another running launch holds it; otherwise its worktree's branch in a name's shape (`feat/x` is `feat-x`), `-2`, `-3` added while taken. A name is letters, digits, `-`, `_` and `.`, not starting with `-`, at most 64 long.
- **It can change while the launch runs:** the session's `rename` tool (its guidance asks it to name itself after its task once it knows it), and `lup-dev rename LAUNCH NAME` at the operator's terminal. A name another launch holds is refused, saying whose. Since nothing is filed by name, a rename moves nothing: it's looked up each time it's used. The first lup keyed sockets by names, and a rename moved them out from under every peer holding the old one.
- **Wherever a launch is named,** by `lup-dev inbox send`, `lup-dev mount --launch` and `lup-dev rename`, its name, its id or its worktree does; several launches in one worktree are told apart by name. `lup-dev inbox` says who sent each item by its launch's name.
- **A session is told its name at its start,** and the name is kept by the runtime's id for the session in lup's state (`session-names.json`): a later launch resuming that conversation takes it back, where no running launch holds it, with a new id.
- **A subagent is named under the conversation that spawned it** (`w/explore-auth/grep-tokens`), its own name never its launch's, so a subagent's rename can't take its session's name: the first lup let a session and its subagent end up answering to one name, and sends between them stopped arriving. At a subagent's first hook, the service reads what its runtime recorded of its spawn (`Spawns`, each adapter's `spawned`): its name, where its parent gave one, the subagent that spawned it, where one did, and its kind; lup derives no name of its own. Claude Code records each beside the session's transcript, `<session>/subagents/agent-<id>.meta.json`; Codex at the top of the subagent's own rollout, its `session_meta` (`docs/field-notes.md`, *Subagents' records*).
  - **One spawned without a name** is called by its kind and its runtime's id (`w/Explore·a1`) and asked, beside its next call, to name itself after its task with `rename`; never at its turn's end, which it couldn't then leave. The conversation that spawned it is told once to give names, where its spawn takes one: on Claude Code the session's own conversation (`name` on `Agent`), since a subagent's `Agent` takes none. On Codex, never: the first `spawn_agent` takes no name and the second requires one.
  - **`rename` from a subagent** names that subagent alone, refused where another subagent of the launch holds the name, saying whose; the name its runtime gave it at its spawn, which its parent's own tools use, stays as it was.
  - **Kept with the launch** (`<launch>.conversations.json`), so a restarted service knows each subagent's name and place; `lup-dev sessions` shows each launch's conversations as a tree, and `lup-dev inbox` says who sent an item by its path.
- **The runtime's own title** follows where the runtime has a way. Claude Code: the start's answer sets `sessionTitle` (its `hooks` docs: "with the same effect as `/rename`"), so `/resume` and `claude --resume <name>` show lup's name; a title the operator gave with `/rename` arrives as the start's `session_title` and is taken in a name's shape (`Naming Review` is `naming-review`) where it's free. No `--name` is passed at launch, since a resumed conversation would lose its own title to it. A rename mid-session reaches Claude Code's title at the session's next start. Codex: a gap, declared. Codex names threads (`/rename`, its own generated titles, `codex resume <name>`), but sets a name only through its app server's `thread/name/set`, and a launched Codex runs its app server inside its own process (`--no-daemon`), which nothing outside reaches; its hooks neither carry a thread's name nor set one (`hooks/src/schema.rs`, `deny_unknown_fields`; read at `rust-v0.163.0`). lup's names work on Codex everywhere in lup; Codex's own title is its own.

### Trust on launch

The code that runs on the operator's machine, outside every room, is approved before it runs, since what changes the walls goes through the operator (`DESIGN.md`, *Who it's for*). There's no install step to remember: the launch itself asks, the first time and whenever that code changed (`launch/trust.py`, whose docstring says the rest).

- **The host zone** is what the host runs for a project:
  - its declaration (`lup_project.py`, or the package `lup_project/`), and every file of the project the host runs or reads for it: each of the project's own modules the declaration imports, with the `__init__.py` of each package holding one, and in turn what they import; and each conditions module its modules name, with the packages holding it, which finding it runs;
  - the `lup-dev` it runs (`Lock.tool`, read from the tip's `uv.lock`). Where the lock resolves `lup-dev` from the repository's own workspace, as lup's does, that's uv's files (`pyproject.toml`, `uv.toml`, `uv.lock`, `.python-version`), the `pyproject.toml` and `src/` of each workspace package `lup-dev` needs, the engine's source (`packages/lup-dev/checker/`), and the dashboard, which the person's own copy installs beside `lup-dev` (`WorkspaceTool.beside`; `docs/dashboard.md`). Where it pins a release from an index, that's the release and the version of every package it needs, which the copy is held to, so a dependency bump the host doesn't run asks nothing. A lock resolving `lup-dev` from git, a URL or a path outside the workspace is refused, naming it: a copy built from git would lack the engine, which is built, never committed;
  - the person's own layer, `lup_project.local.py` (`docs/declaration.md`, *Where it lives*; `docs/related-repositories.md`, *A person's own layer* and *Trusted by its content*), which git ignores, so it's in the zone by its content (`Zone.local`), read from the repository's main worktree whichever worktree trust runs from (a bare repository's own directory in lup's layout), with what it imports of the commit. A room writes the worktree, so an edit made there runs nowhere until approved: the approval keeps the copy approved (`Approval.local`), which the judge puts beside the commit's export (`Worktree.exported`) and a launch beside its own (`approved_declaration`). Its content joins the fingerprint only where there's one. Where it changed, was created or removed, its diff is in the summary itself (`compared`), since git's count can't show it. Approved where nothing else changed, nothing is installed and no service restarts.
- **Read at the integration branch's tip** (`LUP_INTEGRATION_BRANCH`, `dev` by default), never a branch's own copy; where the repository has no such branch, at the worktree's `HEAD`. What's approved is what runs: the host service answers the repository's hooks with the copy installed from that commit, and the judge reads the declaration there, its commit kept with the approval (`approval.py`; `docs/judging-writes.md`, *The declaration, from the approved commit*). A commit landing on the tip judges nothing until it's approved.
- **Found without running the project's code** (`declared`): the tip's Python modules and project files are exported from git's objects into a scratch directory, and the declaration is read there with `ast`, its imports followed to the files they resolve to as the judge's import would find them (from the root, `src/`, and each uv workspace member, by Python's own path finder, which imports nothing); and the string a module gives as its `conditions` found the same way. A conditions module is read on the host, never run, so what it imports isn't followed. Every import counts, a `TYPE_CHECKING` block's or a function's too, since showing more than runs costs only reading. What can't be followed is said with the question: a file that doesn't parse, a relative import leaving its package, a conditions module that isn't there. Loading the declaration to find them would run the project's code on the host before the operator was asked. Not followed: a module imported by a name computed at run time, or a conditions module named by anything but a string.
- **Its fingerprint is kept with the copy approved,** per repository, in lup's state (`repositories/<id>/approved.json`): git's listing of the zone's files at the commit (each path, mode and object) with the `lup-dev` it runs, so a commit that leaves the zone alone asks nothing.
- **Changed, or never approved,** the launch asks, yes or no, a summary first (`Change.summary`): what's approved and why it runs on the host ("The host runs this repository's declaration and this `lup-dev` outside every room: they judge its sessions' writes, and carry out their pushes and GitHub actions with your credentials."); the commit approved before and the tip; then git's own count of each file, `git diff --stat --compact-summary`, coloured, as git prints it, nothing of it parsed, wide enough that git never shortens a path, its bar 40 columns at most. Then "Show the whole diff?", no by default, a yes paging it; then "Approve?", no by default. The first approval on lup's own repository held about 110 files and 24,000 lines, unusable as a whole diff, so the summary comes first and stays on screen when the question comes. A first approval trusts the zone as it is ("Trust this repository's host zone as it is at …?"): the operator chose it by pulling it, and what trust guards is what changes afterwards, through agents' pushes they haven't read; its files are read by their roles alone, asking nothing, so the dashboard folds each, and no engine runs (`Trust.trusted_whole`).
  - git's own diff and count, with no external diff command or text conversion the repository's configuration could name; a path joining the zone shown whole, in a count of its own; everything whole where the approved commit is gone from the repository. A release's change is said by its versions.
  - **The question is an item in the operator's inbox** (`Approval`, `inbox/store.py`; `AskApproval`), starting the host service where none runs, which the launching terminal answers too. Its whole diff is kept beside it, read only on request (`lup-dev inbox show N --diff`), and each file it changes, whole, with the judge's reading of it, which the dashboard shows (`docs/dashboard.md`, *The review*). From the second approval on, the zone's change is judged as a move of `HEAD` is, each file against the commit approved before, by the declaration approved last, read from its commit with the person's own layer approved beside it (`Trust.read`); the tip's declaration is never imported before it's approved. The launch waits on it over a control connection held open until it's answered (`AwaitApproval`, `HostClient.held`); its terminal prints the summary, says it's item *N*, and asks, watching its own input and that connection at once (`select`). Answered there, the answer answers the item (`AnswerApproval`); answered elsewhere first (`lup-dev inbox answer N`, which asks as the terminal does or takes `--approve` or `--decline`, or the dashboard), the terminal stops asking, drops what was typed, and says so: "Item 12 was approved elsewhere." The first answer holds.
  - **The judge's reading comes in two passes,** so a type check, seconds on lup's zone, doesn't hold the question up (what each costs is in `docs/field-notes.md`, *Judging writes*). Before it's asked, each file is read from its parse alone (`Judge.parsed`, through the engine's `parse` command, `EngineParser`): a file created, written whole or on a protected path, its public names, each `ignore` it adds, and its directives' own problems, with no rule run; the approval goes in the inbox with that reading, its types to be read (`Approval.typing`), and where this fails, the files go unread and the summary's last line says why. Once it's in the inbox, the host service reads its types, whoever asked it (`TypeReader`, `inbox/typed.py`, a companion of the service, through `Trust.typed`, in a thread off its event loop): the whole judgement, lup's rules included, the engine and ruff run through the declaration's runner in the worktree it was asked from. Each file's reading is replaced with it and the item kept again, which the dashboard's watch sees; where it fails, the files keep the reading of their parse, and the summary's last line says why. An approval whose reading a stop cut short is read by the next service, so a launch interrupted while its approval's types are read leaves none half-read.
  - **Two launches at once** asking about the same zone wait on one approval, and either one's answer, or the inbox's, reaches both; the first to act on it installs and records, the other reads what it recorded.
  - **Asked after a push, with nobody waiting:** a push from a room that moves the integration branch puts the approval of the zone at its tip in the inbox, where it isn't the one approved (`Trust.proposed`; `proposed_after`, `cli.py`, which the push handler calls once the push is done), so the operator needn't notice the code the host runs changed. It names the session that pushed, which the operator's comment on their answer reaches as a note (`docs/host-tools.md`, *Parties and items*). Whatever fails is said in the service's log, and the push stands; a repository whose git directory holds a `commondir`, which would lead git elsewhere, isn't read. `lup-dev inbox answer` acts on a yes as a waiting launch would (`Trust.settle`, once between them), unless the branch moved again since it was asked, when nothing is installed and `lup-dev trust` asks anew. An approval of a newer zone of the same repository supersedes one still waiting (`Superseded`).
  - **A host service restarting while a launch waits,** as approving lup's own repository restarts it, closes the waiting connection with no reply; the launch waits on the item again from the service that runs next, giving a restart by another's hand its patience before starting a service of its own (`HostClient.rejoined`). A service whose `lup-dev` doesn't know approvals refuses the kind, and the launch says so, with `lup-dev host stop` as what to do.
  - **Interrupted** (Ctrl-C), the item stays waiting, and the next launch asking about the same zone joins it.
- **Yes:** the commit is exported whole into a scratch directory, each file written from git's objects (`Git.export`, `git.py`), never through `git archive`, which applies the repository's `.gitattributes` and could make its copy differ from the diff approved; the engine is built there through the declaration's own step and runner, as the gate builds it, and `uv tool install` installs `packages/lup-dev` from there, held to the lock (`Toolchain`). It's installed as the repository's own judge, in a place of its own under lup's data, `$XDG_DATA_HOME/lup/judges/<repository>/` (`Layout.judge`), with `UV_TOOL_DIR` and `UV_TOOL_BIN_DIR` set for that install alone. On lup's own repository, whose copy is lup's own command (`lups_own`), it's installed as the user's `lup-dev` too, and the host service, which runs from it, restarted on it (its rooms keep their sockets, and their bridges reconnect). The approval is recorded, and the session launched.
- **No:** the session launches on the copy approved before, and the launch says the tip isn't the code judging it; with none approved yet, it doesn't launch. Declined from any terminal, every launch waiting does the same.
- **Each repository's own judge.** One host service runs for the user, from the per-user install; each launch's hooks are judged by its own repository's approved copy, whose command its registration names. So every session is judged by the code approved for its repository, and a second project's approval can't replace the first's judge, without a service per repository. A copy approved but missing from its place is installed from the approved zone at the next launch or `lup-dev trust`, asking nothing.
- **What it costs:** each repository's copy is a Python environment of its own, about the size of the per-user install, and a judged hook pays a process's start on top of judging. After a large merge the next launch's diff is large; that's the review, a summary first.

### The room

#### The image

- **lup's base, then the packages the selected modules ask for** (`launch/images.py`). The image is Arch Linux's, its mirror set to one day's snapshot of the Arch Linux Archive, the day its base image was made, which lup's release pins (`RoomBase`, `catalog/room.py`), then one `pacman -Syu` of every package the selected modules name: with the base and the day pinned together the upgrade finds nothing to do, where `-Sy` alone would be Arch's unsupported partial upgrade were they ever to part. git alone builds in 7 s and adds 137 MB to the 408 MB base; size isn't the constraint, leaving nothing behind is (*Footprint*).
- **Each module has a `packages` part,** a selection like every other kind, each package with its reason:

  ```python
  class Studio(Module):
      packages: Packages = Packages.of(
          Package(name="ffmpeg", why="encodes the episodes"),
          Package(name="noto-fonts-cjk", why="pages set Japanese text"),
      )
  ```

  A requirement names the package providing it in lup's image (`Requirement(tool="node", …, package="nodejs")`), and that package joins the image without being listed twice. The image is derived from the declaration, so it can't drift from what the modules need. Mounting the host's binaries instead fails on linkage: the host's `uv` needed `libjemalloc.so.2`, and Arch's `node` links abseil and icu.
- **`Core`'s default `packages` is the standard machine** (`StandardMachine`, `catalog/room.py`): every agent meets the same one, whatever the host is, with none of the operator's shell setup. The runtimes run an agent's commands in the user's shell, aliases included, and on this machine that shell aliases `cp`, `grep` and `ls` to other tools. It holds, each group with its reason:
  - **the shell:** bash, coreutils, findutils, grep, sed, gawk, diffutils, file, which, less, tree, procps-ng, util-linux, lsof, inetutils, tzdata, and the `en_US.UTF-8` locale;
  - **an agent's everyday work:** git, curl, ca-certificates, openssh, jq, go-yq, ripgrep, fd; ast-grep, patch, unzip, zip; hyperfine, bc, strace, inotify-tools; make; python, for scripts outside a project;
  - **for lup and the runtimes:** socat (the hook, *The one hook and the host service*); poppler, since Claude Code's Read renders a PDF's pages with `pdftoppm`; ttf-liberation, one font family, so anything that renders text finds a face;
  - **editors,** for Ctrl+G, which opens `$EDITOR` in the room: vim, neovim, nano, emacs-nox and helix.

  github-cli isn't among them: the room holds no GitHub login, and reaches GitHub through the host (`docs/host-tools.md`, *GitHub through `gh`*).
- **From the modules:** nodejs with `CodeRules` (the engine is pyright's code, run on Node); uv with `Python`'s runner; npm and Chromium with lup's own module, `LupDevelopment`.
- **The pinned snapshot** makes a build reproducible, and every package is at least as old as the pin (`docs/field-notes.md`, *Package age gates*). Some days are missing from the archive (2026-08-16's `core.db` answers 404), so a pin is checked when it moves. A tool whose snapshot version is too old for its requirement fails its check, naming both versions.
- **Tagged by its definition's digest** (`lup-room:<digest>`), and built when that tag is missing.

#### Footprint

The first lup left 46 images of 4.5 to 5.5 GB on this machine, kept alive by readable per-checkout tags, and 25 GB of per-project environments nothing pruned. Here:
- one image per definition, labelled with its project; after a build, the project's older lup images that no container uses are removed;
- no environment of lup's own: the project's `.venv` is shared (*The project's environment, shared with the host*);
- the CLI cache keeps each runtime's current version and the one before it, for a session still running: about 250 MB a version for Claude Code, 430 MB for Codex's package;
- every build is recorded with its duration and size, one JSON line in lup's state.

#### The CLIs

- **The latest, fetched at launch** (`launch/clis.py`). A launch asks each vendor's own release channel, the one its installer uses, for the latest version, downloads it into lup's cache on the host when it's newer, checks its published checksum, and mounts it read-only into the room. So `lup-dev launch claude` runs the latest Claude Code, whatever the host has installed, or without one. Offline, the cached version runs, and the launch says so.
  - The channels, read in each installer (`docs/field-notes.md`, *The CLIs' release channels*): Claude Code's `downloads.claude.ai`, a version's binary checked against its manifest, downloaded compressed with zstd as the installer does; Codex's `releases.openai.com`, its package checked against the release's `digest`, unpacked whole, since the binary runs helpers found beside it. A download that doesn't match is never used, and the cached version runs, saying why.
  - Each channel is spelled in its runtime's adapter (`Channel`, `adapters/claude.py`, `adapters/codex.py`), since lup's rules keep a runtime's name out of every other module; `launch/clis.py` holds the cache and the seam the adapters fill.
  - The checksums arrive over HTTPS from the vendor; the vendors' signatures aren't checked (*Where it's going*).
- **Never baked into the image:** the first lup installed its CLIs into the image from npm at every release, a 1 GB layer rebuilt on most days.
- **Asks from code keep the CLI their SDK pins** (`docs/library.md`, *Pinned runtimes*), since their guarantees are checked per version, which a launched terminal, the operator's own, doesn't need. In the room, the CLI's own updater is off, since its file is read-only.
- The CLIs run on the bare base image: Claude Code's native build links only glibc; Codex's is static, and ships its own `rg` and `bwrap`.

#### The mounts

Everything is mounted at its host path: a linked worktree's `.git` file and the environment's links hold absolute paths, and the runtimes key their history on the working directory's path (`maintaining_room`, `launch/room.py`; each adapter's `terminal.py` in `lup`).

| What | Mode | Why |
|---|---|---|
| The repository: its git directory and every worktree, as one tree | read-write | the agent's work, and the other worktrees it's asked to read or clean up |

- **One mount for the whole repository.** A mount point can't be deleted from inside, so with each worktree mounted on its own, as the first lup did, agents couldn't remove a worktree they were done with ("EBUSY"). Mounted as one tree, `git worktree add` and `remove` work as on the host, and an agent reads any other worktree it's pointed at. The refs are writable too: an agent can move or delete a branch, and the reflog keeps what was moved. A worktree's `.git` file stays writable for the same reason (`docs/worktree-links.md`). The tree is the nearest directory holding the git directory and every worktree; where that would hold the operator's home (a worktree kept far from the others), the launch refuses and says to keep them under one directory.
- **Other repositories, read-only** (`related`): a relative path is from the directory holding the project's own repository (the parent of a bare repository's git directory, or of a clone's working tree), an absolute one as it says, a leading `~` the operator's home. One that isn't there is passed over, said once by the launch and marked missing in the guidance. One overlapping the room's own mounts, the project itself, a directory inside what the room mounts, or one holding it, is refused, naming both: mounted read-only, it would sit over or under what the room writes.
- **Not mounted:** the SSH agent, `gh`'s login, and the rest of the home, the operator's shell configuration among it. `~/.gitconfig` isn't either: it holds the operator's aliases and an LFS filter the image lacks, so the git identity is passed as `GIT_AUTHOR_*` and `GIT_COMMITTER_*`, read from the host's git.

#### The room's git

`git push` and `git fetch` work in the room as on the host, carried out by the host with the operator's credentials, within the limits the project's declaration sets (`docs/host-tools.md`, *git through a remote helper*, *What the declaration allows*).
- **`GIT_CONFIG_GLOBAL=<launch>/gitconfig`,** the room's own git configuration in place of the operator's, which rewrites each of the repository's remotes to lup's helper, records no upstream, and names the gate a push to the integration branch runs first (`room_config`, `remote/config.py`).
- **`git-remote-lup` first on the room's `PATH`** (`<launch>/bin`, then the image's own: `ROOM_PATH`, `layout.py`), written from `remote/helper.py`, which runs on the room's Python with the standard library alone. Both files are mounted read-only on every runtime, since only Claude Code's terminal mounts the launch's directory.
- **Refused at launch** (`room_git`, `launch/room.py`): a repository whose `config` sets `extensions.worktreeConfig`, under which git reads the git directory's `config.worktree` too, which the room writes; and one whose `config` includes, through `include.path` or any `includeIf` whatever its condition, a file inside one of the room's mounts, its own or its terminal's, each include resolved as git resolves it (relative to the file holding it, `~` the operator's home, an `:(optional)` one too) and followed through every file it includes. Either would have the host's git, pushing for the room, read what the room wrote (`docs/host-tools.md`, *Running git on the host*).

#### The user, the process, the network

Every run on the engine is walled the same way (`Podman`, `packages/lup/src/lup/rooms/engine.py`):
- `--userns=keep-id`: the operator's uid inside, so what the agent writes is the operator's on the host.
- `--init`: without it, the first lup piled 4,045 zombies against its pids limit, and an unrelated test run failed.
- `--cap-drop=all` and `no-new-privileges`, so no inherited capability carries in.
- No memory or pids limit by default: the pids limit counts threads, and the first lup's 4,096 broke a test run.
- The home a tmpfs owned by the operator, and each directory between it and a mount inside it too, since podman makes the missing ones owned by root, and uv refused a root-owned `~/.cache`; no log driver, so the session's output isn't kept in podman's logs; `--pull=never`, so a run never fetches an image by a short name.
- **The host's network.** The room shares the host's localhost both ways: a preview server an agent starts opens in the operator's browser, and the agent reaches what the operator runs, for working on something together live. The sign-in's browser callback reaches the CLI too, which the first lup found failing without it. The cost: code in the room reaches anything listening on the host's loopback; the walls are there so nothing explodes, not to contain an agent (`DESIGN.md`, *Who it's for*). A room can declare its own network instead.
- **A terminal:** `-it`, with no detach keys, so Ctrl+P reaches the program; `TERM`, `COLORTERM`, `LANG`, `TZ`, `EDITOR` and `VISUAL` passed (`TerminalVariables`, `settings.py`). The terminal's size carries through. The first lup's sessions lost colour, their locale, their time zone and Ctrl+G until it passed these and installed the editors.

### The project's environment, shared with the host

- **One environment.** The worktree's `.venv` is the host's, used as it is. Both sides run the same Python, the host's interpreter mounted at its own path, so one `.venv` is valid on both: the first lup's container ran the image's system Python while the host's `.venv` pointed at a uv-managed one, so each side took the other's environment as broken and rebuilt it, and its way out, an environment per project root outside the checkout, grew to 25 GB across 31 directories nothing pruned. Built into the image, an environment would rebuild the image at every change of the lock; installed at each start, it would take minutes the first time.
- **The runner says what a room must mount:** `Runner.room()` returns its mounts, variables and interpreter (`RoomNeeds`, `declaration/runner.py`; `docs/declaration.md`, *The runner*). `Uv()` gives uv's interpreters read-only and uv's cache read-write, at their host paths, with `UV_CACHE_DIR`, `UV_PYTHON_INSTALL_DIR` (so a worktree made in the room gets its `.venv` on the store's interpreter rather than the image's) and `UV_PYTHON_DOWNLOADS=never`. `Plain()` mounts nothing, and a project's own runner says what it needs.
- **The interpreter must resolve inside.** A launch refuses an environment whose interpreter doesn't resolve under the room's mounts, naming it, with the runner's remedy: without the interpreter, `uv run` printed "Ignoring existing virtual environment linked to non-existent Python interpreter" and set about recreating the shared `.venv`, which `UV_PYTHON_DOWNLOADS=never` stops. An environment on a system interpreter, outside uv's store, is refused with how to move it onto one uv manages.
- With these mounts, `uv run --frozen pytest` audited the environment and wrote nothing to `.venv`, and lup's whole suite passed in the room in 417 s, against 418 s on the host.

### Your login and history

**The operator's own `~/.claude` and `~/.codex` are mounted into the room, read-write, at their paths.** A first launch needs nothing: it's the login the operator already has.
- **One login, so nothing to keep in step.** Claude Code replaces its credentials file inside `~/.claude`, and the whole directory is the mount, so the room and the host read and write the same file; Codex rewrites `auth.json` in place. A refresh on either side is a refresh for both, as with two sessions on the host. `/login` and `codex login` work in the room, and log the host in with it. Copies of one login would strand each other: when one refreshes, the provider rotates the refresh token, as the first lup's per-repository copies found.
- **History is the operator's own.** Each runtime keys its sessions on the working directory's path, which is the same in the room, so `lup-dev launch claude --resume` finds the earlier sessions, and the host's `claude --resume` sees the room's.
- **The operator's preferences carry in.** `~/.claude/settings.json` holds the theme, model, editor mode and the like, and loads in the room as the user's settings.
- **What changes in the room:**
  - Claude Code's state file (`~/.claude.json`: onboarding, folder trust) is the room's own, written fresh into the room's home at each launch with onboarding done and the repository trusted, so concurrent starts can't race on the operator's (16 starts on one file left the first lup with `{"autoUpdates": false}`);
  - the account's connectors, which arrive with the login (claude.ai's, Codex's apps), aren't fetched in the room unless the operator's own settings or the declaration ask for them (*The settings compiled for each runtime*);
  - Codex's plugins and the operator's own MCP servers are off in the room: they're set up for the host;
  - Codex runs with `--no-daemon`, apart from the host's daemon on the same home.
- **What the agent can read:** the login and every transcript in those directories. lup isn't containing the agent, and the login is the runtime's own, readable by any session without a container.

lup's settings reach each runtime as flags and files of the launch's own, never written into the operator's directories or the repository (`adapters/claude/terminal.py`, `adapters/codex/terminal.py` in `lup`, whose docstrings give what each rests on).

- **Session settings are `Core`'s `session` part** (`SessionDefaults`, `catalog/room.py`), in neutral terms each adapter spells: the subagents' prompt cache, auto memory, idle compaction, the built-in tools removed from context, and the account's connectors. lup's own needs aren't a project's to change, since lup's mechanisms rely on them.
- **A person's own runtime settings outrank lup's defaults, and a project's declaration outranks theirs.** Lowest first: the runtime's default; lup's defaults (what `Session()` holds with no field set); the person's own runtime settings; the fields of `Session` some layer of the declaration sets, the person's own layer (`lup_project.local.py`) the last of them.
  - **The split is lup-dev's:** the resolved session says which fields a layer set (`SessionChoices.declared`; `docs/declaration.md`, *What a launch reads*), and `session_settings` (`launch/session.py`) puts those in the library's `TerminalSettings.session` and the rest in `TerminalSettings.defaults`.
  - **The library imposes `session`, and passes each of `defaults` only where the person's own settings don't set it** (`TerminalSettings.passed`): each adapter reads, once at launch, which fields their own files set (`OwnSettings.sets`, `OperatorConfig.sets`), so a change they make mid-session isn't followed. Claude Code reads `~/.claude/settings.json`, where a field counts as theirs by its key (`subagentPromptCacheTtl`, `autoMemoryEnabled`, `disableClaudeAiConnectors`) or by its variable in the file's `env`, which Claude Code applies over its environment at start and which outranks the key. Codex reads `config.toml`'s `[features]`, by the feature's key or the older key Codex still reads for it (`memory_tool`, `connectors`).

  - **What can't be imposed, said in each adapter:** Claude Code turns the connectors off when any source says so, and nothing turns them back on, so a project asking for them can't outrank a person who turned them off; `FORCE_PROMPT_CACHING_5M` in a person's `env` keeps every cache at five minutes. The removed tools are never the person's to set: permission rules merge across scopes, their own deny rules adding to lup's and none taking one back.
- **Idle compaction is off by lup's default,** where a runtime has it: a session left waiting, on the operator or on a hold, comes back to its conversation as it was, not to a summary made meanwhile. Compaction when the context fills stays the runtime's own: turned off, a full session would stop.
  - **Claude Code** (2.1.296) has `idleCompaction`: "Set to false to stop Claude Code from compacting a long conversation while the session is idle. Setting it to true does not turn idle compaction on." So `true` is passed only where something says it, so a project turning it on outranks a person's `false`, and lup's default `false` yields to a person's `true`.
  - **Codex** (0.162.1) has none: it compacts when the context passes `model_auto_compact_token_limit`, and at a turn's end past `model_post_turn_compact_threshold_percent`, off unless set. The adapter declares the gap and compiles nothing for it.
- **The account's connectors are off by lup's default** (`account_connectors`): the tools an account's claude.ai connectors or Codex's apps bring reach the operator's mail and files, so a room fetches none unless the person's own settings or the declaration turn them on.
- **The removed tools** are those that weigh in every turn and go unused: an interactive session carries 113 KB of built-in tool schemas, `Artifact` alone 55 KB. lup's default removes `Artifact`, `SendFeedback`, `Workflow`, `ScheduleWakeup` and `ReportFindings`, and the native worktree tools, `EnterWorktree` and `ExitWorktree`. The native messaging tools (`SendMessage`, `ListAgents`) stay with the native `Agent`, since a session resumes a subagent it started through them. Codex can't remove a built-in tool by name, only whole feature groups, so the removed tools are Claude Code's alone, a gap its adapter states.
- **Native subagents stay on,** since lup has no spawn of its own, and without them a session couldn't delegate at all.

### Guidance

- **One document, rendered at launch** from the selected modules' `guidance` sections, in the order the declaration resolves them, with Jinja (`render`, `launch/guidance.py`; `docs/declaration.md`, *What a launch reads*). Each section's text is read from its file in the project, or from the Python package shipping it.
  - **A section names the project's commands through the runner:** `{{ run("lup-dev check") }}` becomes the runner's command, `uv run lup-dev check` for `Uv()`, so no section spells uv. `run` reads its argument as a command line with `shlex` and spells it with `Runner.command`, the gate's, since the commands an agent runs may sync the environment as the gate's do.
  - **A module's section names where its data is mounted,** `{{ data("transcripts") }}`, and asks whether it is, `{% if mounted("transcripts") %}`; a section rendering to nothing is left out.
  - **A name a section doesn't have is refused,** naming the section (Jinja's `StrictUndefined`), rather than rendered as nothing. So are a section whose file or package isn't there, and a `run` whose argument isn't a command line.
  - **Rendered in Jinja's sandbox** (`SandboxedEnvironment`): an agent can write a section's file, since Markdown is docs and allowed, and rendering runs on the host, outside every room, where a template reaching through `run`'s attributes to Python's builtins would run the agent's code. The sandbox refuses every attribute starting with an underscore.
  - **The document opens with one line** (`OPENING`) on how its sections stand to each other and to the runtime's own prompt: it adds to the runtime's instructions and replaces none of them, and where two sections differ, the later one holds. Sections are joined by a blank line, each bringing its own heading.

It's always in context, one text with one order of precedence, rather than fragments from several files that may disagree. ### The one hook and the host service

#### In the room: a pipe

Each hook command pipes the runtime's payload, unchanged, to the launch's socket with `socat`, and prints the answer, so nothing in the room parses it. It's one command for every runtime and event (`piped`, `launch/session.py`), `sh -c` running this script, each word quoted with `shlex`:

```
socat -t 90000 - UNIX-CONNECT:/run/lup/hook.sock || { echo 'lup: this hook couldn'"'"'t reach lup'"'"'s host service on /run/lup/hook.sock, so it wasn'"'"'t judged. On the host, `lup-dev host` serves this session again.' >&2; exit 1; }
```

`-t` is how long socat waits for the answer once the payload is sent: 90,000 s, 25 hours, above a hold's day, the same as the hook's own timeout (`hooked`). Any failure, socat's own or a shell without it, ends the command with status 1 and a line on standard error. Status 2 would block the call on both runtimes, so the command never ends with it.
- **The judge stays on the host,** for practical reasons, not to guard it: the judge asks a warm engine per worktree, a pyright process, shared on the host with the operator's own gate runs, where a cold one in each room would make the first edit wait for the whole project to type-check; the copy the operator approved is the one that judges, where in the room a branch reshaping the judge would judge with its own edits; and holds wait for the operator's answer, which comes from the host.
- **What each runtime does with each end of the hook,** from Claude Code's hooks reference and Codex's source (`hooks/src/events/`, each event's `parse_completed`); each adapter's docstring holds the evidence:

  | The hook | Claude Code | Codex |
  |---|---|---|
  | The service's answer, status 0 | the decision it holds | the decision it holds |
  | Status 0, nothing printed | "no decision to report": the call goes through the normal permission flow | the run completes with no decision |
  | Status 1: the service unreachable, or socat missing | a non-blocking error: "a `<hook name> hook error` notice in the transcript with `Failed with non-blocking status code:` and the first line of your hook's stderr", and "the action goes ahead" | the run marked failed, with the entry "hook exited with code 1" (the hook's standard error isn't shown), and the call goes on |
  | The launch's judge can't answer (below) | a file tool's write is denied, telling the agent why; any other hook warns the operator in `systemMessage`, the call going on | at `PostToolUse`, the agent is told beside the call's result; any other hook warns the operator in `systemMessage`, shown as a warning entry, the call going on |

  A hook that can't be judged goes on, since the judge steers and doesn't guard (`DESIGN.md`, *Who it's for*); what goes on is said where the runtime shows it, rather than read as no decision. Only a file tool's write on Claude Code is refused, as when judging itself fails: let through unjudged, it would land unseen.
- **The events** are each adapter's `hooks`: Claude Code's `SessionStart`, `PreToolUse` on every call, and `Stop` and `SubagentStop`, so the host service hears each conversation's start, calls and turn's ends, as the inbox needs (`docs/host-tools.md`, *How an agent is told*); Codex's `SessionStart`, `PreToolUse` and `PostToolUse`, since Codex is judged after each call, and `Stop` and `SubagentStop`.
  - **Which of them the judge reads** is the adapter's word (`heard`): on Claude Code, `SessionStart` and the file tools' writes (`WRITING`), judged before they land; on Codex, every one. The service answers the rest itself, without starting the judge's process: what the runtime takes as no decision, never a block, with a call to lup's tools stamped with its caller. Such a hook costs 4.5 ms end to end, against 665 ms for one the judge's process answers (`docs/field-notes.md`, *A hook the judge doesn't read*).
  - **Codex's turn's end is hooked** because Codex sends no `PostToolUse` for a call that didn't succeed (a patch that failed to apply, a call interrupted), so the call stays counted and its session's checkpoints wait on it; the turn's end clears what the conversation left, and holds the turn on what it left unclean, once per finding (`docs/judging-writes.md`, *The turn's end*). Claude Code's room has no checkpoint, so its judge reads no turn's end, and the service answers its turn's ends itself.
- **A protected path's ask on Claude Code** is the runtime's own prompt: a hook's `ask` prompts under `bypassPermissions` too (`docs/field-notes.md`, *Launch, live*). Where a runtime can't ask before a call (`Runtime.asks_before`), as on Codex, the change is held until it's answered with `lup-dev holds` (`docs/judging-writes.md`, *Asking the operator*).

#### On the host: the service

The host service is a program lup runs on the operator's machine, outside every room, which rooms call for what only the host can do (`host/service.py`): the judge for each hook; lup's inbox and its tools, served on each launch's `mcp.sock` (`docs/host-tools.md`, *The inbox*); GitHub with the operator's `gh` and its login (`docs/host-tools.md`, *GitHub through `gh`*); pushes and fetches with the operator's credentials (*The room's git*); the clipboard (`docs/host-tools.md`, *The clipboard*); and the dashboard, which it runs as a child for as long as it serves (`docs/dashboard.md`, *Running*).
- **One per user,** the installed `lup-dev`'s, started detached by the first client that finds none answering (`Detached`, `python -m lup_dev.cli host` with the interpreter running the client), and running until it's stopped, as the engine is found or started on demand. What it prints is appended to `service.log` in lup's state, which the client names when the service doesn't answer within 10 seconds. It holds a lock for its whole life, which the OS frees, so a second `lup-dev host` refuses, naming the socket; a control socket left by a service that died is replaced. Launches starting at once may each start one; all but the first refuse, and each client waits until the socket answers. Its waits go through `lup_dev.clock`, so its tests drive time.
- **Each launch judged by its repository's own copy** (*Trust on launch*): a registration names the copy's command, and each hook its judge reads is answered by running it, `<copy>/bin/lup-dev hook <runtime>`, a process of its own for each hook, the payload on its input and its answer what it prints (`judged`, the `judge` seam its tests stub). A registration whose copy isn't there is refused, saying that approving the repository's host zone installs it.
- **Each launch's modules** run in a process of their own, of the repository's approved copy, started when the launch opens and stopped when it ends (`host/workers.py`, `worker.py`): their tools, their answers to the room's requests, and their hooks at lup's moments (`docs/declaration.md`, *What a module is*).
- **Each hook read through the `Courier`** (`host/courier.py`; `docs/host-tools.md`, *Who's calling*), which `cli.py` builds from the adapters, as it builds the `Answerer`. Its `heard` says the hook's event, the runtime's ids for the session and the subagent, the call and its tool, and whether the judge reads it. The service mints lup's own id for each conversation the first time a hook names it (`Conversations`). A hook the judge doesn't read the service answers itself, without starting the judge. Every answer goes out through the `Courier`'s `told`, which adds what the conversation is told and rewrites a call to lup's tools to carry `caller` and `call`. What it's told is the `Post`'s, the inbox's (`inbox/delivery.py`), asked at every hook with what room the judge's answer leaves (`Heard.fits`), and put back as waiting where the hook was gone before its answer was written. A payload the `Courier` can't read goes to the judge as it is; an answer of the judge's it can't add to goes out as the judge gave it; either is said.
- **Sockets per launch,** in a directory of its own, mode 0700, mounted into that launch's room at `/run/lup`: `hook.sock` for the hook; `mcp.sock`, lup's tools for the launch's session; `request.sock`, one typed request per connection from the room's programs (`docs/host-tools.md`, *The server*, *The room's requests*); and Claude Code's `messages.sock`, the session's own. The service knows which launch speaks by the socket it hears it on, and the sockets go with the launch. Seen through `SO_PEERCRED`, a room's process has the operator's uid (keep-id), so the uid can't tell a room from the operator; the socket can. One socket for every room would have each request name its launch, which the room would then say of itself; HTTP on localhost would be reachable by every process on the machine, and couldn't tell rooms apart.
- **Its control is a socket on the host only,** taking typed requests: one JSON request per connection, a pydantic model discriminated by `kind`, and one JSON reply (`host/protocol.py`). The service's own kinds are a launch's registration, its renaming and its end, listing the launches served, and stopping the service. Modules register the handlers for their kinds: the inbox's, behind `lup-dev inbox` (`inbox/protocol.py`), and the dashboard's.
  - A handler (`Handler`) names the model of its requests and answers each on the event loop; `Route.to(handler)` routes its kind there, read from the model, so the kind is spelled once, and a kind is added without editing the service or the protocol. Two handlers for one kind, on the control socket and the room's alike, and two modules serving one tool, are refused when the service is built.
  - Any control request can also be watched, on the service's watch socket beside the control socket: answered at once, then again each time its reply changes (`docs/host-tools.md`, *Watching*).
  - What the service can't carry out is replied as `Refused`, with why: a request that doesn't parse, a kind no handler answers, a launch registered twice or running a runtime lup doesn't know, ending a launch that isn't served, and a handler's failure, which is said with its traceback.
- **Every program it runs for a launch is spawned through asyncio and awaited on the event loop** (`judged`, with `Asked.directory` where the program runs): each hook's judge, each `gh` and each git for a room. The loop goes on serving meanwhile, and a hold holds its judge's process, nothing of the service's, while it waits. A wait cancelled, as when the service stops, kills its program. It runs a program other than with `sh`, with an `ignore` saying why: `sh` forks, running Python in the child before the program starts, which can deadlock a process with threads (#23), and waiting on it would hold a thread per program for as long as it runs.
- **Where the judge can't answer,** its command missing, or ending with any status but 0 (`lup-dev hook` answers judging's own failures in the hook's terms, so it fails only where it can't read the payload, or can't start), the service answers in the runtime's own terms through the `Answerer`, which `cli.py` builds from the adapters (each adapter's `unanswered`; what each runtime then does is in the table above). What the judge wrote to its standard error is said in full in the service's output, and the answer points there. socat prints nothing and ends with status 0, which the runtime would take as no decision, only where answering failed even so, which the service says with its traceback.
- **A launch outlives a restart of the service.** Each launch is recorded beside its socket directory, under lup's runtime directory, and a service started after one stopped serves every recorded launch again, binding its sockets in the directory the room mounted, and brings the room's programs up to its copy. Its hook goes on at the next call; lup's tools come back through the bridge (`docs/host-tools.md`, *The server*). A stop closes the sockets and keeps the records, without waiting for the answers in flight: their judges are killed, and their hooks hear nothing. A launch's end removes its record and its directory.
- **A launch whose launcher died is swept by the next launch.** Its launcher holds the launch's own lock (`Layout.launch(id).lock`, under lup's state) from before it registers until its registration ends, a lock the OS frees when the launcher dies. Before registering, a launch lists the launches served (`ListLaunches`) and ends each whose lock it can take and whose container podman no longer has (`Podman.exists`), removing its directory, and says so (`swept`, `cli.py`). Both, since either alone ends a live launch: a container is made moments after its registration, so the container alone would end a launch still starting; and a launcher killed while its room runs on (a terminal closed under it) leaves a session still calling its hook.

### Modules and public API

#### The library

One declaration compiles to SDK options for an ask and to a command line for a terminal, and a room runs that terminal behind a wall (`DESIGN.md`, *Defaults*: "Every agent runs in a container"), so the terminal compile and the room are the library's:

```python
from lup import Claude
from lup.rooms import Container, Image, Mount, Room

room = Room(
    agent=Claude(model="opus"),
    container=Container(
        image=Image(definition=CONTAINERFILE, project=str(repository)),
        mounts=[Mount(source=repository), Mount(source=hooks, read_only=True)],
        network="host",
    ),
)
status = room.launch(arguments=["--resume"], settings=settings)   # a terminal; returns the CLI's exit status
```

## Where it's going

- **Proposals and holds** replace the per-call checkpoint and reshape the hooks; a held call in Codex's code mode, which the agent sees pending in a cell and can end its turn past, is answered there.
- **The dependency guard.**
- **Rooms from code:** a `Room` that's an `Agent`, with `ask` and `spawn` in a container (`docs/library.md`, *Where it's going*); the SDK on the host has driven the CLI in a container over stdio, the CLI reaching an in-process tool on the host.
- **lup's spawn,** with the native `Agent` and Codex's subagent tools denied by default once it exists.
- **Skills** compiled from the modules' `skills` part into the launch's directory, on both runtimes.
- **Guidance checked** against the commands the project serves, once `Commands` say what those are (`docs/declaration.md`, *The command line*); and `lup launch` in place of `lup-dev launch`.
- **The removed tools** set from what a live room's `/context` shows weighs and goes unused (`CronCreate`, `RemoteTrigger`, `PushNotification`, `NotebookEdit` and `DesignSync` are the candidates).
- **The CLIs' signatures checked,** beside their checksums: a GPG signature on Claude Code's manifest, a Sigstore bundle for each Codex package (#63).
- **Codex's `additionalContextLimit`** on `PostToolUse`, raised in the room so a report past 2,500 tokens arrives whole; the library's `Hook` has no field for it.
- **Devices and a browser in the room,** and Codex's clipboard through a private display bridged to the host, each with the first lup's evidence in `docs/field-notes.md`; budgets and `accounts`.
