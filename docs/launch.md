# Launch: a session in a room

`lup-dev launch claude` (or `codex`) starts the runtime's latest CLI in a podman container holding the repository, the room, on a home of the rooms' own, logged in with an account. The session's settings and guidance are compiled from the project's declaration at the commit the operator approved (`docs/trust.md`), and passed outside the repository. One hook carries each of the session's events to lup's host service on the operator's machine (`docs/host.md`), which judges its writes and serves lup's tools.

## The command

```
lup-dev launch claude|codex [--name NAME] [--profile PROFILE] [--account ACCOUNT] [--mount DIR|MODULE]… [--mount-rw DIR]… [<the runtime's own arguments>] [-- <the runtime's own arguments>]
lup-dev mount [--rw] [--launch LAUNCH] DIR|MODULE
lup-dev rename LAUNCH NAME
lup-dev sessions [--all]
lup-dev account list
lup-dev account logout ACCOUNT [RUNTIME]
lup-dev account migrate [--move] [--shared]
```

- **A launch starts in the worktree it's run from,** and passes every argument it doesn't know to the CLI, so `--resume`, `-p` and `--model` reach it, and every one after `--`, so the runtime's own flag of a name lup takes reaches it there: `lup-dev launch codex -- --profile fast` hands Codex its own profile. It exits with the CLI's status, and refuses to run inside an agent's session.
- **`--profile`** chooses the profile the launch runs on, and **`--account`** the account its runtime logs in with, in place of the profile's (*Accounts and profiles*).
- **`--mount`** lends a directory to this launch alone, read-only, at its own path, and `--mount-rw` writable; the guidance lists each under *Lent to this launch*. `--mount transcripts` lends a module's data instead. A repository every session should read belongs in the person's own layer (*Related repositories*).
- **`lup-dev mount`** lends a directory to a room that's already running, under its `/lent`, and tells the session where through the inbox.
- **`rename` and `sessions`** name and list the launches (*Names*).
- **`account list` and `account logout`** list the accounts and log one out (*Accounts and profiles*); **`account migrate`** moves the repository's sessions from the operator's own directories into its rooms' home (*Moving over*).

**What a launch does,** in order (`launched`, `cli.py`):
1. checks the code the host runs against the copy the operator approved, and asks where it changed (`docs/trust.md`);
2. reads the declaration at the approved commit, exported from git's objects, so neither a branch nor an edit made in a room changes the room a launch runs in, and chooses its profile and account from the person's profiles approved with it, refusing a name that's neither (*Accounts and profiles*);
3. checks the host's requirements: podman and git, and `gh`, `notify-send`, a clipboard program and `qrencode`, each optional and said where missing; and names the repository on GitHub;
4. starts the host service where none answers, and fetches the runtime's latest CLI where a newer one is out (*The CLIs*);
5. finds the related repositories and the operator's editor, builds the list of values never published (`docs/private.md`), and makes the room, refusing what can't be mounted safely before an image build that may take minutes;
6. builds the room's image where it's missing, and compiles the session's settings on its home of the rooms' own and renders its guidance (*A home of the rooms' own*);
7. looks for the files with a secret's name whose content their repository's git objects don't hold, in the repository's tree and each related repository mounted, and names each it hides (*Files with a secret's name*); says a home not made yet, an account with no login for the runtime, and what was left out of the configuration copied in, where that changed;
8. removes the environments a crashed launch left, registers with the host service, which opens the launch's sockets, makes the account's login where there's none, writes the settings and the configuration's copies into the launch's own directory under lup's state and what the home's mounts land on, and runs the container in the foreground, the CLI behind the start making the worktree's environment (*The project's environment, the room's own*);
9. when the CLI exits, carries back what the session saved of its preferences into the profile's configuration, says the first change it saw of the account's login, ends the registration and removes the launch's directory, its room's home, its environments, and each `.venv` that appeared in a worktree while it ran, and names each file with a secret's name that appeared or changed in the repository's tree meanwhile, removing none.

A container starts in under a second; an image already built and a CLI already current cost nothing more.

## Names

A launch has an id, which never changes and under which everything of it is filed, and a name, for people and commands (`host/names.py`):
- **At launch** it's `--name` exactly, refused where another running launch holds it; otherwise the worktree's branch in a name's shape (`feat/x` is `feat-x`), numbered while taken.
- **It changes** with the session's `rename` tool or `lup-dev rename`. Nothing is filed by name, so a rename moves nothing, and a name is looked up each time it's used: the first lup kept paths by name, and its sessions met an earlier session's stale socket.
- **A subagent is named under its conversation** (`dev/explore-auth`), so its rename can't take its session's name. It keeps the name its parent gave at the spawn, where one did; otherwise it's asked to name itself.
- **The container is `lup-<repository>-<name>`,** renamed with the launch, so `podman ps` says which session each runs.
- **The runtime's own title follows** where the runtime has a way. Claude Code's, the one `/rename` sets, is given the launch's name through `sessionTitle` at each start and at each prompt, wherever the title the hook carries differs, so a rename through lup reaches it at the session's next prompt (`lup_dev/adapters/claude.py`). Codex's hooks neither carry a thread's name nor set one, at a start or a prompt, a gap its adapter declares with its evidence (`lup_dev/adapters/codex.py`).
- **The operator's own rename in the runtime is taken** at the session's next prompt or start, in a name's shape (`Naming Review` is `naming-review`), and the agent is told. One that can't be a name, or that another launch holds, is said in the service's log, and the runtime is given lup's name back.
- **lup keeps each session's title as it last left it in the runtime:** the one it gave, once the answer giving it was written, else the one it found there. Only a title other than that one is the operator's: a resume carries the title lup gave at an earlier start, which taken as theirs would undo a rename through lup since, and an answer that never reached its hook leaves the runtime with the title found before.
- **A resumed conversation takes its name back,** where no running launch holds it.

## Accounts and profiles

- **An account** is a login per runtime, kept by its name at `~/.local/share/lup/accounts/<name>/`, a directory per runtime holding the file that runtime's sign-in writes (`AccountLayout`, `layout.py`). It's kept by the account's name, never a project's, so every room on an account shares one login, and a sign-in in one is every room's.
- **A profile** is the whole setting a room runs with, its account among it, declared by the person in `~/.config/lup/profiles.py` (`docs/declaration.md`, *Profiles*).
- **A launch's profile** is `--profile`'s, else the one the person's layer chooses for the repository, else `default`; its runtime's account is `--account`'s, else the profile's for that runtime. A launch runs the profiles approved with the repository's zone (`docs/trust.md`, *Trusted by its content*), and says which profile and account it runs on where either isn't `default`.
- **`lup-dev account list`** lists every account, `default` first, with the runtimes it holds a login for: a login file that isn't empty.
- **`lup-dev account logout`** logs an account out of one runtime, or of every one, by emptying its login file in place. A room's own logout can't remove a login mounted as a single file (`docs/field-notes.md`, *Rooms*), and removing it on the host would leave such a mount holding it. It forgets the login on this machine alone: it isn't revoked with the provider. Like a launch, it refuses inside an agent's session.
- **`lup-dev account migrate`** moves the repository's sessions from before rooms had homes of their own into its rooms' home, a dry run without `--move`, and checks what a host session acts on that rooms could have written (*Moving over*). Like a launch, it refuses inside an agent's session.
- **A launch runs on them:** its runtime keeps its history and state in the home its profile chooses, logs in with its account's file, and reads the profile's configuration over the operator's (*A home of the rooms' own*). An account with no login for the runtime gets an empty file the runtime's own sign-in fills, which the launch says first.

## The room

**The image** (`launch/images.py`) is Arch Linux pinned to one day's snapshot of its archive (`RoomBase`, `catalog/room.py`), with the packages the selected modules ask for, each with its reason (`Packages`), so a build is reproducible and every package is at least as old as the pin. `Core`'s default is the standard machine (`StandardMachine`): the shell's tools, git, jq, ripgrep and fd, `man`, `time` and `tmux`, `nano`, `gcc` for a Python package built from source, and what lup and the runtimes need. Every agent meets the same machine, without the operator's own shell setup, which aliases `cp`, `grep` and `ls` on this host. Where the room has `man-db`, every package's English man pages are kept, though Arch's base extracts none: a `NoExtract` exception appended to its `pacman.conf` keeps them for what the build installs, and the base's own packages, which `--needed` skips, have only their man pages extracted from their packages, about 11 MiB where reinstalling them would add 0.4 GB (`docs/field-notes.md`, *What agents reached for in rooms*). `mandb` then indexes them, since no pacman hook does, for `apropos` and `whatis`. Info pages and `/usr/share/doc` stay out. **The operator's editor,** the one `$VISUAL` names on the host, else `$EDITOR`, which Ctrl+G opens, joins the image at launch where lup knows its package (`Editors`): `nvim` brings `neovim`, `emacs` `emacs-nox`, `hx` `helix`, which Arch installs as `helix`, so the launch links `hx` to it among the room's commands. Only that one is installed, where all five took about 818 MiB in every room; `xxd` comes with `vim` alone. An editor lup doesn't know brings nothing, and the launch says so: the person's own layer adds its package to `Core` (`docs/declaration.md`, *A person's own layer*). The image is tagged by a digest of its definition and project, and built when the tag is missing; after a build, the project's older images that no container uses are removed. The first lup left 46 tags of 4.5 to 5.5 GB each, kept alive by readable names.

**pyright's source** (`PyrightSource`, `lup_dev/pyright_source.py`) is in the image of a repository whose gate builds lup's engine from it, as lup's own does (`LupDevelopment`). A second step clones pyright at the release the launch's worktree's `uv.lock` pins and installs its dependencies with pnpm, from pyright's own lockfile, into `/opt/lup/pyright/<release>`: inside the image build's own container, never on the host, and root's, so the room reads it and can't write it. pnpm runs in a home of the step's own, holding the package age as a room's pnpm settings hold it (*The package age gate*), and that home goes in the same step with what pnpm downloaded, so the layer holds the source alone: 441 MB, the step's commands taking about 8 s (`docs/field-notes.md`, *pyright's source in the room's image*). A step of its own after the packages', so a change of release builds that layer alone, and a branch changing the release gets its image at its launch. The engine's build in the room reads that copy. A worktree pinning another release, or a merge bringing one, has it fetched once into the project's rooms' own directory (`RoomsLayout.pyright`), which the room's `LUP_ROOM_PYRIGHT` names, by the same recipe under the room's own pnpm settings. Never into the host's cache, which no room mounts: what a room wrote there would be bundled into the host's engine at the next approval. The host's builds, trust on launch's and the operator's own, read the host's cache alone.

**The mounts** (`maintaining_room`, `launch/room.py`). The repository, the environment and the operator's own directories are each at their host path, since a linked worktree's `.git` file and the environment's links hold absolute paths, and the runtimes key their history on the working directory:

| What | Mode | Why |
|---|---|---|
| The repository: its git directory and every worktree, as one tree | read-write | the agent's work. One mount, since a mount point can't be removed from inside: with each worktree its own mount, as in the first lup, an agent couldn't remove one ("EBUSY") |
| The git directory's `config` and `hooks/` | read-only | a hook or a `core.fsmonitor` written there would run at the operator's next git command |
| The git directory itself, where it isn't the tree's root (a clone's `.git`) | read-write | under the tree's mount alone, `mv .git .git-real` succeeded and a `.git` of the room's own then stood where the host's git reads; mounted on its own, the move fails ("Device or resource busy", podman 6.1.3) |
| What the runner needs: uv's interpreters | as it says | *The project's environment, the room's own* |
| The project's rooms' own directory: their uv cache, each launch's environments, and pyright's source at a release the image doesn't carry | read-write | *The project's environment, the room's own*; *pyright's source* |
| Over each worktree's `.venv` there as the room starts, an empty directory of the launch's | read-only | the host's environment, hidden from the room: *The project's environment, the room's own* |
| Over each file with a secret's name whose content its repository's git objects don't hold, in the repository's tree and each related repository, an empty file of the launch's; over a directory lup couldn't look in, its empty directory | read-only | *Files with a secret's name* |
| The runtime's own directory for the launch, `<launch>/runtime-home`: the configuration copied in, the settings, the state, everything it writes there | read-write | gone with the launch, so no room leaves another anything to load: *A home of the rooms' own* |
| Inside it, the account's login, alone | read-write | a sign-in in one room is every room's on the account |
| The history the rooms share, the project's home or the one every project shares, which the runtime's directory links into | read-write | a conversation resumes in any room on it |
| The CLI, from lup's cache | read-only | *The CLIs* |
| The launch's directory on Claude Code; on Codex, its requirements file at `/etc/codex/requirements.toml` and the bridge; on both, its `bin/` and `gitconfig` | read-only | lup's settings, guidance and MCP bridge for this launch, and the room's programs |
| The package managers' user-level settings, from the launch's `home/`, at their place in the home | read-only | *The package age gate* |
| The launch's sockets, at `/run/lup` | read-write | the host service (`docs/host.md`). The directory rather than each socket, since a socket mounted as a file pins the old one when the service restarts |
| The data of each module the room mounts (past sessions, by default) | read-only, unless the module says | `docs/declaration.md`, *What a module is* |
| The editor's configuration, `/etc/localtime` | read-only | Ctrl+G opens the operator's editor as they know it, and the clock reads in their zone |
| Each related repository, whole | read-only | *Related repositories* |
| What's lent: `--mount`, `--mount-rw`, `/lent` | as lent | *The command* |
| The launch's own home, `<launch>.home` beside its directory under lup's state, at the home | read-write | podman would otherwise set `HOME` to the working directory, and the CLIs would write their state into the worktree. On disk, where a tmpfs would hold what the room writes in the host's memory. Each directory and file a mount inside the home lands on is made there first, the operator's, since podman makes them root's, and nothing inside another mount (`Invocation.landings`, `packages/lup/src/lup/rooms/engine.py`). Removed as the launch ends, or by the sweep after one that crashed, its read-only directories made writable first, as Go's module cache is, following no link |

Not mounted: the operator's own `~/.claude` and `~/.codex`, the SSH agent, `gh`'s login, `~/.gitconfig` (it holds the operator's aliases and an LFS filter the image lacks, so the git identity is passed as variables), the rest of lup's cache, pyright's source the host builds from among it (*pyright's source*), and the rest of the home.

**The room's git** (`room_git`): git's configuration is the room's own (`GIT_CONFIG_GLOBAL`), rewriting each remote to lup's helper, so `git push` and `git fetch` go through the host with the operator's credentials (`docs/credentials.md`, *git through a remote helper*). A repository whose `config` sets `extensions.worktreeConfig`, or includes a file inside the room's mounts, is refused at launch: either would have the host's git read what the room wrote.

**The package age gate** (`RoomPackageAge`, `launch/room.py`). Nothing published within `Core`'s `package_age`, three days unless the project says, installs through a package manager the room's image holds: a release published with stolen credentials is usually found and pulled within hours. Each package manager lup knows is spelled in its own file (`lup_dev/declaration/package_managers/`), and the launch asks each one the image holds for its user-level settings, writes them into its own directory and mounts them read-only where the package manager reads them in the room's home. User-level settings rather than variables: npm and uv each rank a variable above a project's own setting and a user-level one below it, so a project with its own, stricter or laxer, keeps it (`docs/field-notes.md`, *User-level package age settings*).
- **npm** (`npm.py`) gets `~/.npmrc` holding `min-release-age`, in days, a fraction among them. It doesn't touch a lock: `npm ci` installs what its lock pins, however new.
- **pnpm** (`pnpm.py`) gets `~/.config/pnpm/config.yaml` holding `minimumReleaseAge`, in minutes, rounded up. pnpm 11 reads no age from `~/.npmrc`, and checks even a frozen lockfile's entries against its own, so it holds what a lock pins too; a project's own `pnpm-workspace.yaml` outranks it. The image's step installing pyright's source writes the same settings into its own home (*pyright's source*).
- **uv** (`uv.py`, beside `Uv`, the runner) gets `~/.config/uv/uv.toml` holding `exclude-newer`, as an ISO 8601 duration, only where the project sets its own `exclude-newer`, in its root's `uv.toml`, else its `pyproject.toml`'s `[tool.uv]`, as uv reads them. Without one, a user-level one changes what its `uv.lock` was resolved with: the room's first `uv run` relocked it, downgrading what was newer than the age, and the host's next `uv run` relocked it again. With one, the user-level one leaves its lock alone and is what `uvx` and `uv tool` read, since they read no project's settings. Where the project sets none, the launch says so, naming the line to add to `[tool.uv]`, which gates the project's own `uv run` too. A project nested in the repository with a `[tool.uv]` of its own and no `exclude-newer` still relocks under it; a workspace member doesn't, uv reading a workspace's settings from its root.

**The user, the process, the network** (`Podman`, `packages/lup/src/lup/rooms/engine.py`):
- the operator's uid inside (`--userns=keep-id`), so what the agent writes is theirs on the host;
- `--init`, since without it the first lup piled up 4,045 zombies against its pids limit;
- every capability dropped, and `no-new-privileges`;
- podman's own pids limit, which counts threads: 2048 on podman 6.1.3 (measured in a room), where the first lup's 4,096 broke a test run, so lup means to lift it (#162);
- the host's network, shared both ways, so a server the agent starts opens in the operator's browser, and the sign-in's callback reaches the CLI. The cost is that code in the room reaches what listens on the host's loopback: the walls are there so nothing explodes, not to contain an agent (`DESIGN.md`, *Who it's for*);
- a terminal with no detach keys, so Ctrl+P reaches the program, and the operator's `TERM`, `LANG`, `TZ` and `EDITOR`, without which the first lup's sessions lost their colour, locale, time zone and Ctrl+G.

**The project's environment, the room's own.** Each worktree's environment in a room is its launch's own, made fresh as the room starts and outside the repository, and the host's, the worktree's `.venv`, is hidden from it: the operator's own `uv run` runs `.venv`, and the copies of lup the host runs share files with uv's cache, so neither is the room's to write. The runner says what the room needs (`Runner.room()`; `docs/declaration.md`, *The runner*).
- **Where it is.** The project's rooms have a directory of their own beside lup's other data, `~/.local/share/lup/rooms/<a digest of the git directory>/` (`RoomsLayout`), mounted read-write at its host path: their uv cache, and each launch's environments, one per worktree, at `environments/<launch>/<the worktree's name>-<a digest of its path>` (`lup_dev/environments.py`). One mount, so an environment's files are links into the cache: lup's takes 7 MB of its own where a copy took 717 MB, since no link crosses two mounts (`docs/field-notes.md`, *The room's own environments*). One per project, so one project's room can't write what another's installs from.
- **How uv finds it.** uv takes a project's environment from `UV_PROJECT_ENVIRONMENT`, and has no setting naming one per project. So the room's `uv` is lup's, first on its `PATH` among the launch's commands: it asks git for the worktree it runs in, as the judge does, and in one of the repository's sets `UV_PROJECT_ENVIRONMENT` to that worktree's environment, then runs uv; elsewhere, a scratch project in `/tmp`, it sets none. A worktree made during the launch, by `git worktree add` or by lup's hooks, gets its own at its first `uv`, the gate's worktree at a commit among them, which takes it along when it goes. `uv --directory` or `--project` naming another worktree still gets the working directory's: run it from there. `UV_CACHE_DIR` names the rooms' cache, so a project's own `cache-dir` doesn't apply in a room.
- **Made as the session starts.** The CLI runs behind `lup-environment`, which starts `uv sync --frozen` for the launch's worktree in the background, through lup's `uv`, where the project has a `uv.lock`, so the judge reads its third-party types from the session's first write. The CLI waits for nothing: the start hands over in 0.03 s, and lup's environment is made in 0.15 s from a warm cache, though a project's first launch downloads into an empty one (16 s for lup). Its output is kept beside the environment, and where it fails, the next `uv` in that worktree says so, once.
- **What the judge reads.** The launch records its environments (`Register.environments`), each of its hooks carries them, and the engine reads a worktree's where the room's `uv` puts it, placed by the same function (`docs/judging-writes.md`, *The engine: one typed tree*): as it stands, an environment half made reading as the packages already there. The engine is one per worktree, so two launches working in one worktree each replace the engine the other's hook started, loading the project again.
- **The host's `.venv`, hidden.** Each worktree's `.venv` there as the room starts has an empty directory of the launch's mounted over it read-only, as `config` and `hooks/` are over the tree, so the room neither reads nor writes it: it lists nothing, writing into it fails ("Read-only file system"), and removing or moving it fails ("Device or resource busy"). So `git worktree remove` there fails partway, having removed part of the worktree: `land`'s cleanup asks the room what it mounts first (`findmnt`), and leaves such a worktree whole, saying its `.venv` is hidden from the room, so it's removed on the host. A room moving the worktree itself moves the mount with it, and a `.venv` it then makes where it was is the host's to run: so at the launch's end each `.venv` in the repository's worktrees that wasn't there as it started, told apart by its device and inode, is removed, never following a link (`docs/field-notes.md`, *Paths hidden from a room*). One the operator made meanwhile goes too, to be made again. Paths hidden from the room are a general mechanism (`launch/hidden.py`), `.venv` its first, the files with a secret's name its second (*Files with a secret's name*).
- **Gone with the launch.** Its environments are removed as it ends, so what a package wrote into one doesn't outlive it; a launch that crashed leaves them for the next launch, or the host service's sweep, to remove. The environments' interpreter is the one uv's store holds for the project's Python, its `.python-version` else its `requires-python`, asked of uv from outside any project with no settings file read (`uv --no-config python find --managed-python --system --no-project`), a request that isn't a version or a version specifier refused before uv is asked, since uv runs an interpreter named by its path to query it. The store is mounted read-only at its host path, with `UV_PYTHON_DOWNLOADS=never`; where it holds none, the launch says how to install one (`uv python install`). Nothing of the worktree's environment is read or run on the host for the room (`docs/field-notes.md`, *The judge reads the environment as files*).

**Files with a secret's name** (`launch/secrets.py`). A file in the worktree holding a secret, an `.env`, a key, a credentials file, would be readable by any code the room runs, a malicious package among it, where a secret is meant to reach a room's code through a module's host helper that adds the key, so the room can use it and never carry it off (`DESIGN.md`, *Modules*). The declaration's `secret` role names such files by the names tools give them (`CorePaths.secret`; `docs/declaration.md`, *The kinds*): dotenv's `.env*` and direnv's `.envrc`, Wrangler's `.dev.vars`, keys, certificates and key stores, OpenSSH's key files, credentials in JSON, `.netrc`, `.git-credentials` and `.pypirc`, Terraform's variables and state, and Streamlit's secrets.
- **Which are hidden.** Each whose exact content the object store of the repository it sits in doesn't hold: an ignored one, an untracked one, or one changed to content git never held. Each is hashed as git hashes a blob, and git, pinned to the repository's common directory, is asked whether the store holds that id (`Git.blobs`), never fetching what a partial clone left out, which would send the id to its remote. The room mounts that store and can read every object in it, so hiding a file whose content is there protects nothing: a tracked `.env.example` as committed stays in view, as does a copy of it under another name, or a file staged once, even unstaged since, until git prunes its object. A real value added locally is content git doesn't hold, and a room can't put an object with a secret's content in the store without knowing that content. A file over 1 MiB is hidden unread, whatever it holds, and its line in the launch's list says it was too large to check (`Search.largest`): the files these names give are small, the largest of 86 measured in view 6 KB, and a room could plant a sparse one of a terabyte for the next launch to hash. Which worktree holds a file doesn't matter, so a repository moved on disk, whose worktrees git still lists where they were, is checked as any other, as is a file beside a bare repository's own files. The store rather than a worktree's commit or what git ignores: git's record of where each worktree is goes stale when a repository moves, and a room writes the `.gitignore` files, `info/exclude` and the index git decides what it ignores from, so `git add -f .env` in one launch would leave the next launch's `.env` in view.
- **A store that reads objects from elsewhere** has every file in its repository hidden. Through `objects/info/alternates`, or a link under `objects/`, both of which a room writes, git would answer from another repository's store, which the room doesn't mount, and a file whose content only that store holds would show (`docs/field-notes.md`, *Files with a secret's name*). It's the look a push or fetch makes first (`docs/credentials.md`, *Running git on the host*), with the same gap: a room running on the repository could add alternates or a link between the look and git's answer.
- **Patterns and nested repositories.** A pattern is matched from the root of the worktree holding the file: the nearest directory holding a `.git` file or directory, else the tree, wherever the worktree has moved. In a repository nested in the tree's own, a git directory other than the tree's (a `HEAD` file, `objects/` and `refs/`) and, where it's a `.git`, the clone holding it, such as a clone or a bare copy under a worktree's `tmp/`, every file with a secret's name is hidden; a `.git` directory that isn't one, which git wouldn't read either, nests nothing. Checking a nested repository's files would mean host git reading a git directory the room wrote whole, its `config` among it (#208's class). A linked worktree of another repository can't be told from one of the tree's own once moved, since its `.git` file names where it was, so its files are checked against the tree's store, which the room reads anyway. git runs pinned to each repository's common directory, never through a worktree's `.git` file, which a room writes.
- **Where.** The whole of what the room mounts for the project, its git directory with every worktree, and each related repository mounted, whole; not what's lent (`--mount`, `--mount-rw`, `/lent`), which the operator lends knowing what's in it.
- **Not looked in:** what package managers install, `node_modules/`, `site-packages/` and `dist-packages/`, whose keys and certificates are packages' own (each of 95 `cacert.pem` measured in environments was `certifi`'s), and the hidden `.venv`. By name rather than by a `pyvenv.cfg` in the directory, which a room could plant beside a secret to have the next launch pass over it. A directory lup can't list is hidden whole, and said, since a room could `chmod` one to the same end.
- **How.** As `.venv` is: the launch's empty file mounted read-only at its path, so the room reads it as empty, and writing, removing or moving it fails. `land`'s cleanup leaves a worktree holding one whole, as it does one with a `.venv`. A link isn't hidden, since podman would follow it.
- **When, and what's said.** After the image and the settings, just before the container starts, so a room already running on the repository has the least time to move a secret where the search didn't look; one moved between the search and the start is the gap left. The launch names each file it hides in one list.
- **What a room writes at a secret's path** is left: a room's own `.env` exposes nothing of the host's, and removing what appeared, as the `.venv` rule does, could remove one the operator wrote on the host meanwhile. The host's tools read such a file, a dev server or docker compose, so as the launch ends each file with a secret's name that appeared or changed in the repository's tree is named, for the operator to look at first. A write to one through a file tool asks, as a protected path's does (`docs/judging-writes.md`, *What each change gets*). The room's own `.env` is hidden from the next launch in turn, unless the room put its content in the store, by staging or committing it; one it did is left out of the list as the launch ends too.
- **Its cost** grows with the files in the trees searched, the related repositories' above all: lup's own tree, 206k files, takes 0.5 s; on a machine relating twelve repositories, 1.86M files took 4.6 s more, 3.1 s of it one repository's 1.4M. Asking the stores adds 0.16 s over those twelve, most of it the look for alternates and links (`docs/field-notes.md`, *Files with a secret's name*).
- **Not covered:** a secret in a file named otherwise, such as a token in `.mcp.json` or in a remote's URL in git's `config`, and one behind a link.

**The CLIs** (`launch/clis.py`). Each launch asks the vendor's own release channel for the latest version, downloads it into lup's cache with its published checksum checked, and mounts it read-only, so the latest runs whatever the host has installed; offline, the version cached runs, and the launch says so. Never baked into the image: the first lup's CLI layer, 1 GB, was rebuilt most days. Each channel is spelled in its runtime's adapter (`Channel`). The vendors' signatures aren't checked yet (#63). The cache keeps each runtime's current version and the one before, for a session still running.

**A home of the rooms' own** (`lup.sessions.terminal.RuntimeHome`; `launch/homes.py`; each runtime's `terminal.py` in `lup`). A room never mounts the operator's own `~/.claude` or `~/.codex`: through that mount a package in a room could read the login and every project's transcripts, and write what a session on the host acts on, hooks, skills, plugins and the shell snapshots a running Claude Code session runs before each command.
- **The runtime's directory is the launch's own.** Its variable (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`) names `<launch>/runtime-home`, made fresh, mounted read-write at its path, and removed with the launch. Everything the runtime reads there as configuration or state is the launch's: what's copied in from the layers, the settings, the state file, and whatever else it finds or writes there, Claude Code's `.config.json`, which its 2.1.311 binary prefers over `.claude.json`, Codex's `.env`, whose variables Codex 0.162.0 sets in every command it runs, its SQLite state and its shell snapshots among them (`docs/field-notes.md`, *A home of the rooms' own*). So nothing a room writes there reaches another room, and nothing reaches the host.
- **History is shared, by name.** Only what its adapter names as history is a link from that directory into the home the rooms share: on Claude Code `projects/` (the conversations' records and their auto memory), `file-history/`, `tasks/`, `todos/`, `plans/`, `paste-cache/` and `history.jsonl`; on Codex `sessions/`, `archived_sessions/`, `history.jsonl` and `session_index.jsonl`. The home is the project's, `~/.local/share/lup/homes/projects/<a digest of the git directory>/<runtime>/`, shared by its worktrees and its profiles, so `--resume` and the picker find what any room of the project ran; or, for a profile with `rooms_home="global"`, the one every project shares, `~/.local/share/lup/homes/shared/<runtime>/`. One rule places it (`Layout.room_home`). A launch making one says so: a session from before it doesn't resume in a room until it's moved there (*Moving over*). **Rooms sharing a home read and rewrite each other's history:** every room of the project, whichever profile it runs on and so whichever account; and on a shared home, every project's room on such a profile. A package in one room can read another's conversations and change what one resumes into.
- **Resuming.** A conversation launched on a home resumes in a room, from the host's terminal with `lup-dev launch <runtime> --resume`; one from before the home, kept in the operator's own directory, once `lup-dev account migrate` moves it there (*Moving over*). A host session reads a room's conversation as a document, with `lup-dev transcripts show`.
- **Apart from what rooms write.** The home and the launch's directory are mounted alone, and neither sits under a directory a room writes, the project's rooms' own among them. A mount point can't be moved from inside a room, but a directory above one can, as `mv .git .git-real` did under the tree's mount (*The mounts*), and the host follows a link in a mount's source: a home under the rooms' directory would let a running room move the directory holding it aside and leave a link to the operator's `~/.claude`, which the next launch would mount read-write. The launch makes each item of the history in the home where it isn't, walking from the home and replacing any link a room left on the way (`lup.rooms.homes`).
- **What the host reads of it.** A launched session's record is read in the home its launch registered alone (`Register.home`), as the host service kept it from the launch it first heard the session on, and any other session's in the operator's own directory alone, so a room can't have a record it planted read under another's session id (`lup_dev.host.homes`). A session whose record the operator's own directory holds is never kept as a launch's, though a room's hook names it first; where lup itself moves or copies a session's record into a home, it keeps that home as it does. A path a hook's payload names, inside the launch's own directory, is read as the same place in the home (`Register.own`), never through the links there, which the room can repoint; any other path a payload names isn't read. Every record is read from what was opened, checked to be a file inside its home, without waiting on a pipe, and a line too long to hold is read past (`lup.rooms.homes.opened`, `lines`). The dashboard's drawer, an item's moment, the queue a held call ends on and the subagents' names read so; `Transcripts` keeps each home's records apart, saying whose home each was kept from (`packages/lup-transcripts/README.md`, *Keeping*).
- **The configuration's layers.** The operator's own, unless the profile sets `operator_configuration=False`, then the profile's, `~/.config/lup/profiles/<name>/<runtime>/`, laid out as the runtime's own directory: data the host copies, never runs. Copied on Claude Code: `CLAUDE.md`, `rules/`, `skills/`, `commands/`, `agents/`, `output-styles/`, `workflows/`, `plugins/` without its `data/`, `keybindings.json` and `themes/`; on Codex: `AGENTS.md`, `AGENTS.override.md`, `rules/`, `prompts/`, each of Codex's own profiles, `<name>.config.toml`, so `--profile` after `--` finds it, and the operator's `~/.agents/skills`, read-only in the room's home. A copy keeps a link as a link, never following it on the host, and a later layer never writes through one an earlier layer's copy left. The settings file, `settings.json` or `config.toml`, is merged from each layer with what would hand the room's code a credential or run a command in it left out of each (`lup.sessions.configuration`), and a URL's user and password taken out of what's kept. The launch says what it left out where that changed since the profile's last launch said it, a line for what would run a command and one for the rest.
- **What of your configuration doesn't reach a room, and why.** A room runs a malicious package's code with your configuration in reach, so what would hand that code a credential, or run a command set up for your machine with what the room can read, stays out:
  - your `env` (Claude Code's settings), and Codex's `shell_environment_policy.set`: variables, often credentials, that would be set in the room. Preferences set there, `CLAUDE_CODE_DISABLE_1M_CONTEXT` among them, don't apply in rooms either; a profile will declare the variables its rooms get;
  - credential helpers (`apiKeyHelper`, `awsAuthRefresh`, `awsCredentialExport`, `otelHeadersHelper`), any key named like a credential at any depth (a token, a secret, a password, an API key, a bearer, a cookie), the headers of Codex's `otel` exporters, and the user and password in any URL;
  - your hooks and status line, and any other setting whose value is a command (Claude Code's `fileSuggestion`, Codex's `notify`, a provider's `auth` command): they were set up for your host, and rooms run lup's own hooks;
  - your MCP servers: set up for the host, their `env` often holding a credential, and lup gives a room its own server alone;
  - plugins' `data/`, and `agent-memory/`, your subagents' memories, which hold what they learnt in every project;
  - anything that's a link where an item belongs, since lup never follows one on the host.
  Your plugins are copied, but their install records name paths under your `~/.claude`, which a room doesn't have, so they don't load in a room yet. Skills, agents, commands, `CLAUDE.md`, rules, output styles, keybindings and themes reach it as they are.
- **Settings are the launch's own, preferences carried back.** The merged settings are a file of the launch's, so `/model` and `/theme` save in a room and no room changes another's. At the launch's end, each preference of an allowlist the session changed (on Claude Code the model, effort, output style, theme, editor mode and thinking; on Codex the model, its efforts and verbosity, the personality and the theme) is written into the profile's own file, the rest of it kept, and said; never into `~/.claude` or `~/.codex`.
- **The login** is the account's file (*Accounts and profiles*), `.credentials.json` or `auth.json`, mounted alone where the runtime reads it, read-write; Claude Code refuses a login file that's a link, so it's a mount. The runtime's own sign-in in the room writes it through the mount, measured for Claude Code on the host (`docs/field-notes.md`, *Claude Code's sign-in through a single-file mount*) and, for Codex's save, in a room; Codex's ChatGPT sign-in through the mount is still to be measured on the host. Every room on the account shares the one login: a sign-in in one is every room's, which the launch says the first time it sees the account's login change under it. A runtime's own logout can't remove the file through the mount, so `lup-dev account logout` empties it. Codex is given `cli_auth_credentials_store="file"`, so no keyring is reached for. The cost of one rotating login: no lock spans the rooms, so two refreshing at once can race, and on Codex the loser's token is marked spent (`refresh_token_reused`; `docs/field-notes.md`, *Codex 0.162.1: launching a session*), a gap lup leaves open.
- **What goes with the launch:** besides the configuration, whatever the runtime keeps off the history's list, Claude Code's `/usage` totals and a plugin or skill installed in a room among it, and Codex's SQLite state, which holds its goals and queued input: shared, one room could leave another input to act on. Codex resumes a thread by its id from the shared rollouts; whether its picker lists another launch's thread is to be measured.

**Moving over** (`lup_dev/migration.py`; each adapter's check, `lup_dev/host/written.py`). Before rooms had homes of their own, every room mounted the operator's `~/.claude`, and a Codex room `~/.codex`, read-write, so every session launched then is recorded there, and every record there was written where any room could write. `lup-dev account migrate`, the operator's own in their terminal in the repository, refused inside an agent's session and on a repository nothing is approved for, moves them:
- **What moves.** Every record of the repository's directories, its git directory and each worktree (`Records.kept`), whoever wrote it, into the history the project's rooms share, at the same place there (`projects/<folder>/`, `file-history/<session>/`, `sessions/…`), or with `--shared` the history every project shares: none can be certified as the host's, and moving them all means the host never resumes one a room doctored. It keeps that home for each session it moved (`lup_dev.host.homes.kept`), so the host reads the session there, as a room resuming it has it, and a room of another project naming the session first can't claim it; a session whose record stays in the operator's directory keeps none. Records of other directories stay, said once with that caveat. A Claude Code folder whose sessions say they ran in a directory it isn't named for is no directory's, and moves nowhere (`filed`, `adapters/claude.py`): a line naming the repository, written into another directory's folder, would otherwise have its sessions taken for the repository's. `Transcripts`' copies are the module's own.
- **What of the shared history stays.** Of what else rooms share by name, what's one file for every project, `history.jsonl` (the prompts a session offers again, on both runtimes) and Codex's `session_index.jsonl` (its threads' names), stays whole: moving the repository's part would mean rewriting the operator's file line by line. So do Claude Code's `tasks/` and `todos/`, a session's task lists, which Claude Code empties as a session ends (`docs/field-notes.md`, *A session's record*) and which the drawer replays from the record itself; `plans/` and `paste-cache/`, named by neither a session nor a directory; and Codex's `archived_sessions/`, which a rollout leaves for `sessions/` when it's unarchived, and a later migration moves. In a room, sessions from before come without their old prompts to recall and, on Codex, their names.
- **A dry run first.** Without `--move` it says each record that would move, with its files and size, and what would be left and why, changing nothing. `--move` refuses while a launch of the repository runs, its launcher holding its lock, since its session would go on writing where its record was; a session on the host isn't seen, so it says to end those too.
- **How it moves.** Reached a directory at a time by descriptor, from the operator's directory and from the home, never through a link a room left on the way. A file moves as a second name in the home, then its first removed, so it's the same file, its content, mode and times kept, and a copy `Transcripts` holds of it still matches it; where the home is on another filesystem, or the file isn't the operator's to link, a copy keeping its mode and times. A link aimed inside what moves is made again aimed at its place in the home, as Claude Code links a resumed session's subagents to the first session's records; any other is left, never followed. What the home holds already stays, and so does what would go there; so does a pipe. Nothing is removed that isn't moved: a name once the home holds what it named, a directory once empty. A move stopped between a file's two names finishes at the next.
- **The check.** lup can't tell what a room wrote in the operator's directories from what they did, so for each runtime it says what a host session acts on there as it stands, quoted for the operator to recognize: on Claude Code what `settings.json` runs, sets and lets a session do without asking, `CLAUDE.md`, the skills and what else a session loads, the plugins turned on, the shell snapshots and session environments a session runs before each command, the state of the supervisor of background sessions, the mods sessions made, and the folders whose name and sessions disagree; on Codex what `config.toml` and its profiles run (`notify`, the MCP servers), set, send requests to and let a session do without asking, `hooks.json`, `AGENTS.md`, `rules/` and what else it loads, and the shell snapshots and `tmp/` helpers it runs before each command. It flags only what reads as planted whoever wrote it: a command naming a directory rooms write, and a link where the runtime makes none. What it can't check, it says how to clear; it changes nothing.
- **Logins.** Each account signs in at its first launch, in the room, with a login of its own: no host login is moved into one. The host's own, `~/.claude/.credentials.json` or `~/.codex/auth.json`, was readable by every room: logging out and in again on the host replaces the refresh token they could read, `/logout` then `/login` in a Claude Code session there, `codex logout` then `codex login`, which the migration says where it finds one. Whether a logout revokes the old token with the provider isn't documented.

**Related repositories.** A person names, in their own layer, the other repositories their sessions may read (`Repository`; `docs/declaration.md`, *A person's own layer*). Each is mounted whole and read-only at its host path, its own `config` and `hooks/` with it, and the guidance lists it with what it is, where, and its GitHub identity, which `read_issue` and `find_issues` take as `repository`. One missing on the host is said once and marked missing; one overlapping the room's own mounts is refused, since mounted read-only it would sit over or under what the room writes. Mounted whole means its untracked files can be read from the room, all but those with a secret's name (*Files with a secret's name*): naming a repository exposes the rest of it to the room. Its sessions' records are kept with the project's, and read with `lup-dev transcripts` (`packages/lup-transcripts/README.md`, *Keeping*).

**The clipboard.** A room has no display, so the host service reaches the operator's clipboard for it (`clipboard/`). In the room, `wl-paste` and `wl-copy` are first on the `PATH`, one program under both names on the standard library alone, and the room names a Wayland display with nothing behind it, so a program choosing its clipboard by it reaches for them: Claude Code copies through `wl-copy` and pastes an image through `wl-paste` (`docs/field-notes.md`, *The clipboard*). Each is a request on `request.sock`, which the desktop's own programs answer on the host, `wl-paste` and `wl-copy` or `xclip`, one of them an optional requirement. A read past 32 MiB is refused. The cost: anything in a room can read what the operator copies, a password among it, and replace it. Codex reads the clipboard through X or Wayland's own protocol rather than a program, so it isn't reached this way.

## The settings compiled for each runtime

lup's settings reach the runtime as flags and files of the launch's own, never written into the operator's directories or the repository (`adapters/claude/terminal.py` and `adapters/codex/terminal.py` in `lup`, whose docstrings give what each rests on):

| | Claude Code | Codex |
|---|---|---|
| Where | `--settings <launch>/settings.json` with `--setting-sources user`: the home's user settings load, the operator's and the profile's layered; the repository's `.claude/`, `.mcp.json` and `CLAUDE.md` don't | `-c` overrides on the home's configuration, the operator's and the profile's layered, and `--no-daemon` |
| No prompts, since the room is the wall | `--permission-mode bypassPermissions` | `--dangerously-bypass-approvals-and-sandbox` |
| The hook | in the launch's settings | managed hooks in a mounted `/etc/codex/requirements.toml`, with `allow_managed_hooks_only` |
| lup's tools | `--mcp-config` and `--strict-mcp-config`; `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS=0`, so a held call isn't moved to the background after two minutes; lup's server loaded as a channel, `--dangerously-load-development-channels server:lup`, so what waits for an idle session is pushed to it | `mcp_servers.lup`, the only one: the operator's are left out of the home's configuration; nothing a server pushes reaches the session, a gap its adapter declares |
| Guidance | `--append-system-prompt-file`, with `--system-prompt-snapshot off` | `additional_developer_instructions` in the requirements file |

**lup's server is a channel on Claude Code,** so an idle session reads what's pushed to it as its turn's prompt, the operator's words as theirs (`docs/inbox.md`, *How an agent is told*). Claude Code shows "WARNING: Loading development channels" at each start, a resumed session's too: confirm "I am using this for local development"; Exit quits. A channel Claude Code doesn't load drops what's pushed: where channels aren't on for the account, an organization's `channelsEnabled` blocks them, or the session runs on a third-party provider, its startup notice says so, and the service says once that the launch took no push and wakes it through its messaging socket from then on.

**Session settings** are `Core`'s `session` (`SessionDefaults`, `catalog/room.py`), in neutral words each adapter spells where its runtime has the setting; Codex has none for the subagents' prompt cache, removing a built-in tool or idle compaction, gaps its adapter declares:
- **idle compaction off,** so a session left waiting on the operator comes back to its conversation, not to a summary made meanwhile;
- **the account's connectors off,** since they reach the operator's mail and files;
- **built-in tools removed:** those that weigh in every turn and go unused, since an interactive session carries 113 KB of built-in tool schemas, `Artifact` alone 55 KB; and the native worktree tools, since a worktree for another agent's work is lup's spawn's to make (#117);
- **auto memory off,** and **the subagents' prompt cache** at an hour.

They layer, lowest first: the runtime's default, lup's defaults, the person's own runtime settings as the home has them, then the fields some layer of the declaration sets. What can't be imposed, such as Claude Code's connectors once a person turned them off, each adapter says.

**The model and the effort are the person's own:** a declaration names none, so no `--model` is passed, and each runtime reads their choice from the home's settings, the operator's and the profile's layered, `/model`'s in a room carried back into the profile's.

## Guidance

One document, rendered at launch (`render`, `launch/guidance.py`, whose docstring has the details):
- **the selected modules' sections,** in the declaration's order, each read at the approved commit or from the package shipping it, and rendered with Jinja in its sandbox, since an agent can write a section's file and the rendering runs on the host;
- **then lup's tools,** each by its name and summary, since the runtimes defer them behind their tool search, and agents told nothing of deferred tools concluded they didn't exist (`docs/inbox.md`, *Found through tool search, listed in the guidance*); then the related repositories, and what's lent to this launch;
- **then the person's own section, `AGENTS.local.md`,** last, so it holds where it differs. It's a protected path, since git ignores it and nothing else would show the operator a change to it.

**Delivered at system level,** on both runtimes: Claude Code's `--append-system-prompt-file`, its documented route for instructions that must hold, where a `CLAUDE.md` arrives as a user message "with no guarantee of strict compliance"; Codex's managed developer instructions. The runtimes' own loading of the repository's `CLAUDE.md` and `AGENTS.md` is off, so nothing arrives twice, and Codex would cut an `AGENTS.md` past 32 KiB without a word.

**A resumed conversation runs under this launch's guidance.** By default each runtime keeps a conversation's first instructions, so a path or a mount that moved would go stale without a word. Claude Code renders the prompt afresh at every request with `--system-prompt-snapshot off`; Codex sends its managed instructions again whole at a resume where they changed (`docs/field-notes.md`, *A conversation resumed in a later launch*). What the conversation's earlier turns saw still came from its earlier launch, so `Core`'s guidance says the room holds where they disagree; telling the conversation what changed is #73.

**Codex's ceiling.** Codex refuses to start past 10,000 estimated tokens of managed instructions, at 4 bytes a token, counted with the markers it sends them between and the notice opening them at a resume, so a render past it is refused at launch, naming its size and the limit. A workspace's own managed requirements outrank the system file, so a workspace setting managed instructions of its own drops lup's.
