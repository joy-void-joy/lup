# Launch: a session in a room

`lup-dev launch claude` (or `codex`) starts the runtime's latest CLI in a podman container holding the repository, the room, on a home of the rooms' own, logged in with an account. The session's settings and guidance are compiled from the project's declaration at the commit the operator approved (`docs/trust.md`), and passed outside the repository. One hook carries each of the session's events to lup's host service on the operator's machine (`docs/host.md`), which judges their writes and serves lup's tools.

## The command

```
lup-dev launch claude|codex [--name NAME] [--profile PROFILE] [--account ACCOUNT] [--mount DIR|MODULE]… [--mount-rw DIR]… [<the runtime's own arguments>] [-- <the runtime's own arguments>]
lup-dev spawn claude [--name NAME] [--resume SESSION] [--profile PROFILE] [--account ACCOUNT] [-- <the runtime's own arguments>]
lup-dev spawn interrupt LAUNCH
lup-dev spawn end LAUNCH
lup-dev spawn trial [--model MODEL]
lup-dev mount [--rw] [--launch LAUNCH] DIR|MODULE
lup-dev rename LAUNCH NAME
lup-dev sessions [--all]
lup-dev account list
lup-dev account logout ACCOUNT [RUNTIME]
lup-dev account migrate [--move] [--shared]
```

- **A launch starts in the worktree it's run from,** and passes every argument it doesn't know to the CLI, so `--resume`, `-p` and `--model` reach it, and every one after `--`, so the runtime's own flag of a name lup takes reaches it there: `lup-dev launch codex -- --profile fast` hands Codex its own profile. It exits with the CLI's status, and refuses to run inside an agent's session.
- **`--profile`** chooses the profile the launch runs on, and **`--account`** the account its runtime logs in with, in place of the profile's (*Accounts and profiles*).
- **`--mount`** lends a directory to this launch alone, read-only, at its own path, and `--mount-rw` writable; the guidance lists each under *Lent to this launch*. `--mount transcripts` lends a module's data instead. A repository every session should read belongs in the person's own layer (*Related repositories*).
- **`lup-dev spawn`** starts a session lup holds with no terminal, interrupts one, ends one, and tries the whole of it once (*A session held with no terminal*).
- **`lup-dev mount`** lends a directory to a room that's already running, under its `/lent`, and tells the session where through the inbox.
- **`rename` and `sessions`** name and list the launches (*Names*).
- **`account list` and `account logout`** list the accounts and log one out (*Accounts and profiles*); **`account migrate`** moves the repository's sessions from the operator's own directories into its rooms' home, which a launch offers to do itself (*Moving over*).

**What a launch does,** in order (`launched`, `cli.py`):
1. finds its repository once (`located`): through the worktree it's run from, the operator's starting point, or, for an agent's spawn, as the host recorded the spawner's, never through the worktree; and refuses a worktree the repository doesn't name back (`Git.listed`), saying where that's a submodule's checkout, or one whose git directory sits apart (`--separate-git-dir`), and otherwise that `git worktree repair` mends a worktree moved or recorded through a link. Every step after takes that git directory as given, git pinned there (`Git.pinned`), never finding it through the worktree again: a room writes every worktree's `.git` file and the git directory's `worktrees/`, so a later look could be led to another repository approved on this machine, whose tree the room would then mount read-write. A room can't make a repository whose git directory it doesn't write name its worktree back;
2. checks the code the host runs against the copy the operator approved, and asks where it changed (`docs/trust.md`);
3. reads the declaration at the approved commit, exported from git's objects, so neither a branch nor an edit made in a room changes the room a launch runs in, and chooses its profile and account from the person's profiles approved with it, refusing a name that's neither (*Accounts and profiles*);
4. where the operator's own directory for the runtime still holds sessions of the repository from before rooms had homes of their own, offers to move them into the home the profile chooses, and, on a yes, moves them and says what to check of that directory (*Moving over*);
5. checks the host's requirements: podman and git, and `gh`, `notify-send`, a clipboard program and `qrencode`, each optional and said where missing; and names the repository on GitHub;
6. starts the host service where none answers, and fetches the runtime's latest CLI where a newer one is out (*The CLIs*);
7. finds the related repositories and the operator's editor, builds the list of values never published (`docs/private.md`), and makes the room, refusing what can't be mounted safely before an image build that may take minutes;
8. builds the room's image where it's missing, and compiles the session's settings on its home of the rooms' own and renders its guidance (*A home of the rooms' own*);
9. looks for the files with a secret's name whose content their repository's git objects don't hold, in the repository's tree and each related repository mounted, and names each it hides (*Files with a secret's name*); says a home not made yet, an account with no login for the runtime, and what was left out of the configuration copied in, where that changed;
10. removes the environments a crashed launch left, registers with the host service, which opens the launch's sockets, makes the account's login where there's none, writes the settings and the configuration's copies into the launch's own directory under lup's state and what the home's mounts land on, and runs the container in the foreground, the CLI behind the start making the worktree's environment (*The project's environment, the room's own*), or, for a held launch, piped to its launcher (*A session held with no terminal*);
11. when the CLI exits, carries back what the session saved of its preferences into the profile's configuration, says the first change it saw of the account's login, ends the registration and removes the launch's directory, its room's home, its environments, and each `.venv` that appeared in a worktree while it ran, and names each file with a secret's name that appeared or changed in the repository's tree meanwhile, removing none.

A container starts in under a second; an image already built and a CLI already current cost nothing more.

## A session held with no terminal

A held launch is the same launch with its last step changed: rather than opening the CLI in a terminal, its launcher holds the runtime over the room's input and output, so the operator talks to the session through lup, the inbox's words reaching it as its turns and its answers coming back as any session's turn's ends do (`lup_dev/launch/held.py`, `lup.sessions.held`). The same guidance, tools, hooks, judge and room.

- **Who starts one.** An agent, through lup's `spawn` (*An agent's spawn*); and `lup-dev spawn claude`, the operator's own in their terminal, refused inside an agent's session as `launch` is. It checks what the host runs first, there, where an approval can be asked, then puts one request to the host service (`Spawn`, `host/held.py`). The service mints the launch's id and starts its launcher apart from itself, in a session of its own, from the `lup-dev` it runs (`lup-dev spawn launcher`, hidden), writing what it says to `<launch>.log` beside the launch's lock. The service answers at once with the launch's id and its log, and the command then waits for the session to be up (`AwaitHeld`), saying its name, the runtime's id for its session and where its log is; where the launcher ends first, it says the end of that log. Ctrl+C there gives the launch up (`Abandon`): its launcher is ended, so an approval it waits on in the inbox, answered later, starts nothing; a launcher waits on one an hour at most. Answering that approval restarts the host service, as any approval does: the command asks its wait again of the service that runs next, which knows the launcher by its process, the launcher's word that its session is up reaching that one. Its arguments are `launch`'s, `--resume SESSION` resuming that session in this worktree. Codex has no held session yet, and is refused (`Codex.held` says how it would be held).
- **The launcher** does the launch's whole setup as a terminal's launcher does, in the order *The command* gives, its approval asked through the inbox alone where the zone changed since the command checked it, an agent's spawn's never (below), then holds the session (`Holder`). It's a process apart from the host service, so a restart of the service, which every approval makes, doesn't touch the session. It ends the session when the runtime exits, the operator ends it, or it's asked to end itself (`SIGTERM`): its input's end written first, so a turn under way finishes, the runtime asked to end two minutes later and made to two minutes after that, then the room stopped; then the launch ends as any does. The room is stopped however the launcher's hold ends, a failure among it; where podman can't stop it, that's said and the launch stays registered, for the sweep to stop it once the launcher is gone.
- **Called up once a hook is heard.** The launcher says the session is up only once the host heard its first hook (`CalledUp`), which Claude Code runs as it starts, before anything is sent to it. Where none comes within a minute it ends the session and says why: a runtime that ran no hook, as a CLI update could make it, would run without lup's judge.
- **What it runs.** Claude Code's terminal command, every flag of lup's kept, with `--output-format stream-json --verbose --input-format stream-json`, and no `-p`: Claude Code's docs say `--bare` will become `-p`'s default, and a bare session runs no hooks and refuses a subscription login. No channel and no messaging socket, which a held session has no use for (`lup.adapters.claude.held`). Its session is named up front, `--session-id` for a new one, `--resume` for one it resumes.
- **Its input and output are a socket only the launcher holds.** A process of the same user can open another's pipe again through `/proc/<pid>/fd/0` and write a turn the runtime takes as the operator's, but not a socket ("No such device or address", `docs/field-notes.md`, *A session held with no terminal*). So the launcher listens on `session.sock` in the launch's socket directory, `/run/lup` in the room, for one connection, and the container's command is `python3 -I <launch>/connected.py /run/lup/session.sock`, then the room's own start (`lup-environment`), then the runtime: the wrapper connects, puts the connection on its input and output, and runs the rest in its place (`lup.sessions.connected`, `Room.hold`). The launcher accepts one connection and closes and removes the listener, and podman runs with no `-i`, its input nothing. **Why nothing in the room can win that connection:** the room is a container of its own, started for this launch, and its image runs no program of its own (no `ENTRYPOINT`, its `CMD` replaced by the launch's command); with `--init`, podman's init is its first process, running only that command, whose first program is the wrapper, which connects before it runs anything else. `lup-environment`, which starts `uv sync` and with it the first code of the project's in the room, runs only after, in the wrapper's place, and the runtime after it. No other room mounts this launch's socket directory. What could reach the listener before then is a process of the operator's own on the host. Should something have connected first, the session's own program finds the listener gone and fails, and the launch with it. The trial checks from inside the room that its processes can't reach the session's input, and that none but the runtime holds it. **The kernel must keep a process from tracing its siblings:** where Yama's `ptrace_scope` is 0, or Yama isn't there, any process of a user may trace any other, and one in a room could write the held session's turns through the runtime's own memory, whatever its input is. A room's kernel is the host's, so a held launch refuses there, saying so, and the trial's step fails (`untraceable`); at 1, most distributions' default, a process traces its own descendants alone, and the runtime is no room process's descendant.
- **The operator's words** reach an idle held session as its next turn: the host gives its launcher what waits on a socket beside the launch's lock, `<launch>.sock`, which no room mounts, so nothing in a room can type a turn as the operator; the launcher writes it as a user turn (`docs/inbox.md`, *How an agent is told*). A busy one is told at its next call, as any session is. What waits as a held session's process starts, started or resumed, isn't told it at its start, where no turn would begin on it: it's given as its first turn once its launcher calls it up (`Delivery.called_up`), an agent's brief among it. The launcher calls it up once the host has its first hook named, which can be before that hook is answered: so the call-up notes the session in its launch itself, and what it gives is tagged with that launch, which the start then leaves be (`started_anew`), so it's given once whichever comes first, never told again beside a hook. What a process of an earlier launch left, a turn it was in when it ended, says nothing of the one called up. A failure giving it refuses nothing, the session up all the same, and since an idle held session sends no hook that would tell it, the sweep gives it again until it's given (`Delivery.rewoken`), each held session's at once, apart. The launcher answers once the turn is on the session's input, never waiting for its runtime to read it, which any process of its room can stop (`ClaudeHeld.written`); the host gives up on a launcher that doesn't answer a turn or an interrupt within 30 seconds, or an end within six minutes (`Holders.answering`, `Holders.ending`), so none holds the sweep, the operator's words, or another session's turn. A turn given and not yet taken counts its session busy (`Delivery.wake`) until its turn's start carries it, whatever hooks come first, a compaction's start or a turn's end among them, so nothing is given twice; a new process of the session, or a hook from another launch running it, voids it, and what it held is told as anything waiting.
- **An interrupt,** `lup-dev spawn interrupt`, which the dashboard will call (`Interrupt`), ends the turn under way at once, its foreground command killed, a command in the background running on; the session is then taken for idle, an interrupted turn running no turn's end, and given what came meanwhile.
- **Its end, and its way back.** `lup-dev spawn end` ends it and its room, once a turn under way finishes (`End`). `lup-dev spawn claude --resume SESSION` holds it again, in the same worktree, and `lup-dev launch claude --resume SESSION` takes it over in a terminal: finding it held, the launch asks whether to end it, and resumes it here on a yes, or with `--take-over` does so asking nothing; it waits up to a minute for the held launch to let the session's lock go, which it does just after its end is answered. Each is the other's way back. A session that never took a turn has no record to resume.
- **One writer.** Claude Code lets a second process write a session another is running, and its one record branches (`docs/field-notes.md`, *A session held with no terminal*). So a launch whose session's id is known before its room starts, a held one's always and a terminal's resuming one by its id, holds a lock on that session's writer while its room runs (`Writing`, `Layout.writer`), refusing where another launch holds it, naming that launch. A launch whose session isn't named up front holds no lock, a terminal's started with no id, `--continue`d or after `/clear`, so a launch also refuses a session the host heard a served launch's hooks name, its latest. Not covered: the runtime's picker (`--resume` with no id, or with a search term) and `/resume` inside a session, whose choice lup never sees, and a runtime's own process a room's shell runs, `claude --resume <id>` against the history the rooms share, which runs none of lup's hooks.
- **What the host knows of it.** Its registration says it's held (`Register.held`), so the host wakes it through its launcher, and the sweep stops its room once its launcher is gone, where a terminal launch's room is left to its session: Claude Code outlives its input's end during a call, a held hook or a background command, spending on with no one reading (`docs/host.md`, *Restarts and the sweep*).
- **`lup-dev spawn trial`** tries all of it once on the operator's machine, which no room can, having no podman: in a scratch worktree beside the one it's run from, made by git pinned to the repository's common directory at the approved commit, a held session started and answering, interrupted, in a command and in `wait_inbox`, outliving a restart of the host service, spawning a side job whose report comes back to it, ending there, and resuming it with a `send`, handing a concern over to one the operator then talks with directly, ended, the one it handed the concern to running on, resumed held, taken over by a terminal launch and held again, a few short turns on Haiku unless given `--model`, on a host service running a copy of lup that holds sessions. The two it spawns run on its model too, as every spawn runs on its spawner's launch's. Its terminal launch takes the session over by `--take-over`, its input closed, so nothing it asks is answered, an approval above all, which its trust then waits for in the inbox; the step fails where it asks anything. From inside the held room, as one of its processes, it tries to write a turn to the input of each process whose input is a socket, the runtime's a pipe too, never `/dev/null`, which podman's init has, its command line carrying the whole command it runs; it fails where the session answers that turn, where another process holds the session's socket, or where the kernel lets one process trace any other, and its report names each process it tried and how, so a false result shows itself. Through `podman exec`, as the host service runs the room's git making a spawn's worktree and `land`'s in the room (`executed`), it runs a command that never ends in the held room, killed past five seconds with its process group; it fails where the service's wait on it outlives the kill, as where something outside the group held its output open, and says whether the command ran on in the room. Before removing its worktree it ends every held launch the host serves in it, one whose start it lost among them, and each its sessions spawned, whose worktrees and branches it removes too. It files its report in the inbox, a line per step with what it saw and how long it took, and what each failure means (`lup_dev/launch/trial.py`).

## An agent's spawn

An agent in a room starts another through lup's `spawn` tool: a held launch as `lup-dev spawn` starts one, in a room and a worktree of its own, its parent the agent who spawned it (`lup_dev/launch/spawning.py`). It's how the operator talks with whoever builds the thing: the agent spawned asks them directly and is answered in its own buffer, and lands its own branch.

- **The call** is `spawn(name, brief, concern=None, start=None)`, and returns at once, with its name, its worktree, its branch and where its launcher writes, the launch's setup running behind it. `name` names it and its branch, in a few words. `brief` is the spawner's message to it, an item from them in both drawers, given as its first turn once it's up. `start` is the local branch its worktree starts from, by its short name, else the integration branch the declaration approved names. The runtime is the spawner's; Codex, with no held session, spawns none.
- **Two kinds, by whether a concern is handed with it.** A side job for the spawner, with no `concern`, as a native subagent is: its report, what it ends a turn saying, is handed to them whole as a subagent's end is (`Ended`), but loud, since no runtime wakes them for it: it holds their turn's end once, wakes them idle, and returns their `wait_inbox`; it isn't put before the operator, but where it answers words of theirs, as a subagent's last words aren't. Then it ends, its launcher asked to end it once that turn's end is answered, so none waits idle counted against the limits; what they `send` it after resumes it held in its worktree, its context kept, the message its first turn, as `lup-dev spawn --resume` holds one (`SpawnTools.resumed`), from what the host kept of its start by the session's id it minted (`Layout.side_job`), which the sweep removes once its worktree is gone (`Sweeping.forgotten`), counted as a spawn, the sender its spawner again. One still working ends when the launch that spawned it ends, its launcher asked to end it, or the sweep finds that launch no more served (`orphaned`, `cli.py`), each end awaited on the service's loop, holding none of the threads its hooks wait on (`side_job_ended`), as after a side job registered once its spawner had ended, or a restart cut the spawner's end short; or when the operator ends it. Its worktree and branch stay, for its resume. A concern handed over, with `concern`, an existing thread or a title opening one under where the spawner works: the session spawned holds it and works in it from its start, what it says lands there, its turn's ends before the operator as any session's are, and its spawner hears none of it, not even a line, reading it in the thread where they want to. Once handed, it's theirs. It lives until the operator ends it. Its spawner hears two lines of it, each a quiet message from its session, no wake but returning their `wait_inbox`: when it says the concern is done, naming it and nothing of its account, and when it ends, and where its reports are (`Delivery.told_spawner`); `send` is there for more.
- **Its parent, the host's record, never the room's word.** The launch records who spawned it (`Register.spawner`): the spawner's launch, the conversation that called, as lup's hook stamped the call on that launch's `mcp.sock`, and the concern handed. Its session's own conversation is that conversation's as a subagent is their parent's (`Delivery.parent_of`): `send` reaches `parent` from it, and it by its name from its spawner; a side job starts quiet on its spawner's thread as a subagent does, and what either kind sends the operator is told none of the conversations above it (`Concerns.forebears`). `lup-dev sessions` lists it under the launch that spawned it, saying by whom and which kind, and the review nests it under its spawner. Its parent is read from its launch's record at each hook and at its call-up, never kept from an earlier launch. A held launch records the session its launcher named (`Register.session`), and a hook on its socket naming another is answered with nothing, so a process of a spawned room can't speak as another session of the repository, its spawner among them. The other way too: a hook on any launch's socket naming a session another served launch of the repository runs, a held one's named session or the one a terminal launch's latest hook named, is answered with nothing (`Launches.runner_of`), so a room, its spawner's among them, is neither told what's for a session the operator talks with directly nor heard as it, its turn's end put before the operator in that session's name. A terminal launch is bound to no first session: a clear or a resume moves it to another in the same process, which a hook of its room could say just as well, so it's held to the one its latest hook named. A session no served launch runs, an ended one's, a room can still name. Walking a conversation's parents stops where they loop. Resumed in a launch of the operator's, it has none.
- **Its worktree** is made at the call, at `tree/<branch>` in the repository's git directory, inside what every room of the repository mounts, on a branch named after `name`, the next number where a branch or a worktree has it, by the spawner's room's own git through `podman exec`, as `land` removes worktrees: never by the host's git, whose checkout would run the filters and hooks a room's commits choose. Its environment is made as its room starts, as every launch's is (*The project's environment, the room's own*).
- **What a room can make of it, and nothing more.** The repository is the one the host recorded for the spawner's launch, which the launcher takes as given, never finding it through the worktree, and it refuses a worktree that repository doesn't name back (`located`, *What a launch does*). `name` reaches git and a path only as a branch's shape (`branch_named`): ASCII letters, digits and `-`, never first. `start` is held to a branch's short name, then git's `check-ref-format` on `refs/heads/<it>`, which expands no `@{-1}` as `--branch` would, and read by git pinned to the common directory as `refs/heads/<it>`, peeled to a commit, whose id alone reaches the room's git. The command is a list run with no shell. The brief reaches the inbox alone; the call names no runtime, none of its arguments, no profile and no account: the launch runs on the repository's default profile, and on the model the spawner's own launch's arguments named, where they named one (`Register.model`), the host's record of what the operator gave it, never the room's word. Another repository can't be named yet.
- **How many:** 32 sessions agents spawned run at once on the host at most, and 16 of one repository's, counted from those served, those whose launcher started and hasn't registered, a service before this one's among them, kept beside their lock while their launcher runs (`LaunchLayout.spawned`), and the spawns under way, about 300 MB of a held runtime each: against a loop of spawns, not a budget. Past either the call is refused, naming them.
- **Nothing a room can slow holds the service, or another room's spawn.** A room can make any ref, or `packed-refs`, a pipe nothing writes, which holds git reading it forever: the host's git reading `start` and the branches taken runs in the repository's own threads, off the service's loop (`threaded`, `git.py`), killed past 30 seconds, the free number read in one call and a hundred at most tried; `podman exec` running the room's own git to make the worktree is killed past two minutes with what it started (`Program.within`), and the worktree removed all the same, since that git can run on in the room and make it. No lock is held across either: a spawn is counted, and takes its branch, between two awaits, so two calls at once can't both pass a limit nor take one branch.
- **A spawn that never comes up** is told its spawner as a problem from it, naming its launcher's log for the operator, never what it says, which can name what's no room's to read, once the sweep collects the launcher (`SpawnTools.lost`). Not told: one whose launcher ended after an approval restarted the service, which the service started since doesn't know.
- **A spawn refused partway** leaves nothing behind it can remove: the worktree and branch made for it are removed by the spawner's room's git, where its launcher couldn't start or its brief couldn't be sent, and a launcher already started is ended, so no session comes up with no brief. A concern the call opened stays, said in the refusal.
- **A spawn's launcher asks no approval** (`Trust.asking`): a room could otherwise choose when the operator is asked, moving the running branch and then spawning, each spawn's launcher waiting up to an hour on the answer. Where the tip's host zone isn't the one approved, it runs on the copy approved before, as a decline leaves it, says so in its log, and records both commits (`Register.behind`), which the session's opening line names, so an agent needing the newer asks the operator; where none was ever approved, nothing launches, and its spawner is told it never came up. Asks come from the operator's own launches and from pushes alone.

## Names

A launch has an id, which never changes and under which everything of it is filed, and a name, for people and commands (`host/names.py`):
- **At launch** it's `--name` exactly, refused where another running launch holds it; otherwise the worktree's branch in a name's shape (`feat/x` is `feat-x`), numbered while taken.
- **It changes** with the session's `rename` tool or `lup-dev rename`. Nothing is filed by name, so a rename moves nothing, and a name is looked up each time it's used: the first lup kept paths by name, and its sessions met an earlier session's stale socket.
- **A subagent is named under their conversation** (`dev/explore-auth`), so their rename can't take their session's name. They keep the name their parent gave at the spawn, where one did; otherwise lup asks them to name themselves.
- **The container is `lup-<repository>-<name>`,** renamed with the launch, so `podman ps` says which session each runs.
- **The runtime's own title follows** where the runtime has a way. Claude Code's, the one `/rename` sets, is given the launch's name through `sessionTitle` at each start and at each prompt, wherever the title the hook carries differs, so a rename through lup reaches it at the session's next prompt (`lup_dev/adapters/claude.py`). Codex's hooks neither carry a thread's name nor set one, at a start or a prompt, a gap its adapter declares with its evidence (`lup_dev/adapters/codex.py`).
- **The operator's own rename in the runtime is taken** at the session's next prompt or start, in a name's shape (`Naming Review` is `naming-review`), and the agent is told. One that can't be a name, or that another launch holds, is said in the service's log, and the runtime is given lup's name back.
- **lup keeps each session's title as it last left it in the runtime:** the one it gave, once the answer giving it was written, else the one it found there. Only a title other than that one is the operator's: a resume carries the title lup gave at an earlier start, which taken as theirs would undo a rename through lup since, and an answer that never reached its hook leaves the runtime with the title found before.
- **A resumed conversation takes their name back,** where no running launch holds it.
- **Names are one set per repository with its threads** (`docs/inbox.md`, *Threads*): a name a thread has is refused by `rename` and skipped by a launch's default, and taking a name gives a session nothing of what an earlier one of that name held. A name holds a letter, so `@` never reads it as an item's number.
- **lup names an agent by it,** to the operator and to other agents: a tag's `from`, `inbox`'s lines, `send`'s answers, `lup-dev inbox`, the bearings and the dashboard each say a conversation's path, with their runtime's ids beside it only where another conversation of the repository has the same path, as a session cleared in their launch keeps the launch's name, and by those ids alone where lup kept no name (`inbox/roster.py`). The dashboard names an agent who isn't running, or isn't their launch's latest session, by the paths the inbox's listing and the threads it reads carry (`Items.paths`, `ThreadsRead.paths`, `ThreadShown.paths`), since no launch it lists names them; where another shares the path, the first 8 characters of their runtime's id go beside it, as git abbreviates a commit (`dashboard-review c0fa70bc`; `calledBy`, `page/src/App.tsx`), never the id whole, which runs a line on.

## Accounts and profiles

- **An account** is a login per runtime, kept by its name at `~/.local/share/lup/accounts/<name>/`, a directory per runtime holding the file that runtime's sign-in writes (`AccountLayout`, `layout.py`). It's kept by the account's name, never a project's, so every room on an account shares one login, and a sign-in in one is every room's.
- **A profile** is the whole setting a room runs with, its account among it, declared by the person in `~/.config/lup/profiles.py` (`docs/declaration.md`, *Profiles*).
- **A launch's profile** is `--profile`'s, else the one the person's layer chooses for the repository, else `default`; its runtime's account is `--account`'s, else the profile's for that runtime. A launch runs the profiles approved with the repository's zone (`docs/trust.md`, *Trusted by its content*), and says which profile and account it runs on where either isn't `default`.
- **`lup-dev account list`** lists every account, `default` first, with the runtimes it holds a login for: a login file that isn't empty.
- **`lup-dev account logout`** logs an account out of one runtime, or of every one, by emptying its login file in place. A room's own logout can't remove a login mounted as a single file (`docs/field-notes.md`, *Rooms*), and removing it on the host would leave such a mount holding it. It forgets the login on this machine alone: it isn't revoked with the provider. Like a launch, it refuses inside an agent's session.
- **`lup-dev account migrate`** moves the repository's sessions from before rooms had homes of their own into its rooms' home, a dry run without `--move`, and checks what a host session acts on that rooms could have written (*Moving over*); a launch offers the same move for its runtime, before its room starts. Like a launch, it refuses inside an agent's session.
- **A launch runs on them:** its runtime keeps its history and state in the home its profile chooses, logs in with its account's file, and reads the profile's configuration over the operator's (*A home of the rooms' own*). An account with no login for the runtime gets an empty file the runtime's own sign-in fills, which the launch says first.

## The room

**The image** (`launch/images.py`) is Arch Linux pinned to one day's snapshot of its archive (`RoomBase`, `catalog/room.py`), with the packages the selected modules ask for, each with its reason (`Packages`), so a build is reproducible and every package is at least as old as the pin. `Core`'s default is the standard machine (`StandardMachine`): the shell's tools, git, jq, ripgrep and fd, `man`, `time` and `tmux`, `nano`, `gcc` for a Python package built from source, and what lup and the runtimes need. Every agent meets the same machine, without the operator's own shell setup, which aliases `cp`, `grep` and `ls` on this host. Where the room has `man-db`, every package's English man pages are kept, though Arch's base extracts none: a `NoExtract` exception appended to its `pacman.conf` keeps them for what the build installs, and the base's own packages, which `--needed` skips, have only their man pages extracted from their packages, about 11 MiB where reinstalling them would add 0.4 GB (`docs/field-notes.md`, *What agents reached for in rooms*). `mandb` then indexes them, since no pacman hook does, for `apropos` and `whatis`. Info pages and `/usr/share/doc` stay out. **The operator's editor,** the one `$VISUAL` names on the host, else `$EDITOR`, which Ctrl+G opens, joins the image at launch where lup knows its package (`Editors`): `nvim` brings `neovim`, `emacs` `emacs-nox`, `hx` `helix`, which Arch installs as `helix`, so the launch links `hx` to it among the room's commands. Only that one is installed, where all five took about 818 MiB in every room; `xxd` comes with `vim` alone. An editor lup doesn't know brings nothing, and the launch says so: the person's own layer adds its package to `Core` (`docs/declaration.md`, *A person's own layer*). The image is tagged by a digest of its definition and project, and built when the tag is missing; after a build, the project's older images that no container uses are removed. The first lup left 46 tags of 4.5 to 5.5 GB each, kept alive by readable names.

**pyright's source** (`PyrightSource`, `lup_dev/pyright_source.py`) is in the image of a repository whose gate builds lup's engine from it, as lup's own does (`LupDevelopment`). A second step clones pyright at the release the launch's worktree's `uv.lock` pins and installs its dependencies with pnpm, from pyright's own lockfile, into `/opt/lup/pyright/<release>`: inside the image build's own container, never on the host, and root's, so the room reads it and can't write it. pnpm runs in a home of the step's own, holding the package age as a room's pnpm settings hold it (*The package age gate*), and that home goes in the same step with what pnpm downloaded, so the layer holds the source alone: 441 MB, the step's commands taking about 8 s (`docs/field-notes.md`, *pyright's source in the room's image*). A step of its own after the packages', so a change of release builds that layer alone, and a branch changing the release gets its image at its launch. The engine's build in the room reads that copy. A worktree pinning another release, or a merge bringing one, has it fetched once into the project's rooms' own directory (`RoomsLayout.pyright`), which the room's `LUP_ROOM_PYRIGHT` names, by the same recipe under the room's own pnpm settings. Never into the host's cache, which no room mounts: what a room wrote there would be bundled into the host's engine at the next approval. The host's builds, trust on launch's and the operator's own, read the host's cache alone.

**The mounts** (`maintaining_room`, `launch/room.py`). The repository, the environment and the operator's own directories are each at their host path, since a linked worktree's `.git` file and the environment's links hold absolute paths, and the runtimes key their history on the working directory:

A worktree is one git lists that names the repository back (`Git.listed`): git lists a linked worktree from `worktrees/<id>/gitdir`, a file the room writes, so a room could otherwise name the directory holding the repository, and the next launch would mount all of it read-write; its `.git` file, outside the room's mounts, is the half it can't write (`docs/credentials.md`, *Running git on the host*) |

Not mounted: the operator's own `~/.claude` and `~/.codex`, the SSH agent, `gh`'s login, `~/.gitconfig` (it holds the operator's aliases and an LFS filter the image lacks, so the git identity is passed as variables, read from the repository's own git directory as the launch found it: an `includeIf "onbranch:"` or a worktree's own settings don't choose it), the rest of lup's cache, pyright's source the host builds from among it (*pyright's source*), and the rest of the home.

**The room's git** (`room_git`): git's configuration is the room's own (`GIT_CONFIG_GLOBAL`), rewriting each remote to lup's helper, so `git push` and `git fetch` go through the host with the operator's credentials (`docs/credentials.md`, *git through a remote helper*). A repository whose `config` sets `extensions.worktreeConfig`, or includes a file inside the room's mounts, is refused at launch: either would have the host's git read what the room wrote.

**The package age gate** (`RoomPackageAge`, `launch/room.py`). Nothing published within `Core`'s `package_age`, three days unless the project says, installs through a package manager the room's image holds: a release published with stolen credentials is usually found and pulled within hours. Each package manager lup knows is spelled in its own file (`lup_dev/declaration/package_managers/`), and the launch asks each one the image holds for its user-level settings, writes them into its own directory and mounts them read-only where the package manager reads them in the room's home. User-level settings rather than variables: npm and uv each rank a variable above a project's own setting and a user-level one below it, so a project with its own, stricter or laxer, keeps it (`docs/field-notes.md`, *User-level package age settings*).
- **npm** (`npm.py`) gets `~/.npmrc` holding `min-release-age`, in days, a fraction among them. It doesn't touch a lock: `npm ci` installs what its lock pins, however new.
- **pnpm** (`pnpm.py`) gets `~/.config/pnpm/config.yaml` holding `minimumReleaseAge`, in minutes, rounded up. pnpm 11 reads no age from `~/.npmrc`, and checks even a frozen lockfile's entries against its own, so it holds what a lock pins too; a project's own `pnpm-workspace.yaml` outranks it. The image's step installing pyright's source writes the same settings into its own home (*pyright's source*).
- **uv** (`uv.py`, beside `Uv`, the runner) gets `~/.config/uv/uv.toml` holding `exclude-newer`, as an ISO 8601 duration, only where the project sets its own `exclude-newer`, in its root's `uv.toml`, else its `pyproject.toml`'s `[tool.uv]`, as uv reads them. Without one, a user-level one changes what its `uv.lock` was resolved with: the room's first `uv run` relocked it, downgrading what was newer than the age, and the host's next `uv run` relocked it again. With one, the user-level one leaves its lock alone and is what `uvx` and `uv tool` read, since they read no project's settings. Where the project sets none, the launch says so, naming the line to add to `[tool.uv]`, which gates the project's own `uv run` too. A project nested in the repository with a `[tool.uv]` of its own and no `exclude-newer` still relocks under it; a workspace member doesn't, uv reading a workspace's settings from its root.

**The user, the process, the network** (`Podman`, `packages/lup/src/lup/rooms/engine.py`):
- the operator's uid inside (`--userns=keep-id`), so what the agent writes is theirs on the host;
- `--init`, since without it the first lup piled up 4,045 zombies against its pids limit;
- every capability dropped, and `no-new-privileges`;
- a pids limit of 16,384, which counts threads and is shared by every session, worker, gate and demo in a room: podman's own default of 2,048 made gates fail with errors that don't name it, a gate alone peaking at about 720. It's a limit rather than none, since it's also what stops a fork bomb in a room from taking the host down;
- the host's network, shared both ways, so a server the agent starts opens in the operator's browser, and the sign-in's callback reaches the CLI. The cost is that code in the room reaches what listens on the host's loopback: the walls are there so nothing explodes, not to contain an agent (`DESIGN.md`, *Who it's for*);
- a terminal with no detach keys, so Ctrl+P reaches the program, and the operator's `TERM`, `LANG`, `TZ` and `EDITOR`, without which the first lup's sessions lost their colour, locale, time zone and Ctrl+G.

**The project's environment, the room's own.** Each worktree's environment in a room is its launch's own, made fresh as the room starts and outside the repository, and the host's, the worktree's `.venv`, is hidden from it: the operator's own `uv run` runs `.venv`, and the copies of lup the host runs share files with uv's cache, so neither is the room's to write. The runner says what the room needs (`Runner.room()`; `docs/declaration.md`, *The runner*).
- **Where it is.** The project's rooms have a directory of their own beside lup's other data, `~/.local/share/lup/rooms/<a digest of the git directory>/` (`RoomsLayout`), mounted read-write at its host path: their uv cache, and each launch's environments, one per worktree, at `environments/<launch>/<the worktree's name>-<a digest of its path>` (`lup_dev/environments.py`). One mount, so an environment's files are links into the cache: lup's takes 7 MB of its own where a copy took 717 MB, since no link crosses two mounts (`docs/field-notes.md`, *The room's own environments*). One per project, so one project's room can't write what another's installs from.
- **How uv finds it.** uv takes a project's environment from `UV_PROJECT_ENVIRONMENT`, and has no setting naming one per project. So the room's `uv` is lup's, first on its `PATH` among the launch's commands: it asks git for the worktree it runs in, as the judge does, and in one of the repository's sets `UV_PROJECT_ENVIRONMENT` to that worktree's environment, then runs uv; elsewhere, a scratch project in `/tmp`, it sets none. A worktree made during the launch, by `git worktree add` or by lup's hooks, gets its own at its first `uv`, the gate's worktree at a commit among them, which takes it along when it goes. `uv --directory` or `--project` naming another worktree still gets the working directory's: run it from there. `UV_CACHE_DIR` names the rooms' cache, so a project's own `cache-dir` doesn't apply in a room.
- **Made as the session starts.** The CLI runs behind `lup-environment`, which starts `uv sync --frozen` for the launch's worktree in the background, through lup's `uv`, where the project has a `uv.lock`, so the judge reads its third-party types from the session's first write. The CLI waits for nothing: the start hands over in 0.03 s, and lup's environment is made in 0.15 s from a warm cache, though a project's first launch downloads into an empty one (16 s for lup). Its output is kept beside the environment, and where it fails, the next `uv` in that worktree says so, once.
- **What the judge reads.** The launch records its environments (`Register.environments`), each of its hooks carries them, and the engine reads a worktree's where the room's `uv` puts it, placed by the same function (`docs/judging-writes.md`, *The engine: one typed tree*): as it stands, an environment half made reading as the packages already there. The engine is one per worktree, so two launches working in one worktree each replace the engine the other's hook started, loading the project again.
- **The host's `.venv`, hidden.** Each worktree's `.venv` there as the room starts has an empty directory of the launch's mounted over it read-only, as `config` and `hooks/` are over the tree, so the room neither reads nor writes it: it lists nothing, writing into it fails ("Read-only file system"), and removing or moving it fails ("Device or resource busy"). So `git worktree remove` there fails partway, having removed part of the worktree: `land`'s cleanup asks the room what it mounts first (`findmnt`), and leaves such a worktree whole, saying its `.venv` is hidden from the room, so it's removed on the host. A room moving the worktree itself moves the mount with it, and a `.venv` it then makes where it was is the host's to run: so at the launch's end each `.venv` in the repository's worktrees that wasn't there as it started, told apart by its device and inode, is removed, never following a link or a `..`, through which a path inside the tree by its text leads out of it (`docs/field-notes.md`, *Paths hidden from a room*). One the operator made meanwhile goes too, to be made again. Paths hidden from the room are a general mechanism (`launch/hidden.py`), `.venv` its first, the files with a secret's name its second (*Files with a secret's name*).
- **Gone with the launch.** Its environments are removed as it ends, so what a package wrote into one doesn't outlive it; a launch that crashed leaves them for the next launch, or the host service's sweep, to remove. The environments' interpreter is the one uv's store holds for the project's Python, its `.python-version` else its `requires-python`, asked of uv from outside any project with no settings file read (`uv --no-config python find --managed-python --system --no-project`), a request that isn't a version or a version specifier refused before uv is asked, since uv runs an interpreter named by its path to query it. The store is mounted read-only at its host path, with `UV_PYTHON_DOWNLOADS=never`; where it holds none, the launch says how to install one (`uv python install`). Nothing of the worktree's environment is read or run on the host for the room (`docs/field-notes.md`, *The judge reads the environment as files*).

**Files with a secret's name** (`launch/secrets.py`). A file in the worktree holding a secret, an `.env`, a key, a credentials file, would be readable by any code the room runs, a malicious package among it, where a secret is meant to reach a room's code through a module's host helper that adds the key, so the room can use it and never carry it off (`DESIGN.md`, *Modules*). The declaration's `secret` role names such files by the names tools give them (`CorePaths.secret`; `docs/declaration.md`, *The kinds*): dotenv's `.env*` and direnv's `.envrc`, Wrangler's `.dev.vars`, keys, certificates and key stores, OpenSSH's key files, credentials in JSON, `.netrc`, `.git-credentials` and `.pypirc`, Terraform's variables and state, and Streamlit's secrets.
- **Which are hidden.** Each whose exact content the object store of the repository it sits in doesn't hold: an ignored one, an untracked one, or one changed to content git never held. Each is hashed as git hashes a blob, and git, pinned to the repository's common directory, is asked whether the store holds that id (`Git.blobs`), never fetching what a partial clone left out, which would send the id to its remote. The room mounts that store and can read every object in it, so hiding a file whose content is there protects nothing: a tracked `.env.example` as committed stays in view, as does a copy of it under another name, or a file staged once, even unstaged since, until git prunes its object. A real value added locally is content git doesn't hold, and a room can't put an object with a secret's content in the store without knowing that content. A file over 1 MiB is hidden unread, whatever it holds, and its line in the launch's list says it was too large to check (`Search.largest`): the files these names give are small, the largest of 86 measured in view 6 KB, and a room could plant a sparse one of a terabyte for the next launch to hash. Which worktree holds a file doesn't matter, so a repository moved on disk, whose worktrees git still lists where they were, is checked as any other, as is a file beside a bare repository's own files. The store rather than a worktree's commit or what git ignores: git's record of where each worktree is goes stale when a repository moves, and a room writes the `.gitignore` files, `info/exclude` and the index git decides what it ignores from, so `git add -f .env` in one launch would leave the next launch's `.env` in view.
- **A store that reads objects from elsewhere** has every file in its repository hidden. Through `objects/info/alternates`, or a link under `objects/`, both of which a room writes, git would answer from another repository's store, which the room doesn't mount, and a file whose content only that store holds would show (`docs/field-notes.md`, *Files with a secret's name*). It's the look a push or fetch makes first (`docs/credentials.md`, *Running git on the host*), with the same gap: a room running on the repository could add alternates or a link between the look and git's answer.
- **Patterns and nested repositories.** A pattern is matched from the root of the worktree holding the file: the nearest directory holding a `.git` file or directory, else the tree, wherever the worktree has moved. In a repository nested in the tree's own, a git directory other than the tree's (a `HEAD` file, `objects/` and `refs/`) and, where it's a `.git`, the clone holding it, such as a clone or a bare copy under a worktree's `tmp/`, every file with a secret's name is hidden; a `.git` directory that isn't one, which git wouldn't read either, nests nothing. Checking a nested repository's files would mean host git reading a git directory the room wrote whole, its `config` among it (#208's class). A linked worktree of another repository can't be told from one of the tree's own once moved, since its `.git` file names where it was, so its files are checked against the tree's store, which the room reads anyway. git runs pinned to each repository's common directory, never through a worktree's `.git` file, which a room writes.
- **Where.** The whole of what the room mounts for the project, its git directory with every worktree, and each related repository mounted, whole; not what's lent (`--mount`, `--mount-rw`, `/lent`), which the operator lends knowing what's in it.
- **Not looked in:** what package managers install, `node_modules/`, `site-packages/` and `dist-packages/`, whose keys and certificates are packages' own (each of 95 `cacert.pem` measured in environments was `certifi`'s), and the hidden `.venv`. By name rather than by a `pyvenv.cfg` in the directory, which a room could plant beside a secret to have the next launch pass over it. A directory lup can't list is hidden whole, and said, since a room could `chmod` one to the same end.
- **How.** As `.venv` is: the launch's empty file mounted read-only at its path, so the room reads it as empty, and writing, removing or moving it fails. `land`'s cleanup leaves a worktree holding one whole, as it does one with a `.venv`. A link isn't hidden, since podman would follow it.
- **When, and what's said.** After the image and the settings, just before the container starts, so a room already running on the repository has the least time to move a secret where the search didn't look; one moved between the search and the start is the gap left. The launch names each file it hides in one list.
- **What a room writes at a secret's path** is left: a room's own `.env` exposes nothing of the host's, and removing what appeared, as the `.venv` rule does, could remove one the operator wrote on the host meanwhile. The host's tools read such a file, a dev server or docker compose, so as the launch ends each file with a secret's name that appeared or changed in the repository's tree is named, for the operator to look at first. A write to one through a file tool asks, as a protected path's does (`docs/judging-writes.md`, *What each change gets*). The room's own `.env` is hidden from the next launch in turn, unless the room put its content in the store, by staging or committing it; one it did is left out of the list as the launch ends too.
- **Its cost** grows with the files in the trees searched, the related repositories' above all: lup's own tree, 206k files, takes 0.5 s; on a machine relating twelve repositories, 1.86M files took 4.6 s more, 3.1 s of it one repository's 1.4M. Asking the stores adds 0.16 s over those twelve, most of it the look for alternates and links (`docs/field-notes.md`, *Files with a secret's name*).
- **Not covered:** a secret in a file named otherwise, such as a token in `.mcp.json` or in a remote's URL in git's `config`, and one behind a link.

**The CLIs** (`launch/clis.py`). Each launch asks the vendor's own release channel for the latest version, downloads it into lup's cache with its published checksum checked, and mounts it read-only, so the latest runs whatever the host has installed; offline, the version cached runs, and the launch says so. Never baked into the image: the first lup's CLI layer, 1 GB, was rebuilt most days. Each channel is spelled in its runtime's adapter (`Channel`). The vendors' signatures aren't checked yet (#63). The cache keeps each runtime's current version and the one before, for a session still running.

**A home of the rooms' own** (`lup.sessions.terminal.RuntimeHome`; `launch/homes.py`; each runtime's `terminal.py` in `lup`). A room never mounts the operator's own `~/.claude` or `~/.codex`: through that mount a package in a room could read the login and every project's transcripts, and write what a session on the host acts on, hooks, skills, plugins and the shell snapshots a running Claude Code session runs before each command.
- **The runtime's directory is the launch's own.** Its variable (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`) names `<launch>/runtime-home`, made fresh, mounted read-write at its path, and removed with the launch. Everything the runtime reads there as configuration or state is the launch's: what's copied in from the layers, the settings, the state file, and whatever else it finds or writes there, Claude Code's `.config.json`, which its 2.1.311 binary prefers over `.claude.json`, Codex's `.env`, whose variables Codex 0.162.0 sets in every command it runs, its SQLite state and its shell snapshots among them (`docs/field-notes.md`, *A home of the rooms' own*). So nothing a room writes there reaches another room, and nothing reaches the host.
- **History is shared, by name.** Only what its adapter names as history is a link from that directory into the home the rooms share: on Claude Code `projects/` (the conversations' records), `file-history/`, `tasks/`, `todos/`, `plans/`, `paste-cache/` and `history.jsonl`; on Codex `sessions/`, `archived_sessions/`, `history.jsonl` and `session_index.jsonl`. The home is the project's, `~/.local/share/lup/homes/projects/<a digest of the git directory>/<runtime>/`, shared by its worktrees and its profiles, so `--resume` and the picker find what any room of the project ran; or, for a profile with `rooms_home="global"`, the one every project shares, `~/.local/share/lup/homes/shared/<runtime>/`. One rule places it (`Layout.room_home`). A launch making one says so; a session from before it resumes in a room once it's moved there, which a launch offers first (*Moving over*). **Rooms sharing a home read and rewrite each other's history:** every room of the project, whichever profile it runs on and so whichever account; and on a shared home, every project's room on such a profile. A package in one room can read another's conversations and change what one resumes into. **Auto memory stays with the launch:** where it's on, Claude Code keeps its notes in `projects/<folder>/memory/` by default and loads their `MEMORY.md` into every new session of the project, not only one resumed, so a note a room wrote there would steer every later room unseen, on any profile and account. lup's settings file places it in the launch's own directory instead (`autoMemoryDirectory`, `ClaudeHome.memory`), above the home's user settings, so a person's own `autoMemoryDirectory` can't place it back there, and a project's isn't read; its notes go with the launch, as Codex's memories, kept in the launch's own home, do (`docs/field-notes.md`, *Auto memory on a home of the rooms' own*).
- **Resuming.** A conversation launched on a home resumes in a room, from the host's terminal with `lup-dev launch <runtime> --resume`; one from before the home, kept in the operator's own directory, once it's moved there, which the launch offers before its room starts (*Moving over*). A host session reads a room's conversation as a document, with `lup-dev transcripts show`.
- **Apart from what rooms write.** The home and the launch's directory are mounted alone, and neither sits under a directory a room writes, the project's rooms' own among them. A mount point can't be moved from inside a room, but a directory above one can, as `mv .git .git-real` did under the tree's mount (*The mounts*), and the host follows a link in a mount's source: a home under the rooms' directory would let a running room move the directory holding it aside and leave a link to the operator's `~/.claude`, which the next launch would mount read-write. The launch makes each item of the history in the home where it isn't, walking from the home and replacing any link a room left on the way (`lup.rooms.homes`).
- **What the host reads of it.** A launched session's record is read in the home its launch registered alone (`Register.home`), as the host service kept it from the launch it first heard the session on, and any other session's in the operator's own directory alone, so a room can't have a record it planted read under another's session id (`lup_dev.host.homes`). A session whose record the operator's own directory holds is never kept as a launch's, though a room's hook names it first; where lup itself moves or copies a session's record into a home, it keeps that home as it does. A path a hook's payload names, inside the own directory of the launch whose room ran the hook, the one the host heard it on, is read as the same place in that launch's home (`Register.own`), never through the links there, which the room can repoint; any other path a payload names isn't read, one under another launch's own directory among them. Every record is read from what was opened, checked to be a file inside its home, without waiting on a pipe, and a line too long to hold is read past (`lup.rooms.homes.opened`, `lines`). The dashboard's drawer, an item's moment, the queue a held call ends on and the subagents' names read so; `Transcripts` keeps each home's records apart, saying whose home each was kept from (`packages/lup-transcripts/README.md`, *Keeping*).
- **The configuration's layers.** The operator's own, unless the profile sets `operator_configuration=False`, then the profile's, `~/.config/lup/profiles/<name>/<runtime>/`, laid out as the runtime's own directory: data the host copies, never runs. Copied on Claude Code: `CLAUDE.md`, `rules/`, `skills/`, `commands/`, `agents/`, `output-styles/`, `workflows/`, `plugins/` without its `data/`, `keybindings.json` and `themes/`; on Codex: `AGENTS.md`, `AGENTS.override.md`, `rules/`, `prompts/`, each of Codex's own profiles, `<name>.config.toml`, so `--profile` after `--` finds it, and the operator's `~/.agents/skills`, read-only in the room's home. A copy keeps a link as a link, never following it on the host, and a later layer never writes through one an earlier layer's copy left. The settings file, `settings.json` or `config.toml`, is merged from each layer with what would hand the room's code a credential or run a command in it left out of each (`lup.sessions.configuration`), and a URL's user and password, and each parameter of its query named like a credential or holding one, taken out of what's kept. The launch says what it left out, by the key or the list's entry it was at, never its value where that changed since the profile's last launch said it, a line for what would run a command and one for the rest.
- **What of your configuration doesn't reach a room, and why.** A room runs a malicious package's code with your configuration in reach, so what would hand that code a credential, or run a command set up for your machine with what the room can read, stays out:
  - your `env` (Claude Code's settings), and Codex's `shell_environment_policy.set`: variables, often credentials, that would be set in the room. Preferences set there, `CLAUDE_CODE_DISABLE_1M_CONTEXT` among them, don't apply in rooms either; a profile will declare the variables its rooms get;
  - credential helpers (`apiKeyHelper`, `awsAuthRefresh`, `awsCredentialExport`, `otelHeadersHelper`), any key named like a credential at any depth (a token, a secret, a password, an API key, a bearer, a cookie), the headers of Codex's `otel` exporters and its model providers' `http_headers`, and the user and password in any URL, and each of its query's parameters named like a credential;
  - any value, or entry of a list, holding a credential by its shape, whatever its key: a token in the shape its vendor gives it (`sk-ant-`, `ghp_`, `glpat-`, `xoxb-`, `AKIA` and the rest of `SHAPES`, each with where its shape is documented), a JSON Web Token, or `Bearer` or `Basic` followed by a long word, so a permission rule whose command carries a login is left out whole. **Not covered:** a secret with no shape of its own under a key named otherwise, such as 32 hex digits in a header of a name lup doesn't know, and a `Basic` credential whose base64 breaks at a `+` or `/` within its first 16 characters, which reach the room;
  - your hooks and status line, and any other setting whose value is a command (Claude Code's `fileSuggestion`, Codex's `notify`, a provider's `auth` command): they were set up for your host, and rooms run lup's own hooks;
  - your MCP servers: set up for the host, their `env` often holding a credential, and lup gives a room its own server alone;
  - plugins' `data/`, and `agent-memory/`, your subagents' memories, which hold what they learnt in every project;
  - anything that's a link where an item belongs, since lup never follows one on the host.
  Your plugins are copied, but their install records name paths under your `~/.claude`, which a room doesn't have, so they don't load in a room yet. Skills, agents, commands, `CLAUDE.md`, rules, output styles, keybindings and themes reach it as they are.
- **Settings are the launch's own, preferences carried back.** The merged settings are a file of the launch's, so `/model` and `/theme` save in a room and no room changes another's. At the launch's end, each preference of an allowlist the session changed (on Claude Code the model, effort, output style, theme, editor mode and thinking; on Codex the model, its efforts and verbosity, the personality and the theme) is written into the profile's own file, the rest of it kept, and said; never into `~/.claude` or `~/.codex`.
- **The login** is the account's file (*Accounts and profiles*), `.credentials.json` or `auth.json`, mounted alone where the runtime reads it, read-write; Claude Code refuses a login file that's a link, so it's a mount. The runtime's own sign-in in the room writes it through the mount, measured for Claude Code on the host (`docs/field-notes.md`, *Claude Code's sign-in through a single-file mount*) and, for Codex's save, in a room; Codex's ChatGPT sign-in through the mount is still to be measured on the host. Every room on the account shares the one login: a sign-in in one is every room's, which the launch says the first time it sees the account's login change under it. A runtime's own logout can't remove the file through the mount, so `lup-dev account logout` empties it. Codex is given `cli_auth_credentials_store="file"`, so no keyring is reached for. The cost of one rotating login: no lock spans the rooms, so two refreshing at once can race, and on Codex the loser's token is marked spent (`refresh_token_reused`; `docs/field-notes.md`, *Codex 0.162.1: launching a session*), a gap lup leaves open.
- **What goes with the launch:** besides the configuration, whatever the runtime keeps off the history's list, Claude Code's `/usage` totals and a plugin or skill installed in a room among it, and Codex's SQLite state, which holds its goals and queued input: shared, one room could leave another input to act on. Codex resumes a thread by its id from the shared rollouts; whether its picker lists another launch's thread is to be measured.

**Moving over** (`lup_dev/migration.py`; each adapter's check, `lup_dev/host/written.py`). Before rooms had homes of their own, every room mounted the operator's `~/.claude`, and a Codex room `~/.codex`, read-write, so every session launched then is recorded there, and every record there was written where any room could write. `lup-dev account migrate`, the operator's own in their terminal in the repository, refused inside an agent's session and on a repository nothing is approved for, moves them, as a launch offers to for its runtime before its room starts:
- **What moves.** Every record of the repository's directories, its git directory and each worktree (`Records.kept`), whoever wrote it, into the history the project's rooms share, at the same place there (`projects/<folder>/`, `file-history/<session>/`, `sessions/…`), or with `--shared` the history every project shares: none can be certified as the host's, and moving them all means the host never resumes one a room doctored. It keeps that home for each session it moved (`lup_dev.host.homes.kept`), so the host reads the session there, as a room resuming it has it, and a room of another project naming the session first can't claim it; a session whose record stays in the operator's directory keeps none. Records of other directories stay, said once with that caveat. A Claude Code folder whose sessions say they ran in a directory it isn't named for is no directory's, and moves nowhere (`filed`, `adapters/claude.py`): a line naming the repository, written into another directory's folder, would otherwise have its sessions taken for the repository's. `Transcripts`' copies are the module's own.
- **What of the shared history stays.** Of what else rooms share by name, what's one file for every project, `history.jsonl` (the prompts a session offers again, on both runtimes) and Codex's `session_index.jsonl` (its threads' names), stays whole: moving the repository's part would mean rewriting the operator's file line by line. So do Claude Code's `tasks/` and `todos/`, a session's task lists, which Claude Code empties as a session ends (`docs/field-notes.md`, *A session's record*) and which the drawer replays from the record itself; `plans/` and `paste-cache/`, named by neither a session nor a directory; and Codex's `archived_sessions/`, which a rollout leaves for `sessions/` when it's unarchived, and a later migration moves. In a room, sessions from before come without their old prompts to recall and, on Codex, their names.
- **A dry run first.** Without `--move` it says each record that would move, with its files and size, and what would be left and why, changing nothing. `--move` refuses while a launch of the repository runs, its launcher holding its lock, since its session would go on writing where their record was; a session on the host isn't seen, so it says to end those too.
- **How it moves.** Reached a directory at a time by descriptor, from the operator's directory and from the home, never through a link a room left on the way. A file moves as a second name in the home, then its first removed, so it's the same file, its content, mode and times kept, and a copy `Transcripts` holds of it still matches it; where the home is on another filesystem, or the file isn't the operator's to link, a copy keeping its mode and times. A link aimed inside what moves is made again aimed at its place in the home, as Claude Code links a resumed session's subagents to the first session's records; any other is left, never followed. What the home holds already stays, and so does what would go there; so does a pipe. Nothing is removed that isn't moved: a name once the home holds what it named, a directory once empty. A move stopped between a file's two names finishes at the next.
- **The check.** lup can't tell what a room wrote in the operator's directories from what they did, so for each runtime it says what a host session acts on there as it stands, quoted for the operator to recognize: on Claude Code what `settings.json` runs, sets and lets a session do without asking, `CLAUDE.md`, the skills and what else a session loads, the plugins turned on, the shell snapshots and session environments a session runs before each command, the state of the supervisor of background sessions, the mods sessions made, and the folders whose name and sessions disagree; on Codex what `config.toml` and its profiles run (`notify`, the MCP servers), set, send requests to and let a session do without asking, `hooks.json`, `AGENTS.md`, `rules/` and what else it loads, and the shell snapshots and `tmp/` helpers it runs before each command. It flags only what reads as planted whoever wrote it: a command naming a directory rooms write, and a link where the runtime makes none. What it can't check, it says how to clear; it changes nothing.
- **Logins.** Each account signs in at its first launch, in the room, with a login of its own: no host login is moved into one. The host's own, `~/.claude/.credentials.json` or `~/.codex/auth.json`, was readable by every room: logging out and in again on the host replaces the refresh token they could read, `/logout` then `/login` in a Claude Code session there, `codex logout` then `codex login`, which the migration says where it finds one. Whether a logout revokes the old token with the provider isn't documented.
- **At launch** (`lup_dev.launch.moving`). Before its room starts, a launch walks the operator through the move for its runtime, on both runtimes, so `lup-dev launch claude --resume <id>` carries them over:
  - Where the operator's directory holds records of the repository's directories that would move, it says how many sessions and how much, from the dry run, and that the session it resumes is among them where it is (`Adapter.resumed`: `--resume <id>` on Claude Code, `resume <id>` on Codex). It asks once, `Move them into the rooms' home now? [Y/n]`, Enter answering yes, and asks to end any host session running in the repository first, since `--move` can't see one.
  - On a yes it moves them, as `--move` does, before anything registers. It then says what the check found to act on, and how to replace the host login, the first time a launch says it (`ToldLayout.host_login`): logging the host's own CLI out and in is the operator's, outside lup. It waits for Enter, so that's read before the room takes the terminal. Where nothing needs acting on, it says so in a line and doesn't wait.
  - On a no it goes on, saying a session left there doesn't resume in a room, and that the one it resumes won't. The next launch asks again.
  - With another launch of the repository running, it names each to end, then launch again, and goes on without moving: a launch waiting on others would hang. With no terminal it says how to move them, and goes on.
  - A move, by a launch or `--move`, marks the runtime's records of the repository moved (`ToldLayout.migrated`), and no launch offers it again. Rooms on homes don't write the operator's directory, so a host session run in the repository after the move is the host's, and stays there unless `lup-dev account migrate --move` moves it.
  - The room's own first sign-in is the runtime's prompt in the room, for the account's login, apart from the host's (*Accounts and profiles*).

**Related repositories.** A person names, in their own layer, the other repositories their sessions may read (`Repository`; `docs/declaration.md`, *A person's own layer*). Each is mounted whole and read-only at its host path, its own `config` and `hooks/` with it, and the guidance lists it with what it is, where, and its GitHub identity, which `read_issue` and `find_issues` take as `repository`. One missing on the host is said once and marked missing; one overlapping the room's own mounts is refused, since mounted read-only it would sit over or under what the room writes. Mounted whole means its untracked files can be read from the room, all but those with a secret's name (*Files with a secret's name*): naming a repository exposes the rest of it to the room. Its sessions' records are kept with the project's, and read with `lup-dev transcripts` (`packages/lup-transcripts/README.md`, *Keeping*).

**The clipboard.** A room has no display, so the host service reaches the operator's clipboard for it (`clipboard/`). In the room, `wl-paste` and `wl-copy` are first on the `PATH`, one program under both names on the standard library alone, and the room names a Wayland display with nothing behind it, so a program choosing its clipboard by it reaches for them: Claude Code copies through `wl-copy` and pastes an image through `wl-paste` (`docs/field-notes.md`, *The clipboard*). Each is a request on `request.sock`, which the desktop's own programs answer on the host, `wl-paste` and `wl-copy` or `xclip`, one of them an optional requirement. A read past 32 MiB is refused. The cost: anything in a room can read what the operator copies, a password among it, and replace it. Codex reads the clipboard through X or Wayland's own protocol rather than a program, so it isn't reached this way.

## The settings compiled for each runtime

lup's settings reach the runtime as flags and files of the launch's own, never written into the operator's directories or the repository (`adapters/claude/terminal.py` and `adapters/codex/terminal.py` in `lup`, whose docstrings give what each rests on):

| | Claude Code | Codex |
|---|---|---|
| Where | `--settings <launch>/settings.json` with `--setting-sources user`: the home's user settings load, the operator's and the profile's layered; the repository's `.claude/`, `.mcp.json` and `CLAUDE.md` don't | `-c` overrides on the home's configuration, the operator's and the profile's layered, and `--no-daemon` |
| No prompts, since the room is the wall | `--permission-mode bypassPermissions` | `--dangerously-bypass-approvals-and-sandbox` |
| The hook | in the launch's settings | managed hooks in a mounted `/etc/codex/requirements.toml`, with `allow_managed_hooks_only` |
| lup's tools | `--mcp-config` and `--strict-mcp-config`; `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS=0`, so a held call isn't moved to the background after two minutes; lup's server loaded as a channel, `--dangerously-load-development-channels server:lup`, so what waits for an idle session is pushed to them | `mcp_servers.lup`, the only one: the operator's are left out of the home's configuration; nothing a server pushes reaches the session, a gap its adapter declares |
| Guidance | `--append-system-prompt-file`, with `--system-prompt-snapshot off` | `additional_developer_instructions` in the requirements file |

**lup's server is a channel on Claude Code,** so an idle session reads what's pushed to them as their turn's prompt, the operator's words as the operator's own (`docs/inbox.md`, *How an agent is told*). Claude Code shows "WARNING: Loading development channels" at each start, a resumed session's too: confirm "I am using this for local development"; Exit quits. A channel Claude Code doesn't load drops what's pushed: where channels aren't on for the account, an organization's `channelsEnabled` blocks them, or the session runs on a third-party provider, its startup notice says so, and the service says once that the launch took no push and wakes it through its messaging socket from then on.

**Session settings** are `Core`'s `session` (`SessionDefaults`, `catalog/room.py`), in neutral words each adapter spells where its runtime has the setting; Codex has none for the subagents' prompt cache, removing a built-in tool or idle compaction, gaps its adapter declares:
- **idle compaction off,** so a session left waiting on the operator comes back to their conversation, not to a summary made meanwhile;
- **the account's connectors off,** since they reach the operator's mail and files;
- **built-in tools removed:** those that weigh in every turn and go unused, since an interactive session carries 113 KB of built-in tool schemas, `Artifact` alone 55 KB; and the native worktree tools, since a worktree for another agent's work is lup's spawn's to make (#117);
- **auto memory off,** and **the subagents' prompt cache** at an hour.

They layer, lowest first: the runtime's default, lup's defaults, the person's own runtime settings as the home has them, then the fields some layer of the declaration sets. What can't be imposed, such as Claude Code's connectors once a person turned them off, each adapter says.

**The model and the effort are the person's own:** a declaration names none, so no `--model` is passed, and each runtime reads their choice from the home's settings, the operator's and the profile's layered, `/model`'s in a room carried back into the profile's.

## Guidance

One document, rendered at launch (`render`, `launch/guidance.py`, whose docstring has the details):
- **the selected modules' sections,** in the declaration's order, each read at the approved commit or from the package shipping it, and rendered with Jinja in its sandbox, since an agent can write a section's file and the rendering runs on the host;
- **then lup's tools,** each by its name and summary, since the runtimes defer them behind their tool search, and agents told nothing of deferred tools concluded they didn't exist (`docs/inbox.md`, *Found through tool search, listed in the guidance*); then the related repositories, and what's lent to this launch;
- **then the person's own section, `AGENTS.local.md`,** last, so it holds where it differs. It's a protected path, since git ignores it and nothing else would show the operator a change to it.

**Delivered at system level,** on both runtimes: Claude Code's `--append-system-prompt-file`, its documented route for instructions that must hold, where a `CLAUDE.md` arrives as a user message "with no guarantee of strict compliance"; Codex's managed developer instructions. The runtimes' own loading of the repository's `CLAUDE.md` and `AGENTS.md` is off, so nothing arrives twice, and Codex would cut an `AGENTS.md` past 32 KiB without a word.

**A resumed conversation runs under this launch's guidance.** By default each runtime keeps a conversation's first instructions, so a path or a mount that moved would go stale without a word. Claude Code renders the prompt afresh at every request with `--system-prompt-snapshot off`; Codex sends its managed instructions again whole at a resume where they changed (`docs/field-notes.md`, *A conversation resumed in a later launch*). What the conversation's earlier turns saw still came from their earlier launch, so `Core`'s guidance says the room holds where they disagree; telling the conversation what changed is #73.

**Codex's ceiling.** Codex refuses to start past 10,000 estimated tokens of managed instructions, at 4 bytes a token, counted with the markers it sends them between and the notice opening them at a resume, so a render past it is refused at launch, naming its size and the limit. A workspace's own managed requirements outrank the system file, so a workspace setting managed instructions of its own drops lup's.
