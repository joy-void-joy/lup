# lup's tools and the inbox

Everything between a session and the operator goes through the inbox, which the host service keeps (`inbox/`; `docs/host.md`). A session reaches it through lup's tools, served on its launch's `mcp.sock`; the operator through `lup-dev inbox` or the dashboard (`docs/dashboard.md`).

## lup's tools

| Tool | What it does |
|---|---|
| `ask` | Asks the operator: numbered decisions, each with the agent's lean, or a plain question. With `wait`, the call holds until they answer and returns the answer; without, the answer comes with a later call |
| `note` | Tells the operator an assumption, a doubt or a counterargument, and carries on: news, with no notice |
| `friction`, `how_it_went` | Says what got in the way, the moment it does; says how a piece of work went and felt, once near its end. Each reaches the operator directly, a subagent's too, and a subagent's reaches its parent as well, whole (*Parties and items*) |
| `blocked`, `stop` | Says the work can't go on; ends it by the agent's own choice. Either answer tells the agent to end its turn |
| `send` | A message of a kind (`note`, `problem`, `disagreement`, `question`) to the operator, to the conversation that spawned the agent, or to one of its own subagents, each one the operator reads (*Messages between conversations*): the general verb beside the speaking tools |
| `wait_inbox` | Holds until something reaches the agent, one of its own subagents ending among it, and returns all of it |
| `inbox` | Reads the repository's inbox, changing nothing: what's still waiting, for the operator or an agent, every item with `every`, narrowed by `since` and `until`, by `kinds` and the latest up to `limit`; one conversation's exchange (`conversation`, its subagents' with `subagents`), each item whole with `whole` (*Reading an exchange*); or any of the repository's items whole by its number, its parts with their ids, or one part alone by its id (`part`) |
| `withdraw` | Takes back a message or question the agent sent that no longer needs the operator, with its reason |
| `edit` | Changes what the agent sent the operator: a passage of its text found once, or its text whole, kept beside what it said before, its citations read again (*Editing what was sent*) |
| `judged` | Reads what the judge made of the repository's writes, and its holds, changing nothing (`docs/judging-writes.md`, *The verdict log*) |
| `land` | Merges a local branch onto the integration branch in the room, the gate run on the merge, and lands it once the operator approved each file flagged on what it lands, holding the call while they review; then cleans up after each branch it landed, and says what's still running or waiting to land (`docs/judging-writes.md`, *Landing a branch*) |
| `rename` | Names the session's launch, or a subagent, after its task (`docs/launch.md`, *Names*) |
| `read_issue`, `find_issues`, `file_issue`, `edit_issue`, `close_issue`, `reopen_issue`, `comment`, `edit_comment`, `draft_pull_request` | GitHub, through the operator's login on the host (`docs/credentials.md`, *GitHub through `gh`*) |

- **Who serves which:** the inbox's tools are the core's (`InboxTools`, `inbox/tools.py`), and so are `judged` (`JudgeTools`, `policy/tools.py`) and `land` (`LandingTools`, `policy/landing.py`), which the inbox, below the judge in `lup_dev`'s layers, can't import; `rename` is the host service's own; the GitHub tools are the `GitHub` module's, served from the launch's process of its repository's approved copy (`docs/host.md`, *Each launch's judge and modules*).
- **The speaking tools are the library's** (`lup.tools.speaking`): `blocked`, `stop`, `note`, `friction` and `how_it_went` have the same names and inputs on an ask from code, so an agent's habit carries between the two. In a launched session whoever asked is the operator.
- **`friction` and `how_it_went` each take one text,** in the agent's own words, which the operator's inbox and the dashboard show as written: they're for what's present for the agent at the moment, how the work felt among it, and labelled parts would make them a form, shaping what's said to fit.
- **`wait_inbox` isn't called `wait`,** since on a Codex model in code mode Codex has a `wait` tool of its own, and two tools of one name invite the wrong call.
- **What `judged` and `inbox` list is sized to be read whole, and the call sets the size:** by default the latest 50 verdicts and 20 holds of each state (`limit`, `holds_limit`), and the latest 50 items a line each, or 10 whole (`limit`), never splitting a moment; `since` and `until`, a time or a duration back from now, narrow each alike (`lup_dev/listing.py`, which `lup-dev inbox` shares). Where an answer leaves earlier ones out, its last line says how many, the `until` that reads them, and the limit that lists them all; where it lists what waits alone, it counts the rest, which `every` lists. lup's own log, listed whole after ten days, was 785,000 characters, and its inbox's 271 items, 72,499, past what a tool's result holds.
- **Results are one text block:** Codex shows the model only a result's `structuredContent` where it has one, and Claude Code reads `content`, so a result with both would read differently on each. A large result is the runtime's to keep for now (#164).

**Found through tool search, listed in the guidance.** Each runtime defers an MCP server's tools behind its tool search, Codex where the model supports it (`docs/field-notes.md`, *MCP in a launched session*), so a tool's description can be as long as it needs without costing every request its context: the first lup's 14 coordination tools, always loaded, carried about 10 KB of descriptions (its `coordination/tools.py` and `peer_tools.py`). But agents told nothing of deferred tools concluded they didn't exist, so every session's guidance lists each tool by its name and summary (`listed`, `launch/guidance.py`), and a subagent that doesn't read the guidance is told them once, at its first hook that isn't its turn's end (`introduction`, `host/service.py`), with a line that some subagent types have none of them (#108). A tool's summary is its docstring's first line, 50 characters at most, which `@lup_tool` checks (`ToolSpec.summary`), so the docstring is the one source.

## The operator's face

```
lup-dev inbox                         what's waiting for you, oldest first; --since, --until
                                      and --limit narrow it as the `inbox` tool's fields do;
                                      --conversation, --subagents, --kind, --whole and --every
                                      read your own exchange as the tool reads the repository's
lup-dev inbox show <number>           one item whole; --context its moment, --diff an approval's diff
lup-dev inbox answer <number>         a question: each decision in turn, then a comment;
                                      a conversation's message: your reply; an approval: yes or no
lup-dev inbox done <number>           a message read, off the list; a flagged write approved
lup-dev inbox send <to> <text>        a message to a launch's session, or to a subagent by its path
```

- **Answering** takes each numbered decision in turn, "leaning", "undecided" or "leave open", typed: an empty line asks again, so going with the agent's lean is said, never assumed. `--leaning 1 --undecided 2 --leave-open 3 --comment …` answers without prompts, and `--approve` or `--decline` an approval.
- **A review** is the dashboard's reply covering several items at once, sent whole to each conversation with a comment on its items, a question among them, or a message to it; one whose items were only marked read hears nothing (`docs/dashboard.md`, *The review*).
- **Replying** to a conversation's message, or to a write of its that landed flagged, is a note for that conversation, naming the item it replies to with its first line.
- **A desktop notice** comes with an item waiting on the operator, through `notify-send`, an optional requirement of the host; news and flags raise none.
- **Each command is a request on the host's control socket.** Listing and `show` only read, so an agent's session runs them too: on the host, over the whole inbox, though it never starts the service there (`docs/host.md`, *Using it*); in a room, on its launch's request socket, over its repository's items alone (`docs/host.md`, *Reading from a room*). The rest act for the operator, so they refuse inside an agent's session, as `trust` does, and a room never reaches them: the store isn't mounted.

## Reading an exchange

A session that needs what an earlier one said and was told reads it from the inbox, where it already is: what the session sent the operator, its turns' last words among them, and their reviews, answers and replies (`inbox/reading.py`). The agents' `inbox` tool and `lup-dev inbox` read through one `Reader`, so they can't drift apart; the tool reads every party's items of the repository, and the command the operator's own exchange, the items they sent or were sent, what waits for them unless `--every`.
- **`conversation`** narrows to one conversation's items, those it sent and was sent, every repository's on the host and the room's own in a room. It's named by its path (`flow-review/explore-auth`), its own name, or its runtime's id or the id's start. A session's name is its launch's as lup kept it for the session (`SessionNames`, `host/names.py`), a subagent's as its whereabouts last heard it (`Whereabouts.name`), so it's read by its name once its launch has ended, or, from before they kept it, as its end was told to its parent. Names repeat over time, a branch's above all, so where one names several conversations the one last heard is read, and the answer says so first, naming the others by id and when each was last heard: a reader who never reaches an answer's last line would take one session for another. Lines then name each conversation by its path, the heading giving the ids; the operator's own listing names each by both.
- **`subagents`** adds the items of each subagent below it: every subagent of a session's own, each a subagent spawned and theirs, as their whereabouts keep the conversation that spawned each.
- **`kinds`** narrows to items of those kinds, as a tag's `kind` names them (`ItemKind`, `inbox/delivery.py`), `turn's end` told apart from a note.
- **`whole`** reads each item whole under its heading: one a conversation sent as it wrote it, any other as it was told to whom it was for, a review's words to other agents left out. The operator's words on one of a conversation's items come under it, from each of their items addressed to the conversation, each part with its id, then any reply copies before kept on them, and a turn's end says which of their items it answers (`answers`), so an exchange reads as one thread; where their item is listed too, it says what it said on each item is told under that item. What's on an item that isn't listed stays in its own place, so nothing is left out by where it's told.
- **`lup-dev transcripts show`** gives what the operator typed in a session's terminal, its record's alone; where lup's inbox holds the session's exchange, its last line says how many items, and the `lup-dev inbox --conversation` that reads them.

## A new main session's bearings

A session's own conversation starting with its context empty, started or cleared on either runtime (`Heard.fresh`), is told once, beside its name, where its repository stands (`inbox/bearings.py`, asked through `Bearings`, `host/service.py`). A long main session ends heavy and a fresh one takes over, and the next one had to rebuild what was open from raw records. A resume, a compaction, a fork or a subagent is told nothing, and nothing of it is told again; each line says where to read more:
- **Not landed:** each branch with commits on no remote branch, or whose worktree holds uncommitted changes, with its worktree, its commits there and the last, measured against the remote's integration branch (`LUP_INTEGRATION_BRANCH` on `origin`, as `land` lands it), so a branch the local integration branch merged while its landing waits is still listed.
- **Running beside it:** where more than one other main conversation of the repository runs, each by its name, its id and its worktree, as the service serves them.
- **Waiting for the operator:** the last main session's items and its subagents' first, then the rest: what waits on the operator a line each, news counted by kind, flagged writes by the landing each holds.
- **Landed** on the remote's integration branch since the last main session started, its first-parent history, saying whether that session still runs or when it was last heard, and the `inbox` call that reads its exchange (*Reading an exchange*). The last main session is the latest main conversation of the repository whose whereabouts the inbox keeps, its start when lup first heard it in its launch.

## Parties and items

- **The parties:** the operator, and each conversation of each session, its main one or a subagent. A conversation is keyed by its runtime, its session and its own id within a repository, not by the launch it runs in, so a session resumed in a later launch finds what waited for it.
- **An item** has a number, one sequence per user, cited `@12` wherever lup names it (`cited`, `inbox/store.py`; the page's `cited`, `comments.ts`), which nobody takes for a GitHub issue's `#12`; a command takes it cited or bare, `lup-dev inbox answer @12` or `12`. It has a sender and a recipient, the worktree it's from, when it was made, and its state: waiting, told, answered, done, decided, superseded or withdrawn. It's one of: a message of its kind, the operator's copy of one a conversation sent another (`Message.to`), one the operator sent from reading a conversation holding each passage they replied to with their reply (`Message.passages`); a friction, how it went or a stop; a subagent's end, for its parent; lup's word to a conversation on citations of its that named no passage (`Unresolved`); a question; an answer; a review; trust's approval (`docs/trust.md`); a held change, the judge's or a landing's; a flagged write (`docs/judging-writes.md`, *Asking the operator*, *Landing a branch*).
- **Parts and ids.** An item's text has parts, cited `@414.3` (`PartId`, `inbox/parts.py`): the Markdown blocks of the text, numbered from 1 within the item, a paragraph, a heading, a code block, a quote, a rule, and each item of a list and each row of a table, since a list or a table is usually the whole message and a comment is on one of its lines; read by markdown-it with the table extension the dashboard's parser reads too. The operator's own words are parts of their items as well (`spoken`, `inbox/threads.py`): first what they said on an agent's words (`anchors`), a review's comments, in its order, those on other agents' items counted so the numbers hold for every agent it reaches, the comment a reply to a note carries, each passage's reply in a message sent from reading a conversation, an answer's rulings, then its comment; then the rest, a review's messages and remarks, a message's words on the whole, numbered after any reply copies before kept on the item, so every id those copies gave keeps its meaning. An anchor into an item is then small and stays put: a review quotes a passage by the part it starts in and a cue of its first line, an agent cites the operator's words by their id (*Citing the operator's words*), and `inbox` reads one part alone. An id is a model of two numbers, read by a parser that refuses anything else.
- **Its kind's rank** (`ranked`, `inbox/store.py`), the one place each kind's is said: what waits on the operator first, raising a notice; news next (a note, a friction, how it went, a stop, a turn's last words, a subagent's end); flags last.
- **What an approval, a held change or a flagged write changes** is kept beside it: its whole diff, and each file whole before and after, a binary one by its size, which the dashboard shows. Nothing is cut.
- **An item for a conversation that has ended** goes to its session's main conversation, saying whose it was: a subagent that asked without waiting is usually gone by the time the operator answers.
- **A subagent's parent hears of it.** Each conversation's whereabouts keep the conversation that spawned it (`Whereabouts.parent`), as the runtime recorded the spawn (`docs/launch.md`, *Names*); a subagent's subagent has its own parent, not its session. When a subagent's end is let through, its parent gets a subagent's end (`Ended`): which subagent, by its runtime's id and its name, and whether it ended its turn, was stopped, or failed on an error from the model's API, by the error's kind (`rate_limit`), which says whether trying again makes sense. On Claude Code a failed turn runs `StopFailure` in place of `SubagentStop` (`docs/field-notes.md`, *A subagent's end*). Its last message comes with it only where the runtime doesn't hand it to the parent itself: Claude Code does, in its task notification, a failure's error among it; Codex does for a subagent with a path, spawned by its second `spawn_agent`, and not for one from its first, the default (`docs/field-notes.md`, *A subagent's end*). A subagent's `friction` and `how_it_went` reach its parent too, whole, as a copy of the operator's item, so it can file what got in the way or learn its brief misled. The runtime's own agents (Claude Code's prompt suggestions, `/btw`) have no parent: no type and no spawn's record.
- **Messages between conversations.** `send` takes `to`: `operator`, `parent`, or one of the agent's own subagents (not their subagents) by its own name, its path (`dev/explore-auth`) or its runtime's id, as `inbox` reads them (*Reading an exchange*); the id since a subagent that renamed itself is known to its parent's runtime by its spawn's name and id alone. A message to a conversation is an item for it, told as the operator's are (*How an agent is told*), and not quiet, as a subagent's end is: it's meant to change the other's work as early as it can, so it holds a turn's end once and wakes an idle main conversation. The operator reads a copy, from its sender, saying whom it went to (`Message.to`), news whatever its kind, since it waits on its recipient: a comment or a reply on it reaches its sender, and neither it nor the message is withdrawn. `send`'s answer says how it'll be told, never that it was read. One whom nothing would read is refused, saying why, rather than kept: no parent, a conversation not the agent's own, or a subagent that ended (`SubagentStop`), saying when. Resumed, it's heard again and reached: Claude Code resumes a subagent under the same id (`docs/field-notes.md`, *A subagent's end*), and Codex's resume isn't checked. A parent waiting on a foreground subagent's call (Claude Code's `Agent` without `run_in_background`, or Codex's own wait) runs no hook until that call returns, so it hears its worker's messages beside the call's result: they arrive early from a background worker, or to a parent between calls or in `wait_inbox`.
- **What isn't heard:** a subagent the runtime reports no end for (on Codex, one stopped or failing, a gap its adapter declares), and a background command, which no hook reports at all.
- **Kept on the host** (`$XDG_STATE_HOME/lup/inbox/`), one file per item, written whole. The service is the only writer, and no room mounts it: the first lup's sessions approved their own questions by writing a store they could reach, and its one message log, folded at every read, once lost 121 messages to its trimming.

## How an agent is told

Every item waiting for a conversation is told together, oldest first, by whichever of these comes first (`inbox/delivery.py`), but for a quiet one, which never holds a turn's end nor wakes an idle session:
- **at its next call,** in the hook's answer as `additionalContext`, which Claude Code adds to the model's context beside the call's result, and Codex as a developer message. A call to one of lup's own tools isn't told at its start: told beside `wait_inbox`, an item would reach the model only once the held call returned, and the results of `wait_inbox` and `ask` with `wait` are the items themselves; what waits then goes out at the call's end;
- **at its turn's end,** where some that aren't quiet are still waiting: the hook holds the end once, telling them, which keeps the conversation going. On Claude Code they're `additionalContext`, which reaches the model as the hook's additional context in a system reminder, not labelled an error as a block's reason is; Codex's turn's end takes no `additionalContext`, so there they're a block's reason (`docs/field-notes.md`, *A turn's end told through `additionalContext`*). A turn that ends on an error from the model's API holds nothing, since Claude Code reads none of `StopFailure`'s answer, and leaves the session idle;
- **when it calls `wait_inbox`,** or `ask` with `wait`;
- **when its session starts or resumes,** a session's own conversation starting anew told its bearings first (*A new main session's bearings*);
- **at its turn's start,** beside the prompt it starts on (`UserPromptSubmit` on both runtimes), so the operator typing in its terminal brings what waits with what they typed;
- **when it's idle,** for an item the operator's own act made, or a message one of its subagents sent it, arriving while the session is idle. On Claude Code the items themselves, each whole as its tag, are pushed through lup's tool server as a channel's message (`Delivery.pushed`): the session starts its turn on them inside `<channel source="lup" wake="…">`, read as its prompt with no line saying another session sent them, and no `wait_inbox`. The push is taken when that turn's start carries its token, counting them told, and until then no hook tells them. Where none does within 30 seconds, Claude Code didn't load lup's server as a channel: they're told as anything waiting is, the service says so once, and the launch is woken through its messaging socket from then on, by a doorbell that says each item's number, kind and sender and that `wait_inbox` reads them; the items never go through that socket, since Claude Code frames what arrives there as another session's message (`docs/field-notes.md`, *Piece 2, live*). Only an idle session is pushed to, since Claude Code frames a channel's message taken mid-turn as "NOT from your user" (`docs/field-notes.md`, *Channels*). Codex has no way in, a gap its adapter declares: the item waits for the session's next turn, told beside what's typed in its terminal.

**Quiet items** (`Item.quiet`) are a subagent's news for its parent: its end, and its `friction` and `how_it_went`. They're told at the parent's next call, its turn's or session's start, or by `wait_inbox`, which returns on them, but they never hold its turn's end nor wake it idle: its runtime wakes an idle parent for its subagent's end already, so each end would otherwise cost the parent a turn of its own, and a note for the operator with it. Told beside an item that holds an end or wakes the session, they go with it.

**Told once.** An item is told when it's written into a hook's answer or a held call's result, or carried by a push its session takes, and never again (`DESIGN.md`, *Keeping the operator in the loop*):
- **too long for a hook** (past 10,000 bytes, which Claude Code would save to a file that Claude "can read" but "Claude Code doesn't ask it to"), it's announced there instead, who sent it and its size, and waits for `wait_inbox`, which returns it whole. Nothing is cut;
- **a held call whose turn ended** while it held, as a Codex model in code mode may, returns saying the items come at the next call;
- **a hook gone before its answer was written** puts back as waiting what it would have told.

**As tags.** Each item is told as one tag (`Delivery.tagged`, written by `inbox/tags.py`), saying first what it is, its number and whom it's from, so a quote, the operator's reply to it and their comment on a whole item can't be taken for one another; what it quotes of the agent's own words it points at rather than repeats, since a review that repeated everything the agent said was found "very long" by the end of a session (*Parts and ids*):

```
<review item="546" from="operator" covers="414 416 386 387 388">
<message id="546.3">…the operator's message to you…</message>
<on item="414" kind="note">
<quote part="414.3">…the first line of the passage they selected…</quote>
<reply id="546.1">…their reply to it…</reply>
</on>
<on item="416" kind="question">
<opening>…its first line…</opening>
<comment id="546.2">…their comment on the whole item…</comment>
</on>
<read items="386 387 388"/>
<context>
What the operator said in the same reply on other agents' items and to other agents: not yours to act on, unless it says so.
<on item="417" kind="friction" from="claude session 3a2d…" worktree="…"><quote part="417.1">…</quote><reply>…</reply></on>
<message to="claude session 77e1…" worktree="…">…</message>
</context>
</review>
```

- A quote names the part the passage starts in and is cut to a cue, its first line shortened to 80 characters at a word's end, `…` saying where (`cue`, `inbox/threads.py`): the agent has its own words in its context, and the id finds the rest (`inbox` with `part`). The first line alone saved little, since a passage is usually a whole paragraph, one line of the source however long; over three sessions' reviews the cue saved a third to a half of each. A passage no part holds, as a changed file's lines, is quoted whole. An item they quoted has no `<opening>`; one they commented on whole keeps a one-line opening. Items only marked read are one `<read>`. The context names each other item, its kind and its sender, and carries the operator's words there, never the other item's text.
- Each `<reply>` and `<comment>` of the agent's own carries the id of its part of the review, and so do its `<message>` and each of its `<remark>`s, which a citation of the operator's words names (*Citing the operator's words*); the context's carry none, being nobody's to answer. A comment copies before kept on a reply the agent made quotes that reply by its id: `<quote part="546.6">`.
- A message is `<message item from kind>`; one sent from reading the conversation holds `<quote>` and `<reply id>` for each passage, then the message on the whole; a reply holds `<on>` with its item's `<opening>` and the operator's `<comment id>`.
- A comment written in one of the agent's drawers in the review (`docs/dashboard.md`, *The drawers*) is a `<remark id>` beside the message: its `<quote>` then the `<reply>`. One on code quotes the file's lines as `path:12-14` and the lines, and its `<quote>` says in `changed` which of those lines have changed since the comment was written, by their numbers in the version quoted, or `all` where the file is gone (`Quoted`, `changed_since`), so the agent knows the comment may be about code that's gone.
- An answer is `<answer item from question>`: `<asked>`, a `<decision number lean verdict id>` for each, then the `<comment id>` on the whole, or a plain question's answer as one.
- A tag of an item from a conversation says the name lup calls it by, `name`, beside `from`, the runtime's ids: a session's own, its launch's as lup last kept it; a subagent, its own, where it has one (`Delivery.called`).
- A subagent's end is `<ended item from name>`: how it ended, in lup's words, then its last message as `<said>`, where lup hands it on.
- Citations that named no one passage are `<unresolved item from="lup" of>`: each as a `<citation said>` saying where its words read, if anywhere (*Citing the operator's words*).
- One passed on from a conversation that had ended says whom it was for (`for=`); the doorbell and an item too long for a hook are `<doorbell>` and `<announced>`.
- Text stays as written, the operator's code as code: only `</` becomes `<\/`, so no text closes a tag. The dashboard shows what's inside an item's tag (`Delivery.words`).
- The comments an approval's note and a held change's answer carry stay prose (`remark`).
- An attribute holds an item's bare number, its name saying what the number is; where lup's own words in a tag name an item, it's cited, as everywhere else: "The operator declined @7, the approval your push asked".

**Citing the operator's words.** An agent answers in its own words, and may point at theirs inline, which nothing asks it to: `@820.9[first words … last words]` names a passage of part `820.9` by its first and last words, as a browser's text fragment names one (`#:~:text=start,end`); its words alone where they're short, `@820.9[why not split it]`; `@820[…]` any part of item 820, for words whose tag gave no id; `@820.9` alone the part whole (`inbox/citations.py`). Each is read where Markdown reads text, by an inline rule of markdown-it, so none is read in code, and `\@` keeps one as text; and it's resolved against the operator's words in their items addressed to the conversation, each part as `spoken` numbers it: its words found case aside, any run of white space for one, a straight or a curly quote for either, from a word's start to a word's end. What it finds is kept on the item (`Item.citations`), the passage whole, which the dashboard unfolds it to (`docs/dashboard.md`, *The review*). A citation is read in any of an agent's own words to the operator (a message of any kind, its turn's end, a question, a friction, how it went, a stop), and never stops one: where it reads no passage, or several, the item reaches the operator as written, the citation shown as written and marked, and the agent is told which didn't resolve and where its words read, if anywhere, the places to choose among: in a tool's answer, at once; at a turn's end, in an `<unresolved>` item that holds the end once, after the message has landed (`holding`, *No turn that won't end*), so a session idle for hours doesn't leave a broken citation before the operator all that time. It fixes them with `edit`, whose answer reads them again.

**Editing what was sent.** `edit` takes the item's number and `old`, a passage of its text exactly as it stands, found there once, and `new`, what replaces it, as a file's edit does; or `new` alone, the text whole (`Delivery.edited`, `inbox/edits.py`). It edits the agent's own words to the operator: a message of any kind, its turn's end, a question's text, a friction, how it went, a stop. A question they answered and what was withdrawn are refused, saying to `send` what changed, as is a copy of a message to another conversation, which read it as it was; so are another's item and lup's own. The text before is kept beside the item (`Item.edits`), the citations are read again, and an `<unresolved>` about it still waiting is superseded; the item comes back before the operator where it had left their list, with a notice where its kind raises one, and the dashboard marks it edited, showing what changed, and any comment of theirs on a passage that changed as outdated (`docs/dashboard.md`, *The review*).

**A turn's last message** is the agent's answer: lup puts it in the operator's inbox as a note (`Delivery.concluded`), so what a session ends its turn saying reaches them without the agent sending it again, written as the agent writes anyway, one message rather than answers point by point. It carries the operator's items told to the conversation since its last turn's end (`Message.answers`, `answering`), a review, a message or an answer, which the dashboard shows above it, so the exchange reads as theirs, then the agent's; and its citations of their words are read (*Citing the operator's words*). An end that's held makes one too, before it tells what waits: the turn's next end carries only its own message, so the held one would never reach the operator, and their reply comes at a turn's end most of the time. Each end that says something is its own note, since the agent's next end carries new words (`docs/field-notes.md`, *The end after a held end*). A subagent's last message is its parent's, and makes none, but where the operator's words reached it since it last answered them: then it's put before the operator too (`subagent_answered`), since nothing else of the subagent's would answer them. Both runtimes hand the hook the turn's last message, `last_assistant_message` at `Stop` and at `SubagentStop`. A session's turn that ends on an error from the model's API has no last message of its own: the conversation shows the runtime's text for the error among its steps, so its note says, in lup's words, that the turn ended on that error, its kind and that text. It's the end's one note, the error never made a note as the agent's words, and a reply to it reaches the session, which the failure left idle, so it's woken. `send`, `note` and the rest stay for what stands on its own.

**No turn that won't end.** An agent can always end its turn (`holding`, `inbox/ends.py`). Every hold at a turn's end, the inbox's and the judge's alike, holds once and then lets the turn end, holds once per thing across turns, and never starts a turn of its own: the idle wake is for an item the operator's act made, or a subagent's message.

**Holding a call.** `ask` with `wait` holds its call until its question is answered, `wait_inbox` until anything arrives, a subagent's end since its last call among it, and `land` until the operator answered each hold of its landing. Each runtime's limit on a call is set to 25 hours, above a hold's day: on Claude Code the server's `timeout`, which also raises the 30-minute idle limit of a stdio call, with `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS=0` so a held call isn't moved to the background; on Codex `tool_timeout_sec`. In Codex's code mode the cell yields after 30 seconds and the model may end its turn, so a held call waits for the operator there but the agent may not. A held call survives a restart of the service: the bridge sends it again once the service is back (`docs/host.md`, *Restarts and the sweep*), and the new service finds its wait rather than asking twice, since the item a call made keeps the call's id (*An item's moment*): an `ask` whose `call` already made a question holds on that question, and answered meanwhile, returns the answer at once (`Speaker.asked`); a `land` whose holds already wait on the same file at the same tip holds on them again (`Delivery.held_at_landing`); `wait_inbox` waits on whatever comes.

**An item's moment.** An item an agent's call made keeps the runtime's id for that call, and `lup-dev inbox show N --context` reads the conversation's record around it, from the operator's last words before the call to their next (`inbox/context.py`), which the dashboard folds under the item. Each runtime's adapter finds and reads its own records (`Records`, `host/records.py`).
