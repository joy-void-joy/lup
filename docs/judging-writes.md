# Judging every write: allow, ask or refuse

**One sentence:** lup judges every write in the worktrees of an agent's repository. An `Edit` or `Write` is judged before it lands, on the content it would produce. Anything else (a command, a script, a background process, Codex's `apply_patch`) is judged at the next checkpoint, by comparing each worktree with the last state lup accepted for it. Each change is allowed, asked of the operator, or refused.

**As built, and where it's going.** This note is the judge as built in `packages/lup-dev/src/lup_dev/`. `DESIGN.md` (*Sessions*, *Approval*; *Policy*; *Code rules and the gate*) is where it's going, in a piece of its own: asks become proposals with a dependency guard, with no per-call checkpoint **(leaning)**. Until lup's own dashboard exists, the first lup's stands in: the bridge's interim review hook (`.claude/hooks/interim_review.py`, not registered) can carry Claude Code's prompts there, and the installer parks the judge's own review there (`legacy_dashboard.py`); `docs/review-flow.md`'s drafts flow, superseded (`docs/graveyard.md`), is built behind the command line (`review.py`, `policy/drafts.py`, `policy/submissions.py`), and the judge's hooks don't use it. While lup is being built, its own sessions run only the judgement of each write (before an `Edit` or `Write` lands; on Codex, after each call), with `asks="protected"` (*Installing it here*).

Each choice is stated in the section it shapes, with the alternatives worth remembering. A choice the operator hasn't confirmed yet is marked **(leaning)**.

It covers:
- the three outcomes, and what each kind of change gets;
- judging `Edit` and `Write` before they land;
- the checkpoint and its snapshot store, for everything else;
- which worktrees of the repository a session's writes are judged in, and a move of `HEAD` (a commit, a merge, a checkout) judged once, as a commit's;
- asking the operator: in Claude Code's own prompt, and through holds where a runtime can't ask;
- refusals, which report every finding at once and save the agent's version;
- the typed engine and the code rules (the conventions they enforce are in `docs/conventions.md`);
- type errors and ruff's findings as information at each checkpoint;
- the `# lup:` directives: `ignore`, `defer`, notes, and removing a note;
- tests written as a specification, expressed with protected paths and mounts;
- the verdict log;
- the hooks for Claude Code and Codex, and installing them in this repository.

What it leaves to other pieces:
- keeping the store out of the agent's reach, and refusing reads of secrets: containers;
- edits a session makes in another repository: launch and spawn;
- a shell write into a worktree of the repository the session never reached, and on Codex every write outside the worktree the session started in: rooms, whose mount is the worktree (*Every worktree of the repository*).

## The three outcomes

- **allow:** the call goes through with no prompt. On Claude Code the hook answers `allow`. On Codex nothing needs answering: Codex doesn't ask before an `apply_patch` inside the workspace, and its `PermissionRequest` fires only for a patch that needs approval (one writing outside the writable roots, or retried after a sandbox denial), which lup leaves to Codex's own approval (*What the runtimes do*).
- **ask:** the operator decides before the change lands. On Claude Code it's the runtime's own prompt. Where a runtime can't ask before a call, the change is held: the agent waits inside the hook until the operator answers.
- **refuse:** the change doesn't land, or is put back, with the agent's version saved and every finding reported at once.

Refuse wins over ask: a change with rule findings is refused before the operator is asked about it, so they never review a version that will be refused anyway.

lup never stays silent on a write it judges: its outcomes are allow, ask and refuse, not ask, refuse and silence, since the allow is what keeps routine work from interrupting. Staying silent would send the call to the runtime's own permission mode, which in Manual mode means a prompt per edit.

## What each change gets

| Change | Outcome |
|---|---|
| A test, scratch (`tmp/`), docs or data file, at any size | allow |
| `DESIGN.md` or `AGENTS.md` | ask: they're the operator's |
| A protected path | ask; a protected Python module gets the rules too, so a finding on the lines the change touches refuses it |
| A path the project's declaration excludes | allow, nothing reported; a protected one still asks |
| Production code with a rule finding on the lines the change touches | refuse, every one of lup's findings in the file listed, the agent's version saved |
| A new production file, or overwriting a whole existing one | ask |
| A change to the public API (see below) | ask |
| An added `# lup: ignore` | ask |
| Removing a `# lup:` note present when the session started | allow, and reported |
| Any other production edit | allow, once the rules pass it |

There's no line count: any production edit the rules pass is allowed unless something asks. A size limit (three added lines or fewer allowed, say, and more left to the runtime's own mode) makes agents split their edits to fit it, and in auto mode edits inside the working directory skip the runtime's classifier anyway (Claude Code's permission docs).

**Path roles.** Each path has one role, the first that matches:
1. **protected:** the project declaration; dependency manifests and lockfiles (`pyproject.toml`, `uv.lock`, `package.json`, `bun.lock`); the tools' own configuration files (`ruff.toml`, `.ruff.toml`, `pyrightconfig.json`, `pytest.toml`, `.pytest.toml`, `pytest.ini`, `setup.cfg`, `tox.ini`, `.importlinter`, `uv.toml`, `.python-version`), each read before its table in `pyproject.toml`, so one written unasked would override what the gate checks or which Python runs; what runs outside the agent's reach (`.github/`, git's own directory and hooks (`.git/`, `.githooks/`, `.husky/`), `.pre-commit-config.yaml`, `.vscode/`, `.devcontainer/`, `.claude/`, `.codex/`); what widens a later launch (`sync.json`, `sync.json.local`); secrets (`.env*.local`); `.gitignore`, since what it ignores the checkpoint never sees; and whatever the project's modules add;
2. **operator's documents:** `DESIGN.md`, `AGENTS.md`, asked rather than allowed like other docs and reviewed after;
3. **excluded:** what the project's declaration holds to nothing (the `excluded` role of its modules' `paths`): no lup rules, no ruff or pyright findings reported, writes allowed. A path both protected and excluded stays protected: it still asks, without rules or findings, so exclusion takes the checks away, never the operator's review. Matched before protection, exclusion would let a write to an excluded hook land unasked;
4. **test:** a module pytest collects as a test: under a root it reads (`testpaths` in the nearest `pyproject.toml` holding pytest's options, nested projects included; the root itself without any) and matching its `python_files` patterns, or a `conftest.py` under such a root, which pytest doesn't collect as a test module but which, as production, would gate a suite's fixtures. Test roots the declaration names replace what pytest's configuration says: `Python.tests` changed by a layer, or a module of the project's own holding some. lup's default for them, `tests/`, doesn't, so a project that names none keeps the roots pytest reads, until the gate checks `testpaths` against the declared roots (`docs/declaration.md`, *pytest and import-linter*); then the declared roots alone can be the test role. A source module pytest reads only for its doctests stays production (`docs/conventions.md`, *Tests*);
5. **scratch:** `tmp/` at any depth, and the root's `.lup/`, where the saved versions are;
6. **docs:** Markdown files and the root's `docs/`, not a `docs/` at any depth, which would wave through Python under a package's `docs/`;
7. **data:** JSON, CSV, YAML and other data formats outside a source tree, which is anything under a `src/` directory or under a directory holding an `__init__.py`;
8. **production:** everything else.

Production is the default, so a file nobody classified is gated rather than waved through. Manifests, lockfiles, the tools' configuration files, `sync.json`, secrets and `.gitignore` match at any depth; the protected directories, `.pre-commit-config.yaml` and the operator's documents only at the root.

**A protected Python module gets lup's rules as production code does:** protection adds the operator's review, it doesn't take the rules away, and it exempts nothing. A finding on the lines a change touches refuses it, since refuse wins over ask; a clean change asks, with any design ask beside the protected one, and no approval covers the protected ask. Its type errors and ruff's findings are information like any module's, and must be clean at the turn's end; `lup-dev rules check` reads it too. Were protection to win and the rules not apply, `catalog/` would be checked only by review and by the gate's ruff and pyright. The rules' own examples need no exemption, being strings in the table, and the catalog's one exemption, from `constant-home`, is declared in `lup_project.py` like any project's (*Where a project declares its roles*). `policy/roles.py` says which modules the rules read (`ruled`: production and protected) and whose pyright and ruff findings are reported (`checked`: those, and tests); `policy/judge.py`, `policy/checkpoint.py` and `cli.py` read them. The default patterns are data in `lup_dev/catalog/paths.py`, which the operator reviews, one list per module (`Core`'s and `Python`'s), rather than defaults written into `policy/roles.py`, which holds the matching and reads every role's patterns from the resolved declaration.

**Asking only about protected paths.** A project declaring `Project(asks="protected")` has only a protected path's asks reach the operator; every other ask (an operator's document, a new or whole file, a public-API change, an added `ignore`) is allowed, and lup's rules still refuse. A protected path's change takes effect outside the agent's reach before anything lands, so it can't wait for landing; the rest is reviewed in design notes before the code and in merge commits and pull requests at landing. lup's own repository declares it while lup is being built, with the judge installed only to judge each write and no turn's end (`AGENTS.md`, *How work goes*; *Installing it here*).

A deleted file asks where it's protected or one of the operator's documents, and is otherwise allowed, with no public-API ask, a package's `__init__.py` included. A write is judged in the worktree of the session's repository that holds it, by that worktree's roles under the declaration at the integration branch's tip (*Every worktree of the repository*); a write outside the session's repository isn't judged here.

**Where a project declares its roles:** in its declaration, `lup_project.py` at its root, as the modules it selects (`docs/declaration.md`). Each role is a pattern list in a module's `paths`, which a project changes as any selection: `Core`'s protected paths, operator's documents, scratch, docs and data; `Python`'s protected manifests and tools' files, source trees and Python modules; and its own modules'. Its test roots are `Python.tests`; the rules it lifts from some paths, `CodeRules.exempt`; the Python modules declaring its conditions, each module's `conditions`; and which asks reach the operator, `Project.asks`: `Project(asks="protected", modules=Modules.default().edit(Core(paths=Paths().add(protected=[…], excluded=[…]))).edit(CodeRules(exempt=Exemptions().add(Exemption(rule=…, paths=[…], why=…)))))`. An exemption lifts one rule from every file its patterns match, with the operator's reason, where an `ignore` keeps one finding out on its line. It's applied where findings are kept: the judge (`kept`) and `lup-dev rules check` leave out an exempt rule's findings, and every other rule still holds there; the turn's end reports only pyright's and ruff's findings, so it has nothing to lift. Which rules run is the declaration's rule selection, which every check request carries for the engine to resolve (*How a rule is declared*). Compiling the declaration into the tools' own settings (ruff's and pyright's exclusions among them) is slice B's (`docs/declaration.md`, *lup's settings for ruff and pyright*). Nothing points at the declaration: the loader (`declaration/load.py`) finds `lup_project.py`, or the package `lup_project/`, at the root, and imports it from the root, its `src/`, and each uv workspace member and its `src/`, since the judge runs from its own installed copy; without one, the defaults apply, and one that can't be imported or doesn't resolve is never silently replaced by the defaults (*The declaration, from the integration branch*). The judge reads it from the integration branch's tip, never from the worktree being judged; the gate reads the worktree's own. What judging reads of it is the declaration resolved (`Declaration`, `declaration/resolve.py`): its file, each role's patterns from every selected module, the test roots, the exemptions, the conditions modules, each module's rule selection, the runner's commands and `asks`.

## The public-API ask

A change to what other code depends on is a design change, so it's asked like a new file:
- a name added to or removed from a package's root (`__init__.py`);
- a new class;
- a changed signature of a definition that existed when the session started: parameters, their types, the return type.

A name added to a root asks when it's added; a class asks unless it was in the accepted version before the change or at the session's start. Names created during the session ask nothing more: changing the signature of a definition the session created, or removing a root name the session added, doesn't ask. The operator sees them when the file or class that holds them is asked. Removing a definition or a class that existed when the session started doesn't ask either; removing a name from a package's root does, as listed.

**How it's computed:** the engine reports each file's public surface for the would-be content, for the accepted content before the change, and for the content the session started with; lup compares them (`policy/surface.py`). The surface is every class (nested ones included), every function and method with its signature (parameter names, kinds, annotations, whether each has a default, the return type), and the root's names: its `__all__` where it declares one, otherwise every name it binds, imports included. Private names count.

The ask is tried, not settled: whether it asks too much is measured through the verdict log, and tuned from what the log shows.

## Before an edit lands

For `Edit` and `Write`, lup knows the file's content after the call before anything is written, so they're judged before they land, and the checkpoint judges everything else; judged at the checkpoint too, a refused edit would land and be put back after the fact. The adapter reads each as one of two proposals in lup's own words (`policy/before.py`), so the core never names a runtime's tools:
- **a whole write (`Write`):** the content it carries.
- **a replacement (`Edit`):** the current file with `old_string` replaced by `new_string`, once, or everywhere with `replace_all`; an empty `old_string` on a missing file creates it. It's applied with `str.replace`, the tool's own operation, kept from the `string-replace` rule by one `ignore`; slicing, the other way to apply it, another rule refuses. If `old_string` isn't there exactly as the tool requires, lup allows the call, and the tool fails on its own.

The file's worktree is the one its path is in, which git names (*Every worktree of the repository*). The hook (`PreToolUse`) runs the judgement on that content: the path's role, the code rules through the engine, the public-API comparison, the directives added or removed. It answers allow, ask or refuse. A refused edit never touches the file. The engine checks content that isn't on disk the way pyright's language server checks an unsaved buffer: it opens the file with that content, and puts the disk's back at the next request unless the edit landed (*The engine*).

**What it's compared with** is the accepted content, not the file on disk, so a command's write not yet judged is judged with the edit: an edit to a file a command just created asks as a new file. A write allowed or asked is remembered with its call; when the call finishes, the checkpoint accepts that content as judged, and an asked call that ran means the operator approved it.

**A refused new file** is sent again with `Write` once it's fixed; the prompt is where the operator sees it whole. **A refused edit to an existing file** is fixed in its saved copy and moved into place: the move is a shell write, judged at the checkpoint by its diff against the accepted content, not as a whole-file overwrite. Holding the moved copy at the checkpoint for the operator instead isn't open on Claude Code, which can't prompt there. An approval covers the path for the rest of the session, so a file approved and then refused for a finding isn't asked again once fixed. It covers the asks that show the file's design (a new file, a whole write, a public-API change); a protected path, an operator's document and each added `ignore` are asked every time (`Ask.covered`, `policy/judge.py`).

## After a call: the checkpoint

Everything that isn't an `Edit` or a `Write` is judged after the fact: a `sed`, a script, `cp`, a background process, and Codex's `apply_patch`, whose format lup doesn't parse (`DESIGN.md`, *Policy*: no command's spelling is parsed). A `cp README.md src/new.py` makes a production file without a file tool, and the checkpoint judges it as one. A checkpoint compares each worktree with the last state lup accepted for it, rather than taking a snapshot before and after each call (`policy/store.py`, `policy/judge.py`).

The judging core never sees a runtime. Each runtime's adapter turns its hooks into these events:

| Event | Claude Code | Codex |
|---|---|---|
| session started | `SessionStart` | `SessionStart` |
| call started (id) | `PreToolUse` | `PreToolUse` |
| call finished (id) | `PostToolUse`, `PostToolUseFailure` | `PostToolUse` |
| turn ended | `Stop` | `Stop` |
| a subagent's conversation ended | `SubagentStop` | `SubagentStop` |

The events live in `policy/checkpoint.py`. A runtime is named only in its adapter (`lup_dev/adapters/`): its payloads, its tool names, how it hears a report, and the variables it sets in its commands. The core sees a runtime through `Runtime` (`policy/runtime.py`): its name, whether it asks before a call, and whether this process runs inside one of its sessions. Only `cli.py` lists the adapters, an import contract keeps them behind it, and the `runtime-mention` rule refuses a runtime's name anywhere else (`docs/conventions.md`). Per-runtime hook modules beside a core that names them (`hooks/claude.py`, `hooks/codex.py`) would invite features built per runtime above the adapter, which `AGENTS.md`'s *Both runtimes* rules out.

**A checkpoint runs whenever a call finishes and no other call is running,** and again when the turn ends: one rule on both runtimes, built from the neutral events, rather than Claude Code's `PostToolBatch` and a lock on Codex. It runs in each worktree the session holds, once no call counted there is running (*Every worktree of the repository*). Parallel calls are judged together once the last one finishes; a late background write is judged at the next checkpoint. The checkpoint is before the agent's next model request, so a refusal reaches the agent before it writes its next line.

**Subagents.** A call that runs a subagent (Claude Code's `Agent` or `Task`, Codex's `spawn_agent`) isn't counted as running: its subagent's own calls are, so a subagent's writes are judged as it makes them, and the report goes to the subagent whose call finished. Counting the spawning call instead would judge a subagent's writes only when it ends, and tell only its parent. The checkpoint sees files, not authors, so its report also waits, as mail, for every other conversation whose calls finished since the last checkpoint, and reaches each at its next finished call or the end of its conversation. A subagent's end clears its own calls, runs a checkpoint where none is left running, and holds on what it must be told, never on what's left in its files (below).

**The session's turn's end holds on its own conversation's files (leaning).** A subagent shares its session's id, and a subagent that stops with its own background work running (waiting on a review) isn't done: it resumes later. Held on a worker's files, the session's every turn's end would block on findings in files it didn't write and shouldn't touch, once for every background notification. So:
- **The files touched and watched are kept per conversation,** in the session's record in each worktree: `""` for the session's own, a subagent's id for its. So is what held each conversation's end when it last blocked.
- **Who wrote a file a checkpoint lands.** A file tool's write is the conversation's whose call made it: judged before it landed, it's remembered with its conversation when the call finishes. So is a held write the operator approved. Anything else, a write through the shell or `apply_patch`, is every conversation's whose calls finished since the last checkpoint, and the one the checkpoint runs for: the checkpoint sees files, not who wrote them, and holding a conversation's end on a file it didn't write is the safe side, which the second block lets end. What a move of `HEAD` brought touches no conversation's files. Putting every write on every conversation instead would put a worker's file-tool writes on the session whenever their calls finish together; putting a shell write on the conversation the checkpoint runs for alone would drop it from the one that wrote it whenever another's call finished last.
- **The files importing them.** The importers pass carries the conversations that wrote what it re-checks, each named with its session, since the pass is the worktree's; what it finds is watched for them, in their own session's record, whichever hook collects it. It re-checks what's pending as one batch, and the engine doesn't say which changed file each importer follows, so its errors go to every conversation that wrote into the batch. What a move brought counts as written by the conversations whose calls finished since the last checkpoint, for this alone. Giving what the pass found to the conversations of the checkpoint that collects it would put a worker's importers on the session at its next call's finish; keeping it per batch costs a shape for no gain, since batches merge whenever a pass is running; and each session collecting only what its own conversations caused would leave the rest for a session that may never come back.
- **`Stop` holds on the session's own conversation's files:** the type errors and ruff's findings left in them, and in the files importing them where the pass found errors, each re-checked as it stands. A turn's end watches what the pass found, as a checkpoint does, and re-checks every watched file rather than reading the pass's reports once: the engine reports the same type errors either way (the pass's `typeReport` is a check's pyright findings), with ruff's beside them. Holding on every file the session's conversations touched would hold the session's every end once a worker stopped with background work running; one list kept for the session, with its end only informing, would leave the session's own errors to the gate; and reading findings in a file queued or drafted for review as "waiting on review" would still leave a worker's half-done files that wait on nothing holding the session's end.

**A subagent's end (`SubagentStop`) never holds on findings,** the type errors and ruff's findings left in its files or in the files importing them. A worker waiting on a review has files importing modules that haven't landed, with errors it can't fix: held on them, it would be blocked at every stop. And every worker passes the gate before it hands back, which the session landing its branch runs again. So a subagent's end runs its checkpoint, which judges what changed as any checkpoint does, but re-checks none of its files for what's left: no pyright, no ruff, and no wait for the importers pass, whose findings the next checkpoint or the session's end collects. What it must be told still blocks, each told once (a refusal, a move, mail, and a checkpoint's notices, such as an answer to a hold or a declaration that can't load: *While a subagent works*), and a judge's failure there warns the operator once, as at the session's end. Its files are still kept as its own, so the session's end doesn't hold on them either. Holding it once on its own files and then letting it end on the same findings after a block (`stop_hook_active`, which both runtimes' `SubagentStop` carries: Claude Code's hooks reference; Codex's `subagent-stop.command.input` at `rust-v0.156.1`) would still block a worker once at every stop on errors it can't fix; holding its errors at the end of the conversation that started it would hold the session's every end on a worker's files.

**While a subagent works:**
- **A subagent is at work** from its first call to the end of its conversation (`SubagentStop` on both runtimes), kept per session, beside the session index (`<session>.conversations.json`) **(leaning)**. An end that blocks keeps the subagent going, so it stays at work. A session that starts again (resumed, cleared or compacted) forgets them; one still at work is noted again at its next call. Claude Code's `background_tasks` in `Stop`'s input, the runtime's own list, would stay right when a subagent is stopped, but it's Claude Code's alone (Codex's `Stop` has no such list), "present when the task registry is reachable", and a second source beside lup's own. The spawning call (`Agent` or `Task`, `spawn_agent`) can't mark it, since its hooks don't carry the subagent's id to match to its end; counting it at work only while one of its calls runs would forget it between calls, while it thinks; and the session index (`Holding`) is about worktrees.
- **While one is at work,** the session's end doesn't hold on what's left in a file they both touched: it may be the subagent's, in progress, and it's information. Once none touching it is at work, it holds.
- **A worktree where a subagent's call is running gets no checkpoint at the session's turn's end;** that call's finish runs it **(leaning)**. Otherwise the turn's end would judge the subagent's writes in progress: a file tool's write that landed before its call finished reads as a write through the shell, so a new module would be refused and removed under the subagent, and the report would go to the conversation whose turn ended. A subagent's end runs a checkpoint only where no call at all is left running. Skipping the turn's end's checkpoint wherever any call is running, as a call's finish does, would leave other sessions' calls alone too, but lose the turn's end as the backstop for a call that never reports finishing; another session's call in flight is #34.
- **The session's turn's end that follows a block** (`Stop`'s `stop_hook_active`, on both runtimes) doesn't hold again on the same findings: the same file, place, rule and message, in any order. The agent didn't fix them, and blocking again only repeats the turn (Claude Code overrides a ninth block in a row, but its count starts again at each tool call). The turn ends, and the operator is told so, with the findings. Different findings block again, and a turn's end that doesn't follow a block holds. Ignoring `stop_hook_active` would block a dozen times or more in a row; letting any turn's end after a block through would let it end whatever changed; and comparing findings without their place would read a finding fixed in one place and made in another, of the same rule and message, as unchanged.
- **What the turn's end must tell still blocks,** at either end: a refusal, a move, an answer to a hold, removed notes (at the session's end) and mail are each told once, so they can't repeat; told to the operator with the findings instead, they'd be lost for the agent, since mail is taken when it's read. At the session's end, the findings that don't hold the turn are listed beside them as information. Otherwise that information goes to the operator, in `systemMessage` on both runtimes, as a judge's failure does **(leaning)**: anything a turn's end tells the agent continues the turn, on both runtimes (*The two runtimes*), the very harm of holding, and mailing it to the conversation for its next call would arrive after a subagent has moved on.
- **The gap:** a subagent whose end its runtime never reports (neither runtime's docs say whether stopping one reports it) stays at work until the session starts again: meanwhile a file it shares with the session's own conversation doesn't hold the session's end. The gate still fails on what's left (*Checks owed*).

**It degrades gracefully:**
- a "finished" with no matching "started" leaves the running calls as they are (Codex's `write_stdin` can deliver the original command's `PostToolUse` without a `PreToolUse` of its own), and still runs a checkpoint if no call is running;
- a call that never reports finishing is cleared when its conversation's turn ends, and the turn-end checkpoint judges everything anyway. Claude Code reports no event for a call the operator declined at its prompt, so a declined call stays counted until the turn ends: harmless, but it holds back the checkpoints of that turn;
- the in-flight calls are kept per worktree under a file lock, since hooks for parallel calls run concurrently, each call with its session and its conversation, so a turn's end clears its own conversation's calls and no other's: the session's `Stop` leaves its subagents' calls counted.

**How a checkpoint goes,** in each worktree it runs in:
1. **Snapshot.** The worktree is written into lup's own store as a git tree (a private index, `git add -A`, `write-tree`). Ignored files are left out, as `.gitignore` says. The store is a bare repository outside the worktree, and git runs with `core.fsmonitor` and hooks turned off, since a planted `core.fsmonitor` runs inside a call (`docs/field-notes.md`, *Isolation and effects*). git's `-z` output is read by splitting it on its NUL separators (`nul_separated`, kept from the `string-split` rule by one `ignore`), not through a git library such as dulwich or pygit2, a new dependency.
2. **Compare** with the accepted tree (`git diff-tree`). Nothing changed is the common case after a read.
3. **Set aside what was committed elsewhere.** A changed file whose new content equals its content in a commit that existed at the previous checkpoint, or that arrived from a remote since, isn't judged: that's what a checkout, a pull, a merge, a stash or a `git restore` produce, and that content was judged where it was written. The content git's merge makes from such commits isn't judged either: a merge whose two sides both changed a file writes content no commit held, made from content judged on each side. A file with conflict markers matches no commit, so it's judged, and so is a resolution written by hand. Judging it all would replay history as new writes; setting aside only what equals `HEAD` would let a write committed in the same call through.
   - **How:** the commits are those the repository's refs and the worktree's `HEAD` named at its previous checkpoint, the `HEAD` each other worktree of the repository had at its own last checkpoint (kept per repository, beside the verdict log), and the remote-tracking refs now; `git log --find-object=<blob> <those commits> -- <path>` says whether any of their history holds that content at that path. For a merge (each merge commit `HEAD` reaches that those commits don't, or a merge in progress), `git merge-tree --write-tree` of its parents remakes git's clean merge, and a file equal to its result is set aside when both parents are in the history of those commits; the paths it couldn't merge are judged, and a merge of more than two commits isn't remade (`policy/store.py`, `Elsewhere`). A deletion is set aside when `HEAD` lacks the path and is in the history of those commits (a branch switch, a reset to an ancestor), or when the remade merge lacks it.
   - **Why merges are remade (leaning):** without it, a clean `git merge` of a branch adding a class to a file both sides changed is refused at the next checkpoint as a public-API change made through the shell, leaving the working tree different from `HEAD`. Judging every merge's result again instead would ask the operator a second time about what they reviewed on the branch.
   - **A gap:** a remote-tracking ref also moves when the agent pushes, so one call that writes a file, commits it and pushes it is set aside like a pull. Telling a fetch from a push needs the reflog's messages; the hole is narrow while pushes run on the host, and closes with containers, where pushes go through a host service.
4. **Judge a move of `HEAD` once, as a commit's (leaning).** The worktree's `HEAD` is recorded at each checkpoint, and when a session begins there, in the repository's record of each worktree's `HEAD` (`heads.json`, beside the verdict log), which step 3 reads for the other worktrees. Kept in each store's own state instead, the other worktrees' would take listing them with `git worktree list --porcelain`, whose `worktree <path>` lines would have to be split by hand, then opening each one's store. When it has moved (a commit, a merge, a pull, a checkout, a reset), the files the move changed whose content on disk is the new `HEAD`'s were put there by git, not typed: they're the move's, not the session's. What step 3 didn't set aside of them is content first written in a commit made since the last checkpoint: shell writes committed in the same call, a resolution committed through the shell, commits made while the judge couldn't run. Treated as accepted, content committed on the branch would let anything committed through the shell skip the judge. So it's judged once, against the accepted content before the move, which is also its baseline for the public-API ask and removed notes, and with no session's approvals, since the approvals of the session whose checkpoint found it would let one session's approval cover a commit it may not have made. It's:
   - **never put back:** putting it back leaves the working tree different from `HEAD`, and protects nothing, since the next `git restore` brings the content back unjudged, the commit being among the tips by then;
   - **attributed to no session:** its verdicts are logged without one, with `move` for their tool, since the checkpoint can't tell who committed;
   - **told as a commit's** to the conversations whose calls finished since the last checkpoint, naming the commit `HEAD` moved to, each file with lup's findings on the lines the commits touched, what it asks and the notes it removed. Its findings fail the gate before the branch lands; its asks are kept for the operator as one hold no agent waits on (*Asking the operator*).

   A file changed again after the move is judged in two steps, the move and then the rest against `HEAD`'s content, so the session isn't asked about what the commit brought; a refused rest goes back to `HEAD`'s content, since the move is accepted. Nothing is judged as a move where no `HEAD` was recorded for the worktree yet (a store kept by an earlier judge, until a session begins there or its first checkpoint runs), or where `HEAD` names no commit now: a missing record read as no commit would judge everything the branch has as the move's at the first checkpoint after a reinstall.
5. **Judge** every remaining change exactly as an edit is judged before it lands: role, rules, public API, directives. Content judged before it landed (a file tool's write whose call finished, a hold the operator approved) is accepted as it is; changed since, it's judged from that content.
6. **Refuse** what the table refuses, and what bypassed an ask: on a runtime that asks before a call, a new production file, a public-API change, a suppression, a protected path or an operator's document changed through the shell and not committed (committed, it's the move's: step 4) is refused with a pointer to the file tools, so it comes back through the prompt. That enforces `AGENTS.md`'s *Write with your file tools*. On a runtime that can't ask before a call, it's held instead (*Asking the operator*).
7. **Act:** a refused file goes back to its accepted content, or is removed if it was new, and the agent's version is saved. What's left becomes the new accepted tree.
8. **Report** to the agent, once: everything refused, then what a move brought, then notices (an answer to a hold, a late answer, a declaration standing in), then type errors and ruff's findings as information, then the notes removed; mail for the conversation follows.

The accepted tree starts as a snapshot when a session starts, or first reaches a worktree, and the worktree's `HEAD` is recorded with it. If a stored accepted tree already exists for the worktree, the difference is taken as made while no call ran there: the operator's work or a pull (a write another session's background process makes between its calls reads the same way). It's accepted without judging, unless a call is running there: then another session is at work in it, so the accepted tree stays, the session's starting tree there is that accepted tree, and that call's checkpoint judges what it writes. Judging that difference as this session's would blame it for the operator's work between sessions, and starting a worktree without a store from its `HEAD` would judge the operator's uncommitted work as the agent's. A session that starts again (resumed, cleared or compacted) begins again in every worktree it holds: beginning again only in the one its working directory is in would leave the operator's work between sessions in the others to be judged as the session's.

**Someone else's edit during a session** can't be told apart from the agent's: the checkpoint sees files, not authors. An edit the operator makes in a worktree a session holds is judged as the agent's, and if refused it's put back with the version saved, so nothing is lost. The operator works in a worktree no session reaches, or between sessions.

**Cost**, for each worktree the session holds, measured through the store's own code:
- one snapshot per checkpoint: 70 to 100 ms where nothing changed, about nine git processes, of which the snapshot is 5 ms at lup's size and 10 to 15 ms at nori's 4,000 files; a worktree's first snapshot takes 40 to 50 ms at lup's size and 2.5 to 3.6 s at nori's. The existing projects have 161 to 3,721 tracked files;
- where nothing changed, the checkpoint stops at the snapshot: no comparison when the snapshot is the accepted tree, no declaration loaded, `HEAD` and the refs read once each; the store's state, the session's record and the importers pass's state are still written. With the tests' stub engine on a clone of this repository (97 files), a call's start and finish where nothing changed take 52 ms and 8 git processes with one worktree held, 148 ms and 20 with three; a checkpoint alone takes 37 to 43 ms;
- once for each commit of the integration branch, exporting its declaration: 77 ms for this repository's tip, then 1 ms to load it;
- plus the engine's incremental re-check of the changed files;
- target: under 300 ms per checkpoint on this repository, type check included, for a session holding one or two worktrees.

## Every worktree of the repository

A session starts in one worktree and often works in others. In this repository each branch is its own worktree (`tree/<branch>`), so a session started in `tree/dev` writes in `tree/feat-…`, and its workers write in theirs. The judge covers the worktrees of the session's repository that the session holds (`policy/worktrees.py`) **(leaning)**, rather than pinning a session to the worktree it starts in, which would make one session per worktree the way of working, or leaving the other worktrees until rooms. The store and the session's record are per worktree, the verdict log per repository; a write is judged the same way in any of them.

**The session's repository.** When a session starts, lup reads its repository from its working directory: git's common directory (`git rev-parse --git-common-dir`). A worktree names it, and so does a bare repository's own directory (checked at `lup.git/` and `lup.git/tree/`), so a session started there is judged too, holding no worktree until it reaches one. A session started outside any repository isn't judged, until a later hook's working directory is in one. The session index keeps the repository and the worktrees the session holds, under a lock its parallel hooks share; a worktree is begun inside that lock, so a parallel hook never finds it half begun. A worktree whose root is gone (`git worktree remove`, as landing a branch does) isn't held: there's nothing in it to judge, and a checkpoint can't enter it.

**A write's worktree, from its path.** For an `Edit` or a `Write`, lup asks git from the file's nearest directory that exists: `--show-toplevel` names its worktree, `--git-common-dir` its repository **(leaning)**. The path isn't matched by prefix against `git worktree list`, one call per session, which would judge a nested repository's files as the outer worktree's though no snapshot sees them.
- In a worktree of the session's repository, it's judged there, by that worktree's accepted content and roles, under the integration branch's declaration.
- In another repository, or in none, it isn't judged, nor refused: the runtime decides. A repository nested inside a worktree is another repository: git says so, and the checkpoint's snapshot doesn't see inside it either.
- In the repository's own git directory, which in a layout like this one sits outside every worktree (`lup.git/config`, `lup.git/hooks/`, `lup.git/worktrees/`), it asks, as `.git/` does inside a worktree: those files run outside the agent's reach **(leaning)**. Left to the runtime as a path outside the repository, an edit to `lup.git/config` or `lup.git/hooks/` would get through unasked. No snapshot covers that directory, so only the file tools' writes there are judged. Its verdict names the git directory where a worktree would be, and no store keeps the write until its call finishes, so its answer isn't logged.

**The worktrees a session holds:**
- the worktree it started in;
- each worktree one of its file tools writes in;
- each worktree a hook reports as its working directory. Claude Code's hooks reference: "`cwd` follows Claude: the `cwd` field in the hook's input JSON is the worktree root after Claude enters a worktree, and the new directory after Claude runs `cd`." So after a `cd ../feat-x` in the session's own conversation, the next hook holds `feat-x`.

A subagent's hooks carry its session's id, so a worker's worktree is held by the session that started the worker. Reaching a worktree begins the session there as a start does: the accepted tree becomes the worktree as it stands (unless a call is running there), and the session's starting tree there is recorded, which the public-API ask and removed notes compare with.

**Which worktrees a checkpoint looks at.** Three options, costed with the figures above (*Cost*), for a repository of 3 worktrees, and for nori's 36:

| Option | Cost per checkpoint | What it judges |
|---|---|---|
| Every worktree of the repository | ~80 ms for each worktree: 0.25 s for 3, ~3.5 s on nori; and the first checkpoint that sees a worktree pays its first snapshot, 2.5 s each at nori's size | Everything, but also the operator's own worktree and other sessions' worktrees, as this session's writes. And the calls counted must span the repository, so one session's long call holds back every other session's checkpoints |
| The worktrees the session holds | ~80 ms for each held worktree, usually one to three: a session in one worktree pays for one | Every file tool's write, and every shell write into a worktree the session reached; not a shell write into a worktree it never reached |
| Those changed since their record | The same as every worktree: knowing that a worktree changed takes the snapshot's pass over its files, and once that pass is done the snapshot costs almost nothing more | The same as every worktree |

**Leaning: the worktrees the session holds.** It costs a session in one worktree what one worktree costs, never judges the operator's worktree or another session's, and covers file tools' writes in other worktrees, and shell writes where the session works.
- **The gap:** a shell write into a worktree the session never reached (no file tool there, never its working directory) isn't judged, and is accepted when a session next reaches that worktree. `AGENTS.md`'s *Write with your file tools* makes a session's first write in a worktree a file tool's. Rooms close the gap: a room's mount is its worktree.
- **On Codex** a session holds only the worktree it started in **(leaning)**. Its hooks' `cwd` is the "Working directory for the session", and its `Bash` and `apply_patch` carry only `tool_input.command` (its hooks docs), which lup doesn't parse. Under its `workspace-write` sandbox a write elsewhere lies outside the writable roots, so Codex's own approval decides it, and lup doesn't judge it. That's the declared gap on Codex until rooms; reading the files an `apply_patch` names from its headers would close it by hand-parsing an agent's output. A project that adds its other worktrees to the writable roots widens it, and so does running Codex without its sandbox (`danger-full-access`), where such a write lands unasked and unjudged.
- **The alternative worth weighing:** add a sweep of every worktree at the turn's end to the held ones. It catches shell-only writes on both runtimes, once per turn, where the turn's end already waits for the importers pass. Its price is the first one's: the operator's uncommitted work in any worktree is judged as the agent's.

**One checkpoint per worktree.** A call counts in every worktree its session holds when it starts. When a call finishes, a checkpoint runs in each worktree the session holds where no counted call is still running, one after another, and the agent hears their reports together. The turn's end runs over every worktree the session holds: the checkpoint, the importers pass, the type errors and ruff's findings left in what it touched, and the notes removed, each file named in full. The calls running are kept per worktree, each with its session and conversation: one set per repository would let any session's long call hold back every other session's checkpoints, and one set per session would let a checkpoint judge another session's write in progress in a worktree they share.

**What's kept where:**

| What | Kept | What it holds |
|---|---|---|
| The store: snapshots, the accepted tree, the state (commits seen, saved versions, files held) | per worktree | What judging that worktree compares with and restores from |
| Each worktree's `HEAD` at its last checkpoint | per repository, beside the verdict log (`heads.json`) | Read by every worktree's checkpoint: its own, to see `HEAD` move (step 4), and the others', as commits judged (step 3) |
| A session's record: approvals, files touched and watched by each conversation, writes pending, content judged and its conversation, notes removed, mail | per worktree, per session | A session has one in each worktree it holds; an approval covers the path in its worktree only, since across the repository's worktrees an approval on one branch would cover different content on another |
| The calls running | per worktree (`running.json`) | Each call records its session and conversation; it counts in every worktree its session holds |
| Saved versions | `<worktree>/.lup/saved/` | The agent's refused versions, which it edits and moves |
| Holds | per worktree's store | A checkpoint over several worktrees can make a hold in each, waited on one after another; a move's hold names its commit, and keeps the verdicts its answer is logged against |
| The importers pass | per worktree | The turn's end waits for the pass of every worktree the session holds |
| The engine | per worktree | A session writing Python in several worktrees runs an engine in each, each 1.5 to 2.7 GB on a 700-file project (the spike), until it's idle |
| The declaration | the integration branch's tip, one for the repository | Below; loaded when a checkpoint or a write first needs it, not for a call's start or finish alone |
| The verdict log | per repository | Each verdict names its worktree |
| The session index | per session (`session-index/<session>.json`) | The repository and the worktrees held |
| The subagents at work, and what held each conversation's end when it last blocked | per session (`session-index/<session>.conversations.json`) | A subagent shares its session's id, and each conversation's end reads them whichever worktree it's in |
| The importers pass: what's pending, what it found, and the conversations that wrote what it re-checks | per worktree (`importers.json`) | Each conversation named with its session, since any session's hook may collect what the pass found |

**State an earlier judge wrote** never breaks a running session. The session index and the calls running live in `session-index/` and `running.json`; the earlier files (the index's `$XDG_STATE_HOME/lup/sessions/<session>.json`, each store's `calls.json`, and the repository's `declaration.json`, the last declaration that loaded as an earlier judge kept it) are left unread: reading their shapes too would be a compatibility shim, and refusing them with an error would fail every hook of every running session until it's restarted. A session running when the judge is reinstalled is picked up from its next hook's working directory, its starting tree and its record in each store kept; a call in flight then is forgotten, so its finish is a finish with no start. A store has no `HEAD` recorded until a session begins there or its first checkpoint runs, so a commit made before that isn't judged as a move. A verdict line without a worktree reads with none, and a hold without a commit as one an agent waits on. The session's record keeps its file, since moving it would forget its approvals, pending writes and mail; a field added to it reads as empty from a record written before it existed, and a record whose shape changed is read by nothing but the session that wrote it, which starts afresh to load. Content judged without its conversation reads as the session's own, and an importers pass's state without the conversations that wrote what it re-checks reads as no one's, so what it found is told at the next checkpoint but holds no end.

**The declaration, from the integration branch.** Every worktree of a repository is judged by the declaration committed at the integration branch's tip, never by the worktree's own. As the judge's code comes only from the installed copy, a branch can't change what judges it. A branch's edits to `lup_project.py` take effect when they land on `dev`, as rules take effect when the operator installs them; a branch that needs a declaration change lands it first, as a hotfix on `dev`. An uncommitted edit in the `dev` worktree takes effect when it's committed.
- **Which branch (leaning):** `dev` by default, named by a `lup-dev` setting, `LUP_INTEGRATION_BRANCH`, set where the hooks run (the operator's environment, or `.claude/settings.json`'s `env`, both out of the agent's reach). A `[tool.lup]` key would have to be read from some branch before the branch is known, and a branch could repoint it; a git config key (`lup.integration`) an agent's shell can rewrite unjudged, since no snapshot covers the git directory; and the remote's default branch (`origin/HEAD`) is `main` here, which isn't where work lands.
- **Without that branch (leaning),** a repository is judged, worktree by worktree, by the declaration each one's `HEAD` commit holds, and by the defaults before its first commit: uncommitted edits never judge, but a branch's own commits do there. The worktree's own files would let uncommitted edits judge; the defaults would silently drop the project's protections; and an error until the setting names a branch that exists would stop judging in every such repository.
- **Loaded when a judgement first needs it,** so a call's start and a finish that runs no checkpoint load none. Loaded at every hook, it would cost an export and an import each, and a broken declaration would fail calls that judge nothing.
- **How a commit's declaration is imported:** the commit's Python modules (`.py`, `.pyi`) and its `pyproject.toml` files (`git ls-tree`, then `git archive` of those paths) are exported once, into the repository's state (`declarations/<commit>/`), written whole before they're moved into place; earlier commits' exports are removed, so while a stand-in judges (below), the failing tip and the stand-in's commit remove each other's export, and both are exported again at each load **(leaning)**. An import hook reading modules straight from git's objects would write nothing, but is an importer to keep, and leaves modules without a file; an export into a temporary directory at every judgement is an archive each time; and the whole tree would carry data and assets too. The declaration is read from the export, importing from its root, `src/` and workspace members as from a worktree's, and the conditions modules its modules name are read there too: the declaration and what it names come from one commit. Reading the conditions modules from the worktree being judged would let a branch add a condition and name it at once, but split what the declaration names across two commits. Python keeps a module once it's imported, and every declaration is the module `lup_project`, so loading one sets aside a `lup_project` imported before from elsewhere and drops from `sys.modules`, once it's loaded, the modules it imported from where it was read (`declaration/load.py`, `importable`), and only those, so a worktree whose own `lup_dev` runs the check keeps it; otherwise two worktrees' declarations loaded in one process both come back as the first's. An interpreter per declaration would be a Python start per worktree per hook. Finding a conditions module, which imports its parent packages, does the same. Neither writes bytecode: a `__pycache__/` the judge left in a worktree that doesn't ignore it would be judged at the next checkpoint as the session's new file.
- **The gate reads the worktree as it stands** (`lup-dev rules check`, and `Worktree.at`): it checks a branch as it would land, uncommitted edits to its declaration included, and takes no stand-in. Read from the integration branch, the gate would check a branch by a declaration it doesn't land with.
- **The roles' pytest configuration** (test roots read from each `pyproject.toml`) stays the worktree's own: it's pytest's configuration, a protected path, not lup's declaration.

**A declaration that can't load has a stand-in.** A branch that adds a field to the declaration lands on `dev` before the installed judge knows the field, until the operator reinstalls. So each declaration that loads is kept, per repository (`last-declaration.json`, beside the verdict log), and where the one due can't load, whatever importing or resolving it raises (conflict markers, a module dropped that isn't there), the last that loaded judges instead: the field takes effect at the next install, and nothing locks up meanwhile. Denying every file tool's write instead would stop every session in the repository from the moment a declaration field lands until the next install; falling back to the defaults would silently lose the project's protections (`lup_dev/catalog/**` here). It's kept resolved, as the values judging reads (`Declaration`): the declaration itself may hold a module or a runner of the project's own, classes JSON can't bring back, so the runner is kept as the commands it puts before a tool (`Prefixed`, `docs/declaration.md`, *The runner*), which a stand-in runs ruff and the engine with. Re-importing the kept commit's declaration instead would keep it whole, but stands in only while the installed judge can still import it, which a reinstall can end. A commit's `pyproject.toml` that doesn't parse, or whose uv workspace doesn't validate, isn't a failed import: it has no stand-in, and fails the hook. The agent is told once for each failure, with the error, the commit that failed and the one standing in, to pass on to the operator; reinstalling the judge from `dev` is usually the fix. With nothing kept the failure stands, and the gate never takes a stand-in: there, a declaration that can't load fails.

**When judging fails at a turn's end,** the turn ends anyway: the agent can't fix the judge. The operator is warned once for each failure in a session, in the runtime's warning to the user (`systemMessage` on both runtimes), which doesn't continue the turn; anything a `Stop` hook tells the agent continues it, so telling the agent in `additionalContext` would continue the turn on Claude Code as a block does, and blocking once at every turn's end would make the agent repeat a notice it can't act on. Elsewhere, a failure denies a file tool's write, naming it, and other calls go on, told (*The two runtimes*): a crash would read as no decision to the runtime, letting a write meant for review through.

**Reports name each file in full.** A session hears about several worktrees, from any working directory, so reports name each file by its absolute path, as pyright's command line does, and the `mv` that puts a saved copy in place names both ends in full. So does each ask, in the runtime's prompt and in a hold. Paths relative to each worktree, under a heading naming it, would have an agent working elsewhere join them by hand, and leave the operator unable to place an ask when a session works in several. The verdict log keeps paths relative to the worktree it names.

## Asking the operator

**On Claude Code, through its own prompt,** which asks before the change lands, so there's no hold on Claude Code; the interim review hook, where it's registered, can carry that prompt to the first lup's dashboard (*Checks owed*). The `PreToolUse` hook answers `ask`, with a reason naming what's asked: the new path, the protected path, the public name or signature, or the rule and the reason given for an `ignore`.
- A hook's `ask` forces a prompt in auto mode too (hooks docs; tested on this repository for the bare `Write` rule).
- Settings' `ask` and `deny` rules are evaluated whatever the hook answers, so `.claude/settings.json` carries no blanket `permissions.ask` on `Write`, which would prompt for every `Write`.

**On Codex, through a hold.** Codex's `PreToolUse` can't answer "ask", and `apply_patch` is judged at the checkpoint. So an ask on Codex is held at the checkpoint: the agent waits inside the hook, and the operator answers with `lup-dev holds approve <id>` or `lup-dev holds decline <id> --comment …`.
- `lup-dev holds` lists what's waiting, with the diff.
- A decline puts the change back and saves it, and the agent's report gives the operator's comment. An approval with a comment passes the comment on.
- The hook waits up to 24 hours, polling the hold every 2 seconds. Unanswered by then, the change is put back and saved, and the hold stays open: an answer given later reaches the agent at its next checkpoint, and an approval then covers the path, so the saved version can go back into place. Codex's hook timeout has no maximum, so the hooks that can hold take a `timeout` of more than a day (*Installing it here*).
- While a hold waits, the store is released: other calls' checkpoints leave the held files alone.
- This is a declared gap: on Codex the operator answers from a terminal.

**A move's asks, after the fact.** What a move of `HEAD` asks (step 4 of the checkpoint) is already committed, and it isn't put back, so on both runtimes it's kept as a hold that no agent waits on **(leaning)**. Told and logged only, it would reach the operator only through the agent's report; a hold the agent waits on would need Claude Code's `PostToolUse` timeout raised to a day in `.claude/settings.json`, and would block a session that may not have made the commit. `lup-dev holds` lists these apart from the holds an agent is waiting on, with the commit and the diff. An answer is logged when it's given, against the verdicts the hold keeps, and reaches the session that found the move at its next checkpoint, as a late answer does. A decline changes no file: reverting the commit is the operator's, or an agent's at their word. A late answer to a hold whose wait ran out is logged the same way, when it's given; an answer an agent waits on is logged by the waiting hook. Logging an answer when the session that found it hears it would lose it if that session never runs again.

**Nobody answers their own hold.** `lup-dev holds approve` and `decline` refuse to run when their environment shows they run inside an agent's session: Claude Code's `CLAUDE_CODE_CHILD_SESSION`, Codex's `CODEX_THREAD_ID` (*What the runtimes do*). Each adapter reads its own runtime's variable, its runtime's wire spelling, through a small settings model of its own; as fields of `settings.py`, they'd name the runtimes in the core. That stops a mistake, not a determined agent: while agents run on the host as the operator's user, an agent could write the answer itself. The real separation comes with containers, where the hold store sits outside the container and answering runs only on the host.

## Refusals

The refused file goes back to its accepted content, or never changes if it was refused before landing. The agent's version is saved under `.lup/saved/<n>/<path>` in the worktree (`.lup/` is ignored, so saved copies are never judged). The agent fixes the listed lines there and moves the file into place; nothing is resent whole, except a new file, which goes back through `Write` and its prompt.

The report, in pyright's shape:

```
lup refused 1 file. It is unchanged; your version is saved.

/work/lup/src/lup/claude.py (saved at /work/lup/.lup/saved/3/src/lup/claude.py)
  /work/lup/src/lup/claude.py:41:12 - tuple-shape: a fixed-length tuple[str, int] hides what each position means
      steer: name the fields with a pydantic model
  /work/lup/src/lup/claude.py:88:5 - regex: `import re` parses with a regular expression
      steer: use the format's own parser (lup docs rules regex)

Fix these lines in the saved copy, then move it into place:
  mv /work/lup/.lup/saved/3/src/lup/claude.py /work/lup/src/lup/claude.py
To keep a finding, add on its line or the line above (the operator is asked):
  # lup: ignore("<rule>", why="<reason>")
```

Each path is absolute, the `mv` naming both ends in full, since a session's writes are judged in several worktrees and the agent's working directory may be any of them (*Every worktree of the repository*); so is each path an ask names. The example's layout is the code's: `tests/test_report.py` finds the block after "The report, in pyright's shape:", renders the two findings it shows, and checks that the rendering matches the block. Their messages and steers are illustrative: the engine writes a message as what it saw followed by the rule's mistake, and the steer is the rule's own.

**Which findings refuse.** lup's findings on the lines the change touched; for a new file, every line. The refusal lists every one of lup's findings in the file, and what's wrong with its directives, so one pass fixes them all, rather than a resend for each rule; pyright's and ruff's findings are information (below). Findings on untouched lines are listed under their own heading and don't refuse, rather than any finding in a touched file refusing it; they appear mostly where a rule is newer than the code.

## Type errors and ruff's findings

They're information, not refusals, since information never travels on a blocking channel, which a refusal at the checkpoint is:
- at each checkpoint, pyright's type errors and warnings and ruff's findings in the files changed, test files included, as plain context beside the call's result; with them, lup's findings on lines no change touched, and the type errors the background pass found in the files importing what changed. pyright's warnings count as its errors do, not errors alone as the pyright CLI's exit status has it (the engine's `report.ts`), and the gate runs `pyright --warnings`;
- when the session's turn ends, the `Stop` hook refuses to end it while the files its own conversation touched, or files importing them where the pass found errors, have type errors, warnings or ruff findings, saying which; but not in a file a subagent at work touched too, nor on the same findings again right after it refused (*The session's turn's end holds on its own conversation's files*, *While a subagent works*), when they're information. A subagent's end (`SubagentStop`) never holds on them: every worker passes the gate before it hands back;
- the formatter runs when work lands, with ruff's safe fixes (below).

ruff runs with `--ignore-noqa`, and pyright with `enableTypeIgnoreComments = false`; lup filters both through its own `# lup: ignore`, so there's one suppression syntax (`docs/conventions.md`). ruff is the one the project's runner finds in the worktree, as the gate runs it (`docs/declaration.md`, *The runner*): with `Uv()`, lup's default, the project's own where the environment uv gives the worktree has one, else the `PATH`'s **(leaning)**. It runs as the runner's command for the judge, `runner.judging(["ruff", "check", …])`, from the worktree's root: for `Uv()`, `env -u VIRTUAL_ENV uv run --frozen --quiet ruff check …`. The runner is the declaration's the worktree is judged by, kept as its commands (`Declaration.runner`, a `Prefixed`), a stand-in's included, and passed with each run (`Linter.findings`); `lup-dev rules check` passes the worktree's own, as the gate. It reads the would-be content through stdin under the file's name, so the project's configuration applies (`codescan/ruff.py`). It runs with `--exit-zero`, since uv's failures exit 1 as ruff's findings otherwise do, and a failure of either raises `RuffError`, with the runner's or ruff's message, as does a runner whose program isn't on the `PATH`, naming it. uv adds about 12 ms a call (26 ms against 14 ms for one file's check), and the judge runs ruff once for the files on disk and once for each would-be content. `.venv/bin/ruff`, else the `PATH`'s, would miss `UV_PROJECT_ENVIRONMENT`, and until the worktree has its own `.venv` run the session's, another worktree's ruff; `--no-sync`, about 3 ms less, neither makes a missing environment nor syncs it; dropping `VIRTUAL_ENV` from a copy of `os.environ` is what lup's `os-environ` rule refuses; and the `sh` failure, left to propagate, would carry sh's truncated message. Like the engine's, these uv calls never relock (*The engine*).

**A finding ruff fixes safely is never reported to the agent:** not as information at a checkpoint, not at the turn's end. ruff's JSON output gives each finding's fix with its applicability, read as ruff's three values (`safe`, `unsafe`, `display-only`), so an unknown one fails loudly; `ruff check --fix` applies only a `safe` one, so those are the findings marked `fixable` (`codescan/ruff.py`). One whose fix is `unsafe` or display-only, or that the configuration makes unfixable (ruff gives no fix then), is reported: counting any fix at all would hide findings `--fix` leaves, and leaving out findings with an unsafe fix too would leave a rewrite that can change what the code does unreviewed. Fixability is a field of `Finding` (`fixable`, `codescan/contract.py`), and fixable findings are left out where the agent hears them, not where ruff is read: dropped in `Ruff.findings`, they'd make the `ignore` naming one read as unused (`unused-ignore`, a refusal) and vanish from `lup-dev rules check`. Fixing them is the landing session's job: `lup-dev check --fix` applies ruff's safe fixes and runs the formatter before the gate's steps, and the landing step in `AGENTS.md` runs it on the merged result, folding what they change into the merge commit. CI, and the gate run without `--fix`, only check, so a fixable finding still fails the gate until it's fixed. The judge never rewrites a file under the agent, as applying the fixes after each write would. A fixable finding still counts for the `ignore` naming it, which isn't reported unused; `--fix` applies the fix anyway, since ruff doesn't read lup's `ignore`.
- **Why:** a fix ruff makes safely is a mechanical rewrite that changes nothing a reader decides, and told one by one, such findings spend an agent's turns.

**At the gate, `lup-dev rules check`** checks every Python file as the turn's end does, and fails on any finding: lup's (in production and protected modules; tests are exempt), pyright's, ruff's, each through `# lup: ignore`, and each deferral whose issue is closed or whose condition holds. Since ruff and pyright alone don't read lup's `ignore`, this is the check that decides whether a finding is kept. It reports fixable findings too, as the gate's `ruff check` does, so it never passes where the gate fails. It's the gate's `rules` step, so lup's rules hold wherever the gate runs, the judge running or not (hooks off, Codex, CI), and "clean" means one thing everywhere; left to the judge alone, code that breaks them would land wherever the judge isn't running. The judge keeps checking at each write, for early feedback, and its asks stay at the write. Each finding is listed as a refusal lists it, with its steer, its path relative to the worktree.
- **It names no files (leaning):** with no paths, it lists the worktree's files from git (`ls-files -z --cached --others --exclude-standard`: tracked, and untracked but not ignored), keeps those on disk, and checks those the declaration's roles check, so the roles the judge reads decide, and no list of files is written anywhere. A file deleted but not yet staged is left out, since the engine fails a whole check on a file that doesn't exist (`… doesn't exist`), and `-z` keeps a name git would quote (a `"` or a tab in it) as it is. Paths or patterns written in the gate's catalog would be a second list that must agree with the roles; every `*.py` under the root by glob would read ignored directories (`.venv/`) and need the roles anyway.
- **It runs whole (leaning):** lup's findings, pyright's and ruff's through `# lup: ignore`, and the deferrals, whose issues it asks GitHub about through `gh`. So a type error or a ruff finding fails its own step and `rules`, and the report lists it twice; an option reporting only lup's findings and the deferrals would have each finding fail one step, at the cost of an option on the command line. Either way, the gate's `ruff` and `pyright` steps don't read `# lup: ignore`, so a finding one keeps out still fails them (#45).
- **It asks the worktree's engine,** starting one where none answers, as the judge does; one it starts stays for `LUP_ENGINE_IDLE` (15 minutes by default) and keeps its lock and log in the worktree's store, under `$XDG_STATE_HOME/lup/`. A worktree the judge reads has one warm already. An engine that exits after the check would never stay in memory, but would always be cold, and is a mode the engine doesn't have.

**The gate's steps** are the worktree's own declaration's, loaded from its root and resolved (`docs/declaration.md`): `Python`'s from `lup_dev/catalog/gate.py`, and any a module adds. `lup-dev check` runs them from the root, in order, every one even after one fails. Each step's command is the tool alone, run through the project's runner (`runner.command(…)`: `uv run …` for `Uv()`), or as written for a step with `in_environment=False`, so the worktree's own tools and code run, never the installed judge. A declaration that can't be loaded fails the gate, never falling back to the defaults. Before any step, the gate checks every selected module's requirements at once (`docs/declaration.md`, *Requirements*): a required tool missing stops it, naming each one missing, the module needing it and how to install it, and an optional one missing is said once, at the head of the report. In lup's repository:
1. **engine:** the engine's build, when its bundle is missing or older than its sources: lup's own module's step (`LupDevelopment`, in `lup_project.py`), placed before `rules`, since only lup's repository has an engine to build;
2. **rules:** lup's rules, `lup-dev rules check`, which reads that engine;
3. **ruff:** `ruff check --ignore-noqa`;
4. **format:** `ruff format --check`;
5. **pyright:** `pyright --warnings`;
6. **pytest:** the tests;
7. **lint-imports:** the import contracts.

`rules` comes right after the engine's build, which it reads, and before ruff, rather than after pyright with the other checks, or last **(leaning)**: lup's findings lead the report as a refusal leads the judge's answer, and its seconds (1.3 s warm, 5.6 s with the engine cold, over this repository's 66 files) come before pytest's minutes. Every step runs whatever the ones before gave, so the position orders the report and nothing else.

With `--fix`, ruff's safe fixes and the formatter rewrite the worktree first (above): `ruff check --fix-only --ignore-noqa`, then `ruff format`, run through the runner as steps before the gate's and reported like them. `--fix-only` applies the fixes and reports nothing, leaving what's left to the gate's ruff step; `ruff check --fix` would also report what's left and fail, so each finding would be reported twice, and a command of its own would be one more for a landing session to remember to run first. These fix steps are data in `gate.py` (`Fixes`), not beside the gate's steps in `catalog/gate.py`, which leaves the protected catalog unchanged **(leaning)**; the catalog, protected with the rest of the gate's data, is the better home, and moving them there is a small follow-up. lup's rules have no fixes of their own.

## Shell commands

- **On the host:** narrow allow rules in Claude Code's own settings, such as `Bash(uv run pytest:*)` or `Bash(git status:*)`, in place of a vocabulary of commands, which would need a shell-spelling parser (`docs/graveyard.md`). Claude Code matches them, so lup parses no commands; auto mode keeps narrow rules and drops broad ones. Here they're written by hand in `.claude/settings.json` (*Installing it here*). Everything else goes to the runtime's own mode, and what a command writes is judged at the checkpoint either way. The prompts the rest causes are to reach the review dashboard as soon as something can carry them there: the interim review hook does, where it's registered (*Installing it here*).
- **In a container:** every command runs; the container is the wall.
- **A probe owed:** whether a `PreToolUse` hook's `allow` skips auto mode's classifier. No vendor doc says so. If it does, the hook can allow commands itself where the classifier only adds latency.

## The engine: one typed tree

Every lup rule reads one typed tree: each file parsed once and type-checked once, every rule reading types straight from that tree. There's no syntax-only first stage, such as ruff's `banned-api` in front of a syntax checker, and no language server asked about one position at a time: the rules are typed from the first one, so they never grow as a patchwork of syntax checks.

**Pyright's own tree, built against its source at a pinned release.**
- **What it is:** a small TypeScript program built against `packages/pyright-internal` from pyright's repository, shipped prebuilt inside `lup-dev`. It's built, never committed: `packages/lup-dev/checker/build.py` reads the pinned pyright from `uv.lock`, fetches its source once into `$XDG_CACHE_HOME/lup/pyright/`, type-checks and bundles the engine with esbuild (the engine's one npm dependency), and copies the stubs beside it into `lup_dev/codescan/bundle/` (`layout.py`, `Bundle`), which git ignores and the wheel carries. Committing the bundle and its 31 MB of stubs would spare a fresh checkout the build, at the cost of every pyright upgrade landing as a large binary diff.
- **How it runs:** one long-lived process per worktree with a session, loading the project the way pyright does and keeping it warm, on a Unix socket under `$XDG_RUNTIME_DIR/lup/`, not a TCP port, which any local user could reach. A hook that finds none starts it, under a lock so hooks running at once start one; an engine per hook would reload the project each time (1.4 s on this repository). It stops when nothing has asked it for `LUP_ENGINE_IDLE` (15 minutes by default), and at once for a client that expects another build, told apart by the bundle's size and modification time, or another environment (*Which environment*, below), so a rebuilt engine, or one started with another runner, is replaced at the next request.
- **Keeping in step without a file watcher:** a file checked with would-be content holds it until the next request, which puts the disk's back unless the edit landed, so a landed edit costs no second check; an edit judged as the judge asks (the content after, before and at the session's start, each as would-be content) and then landed is what the next file's check reads. A file read from disk is checked by its `stat`, with pyright's own fingerprint deciding; a changed directory re-enumerates the project's files; a changed import search path drops pyright's import cache; a changed configuration (pyright's, and the files the runner says decide the environment: for `Uv()`, `pyproject.toml`, `uv.toml`, `uv.lock`, `.python-version`), or the interpreter the runner named going or replaced, builds a new program, which asks the runner again.
- **Which environment:** the one the project's runner gives the worktree, which the gate's pyright step reads (`docs/declaration.md`, *The runner*). The engine is started with the runner's command for Python (`runner.judging(["python"])`) and the files deciding its environment (`runner.environment()`), each as a JSON list (`--interpreter`, `--environment-files`). Every request carries the same pair, so an engine started with another runner answers stale and is replaced, as one from another build is. The runner is passed with each request (`Checker.check`, `Checker.importers`), the one of the declaration the worktree is judged by, kept as its commands, for the judge, the turn's end and the importers pass alike, so they share one engine; `lup-dev rules check` passes the worktree's own. Building a program, the engine runs that command from the worktree's root, which prints its interpreter (`sys.executable`, as JSON). For `Uv()`, lup's default, it's `env -u VIRTUAL_ENV uv run --frozen --quiet python`, the inherited `VIRTUAL_ENV` left out, since it's the session's and may be another worktree's. That honours `UV_PROJECT_ENVIRONMENT`, and makes the environment if it's missing, synced to `uv.lock`, so the project's own packages resolve to the worktree's sources through their editable installs, from the first check on. The interpreter decides where imports resolve, so it's stamped (followed to what it links to) with pyright's configuration files (`pyproject.toml`, `pyrightconfig.json`) and the runner's (for uv, `pyproject.toml`, `uv.toml`, `uv.lock`, `.python-version`), checked at the start of each request, and a change to the interpreter or any of them builds a new program, which asks the runner again (`checker/src/program.ts`, `interpreterOf`, `setupChanged`). `uv.lock` is stamped so a lock that arrives unsynced, with a merge or a checkout, is synced before the next check reads the environment. The stamps cost a `stat` a file a request, and a rebuild when one changes; asking uv costs about 28 ms a program, against 1.4 s for the program, and making lup's environment from uv's cache took 0.7 s.
  - **Not found another way:** `.venv/bin/python` named directly would miss `UV_PROJECT_ENVIRONMENT` and other platforms' layouts, and before a worktree has its `.venv` read the session's `PATH`; `uv python find`, where the environment is missing, falls back to a bare interpreter without the project's packages; asking uv at every request costs about 28 ms each, for what the stamps see; the client naming the interpreter in each request would move the engine's setup into Python; the engine spelling uv itself would be one more place spelling it, which a project on another runner couldn't change; and an interpreter fixed for the engine's life would keep a branch worktree's checks on another worktree's sources until the engine idles out.
  - **Never the session's environment:** an engine reading the `PATH` or `VIRTUAL_ENV` it inherited from the hook that started it would check a branch worktree against another worktree's modules, and report a method the branch just added as missing.
  - **Never relocking (leaning):** the judge's uv calls, the engine's and ruff's, are `Uv`'s command for the judge, which reads `uv.lock` with `--frozen`: they make and sync the environment, but never write the worktree's `uv.lock`, a protected path the checkpoint would judge as a shell write in the agent's call, and never resolve over the network. A worktree whose `pyproject.toml` has no `uv.lock` beside it gets no environment, and the engine and ruff fail with uv's message (`Unable to find lockfile at uv.lock`, run `uv lock`) rather than reading another. A `pyproject.toml` edited without relocking is read as the lock has it until something relocks, as the agent's next `uv run` or the gate does. Plain `uv run`, as the gate runs it, relocks a stale or missing lock, so in a project without a lock, or with a `pyproject.toml` but not on uv, the judge would write a new `uv.lock` (checked: a `pyproject.toml` holding only `[tool.pyright]` got a `.venv` and a `uv.lock`); `--locked` fails whenever the lock is stale, as after any hand edit to the dependencies.
  - **A project not on uv** declares its runner (#36): `Plain()`, each tool and the interpreter as the `PATH` finds them, or a runner of its own (`poetry run`, `conda run`). Left on `Uv()`, with a `pyproject.toml`, uv reads it as a project without a lock, gives no environment, and its checks fail, saying so; without one, its checks read whichever Python uv finds there (a `.venv` in the worktree or above it, else an installed one).
- **For each judgement:** it checks the given files, on disk or as would-be content. Each rule's check (*How a rule is declared*, below) reads pyright's parse tree, asking pyright's type evaluator for any expression's type. It also reports each file's public surface, the `# lup:` directives, and the modules each file imports. Nothing checks those imports against the import-linter contracts at the edit; the gate's `lint-imports` step does (#39).
- **What comes back:** one list, pyright's errors and warnings and lup's findings in the same shape, as JSON lines the Python side reads into pydantic models. Spans count lines and columns from 1, columns in characters as Python counts them, and leave out the parentheses around an expression.

Pyright has no plugin API, and its published package is one bundled file whose internals can't be imported. Nothing existing does this: Zzzen/pyright-lint has been dead since February 2023; basedpyright, ty, Pyrefly and Zuban offer no extension API; pyright's type server answers one query per expression, which is the oracle approach. mypy's tree in Python stays the fallback if building on pyright's internals turns out too costly to keep up; it would be a second type checker that can disagree with pyright at the edges.

**Measured by a spike** (pyright 1.1.414, about 970 lines of TypeScript, evidence under `tmp/spikes/pyright-rules/` in the `main` checkout):
- **Same answers as pyright:** on the first lup's library, 32 of 32 type errors matched the CLI's exactly.
- **The rules cost under 1% of the check,** at most 8 ms per file.
- **Warm re-checks:** one changed file 65–270 ms median (10–620 range); ten files 0.5–2.7 s, over the target. Nearly all of it is pyright's own re-check, which the type errors need anyway. The machine was heavily loaded, so these are pessimistic.
- **Accuracy:** the typed `string-split` leaves out `shlex.split` and `re.split`, which a syntax-only rule flags. `tuple-shape` caught every alias form tried.
- **Directives** parse in place with pyright's own expression parser.
- **Upgrades:** the rule code compiled unchanged against pyright releases 17 months apart; about 40 lines of project setup broke.
- **Cost:** a 3.5 MB bundle plus 28 MB of standard-library stubs, and 1.5–2.7 GB of memory on a 700-file project. With many sessions, that's per worktree, which is why idle processes stop.

**How the engine answers the spike's questions:**
1. **Aliases:** a tuple alias is flagged where it's defined, and its uses only when it's defined outside the project.
2. **`Any`:** `string-split` fires on a receiver declared `Any`, but not on one pyright can't infer, so findings don't depend on the environment being installed.
3. **Unions:** `str | X` is flagged when any member is `str` or `bytes`.
4. **Tuples:** `list[X]` is the one spelling of a sequence (`docs/conventions.md`), so `tuple-shape` flags every tuple type; edge tuples need no special case.
5. **Files that import a changed one:** the rules read only the changed files, so their findings come at the edit. The changed files' importers are re-checked for type errors in the background, and their errors arrive at the next checkpoint. One background pass at a time per worktree: a change while one runs marks it to run once more afterwards, over everything changed, never a second process. The turn-end check waits for the pass, so no type error surfaces after the session, as one could with the importers left to the gate. It's a lock the pass holds for its whole life (`policy/importers.py`, `ImportersPass`), which the system frees however the process ends: a request adds its files to what's pending and starts a process only when the lock is free; the pass takes everything pending, batch after batch, and releases its lock only once nothing is, under the state's own lock, so no request finds it gone with work left. Two requests racing can start a second process, which finds the lock held and exits without running a pass. Work left pending with no pass running is done by the turn's end while it waits. Checking the pass's process id with `os.kill(pid, 0)` instead of the lock would kill the process on Windows, and be fooled by a reused id. The pass re-checks a file at a time, so a check waiting behind it runs between two files, and a check that changed the disk makes the pass look again (`checker/src/engine.ts`, `checker/src/server.ts`); run whole, it would hold a check behind 27 seconds of re-checking on the first lup's library.
6. **Type stubs:** the pinned standard-library stubs ship beside the bundle.

## How a rule is declared

**One table:** `lup_dev/catalog/rules.ts`, a plain object literal with one entry per rule, keyed by the rule's id. Each entry holds the rule whole:
- **`mistake`:** the mistake it prevents, as a sentence that stands alone;
- **`steer`:** where it steers instead, as a sentence that stands alone;
- **`check(file)`:** how it recognises its case, reading pyright's tree and asking pyright's type evaluator, through the engine's helpers;
- **`examples`:** its specification, as code (below).

```ts
'string-split': {
    mistake: 'Splitting structured text by hand matches the inputs it was tried on, and fails quietly on the rest.',
    steer:
        "Read the text with its format's parser: `shlex.split` for a command line, `urllib.parse` for a URL, " +
        '`email` for headers, `csv` for rows.',
    check(file) {
        for (const call of file.methodCalls(['split', 'rsplit'])) {
            const separator = call.argument('sep', 0);
            if (separator && !file.isNone(separator) && file.isText(call.receiver)) {
                file.report(call.node, `\`.${call.method}(…)\` splits a \`${file.printType(call.receiver)}\``);
            }
        }
        for (const call of file.methodCalls(['partition', 'rpartition'])) {
            if (file.isText(call.receiver)) {
                file.report(call.node, `\`.${call.method}(…)\` splits a \`${file.printType(call.receiver)}\``);
            }
        }
    },
    examples: {
        flags: [{ code: python`…url.split("/")[2]…`, rewritten: python`…urlsplit(url).hostname…` }],
        passes: [python`…shlex.split(line), line.split()…`],
    },
},
```

- **Where it lives:** in `lup_dev/catalog/`, with lup's other policy data, which `lup_project.py` protects: the operator reviews every change to a rule before it lands. Beside the engine in `checker/src/`, the table would sit outside the protected catalog. It's TypeScript in a Python package's directory. The engine's build (`packages/lup-dev/checker/`) compiles the table into its bundle, and the table imports the engine's helpers through a path alias (`checker/…`) rather than relative paths across the tree. The build hands its `tsconfig.json` to the bundler explicitly: the bundler otherwise looks for the one nearest each file, and finds none above the table (checked with esbuild and tsc).
- **Each check stays short,** reading like the rule's sentence. What checks share is a helper in the engine (`checker/src/`), outside the table: finding the calls of a method, whether pyright finds an expression to be text, what a written type denotes with its aliases. A check that grows long is a helper waiting to be written.
- **The engine makes each finding whole.** A check reports where and what it saw ("`tuple[str, int]` is a tuple type"); the engine adds the rule's mistake to the message, and its steer. The judge receives complete findings, which `codescan/contract.py` carries as they come.
- **Python learns about rules only from the engine.** The engine lists its rules (id, mistake, steer, examples) straight from its table, without loading a project (`Checker.rules()`, `lup-dev rules list`). A check carries each module's rule selection as the declaration records it, which the engine resolves against its table, refusing one naming a rule it doesn't have. An `ignore` naming no rule never keeps a finding, so the judge reports it as `unused-ignore`. Python never declares a rule, and needs no `rules.json` compiled from the table, which would be one more generated file.

**Why a table of code:** recognising a case takes pyright's own tree and types. A vocabulary of declared matchers keeps recognition reviewable, but spreads a rule over the vocabulary and the engine. Python rules over `ast` asking the warm engine by position give the same findings as the table on 739 files (a spike, `tmp/spikes/rule-shape/` in the `main` checkout), but need two trees to agree, silently miss types pyright reads in strings outside annotations (`cast("tuple[int, str]", value)`) unless the engine lists them, and their checks cost 10 to 20 times more. The table reads the one typed tree directly.

**Examples are the specification,** held in the entry as code (`examples`), short enough to read with the rule:
- **`flags`:** code the rule flags, each with its `rewritten`, the same code done the steer's way. A rule needs several kinds of case, which a pair of files couldn't hold.
- **`passes`:** near misses the rule must not flag: `.split()` with no separator, `shlex.split(…)`.
- **What the engine's tests check** (`tests/test_engine.py`), placing each snippet as a module of a small package: each of `flags` gets a finding from its rule and no other, so each example shows one rule; each `rewritten` passes every rule, ruff and pyright, so a rule's steer never trips another (`docs/conventions.md`, *Keeping the rules cohesive*), but for pyright's missing-source warning where a steer names a library lup doesn't install and pyright has its stubs (`tqdm`); each of `passes` gets no finding from its rule; and every rule has at least one of `flags`.
- **Kept short:** a rule needing a long example has a check or a steer that's too broad.
- Being strings in the table, they're no Python file of the tree, so no tool needs telling to leave them out, as example files by rule id (`catalog/examples/<id>/flagged.py`, `fixed.py`) would.

**`docs/rules.md` is compiled from the table** (`lup-dev rules docs`, which asks the engine) and committed: the one generated file, in place of a hand-kept table in `docs/conventions.md`. It opens by saying it's generated from `lup_dev/catalog/rules.ts`, and that the table is what to edit. A gate test compiles it again and fails when the committed copy is stale. `docs/conventions.md`'s *The rules* points to it, and a test checks that every rule id it names under *Enforced by:* is one the engine has. The engine's bundle is built, never committed.

**Every module under `catalog/` is protected,** the table included: changing one asks the operator, and a Python module there gets lup's rules as well, at the edit, at each checkpoint and at `lup-dev rules check`.

**Selection and exemptions are the project's declaration's:** which rules run (`docs/declaration.md`), and where a rule doesn't apply (`lup_project.py` exempts the library's front door from `runtime-mention`, since it names the runtimes as the clients a caller chooses between, and the catalog from `constant-home`, since it's where lup's policy data lives). The table describes rules and holds no project's exemptions, none written on a rule's entry. Each check request carries the selection, each module's as recorded with the module's own default, and the engine resolves it and runs the union (`docs/declaration.md`, *Selecting them*): lup's default is every rule but those `catalog/rules.py` leaves out, `runtime-mention` among them, which lup's own declaration adds back. The judge, the turn's end and `lup-dev rules check` send the same selection (`Worktree.selected`, `policy/checkpoint.py`, read from the declaration the worktree is judged by). The selected rules run on every file the judge sends the engine, tests included, and the judge and `lup-dev rules check` keep lup's findings only in the files the roles rule. An `ignore` naming a rule the selection leaves out keeps nothing, so it's reported as `unused-ignore`.

## The `# lup:` directives

`# lup:` comments are the channel for notes in code. The grammar:
- **A directive is written as a call**, read with the engine's Python parser (`checker/src/directives.ts`); each directive is a small model with its fields.
- **Anything that isn't a call is a note:** `# lup: the retry count matches the provider's documented limit`. Notes are collected for the resolver when it exists.
- **A call to an unknown directive is a finding,** so a wrong directive never sits there silently, doing nothing.

**`ignore`:** `# lup: ignore("tuple-shape", why="sh takes its redirections as positional tuples")`, on the finding's line, or alone on a line above it, where it covers the next line holding code, past blank lines and other comments. Every rule accepts it. Adding one asks the operator. An `ignore` without its reason, or whose rule doesn't fire there, is a finding. Removing one is free: it only makes the rule apply.

**`defer`:** work knowingly left undone, written on the code it's about, so the next reader sees the gap is known and tracked instead of fixing it blind or calling it pre-existing:
```python
# lup: defer(issue=12, why="retries ignore Codex's reset time until its SDK reports it")
# lup: defer(when=sdk_reports_cache_ttl, why="read the TTL from the SDK instead of assuming an hour")
```
- **`why` is required:** what's left undone here, in one line.
- **It needs a way to come back: an `issue`, a `when`, or both.** Without either it's a note nothing would ever close, and such notes pile up.
- **`issue`** is an issue number in this repository, or `"owner/repo#7"` elsewhere: a GitHub issue, not a ledger record. The ledger's to-do items point at GitHub issues too, so a `defer` stays valid when the ledger arrives. A `defer` whose issue is closed is reported, so the comment never outlives the work it points at.
- **`when`** names a condition written in Python, which wakes the deferral when it holds. A condition is an instance of lup's `Condition` ABC (one method, `holds() -> bool`), declared in a Python module one of the declaration's modules names for its conditions (`conditions="audiobook.conditions"`). lup ships stock ones (`PythonAvailable(version="3.15")`, `PackageReleased(name=…, version=…)`); a project subclasses its own. The comment holds only the name, not a requirement string spelled in it, so nothing in a comment is ever run, and the condition is typed and tested like any code.
- **Work that isn't about one spot in the code** isn't a `defer`: it's only an issue (as `frozendict`, issue #7).
- **Checked:** its syntax and fields at the edit, and that `when` names a declared condition; at the gate, the issue's state and the condition, which may reach GitHub and the package index (tests stub both).
  - At the edit, the conditions modules are read without running them (`ast`; finding each imports its parent packages): every name assigned at a top level, plainly or with an annotation, counts as declared. Importing them there would run a project's code in every hook. At the gate they're imported, only `Condition` instances count, and two modules binding one name fail it, since names are shared across a declaration's modules.
  - `PythonAvailable(version="3.15")` holds once uv lists a final release of that version (`uv python list`), not by the interpreter running the gate; `PackageReleased(name=…, version=…)` once the package index has that version or a later final release, not that exact version only, yanked ones left out. Both take what they read as a field, so a test hands them a fake.
  - A closed issue (`gh issue view --json state`) or a condition that holds fails `lup-dev rules check`, so the comment is updated or removed before the gate passes; listed without failing, they'd pile up.

**What the judge reports about directives**, as lup findings on the directive's line (each directive answers for itself through a `Comment` base in `codescan/directives.py`): `unused-ignore` (an `ignore` whose rule doesn't fire on the line it covers, from any owner), `malformed-directive` (what the engine reports as malformed: an unknown call, or one missing what it needs), `defer-issue` (an `issue` that's neither a number nor `owner/repo#7`), `defer-condition` (a `when` naming no declared condition), and at the gate `defer-closed` and `defer-due`. They live beside the directives, not in the rule table: the engine doesn't report them for the judge to dispatch on directive kinds (`docs/conventions.md`, *Dispatch*).

**Removing a note** is never refused:
- a note or directive added during this session can be removed freely, so an agent can take back its own `defer`;
- one present when the session started can be removed too, and the removal is reported: the turn-end check lists the notes present at the session's start that the session removed, for the agent's report and the merge commit's message, so feedback never vanishes silently;
- once the ledger exists, a note pointing at a record is removed when its record is closed.

## Tests written as a specification

Some work is built against tests written beforehand: the operator, or an agent they asked, writes the tests a feature must pass, and another session implements until they pass. The failure to guard against is the implementing agent changing the tests to match its implementation, which makes them pass and the feature still wrong.

It needs no construct of its own, such as an `acceptance` path role:
- **asked:** a project adds those tests to its protected paths, so editing one asks the operator;
- **refused outright:** a room implementing against them mounts them read-only, so the wall refuses the write, once rooms exist.

## The verdict log

Every judgement is logged, so how often lup asks, refuses and allows can be measured and tuned instead of guessed or reconstructed from transcripts. One JSON line per verdict, a pydantic `Verdict`:
- time, session, runtime; a move of `HEAD` is logged with no session (checkpoint, step 4);
- the tool, `checkpoint`, or `move`;
- the worktree, and the path in it with its role; a write in the repository's git directory names that directory instead, and a line logged before verdicts named their worktree reads with none;
- the outcome (allow, ask, refuse, hold) and its reasons (the rules that refused, the kinds of ask, or the role that allowed: `rules-pass` for production);
- the operator's answer, when there is one.

It's kept per repository, beside the store, each verdict naming its worktree **(leaning)**, rather than one log per worktree, which would lose the one place measuring a repository. An answer comes after its verdict (when the asked call finishes, or a hold is answered), so it's appended as the same verdict again under the same key, and a reader takes the last line for each key; logging an ask only once it's answered would lose it when a hook dies. `lup-dev verdicts --days 7` summarizes it by outcome and reason, with how asks and holds were answered.

In lup itself, the judge's own source isn't asked about at each edit, beyond the catalog, which is protected: the judge that runs is the installed copy, so an edit in a worktree can't change what judges it. It's protected after the edit and before it runs. Refreshing the installed judge from `dev` shows the operator the diff of its source since the copy they last approved, and the approved copy keeps judging until they approve the new one. The operator sees exactly what will run before it runs; a protected path asked at every edit would review each step rather than what will run. `DESIGN.md`'s *Trust on launch* gives every launch this same review.

**The installer** (`lup_dev/install.py`, `lup-dev install`), run by the operator from the `dev` checkout in their own terminal, so the judge never installs itself. It runs with the checkout's own code (`uv run lup-dev install`), so a change to the installer is reviewed by itself, the dashboard's reviewer included the first time it runs **(leaning)**. The installed copy reviewing the checkout would let only approved code decide an approval, but the copy's list of what the judge carries is the old one, so a path newly carried would go unshown, and the engine's build runs the checkout's code before any review either way. While agents' code runs on the host, this guards against a mistake, not a determined change; containers make it a wall.
1. It refuses inside an agent's session (by the variables each runtime sets, as for holds), so an agent never approves the judge that judges it; and it refuses when the judge's source has changes not committed, which the copy would carry unreviewed.
2. It lists the files the installed judge carries that changed since the commit approved last, or all of them the first time: both packages' `pyproject.toml` and `src/`, the engine's source (`packages/lup-dev/checker/`), and `uv.lock`. Tests and docs aren't carried, so they aren't shown. An approved commit no longer in the repository shows everything. Where none changed, it prints one line and stops: nothing is built, asked, installed or recorded, so the commit approved last stays one the operator reviewed. Reinstalling unasked would mend a removed copy, but print the build's and uv's output; recording the new commit as approved would be an approval nobody gave.
3. It builds the engine (`packages/lup-dev/checker/build.py`), so a build that fails does so before the operator reads anything. The step is the one lup's declaration gives its gate (`LupDevelopment`'s), run as the gate runs it: through the declaration's runner, unless the step says not (`gate.py`, `invoked`).
4. It parks the change as one review in the dashboard, each file whole on both sides, and waits for the answer (*The judge's review, in the dashboard*, below).
   - **With no dashboard served (leaning),** it parks the review anyway and waits: parking appends to the checkout's relay, which a dashboard reads once it's served, and the waiting lines give the command that serves it. It can't look for a served dashboard, whose address the first lup gives only its own launches. Where the first lup's checkout or its host half is missing, it refuses, naming the setting, and nothing installs.
   - **While it waits (leaning),** the terminal shows which commit is reviewed since which, git's own one-line count (`git diff --shortstat`), the review's id, the command that serves the dashboard, that comments sent as remarks outlast the first lup's hour while drafts don't, and that Ctrl-C withdraws the review and installs nothing; then a line for each time the review is parked again, and the outcome with the comments. It shows no file list, per-file counts included, since the counts get read instead of the lines, and no spinner. It looks for the answer every 2 seconds through `Clock`, which tests drive.
   - **In the terminal,** with `lup-dev install --in-terminal`, it shows the review through a pager instead: each file under its own header, naming whether it's created, deleted or modified and the lines it adds and removes, then its hunks with three lines of context, removed lines red and added green; a file whose text is the same on both sides (its mode changed) says so under its header, and no list of files comes first. Then it asks yes or no there, with no note: the operator answering there is at the terminal and briefs the agent themselves. The terminal's review is for when the first lup can't be reached, and only when asked for **(leaning)**: falling back to it unasked would put the review in a pager, where it gets read as its counts rather than its lines, and dropping it would leave no way to install a fix to the judge while the first lup's checkout is broken.
5. Approved, it checks again that `HEAD` is the commit reviewed and that the judge's source has nothing uncommitted, installs `packages/lup-dev` with `uv tool install --force`, and records the commit. If `dev` moved during the review, as when a branch lands in the `dev` checkout, it refuses, and the operator runs it again: a review's wait is the operator's reading time rather than seconds, and installing from an export of the reviewed commit instead would need the engine's toolchain set up there. Declined, nothing changes, and the copy installed before keeps judging.
   - **Either way it prints the operator's note and line comments (leaning),** one `path:line (side): note` each, with paths in the checkout and the `before` side naming the approved commit. They stay where the first lup keeps them, its answers file, which the terminal names; lup keeps no copy. A copy in lup's state (`judge/declined/<commit>.json`) for an agent to read would be a new file and its reader, when the operator who wrote them is at the terminal and briefs the agent; a GitHub issue would be a network call in the installer.
- **How uv installs it.** `uv tool install` from the workspace member's directory honours `lup`'s workspace source, installing it from the checkout as a path dependency; both packages are copies, not editable, and `lup_dev` carries the built bundle. But it resolves the tool's other dependencies afresh, ignoring `uv.lock`, and picks newer versions than the lock pins. So the installer exports the lock's versions (`uv export --package lup-dev --no-dev --no-emit-workspace`) and passes them as `--constraints`, and the copy runs what the gate ran (`Uv.install`). `--with-requirements` would add those versions rather than constrain to them.
- **How git cuts the change into files** (`Installer.review`, `ChangedFile`). `git diff-tree -r -z --no-renames --name-only <approved> HEAD -- <what the judge carries>` lists them, read with the store's `nul_separated` (*After a call: the checkpoint*, step 1); `git ls-tree -r -z --name-only`, once a side, says which side holds each; and `git cat-file blob` reads each side whole, from git's empty tree where no approved commit is known. A rename is a deletion and an addition, since a `Propose` can't show a move. A carried file that isn't UTF-8 text refuses the install, naming it, since no review here can show it; listed by its object id, it would be shown nowhere. Splitting `git diff`'s output at its file headers would hand-parse it, and reading it with a parser such as `unidiff` would be a new dependency, when the dashboard wants documents anyway. `cat-file` on every path, its failure read as absence, can't tell a missing file from another failure; `diff-tree --name-status`'s `-z` output alternates statuses and paths, read by position.

**The judge's review, in the dashboard.** Read in a pager, a long diff with no colour and nothing marking where a file starts gets read as its per-file counts, not its lines. So the installer parks the review in a dashboard that shows each file whole. Until lup's own dashboard exists, that's the first lup's, reached through its host half (`packages/lup/src/lup/policy/assets/host.py` in its checkout, standard library only), as the interim review hook reaches it.

What that dashboard does with such a review, read in its code at `40c2d28` and checked by parking a review through the host half into a scratch repository, then reading it back with the dashboard's own `ReviewDocuments` and `moved`:
- **One review of many files** is its `Propose` call (`devtools/review/propose.py`): a payload holding each file's path and the document it becomes (none for a deletion), with the documents before recorded beside it as the review's preconditions. The page shows each file as a fold under a header naming its path, whether it's created, overwritten or deleted, and its added and removed lines; inside, the hunks with three lines of context, the unchanged lines between them folded, added and removed lines coloured, the source highlighted, with diff, before, after and raw views. Every file opens, since none carries a verdict of the first lup's policy: each header says "no verdict captured".
- **It takes documents, not a diff:** each file whole on both sides, and it works out the hunks itself (`difflib.SequenceMatcher`). The host keeps every string of a kibibyte or more in the relay's store, and nothing caps the files or lines shown; highlighting stops past 400,000 characters a document, well above anything the judge carries (its largest file, `catalog/rules.ts`, is 94 KB).
- **Line comments** anchor to one file's lines on either side (`LineComment`: the path, first and last line, `before` or `after`, the note). They're drafted on the page and sent with the answer, or before it as a remark; both are kept in the host's answers file. A draft not yet sent lives only in the open page, under its review.
- **A review binds the disk.** The dashboard retires a waiting review as stale when a file it recorded no longer stands on disk as recorded (`devtools/review/preimages.py`), and refuses to approve one. The installer's before side is the approved commit while the disk holds `HEAD`, so recorded at the checkout's own paths every changed file reads as moved: the scratch review's three files read as changed, deleted and created. Recorded at an export of the approved commit's files, none moved.
- **It expires a review an hour after it's parked when its requester isn't on the first lup's roster** (`expire_orphaned`, on every sweep), which the installer isn't. The hook's `wait` parks such a review again under a new id.
- **Parking needs no running dashboard:** it appends to the checkout's relay (`.lup/questions.jsonl`), which a dashboard reads once it's served, with every sibling worktree of the roots it's served with. Nothing tells the installer whether one is served: the first lup gives its dashboard's address only to its own launches.

**The code, with (a):**
- **`lup_dev/legacy_dashboard.py`:** `LegacyDashboard`, a `Reviewer`. It loads the host half from the first lup's checkout, exports the approved commit's files, parks one `Propose` naming `lup-dev install` as its requester, waits, parks again after the first lup's hour, reads the answer and every remark, spends an approval through the host, and removes the export. The module also holds `LegacyQueue`, the review flow's `Queue` (`docs/review-flow.md`), with what it parks and keeps.

The review's paths are the export's (`.lup/install-review/<approved commit>/`), since the dashboard retires a review whose recorded files don't stand on disk; the page shows each path under that prefix, and the terminal maps comments back to the checkout's paths.   - **Ctrl-C** withdraws the review by removing the export, so the dashboard retires it as stale at its next look and no approval can release it; left waiting, an approval given later would release nothing and read as if it had.

A declined change is reviewed again once `HEAD` moves, since the review names its commit, or with `--in-terminal`. A fresh review at every run (a run's id in its reason) would leave an earlier withdrawn review of the same files waiting beside it, live again once the export is rewritten.

The rules live in `catalog/rules.ts`. The engine that runs them lives in `packages/lup-dev/checker/`, a TypeScript project built with the table into one file, which is never committed.

The `lup-dev` command is this piece's stand-in until the declaration and CLI piece builds the real `lup` command tree. The commands keep their meaning there; their final names are that piece's call.

## Installing it here

**The judge's whole set** runs `"$(uv tool dir --bin)/lup-dev" hook claude` (or `hook codex`) on `SessionStart`, `PreToolUse`, `PostToolUse`, `Stop` and `SubagentStop`, and on Claude Code `PostToolUseFailure` too, every tool matched. On Claude Code, `Stop` and `SubagentStop` get 1,200 seconds, since the session's turn's end waits for the importers pass (a subagent's end doesn't, so its ceiling is generous). On Codex, every tool is matched by leaving the matcher out; there's no `PostToolUseFailure`, and no `PermissionRequest`, which Codex's adapter doesn't answer; `PostToolUse`, `Stop` and `SubagentStop` get a `timeout` of 90,000 seconds, above a hold's day, and `PostToolUse` an `additionalContextLimit` of 20,000 tokens, so a report arrives whole; past it, Codex keeps the whole text in a file and shows a preview pointing there. Codex runs a project's hooks only once trusted, in its `/hooks`.

**In lup's own repository, while lup is being built,** the judge only judges each write, and no turn's end holds (`AGENTS.md`, *How work goes*).
- **`.claude/settings.json`:**
  - the judge on `SessionStart`, and on `PreToolUse` matching `Edit|Write`: the judgement before an edit lands, and no checkpoint;
  - the interim review hook (`.claude/hooks/interim_review.py`) isn't registered;
  - narrow `Bash` allow rules: the gate's commands (`uv run pytest`, `uv run pyright`, `uv run ruff`, `uv run lint-imports`), the engine's build (`packages/lup-dev/checker/build.py`), local git that can be undone (`git status`, `git diff`, `git log`, `git show`, `git add`, `git commit`, `git worktree list`), and landing on `dev` (a `--no-ff` merge in the `dev` checkout, and pushing `dev`); `gh pr merge` asks.
- **`.codex/hooks.json`:** the judge on `SessionStart`, `PreToolUse` and `PostToolUse`, configured as in the whole set: the checkpoint after each call, the only place Codex's hooks see a patch, and no `Stop` or `SubagentStop`.
- **`lup_project.py`** declares lup's default modules with lup's changes: `asks="protected"`; its test roots, `packages/*/tests`; `runtime-mention` added back to `CodeRules`' rules, and the library's front door exempt from it and the catalog from `constant-home`. Its own module, `LupDevelopment`, builds the engine before the gate's first step, protects `packages/lup-dev/src/lup_dev/catalog/**`, and excludes `.claude/hooks/**`: the interim hooks are uv scripts with their own dependencies, outside the conventions, and go with the bridge. They stay protected.
- **`[tool.lup]`** in `pyproject.toml` still names `lup_project:project`, for the judge installed before the declaration became modules, which reads that pointer; it goes in a commit on `dev` once the operator reinstalls (`docs/declaration.md`, *Building it*).
- **Why the hooks name the tool's bin directory** rather than `lup-dev` on the `PATH`: a shell with a worktree's environment activated finds that worktree's own `lup-dev` first, which is exactly the copy the installed judge exists not to run. `uvx lup-dev` is the other way to reach an installed tool, but where none is installed it fetches a package of that name from the index. Until the operator's first install, the command isn't there, and every runtime treats a hook that fails that way as no decision.
- `.gitignore` has `.lup/`.
- The typed engine is wired in one place, `cli.engine()`, and built by the installer before the copy is made; the installed package carries the bundle.

**With the interim review hook registered,** a configuration lup's repository doesn't run now, the hook carries Claude Code's prompts to the first lup's dashboard, on `PermissionRequest` and `PostToolBatch`, so the prompts that commands outside the allow rules cause reach the review dashboard (*Shell commands*); and the narrow `Bash` allow rules are the gate's commands and read-only git. The hook's own write review isn't registered there, but its code stays: removing it would block every write in a session started with settings that register it.

**Installing or refreshing the judge, and checking it live** (the operator's, from the `dev` checkout):
1. `git -C <dev checkout> pull --ff-only origin dev`, then `uv run lup-dev install` from the checkout, in their own terminal: read the review in the first lup's dashboard (served with `uv run --directory <lup-legacy checkout> lup-devtools dashboard serve --root <dev checkout>`), and approve.
2. `"$(uv tool dir --bin)/lup-dev" --help` lists the commands; `"$(uv tool dir --bin)/lup-dev" rules list` lists the engine's rules.
3. Restart the Claude Code sessions in the repository: a session reads its hooks when it starts. In Codex, trust the project's hooks in `/hooks`.
4. Live checks in a fresh session: ask the agent to add `import re` to an existing module with `Edit`, which should be refused with the report, the file unchanged and the version saved under `.lup/saved/`; ask it to write a docs file, which should pass without a prompt; ask it to edit a protected path, such as `pyproject.toml`, which should ask in Claude Code's prompt.
5. `lup-dev verdicts` (installed or from the checkout) shows those verdicts.

## What the runtimes do

What the judge relies on, read from each runtime's docs and source:
- **Claude Code's hooks:** its hooks reference says `PreToolUse` "runs before a tool call executes" and `PostToolUse` "after a tool call succeeds" (`PostToolUseFailure` "after a tool call fails"), each with the call's `tool_use_id`, and that matching hooks "run in parallel". A call's finish never comes before its start, so the in-flight set stays right; parallel calls' hooks overlap, which the file lock covers.
- **The variables each runtime sets in the commands it runs:**
  - Claude Code's environment-variable reference: `CLAUDE_CODE_CHILD_SESSION` is "set to `1` in subprocesses Claude Code spawns via the Bash, PowerShell, and Monitor tools, hook commands, and status line commands", and, unlike `CLAUDECODE`, "only set by Claude Code itself when it launches a subprocess and not by IDE extensions", whose terminals the operator may answer from. Observed in a session's commands.
  - Codex sets `CODEX_THREAD_ID` in every command its agent runs (`codex-rs/core/src/unified_exec/process_manager.rs` at `rust-v0.156.1`, inserted after the shell environment policy, so a profile can't strip it), with `CODEX_CI=1`. Its hooks run with Codex's own environment, without them.
- **Codex:**
  - Its `PermissionRequest` for `apply_patch` carries `tool_input: {"command": <the patch>}` and no file list (`core/src/tools/approvals.rs`). It fires only when the patch needs approval: under `on-request`, a patch writing outside the writable roots, or retried after a sandbox denial; under `never`, never. Inside the workspace Codex doesn't ask, so lup answers nothing and judges at the checkpoint; a patch reaching outside is left to Codex's approval, since on Codex lup judges only the worktree a session started in (*Every worktree of the repository*). Answering it `allow` would let those through unjudged.
  - Its hooks' `cwd` is the "Working directory for the session", and "`Bash` and `apply_patch` use `tool_input.command`" (its hooks docs): nothing in a payload says where a command or a patch writes, short of parsing them.
  - Its hook `timeout` defaults to 600 seconds with no maximum: `timeout_sec.unwrap_or(600).max(1)` (`hooks/src/engine/discovery.rs`); its docs: "If timeout is omitted, Codex uses 600 seconds for most hooks". A timed-out hook fails open.
  - Its payloads (`hooks/schema/generated/*.input.schema.json`): every hook has `session_id`, `cwd`, `hook_event_name`; `PreToolUse` and `PostToolUse` add `tool_name`, `tool_input`, `tool_use_id` and, for a subagent, `agent_id`; `PostToolUse` adds `tool_response`; `Stop` adds `stop_hook_active`. Its shell tool is reported as `Bash`, `apply_patch` as `apply_patch`, a subagent's start as `spawn_agent`.
  - Its `PreToolUse` can't ask: "`permissionDecision: "ask"` … [is] parsed but not supported yet" (its hooks docs), and a plain `allow` fails open (`hooks/src/engine/output_parser.rs`). lup never answers it.
- **Not used:** Claude Code's own record of a command's edits (`bashEditDiff`), which misses files, a protected one among them.

## Checks owed

- **Auto mode:** whether a `PreToolUse` hook's `allow` skips the classifier. Claude Code's permission docs say a mod's approval skips it, and nothing about a hook's.
- **A judge's `ask` reaching a `PermissionRequest` hook:** whether Claude Code's `PermissionRequest` hook runs for the prompt a `PreToolUse` hook's `ask` causes, which is how the interim review hook would carry the judge's asks. Its hooks reference says each half: a hook's `"ask"` "prompts the user to confirm", and "also forces a permission prompt in auto mode"; `PermissionRequest` "runs when Claude Code is about to ask you for permission to use a tool", and its hooks "run only when Claude Code is about to ask you for permission, or when it would otherwise auto-deny a call that can't prompt". It never says the two meet in so many words, so it's inferred from those.
- **A subagent's working directory in its hooks:** whether Claude Code's `cwd` follows a `cd` in a subagent's calls as it does in the session's own conversation. A subagent's shell starts each call in the project's directory, so its hooks may never report another worktree; its file tools hold its worktree either way (*Every worktree of the repository*).
- **A subagent stopped before it ends:** whether either runtime reports `SubagentStop` for a subagent the operator stops, or one that fails. Claude Code's hooks reference says only that it "Runs when a Claude Code subagent has finished responding"; Codex runs it at the end of each of a subagent's turns. One that isn't reported stays at work until the session starts again, so a file it shares with the session's own conversation tells rather than holds at the session's end meanwhile. Claude Code's `Stop` input lists the session's `background_tasks`, subagents among them, which would settle it there (*While a subagent works*).
