# Judging every write

lup judges every write in the worktrees an agent's session holds: it lets it land, holds it for the operator's answer, or lets it land flagged for them to see, and it tells the agent what lup's rules, pyright and ruff found in it, as type errors are told. The judge steers and doesn't guard (`DESIGN.md`, *Who it's for*): its findings never decide whether a write lands. The code is `lup_dev/policy/` (judging) and `lup_dev/codescan/` (reading code), with the typed engine in `packages/lup-dev/checker/`; the rules themselves are `docs/rules.md`, and the reasons behind them `docs/conventions.md`.

**Every write is judged, whatever tool makes it,** on both runtimes: a file tool's before it lands, where the runtime says what it will write (Claude Code's `Edit` and `Write`); anything else, a command, a script, Codex's `apply_patch`, at the checkpoint after its call; and what a turn leaves, at its end. Each adapter says which hooks its judge reads (`docs/host.md`, *Which hooks the judge reads*).

## What each change gets

| Change | What it asks | By default |
|---|---|---|
| A test, scratch (`tmp/`), docs or data file | nothing | lands |
| An operator's document (`DESIGN.md`, `AGENTS.md`, and in lup's own repository its modules' guidance) | `operator` | held |
| A protected path, or a file with a secret's name | `protected`; a protected Python module gets lup's rules too | held |
| A path the declaration excludes | nothing, and no rule's findings; one also protected still asks `protected`, and a value never published is still told | lands |
| A production file being created | `new-file` | flagged |
| A production file written whole by a file tool | `whole-file` | flagged |
| A change to the public API (*The public-API ask*) | `public-api` | flagged |
| An added `# lup: ignore`, in a module lup's rules read (#173) | `ignore` | held |
| A value never published, on a line the change touches (`docs/private.md`) | `private` | told, and flagged |
| A finding of lup's rules on a line the change touches | the rule's name | told |
| Removing a `# lup:` note present when the session started | nothing; it's said at the checkpoint and the turn's end | lands |
| A deleted file | `protected` or `operator` where it's one | held, or lands |
| Any other production change | nothing | lands, its findings told |

- **There's no line count:** a size limit makes agents split their edits to fit it.
- **Held and flagged are named in the declaration** (`Project.held`, `Project.flagged`; `docs/declaration.md`), in one vocabulary: the two roles that ask, the kinds of change, and lup's rules by their ids. A protected change takes effect outside the agent's reach before anything lands, and an `ignore` takes a check away, so they're held; a design change can be seen once it has landed, before anything is published, so it's flagged.
- **The operator's switch:** "hold each flagged write" holds what the declaration flags for one conversation and its subagents, turned with `h` on its banner in the dashboard's review (`switched`, `host/service.py`): a subagent is held where its own switch is on, or that of any conversation above it.
- **An approval covers the path's design asks** (a new file, a whole write, a public-API change) for the rest of the session, in that worktree, so a file approved isn't asked again as it's worked on.

**Path roles.** Each path has one role, the first that matches (`Roles.role`, `policy/roles.py`): protected (the declaration, manifests and lockfiles, the tools' configuration, what runs outside the agent's reach such as `.github/`, git's hooks, editor and runtime settings, `.gitignore`, and the person's own files git ignores; and the files that hold secrets, the `secret` role, by the names tools give them, `.env*`, keys and credentials, which the host's tools read, and which a room never reads where no commit holds them as they are: `docs/launch.md`, *Files with a secret's name*. The judge's reason names the pattern either way); the operator's documents; excluded; test (a module pytest collects as one, or a `conftest.py` under a test root, or a file the test patterns match wherever it is, TypeScript's `*.test.ts` and `*.test.tsx` by default, which its runners collect); scratch (`tmp/` and `.lup/`); docs (Markdown, and `docs/` at the root); data outside a source tree; and production, everything else, so a file nobody classified is judged. The default patterns are protected data in `catalog/paths.py`; a project changes them in its declaration. Each runtime's settings directory is among them, which its adapter names (`Runtime.settings`) and a test checks, so a runtime added later isn't left out.

**The public-API ask** (`api_changes`, `policy/surface.py`): a change to what other code depends on is a design change. That's a public name added or removed, anywhere in production Python: a name added to a package's root or removed from it, a class added or removed, a function or method added or removed. A name with a leading underscore isn't public, a dunder method aside; a nested function never counts. A signature changed asks nothing: the operator reviews the shape of a module, what there is to call, and not every parameter, which in practice was nearly every flag; copies before asked it, as `signature-changed`, which the holds and items they wrote keep, so the kind is still read and shown (`ApiKind`, `inbox/store.py`). The session is the baseline: a name is added where the version before the write and the file at the session's start both lack it, and removed where both have it, so a name the session created comes and goes freely once asked, and one it took out can go back. A file being created asks `new-file` alone, its names seen with it. The engine reports each version's surface, so each change is asked on its line, a removal on the line it had.

## How a write is judged

**Before an edit lands,** for a file tool's write (`Edit`, `Write`; `policy/before.py`): the content after the call is known before anything is written, so it's judged on that, compared with the content lup last accepted rather than the disk, and its findings are told beside the call. The call's finish confirms the write (`confirm`): what lup accepts moves on to it, so the next write to the file is judged against it, and a file the session created isn't asked about as new again.

**After a call: the checkpoint,** for everything else (a command, a script, a notebook's edit, Codex's `apply_patch`, whose patch lup doesn't parse): each worktree is compared with the last state lup accepted for it (`checkpoint`, `policy/checkpoint.py`; `policy/store.py`). When a call finishes, a checkpoint runs in the worktrees it counted in or its conversation works in, where none of that session's calls still is, so parallel calls are judged together, before the agent's next request. A checkpoint:
1. snapshots the worktree into its own store as a git tree, leaving out what the repository ignores; where nothing changed since the last accepted tree, nothing is judged;
2. compares it with the accepted tree, leaving out files under an open hold;
3. sets aside what was committed elsewhere: content in the history the repository's refs and the worktrees' `HEAD`s named at their last checkpoint, and the remote-tracking refs as they stand, which a checkout, a pull or a `git restore` brings, and git's own clean merge of two such commits;
4. judges a move of `HEAD` once, as its commits', what it brought that wasn't set aside, so a shell write committed in the same call isn't accepted unjudged; it's never put back, since the working tree would then differ from `HEAD`;
5. judges the rest as a write is judged before it lands;
6. accepts it, or puts back what a declined hold refused, saving the agent's version under `.lup/saved/`;
7. reports once: what a move brought, then lup's findings on the lines changed, type errors and ruff's findings, those the conversation wasn't told yet (*Told once*) and doesn't hold back (*Quiet*), then the notes removed, then mail.

**Which calls hold a checkpoint back.** A call counts as running in each worktree its conversation works in (`Holding.works`, `policy/worktrees.py`): where its hooks report its working directory, and where its file tools write. A subagent's hooks report its session's directory whatever it works on, but in a worktree its runtime isolates it in, which they report (*A worktree the runtime asks for*), so a subagent works where its file tools write, and only until they have, where its hooks report; one lup isolates works in its worktree from its first call, whatever they report (*A subagent lup isolates*). A call still running holds back the checkpoints where it counts, so a checkpoint never judges a write half made: a worker busy in its own worktree holds back none of the main conversation's, and two conversations working in one worktree wait on each other. A command writing where its conversation doesn't work isn't waited for there, since lup doesn't parse it; on Codex every conversation works in the session's one worktree (`adapters/codex.py`). A call the runtime never reports finishing, one the operator interrupts among them, holds them back until the runtime shows it over: a turn's start (`TurnStarted`) clears the session's calls whose results their conversations' records hold, as Claude Code records an interrupted call's, and where the runtime names its turns, as Codex does, the conversation's calls of an earlier turn. A prompt can arrive while a call runs, which Claude Code reports with the same hook, so a turn's start clears nothing on its word alone. Otherwise its conversation's turn's end clears it (#172). And no call outlives a room's hook, which waits 25 hours at most: a call counted longer ago, from a session long gone say, is forgotten as the list is next kept (`over`), and so is a file tool's write judged that long ago that no end confirmed. On Claude Code a call to lup's own tools isn't counted, nor one to a tool that only reads (`READING`, `adapters/claude.py`), which changes no file: every other tool is judged, a new one or another MCP server's among them.

**It sees files, not authors.** Someone else's edit in a worktree a session holds is judged as the agent's; the operator works where no session holds, or between sessions. Where a session starts, or first reaches a worktree, the worktree as it stands is accepted, so what changed while the session made no call there isn't blamed on it.

**Every worktree of the repository.** A session starts in one worktree and often writes in others: in lup's repository each branch is its own worktree. The judge covers each worktree of the session's repository the session holds (`Holding`, `policy/worktrees.py`): the one it started in, each one its file tools write in, and on Claude Code each one its hooks report as its working directory. A write outside the session's repository isn't judged. On Codex a session holds only the worktree it started in, since its hooks' working directory is the session's own and its calls carry only the command, which lup doesn't parse. A shell write into a worktree the session never reached is accepted unjudged when a session next reaches it: judging every worktree at each checkpoint would close that, at about 80 ms a worktree, and would judge the operator's own uncommitted work as the agent's.

**A worktree the runtime asks for.** Where the runtime would make a worktree itself, for a session entering one (Claude Code's `--worktree`, `EnterWorktree`, a background session) or a subagent it would isolate where lup didn't isolate it first (*A subagent lup isolates*), lup makes it (`WorktreeAsked`, `policy/checkpoint.py`):
- **from the commit the asking conversation's worktree is at,** a branch not landed yet included, where the runtime's own starts from the repository's `HEAD`, a bare repository's default branch however far the work is from it;
- **on a new branch of the runtime's name for it,** a subagent's `agent-<its id>`, at `tree/<name>` in the repository's git directory (`made_root`, `policy/worktrees.py`), which a room mounts in every layout: beside the others in a bare repository, `lup.git/tree/<name>`, and in a clone's `.git/tree/<name>`, which the clone's own worktree never lists;
- **by the room's own git:** the judge names it and the room's hook makes it (`docs/host.md`, *The one hook*), so its checkout never runs the host's git configuration on what the room committed.

It's new, so nothing in it is the operator's: where the session first reaches it, it's judged from that commit rather than accepted as it stands (`Holding.made`), so a shell write into it before its subagent's first call there is judged at that call's end, and a commit there as a move (#240). Its subagent's hooks report it as their working directory, so the subagent works there from its first call. The runtime keeps it when the subagent ends, and `land` removes it with its branch once the branch lands (*Landing a branch*). lup refuses, saying why, where the asking conversation works in no worktree, its worktree has no commit, the name can't name a new branch, or something is at its root already. Codex never isolates a subagent in a worktree, so it asks for none (`adapters/codex.py`).

**A subagent lup isolates.** A subagent Claude Code would isolate (`isolation: "worktree"`) works apart in a worktree lup makes, and Claude Code makes none: its own isolation guards the subagent's shell, refusing git aimed at another worktree and every command too complex for it to verify, a compound one or a redirect among them, which no setting relaxes (`docs/field-notes.md`, *A worktree for an isolated subagent*). So at the `Agent` call's start (`given`, `policy/checkpoint.py`):
- **lup makes the worktree** as it makes one the runtime asks for (*A worktree the runtime asks for*): from the commit the spawning conversation's worktree is at, at `tree/<name>` in the repository's git directory, by the room's own git (`launch/worktree.sh`), and judged from that commit where the subagent first works. Its branch is named after the call's description, lowercased, each run of anything but letters and digits one `-` (`branch_named`), or `agent-<the call's id>` where that's empty or taken;
- **the call goes on without `isolation`,** its prompt opening on where the subagent works: the worktree, its branch and its commit, and that the working directory its environment names is another conversation's. lup refuses the call, saying why, where it can't make the worktree;
- **the subagent is linked to the worktree at its first call,** by the call that spawned it, which Claude Code records beside the session's transcript, or by the call's result, which names the subagent, as a spawn in the background answers at its launch (`Holding.link`, `Holding.settle`). A spawn that failed is forgotten, its worktree left for `land`.

From then on:
- **its shell's commands start in its worktree:** Claude Code starts a subagent's shell in the session's working directory at each call, so each command, `Bash`'s or `Monitor`'s, is rewritten to change to its worktree first, in the same shell, a compound command, a pipe or a redirect whole. Nothing refuses git aimed at another worktree: every worktree, and the repository's history, stay its to read;
- **its calls count in its worktree** (`Holding.works`), whatever its hooks' working directory says, so they hold back none of its parent's checkpoints;
- **a write of its file tools in the worktree its environment names is refused,** saying the same path in its own: Claude Code resolves a relative path there, in the session's working directory, so the write would land in another conversation's worktree, and the subagent would read its own file back unchanged. A write anywhere else is judged as any is;
- **a subagent it spawns works with it:** a plain one in its worktree, told so, as Claude Code's own isolation passes it on, and one asking `isolation` in a worktree lup makes from its worktree's commit.

Codex never isolates a subagent, so nothing of this reaches it (`adapters/codex.py`).

**The declaration, from the approved commit.** Every worktree is judged by the declaration at the commit the operator approved last (`docs/trust.md`), never by the worktree's own, so a branch can't change what judges it. Before any approval it's the integration branch's tip; without such a branch, the worktree's `HEAD` commit; before any commit, the defaults. It's exported from git's objects once per commit and imported from there, when a judgement first needs it. The gate reads the worktree's own declaration, to check a branch as it would land, and never takes a stand-in.

**A declaration that can't load has a stand-in.** Where the commit due can't be imported, by a judge predating one of its fields say, the last declaration that loaded judges, and at a checkpoint the agent is told once, with the error, to pass on; denying every write instead would stop every session, and the defaults would silently drop the project's protections.

## What the agent is told

**Findings** on the lines a change touched are told with the call, each with its steer (`information`, `policy/report.py`). The report, in pyright's shape:

```
lup's findings on the lines changed (clear each, or keep it with `# lup: ignore("<rule>", why="<reason>")` on its line or the line above, which the operator is asked about; they fail the gate):
  /work/lup/src/lup/claude.py:41:12 - tuple-shape: a fixed-length tuple[str, int] hides what each position means
      steer: name the fields with a pydantic model
  /work/lup/src/lup/claude.py:88:5 - regex: `import re` parses with a regular expression
      steer: use the format's own parser (lup docs rules regex)
```

`tests/test_report.py` checks that this block is what `information` writes for these two findings, whose messages are illustrative.

Findings on lines no change touched, in the files a checkpoint judged, come in a block of their own. pyright's errors and warnings and ruff's findings are told the same way, and fail the gate; none ever holds a write. Production, protected and test modules are checked, before a write lands as at a checkpoint. **What holds in a file is decided in one place** (`Roles.kept`, `policy/roles.py`), for a write's report, a checkpoint's, the files importing a change, a turn's end and the gate alike: nothing where the roles check nothing, lup's findings only where its rules read, so a test has pyright's and ruff's alone, and none of a rule the declaration exempts the file from or that an `ignore` keeps. A file tool's write is told what it holds with its call, which a checkpoint waiting on another call (#86) can't delay, and the checkpoint accepting it (`confirm`) tells it no more, nor mails it to the session's other conversations, since the writer is known. **A finding ruff fixes safely is never told:** such a fix changes nothing a reader decides, and told one by one these findings spend an agent's turns, so the session landing the work applies them (`lup-dev check --fix`). The judge never rewrites a file under the agent.

**Told once.** Each conversation is told a finding when it first appears, and not again while it stands (`DESIGN.md`, *Said once*): every report after a call, a file tool's write, a checkpoint's, its mail to another conversation, says only what that conversation wasn't told yet (`Session.news`, `policy/checkpoint.py`; `news`, `policy/report.py`). A report otherwise says what stands, not what changed: a file's every type error at each write to it, and every importing file's at each checkpoint touching what it imports, which in a refactor moving an API across sixty files came to hundreds of kilobytes a call, almost all said before (`docs/field-notes.md`, *What the post-call report said*). A finding is known by its file, owner, rule and message, and by the text of its line rather than its number, so an edit above it doesn't make it new. What a reading of a file finds replaces what was known of it, for the owners it read: every owner where the file was judged, pyright's where the importers pass re-checked it; so a finding that's fixed is forgotten, and told again if it comes back. A file set aside unjudged, its content committed elsewhere, is forgotten too. A conversation its runtime compacts or clears holds none of what it was told, so it forgets the findings it knew (`SessionStarted.forgotten`) and is told what still stands at its next call; a resumed one keeps them. **The turn's end still lists everything left** in the files its conversation touched, told or not: that list is why the turn can't end.

**Quiet.** During a wide change, a refactor across sixty files or several edits in a row to one file, an agent knows its work is broken and will fix it later, so being told each finding as it appears is noise (`DESIGN.md`, *Quiet*). With lup's tool `quiet` it names the kinds of findings it isn't told after its calls for now (`Quiet`, `policy/report.py`; `policy/quiet.py`): `rules`, lup's findings on the lines changed; `changed`, type errors and ruff's findings in the files changed; `untouched`, lup's findings on lines no change touched; `importers`, type errors in the files importing what changed. These are a report's sections, not owners: `rules` and `untouched` are both lup's. What a quiet holds isn't told, by any report: after a call, a file tool's write, a checkpoint's mail. Nor is it learned: a reading of a file sets it apart (`Look.held`), and of it the conversation's ledger keeps what it was told before and still stands, adds nothing, and forgets what's gone, where a plain reading would forget what it was told before the quiet and tell it again. A call naming other kinds holds those instead, what it held of the rest told as their files are read again. Named with no kinds, `quiet` lifts the quiet and answers with what stands then that the conversation wasn't told, once: in each worktree its session holds, the files it touched read as they stand, lup's findings, type errors and ruff's, and pyright's in the files importing them that it watches, once the importers pass is done, as a turn's end waits for it, against its ledger, which then holds them; not each state in between. A finding fixed while quiet isn't told; one told before the quiet isn't told again. **Nothing else is held:** a refusal, a hold and the operator's answer, a move of `HEAD` and what it brought but its type errors, which are the files changed's, a value never published, a notice, a removed note, and the list a turn's end is held on, which is the gate on ending, not an interruption. Each conversation's quiet is its own, kept with its session's conversations (`Conversations.quiet`, `policy/checkpoint.py`), so every hook of the session reads it whichever worktree it judges in; it lasts until it's lifted or the conversation ends, across turns: a subagent's end ends it; the session's own has no end its runtime reports, and a `/clear` on Claude Code starts a conversation under an id of its own. A compaction or a resume keeps it, and the conversation is told at its start that it's still quiet, since what a compaction keeps may leave out that it asked. The tool is served by the host service beside `judged` and run in the repository's process (`JudgeCalling`, `docs/host.md`, *Each repository's judge and modules*), where the engine the lift reads is warm: an approved copy that predates it refuses the call, and `quiet` answers that it didn't run. The operator's messages and the inbox's other items aren't held (#163).

**Fitted to the hook.** What a hook tells beyond its runtime's cap (10,000 bytes on both, `Runtime.fits`), the runtime moves to a file behind a 2 KB preview the model isn't asked to read, so a report never goes out that long (`fitted`, `policy/report.py`). Past what the judge may take of the hook, its cap less what's kept for the inbox's items beside it (`Bench.reserve`), the report is kept whole in the repository's git directory (`GitDirectoryLayout.reports`, the latest hundred, which every room reads) and told with a line saying where, and each section of findings is told whole while it still fits, in order, else short: its header, then a line per file with how many findings it has of each rule. A refusal, a move, a notice, a removed note and a value never published are always whole. A turn's end held on what's left is fitted the same way.

**The turn's end** clears the calls its conversation left that no hook reported finishing, leaving other conversations' running, and runs a last checkpoint in each worktree the session holds where none of those counts, their finishes running it where one does; a subagent's end, only in the worktrees it works in. Then the session's turn holds while the files its conversation touched have findings, as `Roles.kept` leaves them, but in a file a subagent at work touched too, which may be its work in progress (#32). An end that follows a hold always ends, and a finding a turn already ended past holds no later end until it changes (`docs/inbox.md`, *No turn that won't end*). **An end that doesn't hold says nothing of what's left:** the agent was told each finding as its write was judged, and an end following a hold told it them just before, so all that's left to carry them is the runtime's warning, which reaches the operator and not the agent. Only a judge's failure at a turn's end is told there, once for each failure in a session. A subagent's end never holds on them: every worker passes the gate before it hands back. A subagent is at work from its first call to its end, which a stopped or failed one reaches whatever its end would tell, since its runtime reads no answer then (`ConversationEnded.final`, `policy/checkpoint.py`). A session's turn that ends on an error from the model's API runs none of this, its runtime reading no answer there either: its next turn's end judges what it left.

## Asking the operator

**A held change** waits inside the hook (`policy/holds.py`): a file tool's write before it lands, anything else at the checkpoint. It's an item in the operator's inbox, with its diff and each file whole, read by the judge (`docs/inbox.md`), answered in the dashboard's review or with `lup-dev inbox answer`. The agent's call returns once it's answered, up to a day, with their comment. Approved, the change lands, and the call's result says so in one line, on every runtime and for a file tool's write and a checkpoint's hold alike: "lup held the write to <file> for the operator's review, and they approved it", then their comment where they gave one (`approval`, `policy/report.py`); on Claude Code a file tool's is told in `additionalContext`, since an `allow`'s reason reaches only its debug log. It says nothing of how long they took: the agent needs to know the operator saw the write, not to pace itself on their time. Declined, the change doesn't land, or is put back and saved; unanswered for a day, it's put back and saved, and a later answer reaches the agent at its next checkpoint, an approval covering the path so the saved version can go back. A held file is nobody's until it's answered, a file tool's write as a checkpoint's change (`Held`, `policy/store.py`): no session's checkpoint accepts it or puts it back, and a file tool's write to it is refused, naming the hold. Nobody answers their own hold: answering refuses to run inside an agent's session.

**A call that stops waiting.** The call waiting on a hold holds a lock for as long as it waits, which the OS frees where its process ends (`Holds.waiting`), so `judged` says of each open hold whether a call still waits on it.
- **Interrupted:** where the call's runtime ends its hook, the operator interrupting it, or its launch ends while the repository's process answers it, the host service marks the hook ended (`docs/host.md`, *The one hook*), and the call gives up as on a day unanswered: the change is put back, or a file tool's never lands, the agent's version is saved, and its conversation is told at its next call. A later answer reaches it as after a day.
- **Gone with its process:** where the host service stops, as it restarts on each approval of lup's own code, or the repository's process ends, the hook fails, saying the write stays held, and the hold stays open with its files held. The next checkpoint in its worktree, any session's, settles it as the call would have once the operator answers (`orphans`, `policy/checkpoint.py`): an approval keeps the change, making a file tool's write that never landed where the file is still as it was, and a decline puts the file back, the agent's version saved. Unanswered past its day, it's put back. Its session is told at its next checkpoint, with whether the change is in place.

**A flagged write** lands as it would, and is an item of its own in the operator's inbox, holding no call (`policy/flags.py`): its file whole with the judge's reading of it, ranked last and raising no notice. A later write by the same conversation to the same file joins the item while the operator hasn't read it, so ten edits to one new module read as one item. Marked read with nothing to add, it's approved; a comment on it reaches the agent, and leaves it read but not approved. It keeps the branch its worktree had checked out, and says it holds at landing: that branch's landing waits on it until it's approved (*Landing a branch*). The dashboard's review shows no flag as an item: what a branch changed since the operator last saw it is a drawer under its agent's banner, read as the worktree stands, where Space `a` marks a file reviewed at the version shown and Space `A` every file shown (`policy/since.py`; `docs/dashboard.md`, *The drawers*); `lup-dev inbox` and the `inbox` tool list them still, one line for each conversation's (`docs/inbox.md`, *The operator's face*). Marking a file reviewed approves its flags only where the file still stands at the version shown: a write that came after the page read it, which the operator hasn't seen, keeps its flags waiting, and the branch's landing with them.

**A move's asks** are already committed and aren't put back, so they're a hold no agent waits on, naming its commit; a decline changes no file, and reverting is the operator's call.

## Landing a branch

**`land` moves the integration branch** (`policy/landing.py`; `docs/inbox.md`, *lup's tools*), rather than `git push`: a call to lup's tools can wait a day for the operator (`docs/inbox.md`, *Holding a call*), where Claude Code's `Bash` ends a command after 10 minutes at most. Given a branch and a message, it merges the branch itself; given neither, it lands `dev` as it is, for a change committed there. What it puts on a branch the declaration gates on the remote (`docs/credentials.md`, *What the declaration allows*), `dev` by default, is:
1. a fast-forward of that branch's tip on the remote;
2. a commit the gate passed on: a pass recorded for its tree, as `lup-dev check` records it (*The gate*). The host doesn't run the project's environment, so `land` reads the pass, and where there's none it refuses, saying to run the gate. The room writes the passes: this steers, and guards nothing;
3. approved by the operator in each file the landing changes that's flagged on a branch it lands.

**A branch is merged in the launch's room** (`lup_dev/merging.py`), where the gate on a push runs too: the merge isn't the commit the operator approved, so its gate on the host would run unapproved code there. `land` hands the room the two commits through `podman exec`, behind the project's runner as the launch recorded it (`Register.runner`), and the message on standard input, so nothing goes through a shell's quoting. `lup-dev merge` there:
1. computes the merge apart, touching no checkout and no ref (`git merge-tree --write-tree`). Where it conflicts, `land` names the files and who works in the branch's worktree, and nothing has changed: they merge `dev` into the branch there, resolve, run the gate, and call `land` again. A worker hands its branch back without merging `dev` into it: a clean merge is `land`'s;
2. makes the merge commit with the message, cleaned as `git commit -m` cleans one, `dev` its first parent (`git commit-tree`);
3. runs the gate on it with `--fix` (`check --at`, *The gate*). A branch that held `dev` merges to exactly its own tree, whose pass the branch recorded, so nothing runs. Otherwise the fixes, where they change files, are amended into the merge commit, keeping its parents and message. Where the gate fails, `land` answers with its report, and nothing has changed.

The merge goes onto the local `dev`, or onto the remote's where the local one is behind it, and `land` refuses where each has moved since they parted. A branch already in that history isn't merged again, and `dev` lands as it is, so a `land` sent again after a restart of the service finds its merge made. The host checks the commit the room answers as it checks any landing: its parents read from the commit alone, then the fast-forward and the pass. Then `dev`'s checkout is fast-forwarded to it in the room (`git merge --ff-only`), which refuses rather than touch uncommitted work there; a merge holds a lock until then, so landings merge one at a time, each onto the last. A launch whose record keeps no runner merges nothing, and says so.

**What holds a landing.** The branches it lands are those the landing merged, of the local branches in the tip's history and not in the remote tip's (`landed_branches`): the branch given to `land` (`dev` itself, landed as it is), and each other whose tip is a parent beyond the first of a merge on the first-parent line from the tip down to the remote's, where no branch given was given at that tip and no other branch points at it. The graph can't tell two branches at one commit apart, but `land` knows which branch it was given:
- **one at the tip of the branch landed** was made from it, as a worker that handed a branch back starts its next piece from it, with nothing of its own yet: it isn't landed or cleaned up after, its worktree stays, no flag on it holds, and the answer says so in a line;
- **several at one merged tip, none given,** a branch merged by hand and `dev` landed as it is while a worker made another from it, may each be the one merged: none is cleaned up after, a flag on any of them holds, and the answer names them in a line.

One whose tip is a commit of that line itself, just made from the integration branch say, has nothing of its own in the landing: it isn't landed or cleaned up after, no flag on it holds, and the answer names it, so a session isn't surprised to find it kept. `land` merges with a merge commit, as a merge by hand should: a fast-forward by hand leaves the branch at the tip, which can't be told from one just made there, so it's left alone too. A flag holds it where it's on a branch it lands, or on one of several at a merged tip, by the branch it keeps (`Flagged.branch`), for a file the landing changes, and not approved. A flag on a branch renamed or deleted since holds nothing, and a stale one on a branch name used again holds that branch's landing; a flag with no branch, made on a detached `HEAD`, holds nothing.

**Each file held is a hold of its own,** a held change ranked as waiting on the operator (`AtLanding`, `inbox/store.py`), covering every flag on the file, from the conversation landing, saying where its diff starts:
- **from the version of the file the operator last saw** on the branches landed: a flag or a hold they approved, read or commented on, so after a comment they read what changed in answer to it, never the whole file again, or the version they last marked reviewed in its agent's drawer (`policy/reviewed.py`), whichever came last;
- **from the file at the remote's tip** where they saw none, so the integration branch's own changes don't show. A version they saw before the integration branch changed the same file, merged since, shows that change as well.

**The call holds until each hold is answered.** Approved, marked read or answered yes, each flag it covers is approved, and once all are, it lands. Commented on without approval, or declined, nothing lands: the call returns how each was answered, with their words, which also reach the conversation landing as a note, so they're told where no call waits. What they approved stays approved, and the next `land` holds the rest again. A landing that merged has moved the local `dev` to its merge already, which the answer says: the next `land` lands it with whatever it lands. A later landing's hold on a file supersedes one still waiting from an earlier one.

**Then it pushes and cleans up,** through the host as the room's own push does (`docs/credentials.md`, *Landing through `land`*): after each branch it landed, its copy on the remote, its worktree where it's clean and nobody works in it, and its local branch. Who works where is the judge's session index (`Holding.works`), which places a subagent in a worktree once its file tools wrote there, or, in one lup made for it or isolates it in, from its first call (*A worktree the runtime asks for*, *A subagent lup isolates*): a fresh worktree a worker made itself is kept by which branches count as landed, not by that check (#240). A worktree is removed in the launch's room, through podman by the name its container has at that moment, read from the launch's record, since `rename` renames the container with the launch (`docs/launch.md`, *Names*) and the call may have waited hours; where that container isn't there, the answer says so once, with its name, and names each worktree and branch left. A `git push` to a gated branch still runs the gate in the room, and waits on no flag.

**A flag left nothing to hold is withdrawn.** Once a landing has cleaned up, each flagged write still waiting on a branch that's gone, the cleanup's or one deleted earlier, landed or not, holds no landing; and one on a branch whose flags hold the landing, on a file the landing doesn't change, has nothing left to decide where the file stands at the tip as the flag keeps it, landed before. Each is withdrawn from the operator's inbox, saying why (`Withdrawn`, `inbox/store.py`), and the answer names it. It's left unread, so no later hold or drawer starts from the version it kept as one they saw. One on a branch still there whose file stands otherwise may be a write not committed yet, and waits for that branch's next landing.

**Its answer ends on what's still running or waiting to land,** the fact a session checks next: the subagents of the session landing whose end lup hasn't heard (`Whereabouts.ended`, as complete as each runtime's report of a subagent's end, `docs/inbox.md`, *Parties and items*), then the local branches not on what landed, but the gated and protected ones, each with where it's checked out and who works there, a line each; or that nothing is.

## The gate

**`lup-dev check`** (`gate.py`) runs the worktree's own declaration's steps from its root through the project's runner, every one even after one fails: in lup's repository the engine's and the dashboard's builds where they're stale, then `rules`, `format`, `pytest`, `lint-imports` and `private`. With `--fix`, ruff's safe fixes, the removal of each `ignore` that keeps nothing, and the formatter rewrite the worktree first.
- **`rules`** is `lup-dev rules check`: every Python file the roles check, failing on any finding, lup's, pyright's and ruff's alike, each kept only through an `ignore`. It's the one check deciding whether a finding is kept, so the gate has no `ruff check` or `pyright` step of its own, which would fail on a finding an `ignore` keeps.
- **Work due** (a deferral's issue closed or its condition holding, or an `ignore`'s issue closed) is listed without failing, and kept for the next session's start, where its main conversation is told it, as `SessionStart`'s `additionalContext` on both runtimes (`SessionStarted`, `policy/checkpoint.py`). It's what the gate last found: a pass recorded for the same files runs nothing, so an issue closed since is found at the next gate on a change.
- **A pass is recorded by the files it passed on:** the tree git would commit them as, with the person's own layer's digest, in the repository's git directory, which every worktree and room shares. A later run on the same files runs nothing (`--again` runs it anyway), so a push of files the gate passed on finds that pass. Only the builds stale in its worktree still run, reported beside the pass found, and one failing fails the gate: git ignores what they build, so a worktree just made from a branch that passed has its files but not its engine. `--at <commit>` runs the gate on a commit, in a worktree made at it, which a push to the integration branch from a room runs first (`docs/credentials.md`, *git through a remote helper*). With `--fix` too, what the fixes change is committed in place of the commit, with its parents and message, and named: `land` runs it so on the merge it makes (*Landing a branch*). The pass doesn't yet take the `private` list into account (#146).

## The engine: one typed tree

Every lup rule reads one typed tree: each file parsed and type-checked once by pyright, each rule reading types straight from it, so the rules never grow into a patchwork of syntax checks. pyright has no plugin API and its published package can't be imported into, so the engine is a TypeScript program built against pyright's own source, at the release `uv.lock` pins, so it answers as that pyright does (`packages/lup-dev/checker/`).
- **One warm process per worktree,** holding pyright's program, on a Unix socket, started by the first hook that finds none and stopped when idle (`EngineChecker`, `codescan/engine.py`): an engine per hook would reload the project each time.
- **The project's environment, read as files.** The host never runs a project's environment: a room writes its own, which nothing judges, so whatever ran from it would run on the host at the next judged write. For a room's hook, the engine reads the worktree's environment among its launch's own, outside the repository, where the room's `uv` makes it (`Register.environments`; `docs/launch.md`, *The project's environment, the room's own*); otherwise, the directory the project's runner names (`Runner.venv`; `docs/declaration.md`, *The runner*), `.venv` under `Uv()`; never the session's. It reads its `site-packages` and the paths its `.pth` files list, as pyright reads a virtual environment, an `import` line skipped; the Python its `pyvenv.cfg` records (`version_info`, else `version`) unless pyright's configuration names one; and the host's platform. pyright runs with no access to start a process (`NoAccessHost`), whatever its configuration says, so an environment without a `site-packages` reads nothing rather than asking the `PATH`'s Python. The engine never makes or syncs the environment: it reads it as it stands, a missing one as none, one half made as the packages already there, and an environment made, or a package installed, is read at the next check; the room makes it, at its start and at the session's own `uv run` or `uv sync`. The engine is one per worktree and the environment one per launch, so two launches working in one worktree each replace the engine the other's hook started. `Plain()` names none, so a project with no environment manager is typed from its own files and the standard library's stubs.
- **Confined to the worktree, its environment and its own stubs** (`checker/src/confined.ts`). A link there, or a `.pth` line, could lead pyright to a file elsewhere on the host, which it would read as a module and could quote in a finding: a constant's value in a type error. So every path pyright reads, and every file the engine opens itself, resolves, its links followed, inside one of the three, or isn't there; a file's content is checked on the file opened, through `/proc/self/fd`, so a link swapped between the check and the read can't win, and a named pipe isn't read. An environment that is itself a link holds nothing beyond it.
- **A worktree's file that resolves elsewhere is one lup doesn't read** (`lup_dev/confined.py`). The host reads a worktree's file on disk only where it resolves inside the worktree, checked on the file opened as the engine checks one: the content a file tool's write applies to, what a checkpoint and a turn's end read as it stands, what `lup-dev rules check` and ruff read. One that resolves elsewhere is left out, unjudged and failing nothing, as a file that's gone is, so a project holding a committed link out of the worktree judges as before; the engine, asked for it on disk, says it doesn't exist. Where there's someone to tell, they're told: a file tool's write to it is let through unjudged, saying so, and `lup-dev rules check` names it. A write into the git directory through a link out of it is refused, since its hold couldn't show the operator what it changes.
- **ruff, the judge's own** (`codescan/ruff.py`), never the worktree's: `lup-dev` depends on it, so the copy of lup the operator approved carries it, held to the approved lock, and a branch changing ruff's version is judged by the approved ruff until its copy is approved, as pyright is. A project's release is held to the project's own lock's ruff (`docs/trust.md`). It reads each file on its input, a process a file, under the file's own name so its configuration applies.
- **From the parse alone,** for an approval's first reading, which a type check would hold up (`docs/trust.md`): a file's directives and public surface, with no rule run.
- **The files importing a changed one** are re-checked for type errors in a background pass, since the rules read only the files that changed (`policy/importers.py`); a checkpoint asks for it, and their errors arrive at the next one.

Nothing checks a file's imports against the import-linter contracts at the edit yet; the gate's `lint-imports` step does (#39). What the engine costs is in `docs/field-notes.md`, *Judging writes*.

**How a rule is declared.** Rules live in one table, `catalog/rules.ts`, protected, so the operator reviews every change to a rule. Each entry holds its `mistake` and `steer`, each a sentence that stands alone; its `check`, reading pyright's tree and types; and its `examples`, code it flags with each one rewritten the steer's way, and near misses it leaves alone, which the engine's tests run, every rewrite passing every other rule. The engine adds each rule's mistake and steer to what its check reports, so the judge receives whole findings. It's a table of code, since recognising a case takes pyright's own tree and types. `docs/rules.md` is compiled from it and committed, and a test fails when it's stale. Which rules run, and where one doesn't apply, are the declaration's (`docs/declaration.md`, *Selecting the rules*).

## The `# lup:` directives

`# lup:` comments are the channel for notes in code, each read with pyright's own expression parser (`checker/src/directives.ts`) as a model of its kind (`Comment`, `codescan/directives.py`). A directive is a call: `ignore`, `defer` or `note`. Anything else after `# lup:`, free text or a call of another name, is a note, the same as `note("…")` saying it. The operator leaves notes in code for whoever works there next ("why not `heapq`?"), and a note can't be wrong, so theirs never fail the gate, `# lup: sorted(x) here, why not heapq?` included.

A comment is a finding (`malformed-directive`) only where reading it as a note would hide a mistake: an `ignore` or a `defer` written wrong (missing what it needs, given a keyword it doesn't take, or not parsing as a call), which would otherwise sit there doing nothing, and a call of another name passing `issue=` or `when=`, which only tracking takes, so a mistyped or invented `defer` doesn't lose its way back unseen. Any other call of another name is a note: an `ignore` mistyped as one (`ignor(…)`) leaves the finding it meant to keep reported, so the mistake still shows.
- **`ignore("<rule>", why="<reason>", issue=…)`,** on the finding's line or alone above it, keeps that one finding (`docs/conventions.md`, *Suppressions and directives*). Adding one is held for the operator; removing one is free, since it only makes the rule apply. One that keeps nothing is `unused-ignore`, never told to the agent and removed at landing. `issue` is optional: an `ignore` waiting on an issue, a fix to the rule say, keeps its finding all the same, and once the issue closes it's due, as a deferral is. The issue isn't part of what the operator is asked about: giving an `ignore` one, changing it or taking it away keeps no other finding, so it asks nothing and isn't said as a removal.
- **`defer(issue=…, when=…, why=…)`** marks work knowingly left undone, on the code it's about, so the next reader sees the gap is known instead of fixing it blind. `why` is required, and so is a way back: a GitHub `issue`, or `when`, a condition one of the declaration's modules declares in Python (`Condition`, `codescan/conditions.py`), named and never run from the comment. A `defer` with neither stays a finding, since nothing would ever bring it back.
- **`note("<text>")`** is a note, said as a call: `# lup: note("this looks wrong")` and `# lup: this looks wrong` are the same note, so rewriting one as the other removes nothing. A `note` that isn't one string is a note as written.
- **Due:** at the gate an issue's state is read through `gh`, or through the host in a room, and a deferral's or an `ignore`'s closed issue, or a condition that holds, is listed as due (*The gate*).
- **Removing a note** is never refused; one present when the session started, in either form, is said at the checkpoint and the turn's end, for the agent's report and the merge commit's message, so feedback never vanishes silently.

## The verdict log

Every judgement is logged, one JSON line per verdict, per repository (`policy/verdicts.py`), so how often lup asks, holds and lets through can be measured and tuned rather than guessed: when, which session and runtime, the tool, the path and its role, the outcome with its reasons, and the operator's answer, appended under the same key when it comes, so an ask is never lost to a hook that died. `lup-dev verdicts` summarises it; a launched session, whose room mounts neither the log nor the holds, reads it through `judged` (`docs/inbox.md`, *lup's tools*). Where each store lives is `layout.py`'s.
