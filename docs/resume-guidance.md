# Guidance across launches: a resumed conversation runs under its launch's

A launch puts its guidance at system level (`docs/launch.md`, *Guidance*), and the guidance is where a session learns its walls, lup's tools and what's mounted. A conversation continued in a later launch (`/resume`, or `lup-dev launch <runtime> --resume`) must run under that launch's guidance, or a path or mount that moved goes stale without a word. Each runtime keeps a conversation's first instructions unless told otherwise, so lup gives each one its guidance in a form it sends afresh.

## What we have

- **Claude Code: `--system-prompt-snapshot off`** beside `--append-system-prompt-file` (`packages/lup/src/lup/adapters/claude/terminal.py`). By default Claude Code records the system prompt at a conversation's first request and sends the record at every later request and every resume, "even when a later launch passes different text", until the conversation is compacted; with the snapshot off (2.1.257 and later), the prompt is rendered fresh at every request. A resume after the guidance changed writes the conversation's prompt cache again once, and across launches it has usually expired anyway.
- **Codex: the guidance as `additional_developer_instructions`,** in the requirements file the launch mounts at `/etc/codex/requirements.toml` for its hooks (`Requirements`, `packages/lup/src/lup/adapters/codex/terminal.py`), never as `developer_instructions`. Codex keeps these managed instructions in a thread's state by their hash, and at a resume where they changed sends them again whole, as replacing the earlier ones; `developer_instructions` go only into a thread's first context, so a resumed thread would see a later launch's only once compacted. Two limits:
  - Codex refuses to start past 10,000 estimated tokens of managed instructions, at 4 bytes a token, counted with the markers and notice it wraps them in. `managed` counts the same way and refuses a render past it at launch, naming its size, rather than fall back to `developer_instructions` and the stale guidance with them.
  - A workspace's own managed requirements outrank the system file, so an account whose workspace sets managed instructions drops lup's.
- **`Core`'s guidance says it holds as of its launch** (`declaration/modules/guidance/core.md`, *As of this launch*): where the guidance, or what a resumed conversation remembers, disagrees with the room, the room holds. What the conversation's earlier turns saw, and what hooks told it then, still came from the earlier launch, whatever the runtime sends at system level.

Each adapter's docstring gives the runtime's docs and source these rest on.

## Where it's going

The conversation itself isn't told that the guidance moved since it last ran. The direction: each session's record, which the transcripts module keeps (`packages/lup/src/lup/transcripts/`, today a copy of the runtime's own records), also names each launch the session ran in, with the guidance that launch rendered. At a session's start in a launch other than its last, the host service, the record's only writer, compares the two renders section by section and tells the conversation at `session-started` what changed; a start with nothing to compare against (a fork, a conversation from before the record) is a case of its own. That needs the render's sections by name, the render handed to the host service with the launch's registration, and the hook saying how a session started. What the runtimes give for it is in `docs/field-notes.md`, *A conversation resumed in a later launch*.
