# Hosting: what runs on the operator's machine

Containers don't start themselves: something outside every container runs podman, and whatever runs podman can mount anything of the operator's, so it's as powerful as they are. In lup that something is a module like any other, `Hosting`: parts that hold the machine (`machine=True`), one for the whole machine (`shared=True`), run there from the home repository's approved commit, their doors checked by promises. The home repository's declaration selects it (lup's own does); a project's doesn't.

The only thing that isn't a module is the loader in the `lup` the operator installs, which starts these parts from the commit they approved.

## Who may call them

What's privileged in a machine part is for the machine's own parts alone: its services take `by: Machine`, a party only a call made where those parts run is, never a call carried from a container, the home repository's own branch among them. So code a project runs, an agent, and lup's own unapproved branch can ask for nothing the machine does for itself.

## Containers

`Containers` holds podman (`podman: Program`). It builds an image where its tag isn't there yet (`built`), a Containerfile's text tagged by its digest, so a changed definition is a new tag, from a base image named by its digest and fetched by it first, so the build itself fetches nothing (`--pull=never`); starts a container, detached (`started`); and stops one (`stopped`). Every container it starts stands behind the same walls, whatever asked for it (`Walls`): the operator's uid inside, every capability dropped and no privilege gained, a limit on processes, reaped by `--init`, removed when it ends, no image fetched by a short name, no log kept. A directory mounted into a container is read-only unless its spec says, and lands at its own path, a path holding a comma kept whole; one mounted through a link, or by a relative path, is refused, since podman would follow the link wherever it points. podman failing refuses the call that asked, saying why.

These are the second lup's room's walls, as measured with rootless podman 6.1 (`docs/field-notes.md`, *the engine's command lines*).

## Secrets

`Secrets` keeps each project's secrets, a JSON file each under its own data, outside every repository, readable by the operator alone, so a downstream project's user never learns where: lup asks them for a secret the first time a part holding it starts. Only the machine's own parts read one (`held`), handing a part the secrets kept for its project that it holds and naming those that aren't, for the operator to be asked for; another project's secret of the same name is never among them. Only the operator keeps one (`keep`, a command).

## Trees

`Trees` writes out a commit's files from git's objects (`exported`), for what runs from a commit the operator approved: a room writes the repository's object store, and git reads an object by its id without hashing it, so a planted loose object, a replace ref, a graft or a commit-graph could hand it other content for an id the commit names. Each object is hashed as git hashes one and compared with its id, from the commit down, and a store holding one that isn't what its id says refuses the export, naming it. git runs pinned to the repository's common git directory (`GIT_DIR` and `GIT_COMMON_DIR` both naming it, so it reads no `commondir` a room planted), grafts read from an empty file, replace refs and the commit-graph ignored, no configuration read but the repository's own, nothing fetched for an object a partial clone left out, and `core.fsmonitor` and hooks off. Never `git archive`, which applies the tree's `.gitattributes`. A commit is named by its whole id, never an abbreviated one or a ref. The export is written beside its place and moved there whole, under `Trees`' own data, which a container mounts read-only and nothing else writes; a path or a link that would land outside it is refused, a submodule left out. Carried over from the second lup's `Git.export`.

`Trees` also says which files two commits differ in, from each object's own bytes (`compared`), and gives their whole diff (`diffed`) as git compares the two commits written out, with no repository, configuration or diff driver of anyone's having a say in it, so what the operator reads is what would run.

## Approvals

Nothing of a project runs that the operator hasn't approved: each of its parts runs the commit they approved last (`approval`), from its files as `Trees` writes them out. An approval comes from the review of a landing, whose yes approves the commit it lands (`landed`, which the machine's code that lands it records), or from the operator answering the question asked when a project's running branch moved with no review of theirs, a pull, a push of their own or a first run (`approve`, theirs alone). The question (`question`) says what changed since the commit approved before, the changes in a directory holding a part that holds something called out, as a review highlights what's held, and whether a lockfile or a `pyproject.toml` changed, every part's dependencies; the whole diff is `Trees`'. Each project's approvals are kept in order, a JSON file each, under the part's data.

## Carrying

Each container lup starts gets a directory of sockets of its own (`directory`), in memory (`Runtime`), named by a digest of the container's name, since a socket's path is limited to 108 bytes, and mounted at `/run/lup` in it: `calling.sock`, which it calls out through, and `listening.sock`, which it answers calls on. Who a call is by is `Carrying`'s word, from the directory it came in on, never what the call says: a project's container is its project's `Codebase`, the operator's own directory, which no container mounts, is the `Operator`, and a directory that's neither is refused (`routed`). A call is answered by a part of the caller's project running in one of its containers, the project the operator names for theirs, or else by the machine's own parts, which refuse what none of them serves: never by another project's part, whatever its plan claims, and a part a plan says is the machine's is only ever the machine's own. A part of the caller's project that isn't running, waiting for a secret, refuses saying so. Every socket is a file: rooms share the machine's network, which takes in Linux's abstract sockets, so lup never uses one. Binding the sockets and forwarding calls is the environment's (`lup.environment.running.machine`), told of each directory as it's made (`Listens`); this part keeps where each part runs (`placed`) and decides each route.

## Projects

`Projects` runs a project (`open`, the operator's command, or `opened`, the machine's service) at the commit the operator approved last (*Approvals*), written out by `Trees` and mounted read-only, and refuses one nothing of which is approved yet. It plans the project's declaration in a container, which prints the plan, stops the containers the project ran before, then starts one container for every part holding nothing, and one of its own for each part holding something that isn't the machine's, given only the secrets that part holds, as files in its directory of sockets, which is in memory, read and removed as the container starts: a secret is never on disk outside `Secrets`' store. A part whose secret nothing kept waits, not started, until the operator gives it. A plan in which two parts serve the same name (a tool or a service anywhere in the project, a command or an action in one module) is refused, rather than a call routed to whichever comes first, since the plan comes from the code it plans; so is a module's or a part's name that isn't safe as a directory's or a container's. Each container mounts the project's tree read-only, and the machine's uv-managed interpreters read-only at their own paths, nothing fetched, its Python environment, uv's cache and its parts' data in directories of that container's own under this part's data: it starts on what it synced and kept before, and code running in one container never writes what another imports or reads what another keeps, so a part that stops holding a secret, running in the project's container from then on, never sees what it kept while it held one.

## Promises

`promises.py`, through the harness, the machine's parts started as the machine's own (`by.started(…, machine=True)`), podman stood in for as each promise scripts it (`programs={"podman": Scripted(…)}`): the gate checks what lup asks podman to do, and never runs it.
