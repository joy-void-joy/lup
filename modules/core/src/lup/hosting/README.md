# Hosting: what runs on the operator's machine

Containers don't start themselves: something outside every container runs podman, and whatever runs podman can mount anything of the operator's, so it's as powerful as they are. In lup that something is a module like any other, `Hosting`, named `machine`, as the command line types it (`lup machine …`): parts that hold the machine (`machine=True`), one for the whole machine (`shared=True`), run there from the home repository's approved commit, their doors checked by promises. The home repository's declaration selects it (lup's own does); a project's doesn't.

The only thing that isn't a module is the loader in the `lup` the operator installs, which starts these parts from the commit they approved (*The loader*).

## Who may call them

What's privileged in a machine part is for the machine's own parts alone: its services take `by: Machine`, a party only a call made where those parts run is, never a call carried from a container, the home repository's own branch among them. So code a project runs, an agent, and lup's own unapproved branch can ask for nothing the machine does for itself.

Only a part holding the machine (`machine=True`) runs in the machine's own process. A part one for the whole machine (`shared=True`) that doesn't hold it, the inbox and its store among them, runs in a container of its own, started by the machine from its own code and environment, read-only, holding only what it declares, its data the directory it kept on the machine (`Projects.machinewide`). Every directory the machine imports its code from is mounted there too, a source tree an editable install points at among them, and the program runs isolated (Python's `-I`) from `/`, so no working directory comes before the standard library: run from inside `lup/hosting/`, its `secrets.py` would stand in for Python's own. A container that doesn't listen on its socket within a minute is stopped, and `status` and the machine's log say so, with where what it printed is; a call reaching a container that doesn't answer is refused saying it may still be starting or have ended, and where to look. The machine's parts calling one of its services carry the call there as the machine's (`Inward`), the one call that crosses saying so; every call coming in to the machine is named from its socket, whatever it says. The machine's parts call one project's part, one that runs one per project, by naming the project (`with lup.within("harmon"): await Remotes.pushed(…)`), and `Carrying` aims the call at that project's container running the part, never another's (`aimed`); a call naming no project is refused, and so is one a project's own code makes naming any. Where podman isn't there, nothing runs in a container, no project's code among it, so those parts run in the machine's process and the inbox still answers.

## Containers

`Containers` holds podman (`podman: Program`), an optional program: without it, or with one at a version lup doesn't take, `Containers` isn't made and whatever needs it is refused, opening a project among it, while the machine's other parts answer, so the operator can still keep a secret or approve a commit. It builds an image where its tag isn't there yet (`built`), a Containerfile's text tagged by its digest, so a changed definition is a new tag, from a base image named by its digest and fetched by it first, so the build itself fetches no image (`--pull=never`), and builds it again where it fails, three times at most, since fetching packages fails at times for the network alone; starts a container, detached (`started`); and stops one (`stopped`). Every container it starts is labelled as lup's and its project's, and every container so labelled can be stopped at once (`cleared`), as `Projects` does when the machine's parts start: one a machine that stopped before left running is one nothing routes calls to any more. Every container it starts stands behind the same walls, whatever asked for it (`Walls`): the operator's uid inside, every capability dropped and no privilege gained, a limit on processes, reaped by `--init`, removed when it ends, no image fetched by a short name. What a container that runs on prints goes to a file of its own (`Spec.output`), capped in size, which `Projects` keeps in memory where no container mounts it, so a container that ended unexpectedly can be read after; one run to its end keeps nothing, its caller reading what it prints. Which containers are running is podman's word (`alive`). A directory mounted into a container is read-only unless its spec says, and lands at its own path, a path holding a comma kept whole; one mounted through a link, or by a relative path, is refused, since podman would follow the link wherever it points. podman failing refuses the call that asked, saying why.

These are the second lup's room's walls, as measured with rootless podman 6.1 (`docs/field-notes.md`, *the engine's command lines*), but for what's printed, which a room kept nothing of: a project's container runs unattended, and its output is the only word of why it ended.

## Secrets

`Secrets` keeps each project's secrets, a JSON file each under its own data, outside every repository, readable by the operator alone, so a downstream project's user never learns where: lup asks them for a secret the first time a part holding it starts. Only the machine's own parts read one (`held`), handing a part the secrets kept for its project that it holds and naming those that aren't, for the operator to be asked for; another project's secret of the same name is never among them. A secret set in the machine's environment, under the variable a project's command reads it from (`HARMON_TOKEN`, `lup.doors.parts.variable`), wins over the one kept, so a deployment sets one variable whichever way the part runs. Only the operator keeps one (`keep`, a command).

## Lending

The operator's own credentials act for agents, as their terminal has them: no token of lup's to make, and their remotes' SSH aliases resolve as they do for them. A part holding one of them runs in a container of its own, from approved code, as a part holding a secret does, and is lent it as that container starts, one project's alone:
- **the project's git directory** (`GitDirectory`), its common git directory bound read-write at its own path, its `config` and `hooks/` read-only over it, as a room has it, so the part fetches into the store rooms share and pushes from it;
- **their SSH agent** (`SshAgent`), the socket the machine's `SSH_AUTH_SOCK` names, bound in, and their `~/.ssh` read-only at its own path, every file in it whose first line begins a private key (OpenSSH's, PEM's, PuTTY's) hidden behind an empty one, the machine reading no more of it than that line: ssh reads their configuration and signs through the agent, finding the key by the `.pub` beside where it was (`docs/field-notes.md`, *ssh through the operator's agent*). The socket is bound as a file, so an agent restarted means opening the project again; its directory is never bound, since it may hold the machine's other sockets;
- **their GitHub login** (`GitHubLogin`), the token `gh auth token` prints on the machine (`Logins`), read at each start, so a login they renew is the one the next start uses, and handed over as a secret is, a file in the container's directory of sockets read and removed as it starts, never in its environment, which podman shows.

What the machine can't lend (no `gh`, or no login in it, or no `SSH_AUTH_SOCK`) keeps the part waiting, not started, the project's other parts running, and `status` says why. A part holding none of these is lent none of them.

## Trees

`Trees` writes out a commit's files from git's objects (`exported`), for what runs from a commit the operator approved: a room writes the repository's object store, and git reads an object by its id without hashing it, so a planted loose object, a replace ref, a graft or a commit-graph could hand it other content for an id the commit names. Each object is hashed as git hashes one and compared with its id, from the commit down, and a store holding one that isn't what its id says refuses the export, naming it. git runs pinned to the repository's common git directory (`GIT_DIR` and `GIT_COMMON_DIR` both naming it, so it reads no `commondir` a room planted), grafts read from an empty file, replace refs and the commit-graph ignored, no configuration read but the repository's own, nothing fetched for an object a partial clone left out, and `core.fsmonitor` and hooks off. Never `git archive`, which applies the tree's `.gitattributes`. A commit is named by its whole id, never an abbreviated one or a ref. The export is written beside its place and moved there whole, under `Trees`' own data, which a container mounts read-only and nothing else writes; a path or a link that would land outside it is refused, a submodule left out. Carried over from the second lup's `Git.export`.

`Trees` also says which files two commits differ in, from each object's own bytes (`compared`), and gives their whole diff (`diffed`) as git compares the two commits written out, with no repository, configuration or diff driver of anyone's having a say in it, so what the operator reads is what would run.

`Objects` is that reading, apart from `Trees`; git's companion holds the same reading for every other part, a store pinned (`lup/programs/git/README.md`), which the trial reads a commit through (`lup/landing/README.md`).

## Approvals

Nothing of a project runs that the operator hasn't approved: each of its parts runs the commit they approved last (`approval`), from its files as `Trees` writes them out. An approval comes from the review of a landing, whose yes approves the commit it lands (`landed`, which the machine's code that lands it records), or from the operator answering the question asked when a project's running branch moved with no review of theirs, a pull, a push of their own or a first run (`approve`, theirs alone). The question (`question`) says what changed since the commit approved before, the changes in a directory holding a part that holds something called out, as a review highlights what's held, and whether a lockfile or a `pyproject.toml` changed, every part's dependencies; the whole diff is `Trees`'. Each project's approvals are kept in order, a JSON file each, under the part's data.

## Carrying

Each container lup starts gets a directory of sockets of its own (`directory`), in memory (`Runtime`), named by a digest of the container's name, since a socket's path is limited to 108 bytes, and mounted at `/run/lup` in it: `calling.sock`, which it calls out through, and `listening.sock`, which it answers calls on. Who a call is by is `Carrying`'s word, from the directory it came in on, never what the call says: a project's container is its project's `Codebase`, a session's room is that session's `Agent`, the operator's own directory, which no container mounts, is the `Operator`, and a directory that's none of these is refused (`routed`). A room is one session's, kept from its start (`seated`) until it stops (`left`): a call from it may name which of that session's conversations makes it, a subagent's, and the agent vouched for is that one of that session (`lup.Agent.of`); a call naming a conversation from anywhere else is refused. A call is answered by a part of the caller's project running in one of its containers, the project the operator names for theirs, or else by the machine's own parts, which refuse what none of them serves: never by another project's part, whatever its plan claims, and a part a plan says is the machine's is only ever the machine's own. A part of the caller's project that isn't running, waiting for a secret, refuses saying so, and a command `lup` answers where it's typed (`@lup.command(here=True)`) is refused rather than carried to the project's container, where it would mean nothing. A caller may also ask what they may call (`offered`): they're told who they are, from the socket they asked on, and offered their project's plan with the machine's own parts' beside it, which is what the command line lists and parses for. Every socket is a file: rooms share the machine's network, which takes in Linux's abstract sockets, so lup never uses one. Binding the sockets and forwarding calls is the environment's (`lup.environment.running.machine`), told of each directory as it's made (`Listens`); this part keeps where each part runs (`placed`) and each session's room (`seated`), and decides each route. It also carries a session's event to every part of its project hearing it, in the project's containers and in the session's room, through what the environment gives it (`heard`, `Forwards`); and a part's own event (`lup.heeded`, `Event.fired`), come in on one of its project's containers and from nowhere else, to the parts of that project hearing it in its other containers (`fired`), where one that doesn't answer refuses it, since a check that didn't run let nothing through, and the container receiving one refuses an event only lup tells.

## Projects

`Projects` runs a project (`open`, the operator's command, or `opened`, the machine's service) at the commit the operator approved last (*Approvals*), written out by `Trees` and mounted read-only, and refuses one nothing of which is approved yet. It plans the project's declaration in a container, which prints the plan, then starts one container for every part holding nothing, and one of its own for each part holding something that isn't the machine's, given only the secrets that part holds, as files in its directory of sockets, which is in memory, read and removed as the container starts: a secret is never on disk outside `Secrets`' store. It's lent what it holds of the operator's too (*Lending*), and its image installs the packages its programs are in, an image for each list, built once. A part whose secret nothing kept waits, not started, until the operator gives it. The operator registers a project with their lup (`register`), which keeps it without opening it, a name another project's git directory holds refused. The machine's parts read where git keeps a project registered by its name (`registered`), as a landing reads the branch it lands. The operator reads what runs (`status`, a view, each project a fold of the `project` kind, its containers' lines in the module's `up`, `down` and `waiting` tones): the containers of the machine's parts one for the whole machine, then each project open, the commit it runs, each container, whether it's still running and where what it prints is, and the parts waiting on a secret, or on what the machine couldn't lend them. Each project registered or opened is kept, and as the machine's parts start they open each again (`resumed`), at the commit approved last, every container a machine before them left stopped first; one that can't open is said with why, and the others open. A restart cuts no call: each opening's containers, named with the opening, start beside those the project runs, calls are routed to them, and only then are those stopped, each finishing the calls it's answering before it runs its parts' `Stopping`; where one of the opening's containers doesn't start, those that did are stopped, and the project runs on as it did. A plan in which two parts serve the same name (a tool or a service anywhere in the project, a command or an action in one module) is refused, rather than a call routed to whichever comes first, since the plan comes from the code it plans; so is a module's or a part's name that isn't safe as a directory's or a container's. Each container mounts the project's tree read-only, and the machine's uv-managed interpreters read-only at their own paths, where its uv says it keeps them (`uv: Program`), nothing fetched, uv's cache and its parts' data in directories of what it runs (the project's own container, or one part's), kept from one opening to the next, and its Python environment there too, one for each commit, so a container starting never changes what one still running imports: it starts on what it synced and kept before, and code running in one container never writes what another imports or reads what another keeps, so a part that stops holding a secret, running in the project's container from then on, never sees what it kept while it held one.

## The loader

`lup` calls through the machine's socket (`lup.environment.running.loader`). In a room, `LUP_CALLING` names the room's socket and nothing is started. In the operator's terminal, where nothing answers on the machine's own socket, `lup` starts the machine there and then, detached, so it outlives the command; where podman isn't there, as in a room no lup started, it starts nothing, answers in its own process over the worktree's declaration, and says so.

The machine's parts run from the home repository the machine's layer names (`Core.home`, in `~/.config/lup/lup_project.local.py`), at the commit the operator approved; with none named, from the installed `lup`'s own code (`lup/hosting/installed.py`: lup's default modules, `Hosting` and `Sessions`), installing being the approval, so whoever only builds with lup starts sessions as the operator does. Where the home repository's running branch moved since the commit approved, the operator is asked at the terminal, as adlib asked: a summary first (each file changed, what a part holding something runs and the dependencies called out), then whether to show the whole diff, then whether to approve, each no by default; declined, or with no terminal to ask at, the commit approved before runs, and none approved refuses. `lup` asks the same of the project whose worktree it runs in, where that worktree holds a declaration: where its running branch moved since the commit approved, the operator is asked, and approving opens it again at that commit (`hosting open`). To ask, the loader starts `Trees` and `Approvals` in its own process from the installed `lup`'s code, never the code it's asking about.

The commit approved is written out by `Trees`, its environment synced (`uv sync --frozen`) into one of its own, and the machine started from it, its output appended to a log. Where its socket doesn't answer within a minute, it's stopped and the last commit that came up starts again, saying why; the loader keeps which came up last, and its process, which `SIGTERM` stops: the machine then stops listening and runs its parts' `Stopping`, which stop every project's containers. Where it keeps what it keeps comes from `platformdirs`: its parts' data under the state place, each commit's environment under the data place, its sockets under the runtime place, in memory. A part's data is kept under its module's name and its own (`machine.Approvals`), so where a module was renamed, what its parts kept is moved to the name they have, where that isn't there yet, by the loader before it starts a machine and by the machine as it starts (`lup.environment.running.moving`).

## Promises

`promises.py`, through the harness, the machine's parts started as the machine's own (`by.started(…, machine=True)`), podman stood in for as each promise scripts it (`programs={"podman": Scripted(…)}`): the gate checks what lup asks podman to do, and never runs it.
